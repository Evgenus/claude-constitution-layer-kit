# Constitution Kit — Session Guide

This repository is the **constitution kit**: a portable, project-agnostic governance layer for Claude Code projects, shipped as plugins. It contains the semantic kernel, the module template, and the modules. It contains **no project content, ever**.

Read before any work:
- `INTENT.md` — what this repo is for and what it is not.
- `docs/constitution/CONVENTIONS.md` — the semantic kernel (one page). Authoritative for all vocabulary.
- `module-template/MODULE.md` — the fixed shape every module fills.
- `docs/requirements.md` — the traceability matrix and module specifications (requirement rows per module).
- `docs/rollout-plan.md` — the phases, the kit's own active task-record; not a reading assignment.
- `constitution.yaml` — the kit's own dials file; its `root_policy` key locates the policies that govern this repository's documents ([kernel §3](docs/constitution/CONVENTIONS.md#k3)). Not a reading assignment: open a policy only when working in its territory. Written in block style — one key or one `- ` item per line; flow style, `[]` or `{}`, only for an empty list or mapping — held by `python3 scripts/check-yaml-style.py`, run by the kit's CI; its `--fix` rewrites the file keeping every comment, anchor, alias and quote as written; the kit's CI also validates the file against the kernel's dials schema with a real validator, `scripts/check-dials-schema.py`; the YAML inside Markdown fences is not under the rule, and a consumer's file is the consumer's (decision [dec-0037-dials-file-block-style](docs/decisions/dec-0037-dials-file-block-style.md)).
- `docs/research/` — one current dated comparison per module, written by its module's own research round, and one per mechanism of the kit's own tooling whose change asked for one; a superseded one is kept beside it while cited. Not a reading assignment: open one when changing a mechanism.
- `shared/GATE.md` — the code every gate shares. Read it before authoring a module with a gate.

## Laws of this repository

1. <a id="law-1"></a>**Kernel is authoritative; never restate it.** Modules and documents reference kernel definitions by name — duplication is a defect.
2. <a id="law-2"></a>**Portability ([kernel §6](docs/constitution/CONVENTIONS.md#k6)):** no file in a module references any project — no paths, names, repos, values. Project specifics enter only through the module's dials namespace. Test: the module installs and operates on an empty repository using defaults alone.
3. <a id="law-3"></a>**Sibling independence:** modules depend on the kernel and nothing else. Sibling references only as optional enhancements ("when `const-x` is installed…"). The kit's shared gate code is not a sibling: it has one source under `shared/`, which a module's plugin imports from the installed Python distribution `constitution-layer-kit` and never carries, and which the module's tests reach by links — a module never reaches another module through it (R7 and R8 of [dec-0099-shared-code-installed-as-a-pip-package](docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r7)). Test: kernel + this module + the shared package alone on a bare repo is a functioning installation. If a module seems to need a sibling, the shared concept belongs in the kernel — raise that as a `process`-stakes decision instead of coupling.
4. <a id="law-4"></a>**A module implements exactly its matrix rows.** Its `MODULE.md` cites them. Content beyond its rows is scope creep; a missing row is incompleteness. Both are review findings.
5. <a id="law-5"></a>**Enforcement honesty:** every artifact is `gate` (deterministic, red = fix) or `advisory` (judgment-shaping) — declared, never blurred. Nothing judgment-based is dressed as a check.
6. <a id="law-6"></a>**Teaching errors:** every gate's error message states what failed, why the rule exists (one clause), and the exact fix. Error messages are designed content, reviewed like code.
7. <a id="law-7"></a>**Every gate ships its red→green fixture** in `modules/<name>/tests/` — one input that fails without the check and passes with it.
8. <a id="law-8"></a>**Sizes in characters, never tokens.**
9. <a id="law-9"></a>**Kit decisions follow the kernel's own stakes triage.** Routine → act, note in the commit. `process` (most kit changes) → decision record in `docs/decisions/`, one human yes on the change, named in the merge commit of its pull request — the decider's own merge, since the kit has no second human to approve (decisions [dec-0016-yes-on-the-change](docs/decisions/dec-0016-yes-on-the-change.md) and [dec-0057-pr-flow-merge-names-the-yes](docs/decisions/dec-0057-pr-flow-merge-names-the-yes.md)). Kernel changes are always recorded. Record lifecycle, supersession, and deletion: [kernel §1](docs/constitution/CONVENTIONS.md#k1) and [kernel §5](docs/constitution/CONVENTIONS.md#k5) — not restated here.

## Session conduct

*Every kit session, save the escape below, loads the kit's modules as plugins from its committed `.claude/settings.json`, which declares the clone as the marketplace `claude-constitution-layer-kit` by a relative directory source and enables each module — nothing per clone to load them, in a folder trusted once (decision [dec-0043-kit-plugins-through-project-settings](docs/decisions/dec-0043-kit-plugins-through-project-settings.md)). A module whose gate blocks its own fix is switched off for one clone, its skills and session-start text with it, by `"<module>@claude-constitution-layer-kit": false` under `enabledPlugins` in that clone's `.claude/settings.local.json`, the one per-clone write to the plugin settings, a file the kit's `.gitignore` keeps out of the tree. The rules the modules ship reach the model from them — at session start, as skills, whose descriptions ask to be loaded at their moment and which a module's hooks also name where they meet it, and as hooks — and are not restated here; this block keeps what no module carries. Of the kit's own agents in `.claude/agents/`, the one that writes the kit's tracked files, the implementer, lists the `Skill` tool, so that it can load a skill that its start context or a hook's red names; the others write nothing tracked and keep their tools, so a pointer to a skill that reaches them asks nothing of them (decision [dec-0079-skills-named-at-their-moment](docs/decisions/dec-0079-skills-named-at-their-moment.md)). The gates of those plugins import the shared package from the `python3` the session runs, so each clone installs it once, as [kit-install-guide](INSTALL.md) says. The sessions run that release and not the working tree, so a broken shared change cannot stop the gates that guard its fix. A module that requires a later release stops with `C16`, which blocks nothing in hook mode, until that release is installed (R9 and R23 of [dec-0099-shared-code-installed-as-a-pip-package](docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r9)).*

- **Work starts on a branch.** Every change — one commit or many, routine or recorded — is made on its own branch `work/<name>`, a short kebab-case name of the work, cut from `main`, and reaches `main` as the merge commit of one pull request on the kit's private GitHub remote, `origin`: the branch pushed, `git push -u origin work/<name>`, the pull request opened, `gh pr create`, and merged with `gh pr merge <n> --merge --subject "Work: <name>"`; a local `main` then follows by `git pull`, a fast-forward only. The branch is kept forever after the merge, in the clone and on the remote. Nothing is committed on `main` itself.
  - **Before the merge.** The range check of module [`const-task-close`](docs/requirements.md#const-task-close) is green on the branch — `PYTHONPATH="$PWD/shared" sh modules/const-task-close/plugin/scripts/check-task-close.sh --scan` (a plugin carries no shared code, so a run by hand needs the installed package or that path; `sh scripts/gate-list.sh --run task-close` sets it), over the kit's `coverage` map in `constitution.yaml`: a change that touches code a current-state document describes updates that document in the same change or declares no impact by a `No-Doc-Impact: <pair> — <reason>` trailer on one of its commits, in the message's last paragraph, never by the pull request's description alone, which the kit's CI does not give the check; with `--scan --change <merge>` it audits a landed change. When `main` has moved since the branch's last CI run, the branch merges `main` and waits for CI green again before `gh pr merge`; review holds this, since the ruleset does not ask a branch to be up to date.
  - **The gate list and CI.** The whole gate list — the scans of the modules, the kit's own checks each with its `--self-test` where it has one, the self-test of the eval runner, `scripts/run-evals.py --self-test`, and the range check — is the gate group of `scripts/gate-list.sh`, the kit's one list; its extra group holds each module's fixtures, lint and types, the branch gate's fixture, the fixture of `scripts/setup-claude.sh`, the kit's lint and types, and the types of `scripts/layered-fixture/`. That folder holds a gate of another layer. `scripts/check-layered-items.py`, an entry of the gate group, runs every shared item on it. A module's scan in the list runs with `PYTHONPATH="$PWD/shared"`, since no plugin carries the shared code, and the entry `shared-package`, `scripts/check-shared-package.py` with `--self-test` as its fixture, builds the package from `shared/`, installs it into a fresh virtual environment and imports it there, the one entry that needs the package index (R19 of [dec-0099-shared-code-installed-as-a-pip-package](docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r19)). A module's fixtures run through `python3 scripts/check-aspects.py --run --module <module>`, which collects its tests under pytest, then runs them once, prints pytest's own output whenever it exits other than 0, and holds the tests' items against the module's acceptance table both ways (decision [dec-0080-fixtures-run-through-check-aspects](docs/decisions/dec-0080-fixtures-run-through-check-aspects.md)). The same run holds a count typed on the Runner line of the document's section 10, `<digits> items green` outside code fences, against the tests run; a Runner line without that form, or none, is no finding. Every script under the kit's `scripts/` is kit tooling, never shipped in a module. The kit's CI runs the whole list, `.github/workflows/gates.yml`, on every pull request and on `main` after each merge: one job per module holding its entries, one job `install-guide` running the commands of `INSTALL.md` through `scripts/check-install-guide.py` (decision [dec-0062-install-guide-governed-kind](docs/decisions/dec-0062-install-guide-governed-kind.md)), and one job `kit` for the rest, in parallel, from the list's `--json`; and a job `gates`, green only when every other job is. After its verdict, the job `gates` runs `scripts/metrics.py`, a report of each module's numbers and never a check, and its list of the most complex functions, and uploads both JSON files as the artifact `metrics`; those steps run unless the run is cancelled, and their failure never changes the verdict (decision [dec-0087-module-metrics-report](docs/decisions/dec-0087-module-metrics-report.md)). In each module's job, the fixtures entry runs the module's tests one by one, since CI sets no `CONSTITUTION_KIT_JOBS`, under coverage.py, since CI names a folder in `CONSTITUTION_KIT_COVERAGE`, and writes the lines and branches the fixtures reach into the module's file there, uploaded as the artifact `coverage-<module>`; a failure of coverage.py is a BROKEN line of that entry. The self-test of `scripts/check-aspects.py` holds that mode, so a local run of the gate group needs coverage.py, pytest and pytest-xdist, at the versions the workflow pins. After its verdict, the job `gates` reads those files with `scripts/module-coverage.py`, a report of each module's fixture coverage and never a check, whose numbers no check holds, and uploads its JSON as the artifact `coverage`, in steps that run and fail as the metrics steps do (decision [dec-0089-module-coverage-report](docs/decisions/dec-0089-module-coverage-report.md)). No local run is required, save one: a change that makes a module's eval receipt stale is merged only with a new passing receipt, made before the merge by `python3 scripts/run-evals.py --token-file <file> --module <module>`, and committed. Every case runs in a throwaway container of the image `scripts/eval-container/Dockerfile` defines, with the seccomp filter and the `/proc` mask lifted so that the eval's own sandbox can start, on the pinned Claude Code, logged in with the person's subscription token from `claude setup-token` and never billed by usage, so every receipt comes from one environment, with the change's own `shared/` mounted at `/shared` and made importable the same way, and a receipt's hash covers `shared/constitution_layer_kit/` beside the module's files, since a session loads it (R18 of [dec-0099-shared-code-installed-as-a-pip-package](docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r18)). Each module has its eval cases in `evals/`, which `claude plugin eval` runs three times each on the model `scripts/eval-model` names, and a case passes when every grader passes in every run and no trace of its runs holds `C15`, `C16` or `C17` (R18 of [dec-0099-shared-code-installed-as-a-pip-package](docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r18)). Each container refuses to run its case unless `claude auth status` reports a subscription login. The runner adds a run's attempt to the module's entry of `scripts/eval-receipts.json` and keeps the failed ones beside the one that passed, so that a review sees each failed rerun and does not trust it away; a passing run of a module whose entry already names its files, Claude Code and model and whose last attempt passed is not added, so that a passing run made only to watch owes no commit, while an attempt that is added, a failure as much as a pass, is committed. An entry whose files, Claude Code or model change starts afresh, its earlier attempts kept in git's history (decision [dec-0094-eval-runs-record-only-what-changes-the-verdict](docs/decisions/dec-0094-eval-runs-record-only-what-changes-the-verdict.md)). The kit's `scripts/check-eval-receipts.py`, an entry of the gate group with `--self-test` as its fixture, is red for a module whose receipt is missing, names another hash of the files a session loads and its cases, another Claude Code or model, no attempt, or a last attempt that did not pass, and for an entry that names no module folder: it holds that a passing run was declared for the files as they are, not that it ran. In each module's job, `scripts/check-session-load.py --module <module>`, with `--self-test` as its fixture in the job `kit`, installs the module as the bare-install check does, through the steps both share in `scripts/kit_install.py`, starts one headless session with no login, and holds that the session lists the module's skills and that its start hooks answer, each with output (decision [dec-0093-module-evals-with-local-receipts](docs/decisions/dec-0093-module-evals-with-local-receipts.md)). Those steps also make a throwaway virtual environment of the `python3` they run under, with its system packages, whose `.pth` file names the change's own `shared/`, and put its `bin` first on `PATH` for every session, hook and scan they start, so that no run meets a release a developer installed; the guide's check does the same for its blocks (R17 of [dec-0099-shared-code-installed-as-a-pip-package](docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r17)). For a red before a push, the `gate-list-runner` agent of `.claude/agents/` runs the gate group, the extra group on request, and returns every red line verbatim. The install and session entries and the guide run on the Claude Code that `scripts/claude-code.version` pins; `sh scripts/setup-claude.sh` installs it once per clone, and again after the pin moves, into `.claude-code-pinned/` beside git's common directory, which git ignores, and the list puts it first on `PATH` for those entries alone, when it is there. The kit's `scripts/check-gate-lists.py`, an entry of that list with `--self-test` as its fixture, holds the form of each module's enforcement table, and that every scan a module declares there stands in the list's gate group and in its module's job and runs with `PYTHONPATH="$PWD/shared"` before its command, every `scripts/check-*.py` git tracks at the top of `scripts/` is run by an entry of the gate group, `MODULES` names exactly the module folders, and the workflow's steps, comments aside, call the list's `--json` and `--run`. It holds that neither `scripts/gate-list.sh` nor the workflow, comments aside, names pytest save in an exact pin `pytest==<version>`, passes `--item` or names `PYTEST_ADDOPTS`, nor does a pytest configuration file at the kit root, in `modules/`, in a module's folder or in its `tests/` set `addopts`. It also holds each module folder named `const-<aspect>`, its manifest naming it, listed once in the marketplace at `./modules/<name>/plugin` and enabled, `true`, in the kit's settings, which declare the marketplace as a directory at `.`; neither file names a plugin of that marketplace that is no module folder. It holds each marketplace `description` equal to its manifest's, every top-level `const-<aspect>` key of `constitution.yaml` naming a module folder, and the `types` entry putting on `MYPYPATH` exactly the `plugin/scripts` folders of the modules `scripts/check-schema-mirror.py` imports from, and `../shared`. It holds that the `bash check=scan` block of `INSTALL.md` lists exactly the scans the module documents declare, each as `<module>/plugin/scripts/<name>.sh` with `<name>` the declared scan's name without `.py`, a module with no scan owing no path. It holds that every module folder has its one pair in `const-task-close.coverage` of `constitution.yaml`: named after the folder, with `docs` its `MODULE.md` alone, every `code` pattern under the folder, and `modules/<m>/<path>/**` for each of `plugin/scripts`, `plugin/hooks`, `plugin/skills`, `tests` and `evals` that it has. The entries of that map that are no module's are not judged.
  - **The yes.** Where the change needs a yes, the merge gives it: the decider merges the pull request, or says yes in chat and has the session merge in the decider's name. The merge commit names the yes and carries the `Accepted:` and `Carry-Audit:` trailers in its last paragraph, written with `--body`, or into the merge message on the forge's page. It is the commit that lands the change in the sense of [kernel §4](docs/constitution/CONVENTIONS.md#k4) and completes it in the sense of rule 5 of [plc-0004-decision-records](docs/policies/plc-0004-decision-records.md#r5), the one law 9 asks the yes to be named in. Since the merge of the kit's first pull request, every `Accepted:` and `Carry-Audit:` trailer stands on a merge commit, never on a branch commit.
  - **The local gate.** The gate is `scripts/git-hooks/prepare-commit-msg`: while `main` is checked out it refuses a commit, an amend, a cherry-pick and a revert — `--no-verify` does not skip it — and lets a merge pass whole, a detached HEAD too; the fix it teaches follows what git leaves behind — a cherry-pick, and a revert still in progress, are aborted first, since git will not switch branches in the middle of one; its fixture is `scripts/git-hooks/tests/run.sh`. Git keeps the three settings the gate and the pull need per clone and never versions them — `core.hooksPath`, `merge.ff` = `false`, and `pull.ff` = `only`, without which a plain `git pull` onto `main` makes a merge commit of its own — so in a fresh clone run `sh scripts/setup-clone.sh` once; `--check` tells whether it has run and the hook file is executable. The setup writes `core.hooksPath` as `scripts/git-hooks`; the check also takes the absolute path the Claude desktop app writes into the configuration of each worktree it makes: a path to `scripts/git-hooks` in the top folder of a checkout that shares the clone's git common directory — the main checkout or one of its worktrees, never another clone — and no other. Git runs the hook file in the folder the value names, so with either value that file must be executable, and under the absolute path it is that checkout's copy of the hook (decision [dec-0095-setup-check-takes-the-app-hooks-path](docs/decisions/dec-0095-setup-check-takes-the-app-hooks-path.md)). What the gate cannot hold, left to the rule "Work starts on a branch", is whatever moves `main` without passing that hook: `git am`, a rebase of `main`, a fast-forward asked for on the command line (`--ff`, `--ff-only`), a push into `main`, `git reset`, `git update-ref`, `git branch -f`; and a merge concluded by hand can carry any content.
  - **The shared `main`.** On the remote, `main` is held by the repository's ruleset: a pull request before every merge, with no approval required, since the kit's only human is the author; no force push; no deletion; no one on its bypass list; the check `gates` green. The repository allows merge commits only, squash and rebase off, and keeps a branch after its merge. So whatever is done to a local `main` in those ways reaches the shared one only through a pull request's merge; a local `main` stays unheld, and the hook stays as the fast local check (decision [dec-0057-pr-flow-merge-names-the-yes](docs/decisions/dec-0057-pr-flow-merge-names-the-yes.md)).
  - **Worktrees and scratch folders.** A session's worktree is a folder of `.claude/worktrees/` in the main checkout, where the Claude desktop app makes its own, and the kit's `.gitignore` keeps that folder out of the tree; a session that makes one itself runs `git worktree add .claude/worktrees/<name> -b work/<name> main` in the main checkout. Scratch work — a copy, a clone, a message file, an agent's probe folder — goes in the session's scratch directory, outside the repository; what must outlive the session goes in `local/`, which git ignores. Before the merge, the session removes the scratch folders that it and its agents made. After the merge, once `git pull` has brought it into the main checkout's `main`, the session removes each worktree it made or the app made for it, with `git worktree remove <path>`, never with `--force`, when `git status` there is clean and the worktree's `HEAD` is in that `main`; the branch stays, and so does a worktree whose commits are not in `main`. A worktree made by or for another session is removed only with the decider's yes. Review holds this bullet; no check does (decision [dec-0111-worktrees-and-scratch-folders](docs/decisions/dec-0111-worktrees-and-scratch-folders.md)).
- <a id="references"></a>**References are clickable; handles are scoped.** The chat rule — every reference to a file, a section or a document a markdown link wherever the file exists, a handle local to its message, decision or session, its source named when a cite crosses that boundary — and the document rule — a bare handle local to its own document, a link to the target's anchor across documents ([requirements A5.5–A5.7](docs/requirements.md#a5)) — are module [`const-referencing`](docs/requirements.md#const-referencing)'s, both taught by its skill; only the chat rule is printed at session start. A commit message is read long after its session, by a reader who has neither the session nor a document outside the repository. So every handle in a commit message names its source: a key of a tracked document names that document in the same message; a handle of a document outside the repository names that document — "hardcode audit G4 B1", never "G4 B1" alone; a handle local to a session or a chat names the work or the decision it came from — "item I3 of the ID-collision follow-up of 2026-10-11". The module's chat rule carries this for a handle local to a message, a decision or a session; the rest is the kit's own. Review holds it (decision [dec-0082-handle-migration-in-records](docs/decisions/dec-0082-handle-migration-in-records.md)). In the Markdown files git lists, save the comparisons, a carry list, code and HTML comments, the kit's `scripts/check-handle-forms.py` holds that a citation of a decision record's ruling links the ruling's anchor, `R7 of [dec-…](…#r7)`; it is another entry of the gate list, run by the kit's CI, with `--self-test` as its fixture (decision [dec-0083-handle-forms-held-by-a-kit-check](docs/decisions/dec-0083-handle-forms-held-by-a-kit-check.md)). The kit's verbose handles are "law 3 of CLAUDE.md" (a form that holds while the laws are numbered), "dial `ns.key`", "requirement [A5.3](docs/requirements.md#a5-3)" or "[aspect A5](docs/requirements.md#a5)"; the kit's reference forms are its `lanes` in `constitution.yaml`. A bare aspect handle, "A5", is held by review and not by a lane, since the letter and a number collide with the message keys of the kit's documents. The gate is the scan of module [`const-referencing`](docs/requirements.md#const-referencing), `sh modules/const-referencing/plugin/scripts/check-references.sh --scan`, an entry of the gate list the kit's CI runs. Module prose is the files under `modules/` and `module-template/`, which name a module "module `const-x`". Everywhere else — every other kit document, and chat — a module is cited by a link to its specification anchor, with the plugin name as text. A kit template under `templates/`, copied into another folder where a relative link would break, names the module plain, with the link's path from the copy's folder in a code span. A frozen research comparison keeps the form it was frozen with ([rule 7 of plc-0005-research](docs/policies/plc-0005-research.md#r7)); in one not yet frozen, review holds the link. A third exception is the module table of the root README, which links a module to its `README.md`, the landing page, so that a reader on GitHub lands on the plain-language page first; outside these three places and module prose, and in chat, the specification anchor stays the citation and the module's handle (decision [dec-0077-module-readme-pages](docs/decisions/dec-0077-module-readme-pages.md)). In the Markdown files git lists, save module prose, the templates and the comparisons, the kit's `scripts/check-module-links.py` holds the link where a module's name stands in a code span after the word "module" or "modules", capitalized or not; a name standing alone, or any name after the first of a plural, is held by review. The check is another entry of the gate list, run by the kit's CI and never at write time, with `--self-test` as its fixture (decisions [dec-0049-module-links-held-by-a-kit-check](docs/decisions/dec-0049-module-links-held-by-a-kit-check.md) and [dec-0051-module-citation-rule-in-the-guide](docs/decisions/dec-0051-module-citation-rule-in-the-guide.md)).

## Developing a module

1. `cp -r module-template/ modules/const-<name>/` — kebab-case, `const-` prefix; name it in its manifest, in `MODULES` of `scripts/gate-list.sh` (a scan also in `GATES`, `job()` and `commands()`), in `.claude-plugin/marketplace.json`, as `const-<name>@<marketplace name>` in `.claude/settings.json`, in its pair in `const-task-close.coverage` of `constitution.yaml` (code `modules/const-<name>/plugin/scripts/**`, `plugin/hooks/**`, `plugin/skills/**`, `tests/**` and `evals/**` for the folders it has, docs its `MODULE.md`) and, where it has a scan, in the `bash check=scan` block of `INSTALL.md` step 8, all held by `scripts/check-gate-lists.py`. The template's relative links gain one `../` level in the copy; the scan of module [`const-referencing`](docs/requirements.md#const-referencing) turns red until they are fixed.
2. Research first: a subagent surveys how this module's matrix rows are addressed today — official Claude Code documentation for the native surface, community harnesses, applicable tools — and returns one dated comparison in kit vocabulary at `docs/research/res-<nnnn>-const-<name>.md` — created through the command of module [`const-locations`](docs/requirements.md#const-locations) from `templates/research-comparison.md`, the subagent filling its placeholders, numbered as rule 6 of [plc-0005-research](docs/policies/plc-0005-research.md#r6) says: candidate approaches, mechanism class, maturity, cost, one recommendation per mechanism with reasoning (decision [dec-0010-module-research-per-module](docs/decisions/dec-0010-module-research-per-module.md)). Earlier design work is a clue set, never a source: nothing enters unverified, and its vocabulary — its aspects numbered one to ten, its D-numbers, its register rulings — does not enter at all. Raw material stays in the subagent; only the comparison returns.
3. Fill `MODULE.md` top-down from the module's matrix rows, moving the module's specification from the requirements document into it and leaving a one-line stub under its anchor there, which stays the module's handle; every section filled or "none" with one line of reasoning. Before writing the artifacts table, confirm or overturn the matrix's recommended enforcement for each row from the comparison, naming on every step down what the native option cannot do.
4. Implement artifacts: hooks/scripts for gates (paths via `${CLAUDE_PLUGIN_ROOT}`), skills for procedures and advisory rules, eval cases, `INSTALL.md` with at most one CLAUDE.md pointer line, and `README.md`, the module's landing page for a reader on GitHub, filled from the template's `README.md`. That page is of the root README's kind — user-facing, informational, in no policy's territory, with no envelope, binding nothing. Its first section opens with the manifest's `description` as written and says the rest in plain words; its second states the problem and how the module resolves it; its implementation is told at a high level, one paragraph per tool, then one on its settings; its links are the module's own `INSTALL.md` and `MODULE.md` alone, never a requirement row, a record or a comparison. Law 2 holds for it by review, since the kit's portability check reads a module's installed components alone. A change to it is routine, like one to the root README (decision [dec-0077-module-readme-pages](docs/decisions/dec-0077-module-readme-pages.md)). The eval cases sit in `evals/<case>/case.yaml`, at least one per module, each named as an `eval` item of the module's acceptance table. A case sits outside its plugin, so it names it: `plugins:` lists `../../plugin`. There is one per skill, held by `tool_used` on `Skill`, by a `regex` on the run's trace that no `Write` or `Edit` comes before the call that names it, by a grader on the work's result where the work leaves one, since the `regex` does not see a change made through `Bash`, and, where the skill's moment is a command, by `tool_order` putting the skill before it. There is one per command a rule makes mandatory, a script the module ships, held by `tool_used` on `Bash` and by a grader on what it did, joined with its skill's case where the skill makes it mandatory at its own moment; and one per start rule that carries a rule of its own, held by `regex` where a pattern can see the rule and by `llm` only where none can. A run starts in an empty folder, so a case that needs a project has a `scaffold.sh` beside it. The parts that install sit in the module's `plugin/` folder, the plugin root: `.claude-plugin/` and `INSTALL.md`, and those of `hooks/`, `skills/`, `scripts/`, `requirements.txt`, `commands/` and `agents/` that the module has. A project installs that folder alone. `MODULE.md`, `README.md`, `tests/` and `evals/` sit beside it and are never installed (decision [dec-0098-modules-install-from-a-plugin-subfolder](docs/decisions/dec-0098-modules-install-from-a-plugin-subfolder.md)). Only `.claude-plugin/plugin.json` lives inside `.claude-plugin/`; the other parts sit at the plugin root. Each manifest names `Apache-2.0` in `license`; in `author`, a module's names the author `NOTICE` names and the template's keeps a placeholder. The Apache License 2.0 is the kit's one license for the whole tree, documents and code alike: `LICENSE` at the kit root is its text, `NOTICE` beside it its credit, which holds no email address, and no file takes a license header (decision [dec-0063-apache-license-with-notice](docs/decisions/dec-0063-apache-license-with-notice.md)). Script runtime (decision [dec-0015-pre-module-audit-rulings](docs/decisions/dec-0015-pre-module-audit-rulings.md)): a script that reads YAML — the envelope, the dials file — is Python 3 with PyYAML; one that reads none may be POSIX shell. A missing interpreter or library is a configuration failure, never a silent pass: exit 1, with where to get the interpreter or the library's install command in the message. The one exception is the shared package. Its failure names the module's `INSTALL.md`, since one command that installs an exact tag could replace a newer release another module needs (R16 of [dec-0099-shared-code-installed-as-a-pip-package](docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r16)). The Python floor has one source, `FLOOR` in `shared/constitution_layer_kit/preflight.py`; every copy of it, records and comparisons aside, and each entry's [`C1`, `C14`, `C15`, `C16` and `C17`](shared/GATE.md#g3) clause are held by the kit's `scripts/check-copies.py`, an entry of the gate list with `--self-test` as its fixture. Every Python script follows the sixteen gate-script rules of [template §6](module-template/MODULE.md#t6) (decisions [dec-0020-gate-script-rules](docs/decisions/dec-0020-gate-script-rules.md), [dec-0026-imports-at-the-top](docs/decisions/dec-0026-imports-at-the-top.md)). The configuration of the linter, formatter and type checker — `ruff`, `mypy --strict` — is the kit's own development routine, in `pyproject.toml` at the kit root with the commands to run; no module ships tool configuration. Its lint holds ruff's `C901` at a complexity of 15 over the modules, the shared code and the kit's scripts. The functions above it when the rule came in, on 2026-10-13, were split below it since and lost their marks. Any function above it, one of those included, carries `# noqa: C901` only where a change marks it, with its reason on the `def` line; a reason in a module's files or in the shared code names no record. A new mark is held by review, and a commit of the change that adds it says in its message why the function stays whole (decisions [dec-0088-ruff-complexity-limit](docs/decisions/dec-0088-ruff-complexity-limit.md) and [dec-0090-complexity-marks-split-away](docs/decisions/dec-0090-complexity-marks-split-away.md)). Shared gate code: what every gate needs has one source under `shared/`, described in [kit-shared-gate-code](shared/GATE.md). It reaches a project as the Python distribution `constitution-layer-kit`, which pip installs from a git tag, and a plugin holds none of it. A module's Python entry files state the release they need, `REQUIRES`, import the package, and call `cli.version_failure` right after they import `cli`. Its `INSTALL.md` gives the pip command at that tag, and `scripts/check-copies.py` holds both. Its tests link to the package and to the module's own packages by relative symbolic links. The package holds the shared test files in its subpackage `testing`. A plain file, `tests/test_shared_items.py`, brings the shared items in. `scripts/check-shared-links.py` is the gate, red for anything at `plugin/scripts/constitution_layer_kit` (R5, R6, R7, R8 and R15 of [dec-0099-shared-code-installed-as-a-pip-package](docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r5); R2 of [dec-0107-shared-test-files-in-the-distribution](docs/decisions/dec-0107-shared-test-files-in-the-distribution.md#r2) for the plain file). A module fills the interface of [its §2](shared/GATE.md#g2), and writes only its own model, messages, checks and modes. What may be admitted there, and when a shared part may be widened for one module, is rule 2 of [plc-0009-shared-code](docs/policies/plc-0009-shared-code.md#r2); a change to the package raises its `__version__` as [rule 11 of that policy](docs/policies/plc-0009-shared-code.md#r11) says. A change to the shared code bumps no module's version by itself: after it, a module's version moves only when the module needs a later release and raises its `REQUIRES`, a bump made by hand ([rule 7 of that policy](docs/policies/plc-0009-shared-code.md#r7)). Territory matching in the default dialect goes through `git check-ignore`, verified at authoring.
5. Prove twice: fixtures against a bare temp repo (the parts of laws 2–3 a run can test, in the kit's CI: the [A12.1](docs/requirements.md#a12-1) grep of law 2, `scripts/check-portability.py`, and each module's bare-repo install alone, from the change's GitHub repository and branch — a pull request's head, or `main` on a push — `scripts/check-bare-install.py`, entries of the gate list each with its `--self-test` as its fixture; the rest of law 3, sibling references only as optional enhancements, by review), then live. The live proof is in this repository for modules whose objects the kit holds: governed documents of a kind it holds, the code territories its own current-state documents describe, its own session conduct, both the rules its guide keeps and those its modules carry (the kit is consumer zero) — and in a consumer project: session in the project, plugin loaded from the module's `plugin/` folder in this repo (check current plugin-dir and marketplace mechanics against the official docs, never memory). A project's install holds no tests. A project may run the fixtures from a kit clone at the commit its install records. When no consumer exists yet, the record and the yes follow the kit-live proof; the consumer-live proof is a named step of the consumer's bootstrap, and a finding there is a fix — with a version bump once the module is published — priced by its stakes. Each acceptance item names the matrix rows it proves ([template §10](module-template/MODULE.md#t10)). The eval cases are proven by a local run, `python3 scripts/run-evals.py --token-file <file> --module <name>`, whose receipt `scripts/check-eval-receipts.py` holds. A `live` item that proves a session's behaviour alone, and whose proof does not run in a consumer project, becomes an `eval` item where a case covers it whole: the `eval` item replaces it, and the proof it asks for is owed no more. Every other `live` item stays `live`, and the proof it asks for stays owed: one that no case covers whole, one that proves a scan over the kit's tree, and one whose proof runs in a consumer project, deferred or not. A scan item and a consumer-project item stay `live` because an eval runs in an empty folder, which a scaffold seeds where a case needs a project: it proves no scan over the kit's tree, and it runs in no consumer project. An `eval` item counts as run when its module's receipt is current: green when its last attempt passes, red when it does not. That is a run that was declared, not one the kit sees. The kit's `scripts/check-aspects.py` holds those tags, one entry of the gate list; with `--run` it runs the tests and gives each matrix row the result of its own items — a status derived on each run and stored nowhere, never a green for a row no run examined. `--module <name>` narrows the run, `--self-test` is its fixture (decision [dec-0054-acceptance-items-name-their-rows](docs/decisions/dec-0054-acceptance-items-name-their-rows.md)).
6. Validate fresh-context before the human yes, in two passes, both mandatory. First, a subagent holding only the module's files, the template, this file, and the module's matrix rows — never the authoring reasoning — reviews against laws 2–7 and every template section. Its mutation probes run through the `mutation-probe-runner` agent of `.claude/agents/`, and the live items of step 5 through the `live-proof-runner` agent there, each on a copy or a clone in the scratch directory, the kit read-only to both. A headless run in a clone or copy the platform has not been told to trust silently loads no plugin through settings, so the runners pass `--plugin-dir` per module. Second, the carry audit of [rule 2 of plc-0004-decision-records](docs/policies/plc-0004-decision-records.md#r2), run through the kit's `carry-audit` skill — its regression and confirming readers the `regression-reader` and `confirming-reader` agents of `.claude/agents/`: fresh readers, each round pinned to one commit, their scope computed by `scripts/check-carry-lists.py --scope` and never chosen. Full readers read in full the records the change adds or edits and those the module's decisions section cites; regression readers, every other record that cites a file the change touched, asked only whether that file still states what the record ruled. For each added record, a blind reader who never sees it answers the author's questions from the current-state documents alone. Where the change makes wording edits in accepted records or frozen comparisons, one more reader reads each against the kinds their policies list. Every finding of either pass is fixed or justified in a commit message of the change, the merge commit included — never only in the pull request's description, which git does not keep (decision [dec-0009-module-routine-validation-and-inputs](docs/decisions/dec-0009-module-routine-validation-and-inputs.md), and R9 of [dec-0057-pr-flow-merge-names-the-yes](docs/decisions/dec-0057-pr-flow-merge-names-the-yes.md#r9) for the commit message). The commit that names the yes carries the audit's receipt of [rule 5 of plc-0004-decision-records](docs/policies/plc-0004-decision-records.md#r5); `scripts/check-carry-lists.py` gates the carry lists, every ruling's anchor and the receipt — which shows that an audit was declared and accounted for, not that it was run — and whether a ruling is carried stays the readers' judgment.
7. Version bump on every change of a module once published, save a change to the shared code, which bumps none by itself (step 4); consumer projects update by version. A draft, at `0.0.x`, need not be bumped — for a change of its own or a consumer-live finding alike — and may still be bumped within `0.0.x` (decision [dec-0053-drafts-keep-their-versions](docs/decisions/dec-0053-drafts-keep-their-versions.md)).

## Never in this repository

Project content or references (law 2). References to any location outside this repository other than a public URL — no local folder, no sibling repository, no absolute filesystem path; information from such places enters only after verification, cited to the public source that verified it (in markdown files the scan of module [`const-referencing`](docs/requirements.md#const-referencing) turns red on an absolute path under a home directory or a `file:` link — scripts and configuration are held by review, and a module's installed components also by the kit's `scripts/check-portability.py` for the forms of [requirement A12.1](docs/requirements.md#a12-1)). A placeholder path in install instructions — a consumer's clone location, the platform's own configuration directory — is not a reference. Knowledge-layer content (separate layer, separate concern). A parallel component model — Claude Code's plugins/skills/hooks/agents are the mechanical kernel; this repo adds semantics only. Machinery for failures no consumer has hit — growth is friction-earned, via consumer commit notes recurring on a theme. A count of the modules in the install guide or the README: a number word drifts without a sound when a module is added, so both name the modules without one. The lists a new module joins that `scripts/check-gate-lists.py` holds are the ones step 1 of "Developing a module" names; the module table of the root README is held by review.
