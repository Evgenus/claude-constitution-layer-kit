# Constitution Kit — Session Guide

This repository is the **constitution kit**: a portable, project-agnostic governance layer for Claude Code projects, shipped as plugins. It contains the semantic kernel, the module template, and the modules. It contains **no project content, ever**.

Read before any work:
- `INTENT.md` — what this repo is for and what it is not.
- `docs/constitution/CONVENTIONS.md` — the semantic kernel (one page). Authoritative for all vocabulary.
- `module-template/MODULE.md` — the fixed shape every module fills.
- `docs/requirements.md` — the traceability matrix and module specifications (requirement rows per module).
- `docs/rollout-plan.md` — the phases, the kit's own active task-record; not a reading assignment.
- `constitution.yaml` — the kit's own dials file; its `root_policy` key locates the policies that govern this repository's documents ([kernel §3](docs/constitution/CONVENTIONS.md#k3)). Not a reading assignment: open a policy only when working in its territory. It is written in block style — one key or one `- ` item per line; flow style, `[]` or `{}`, only for an empty list or mapping. That style is held by `python3 scripts/check-yaml-style.py`, run by the kit's CI. Its `--fix` rewrites the file keeping every comment, anchor, alias and quote as written. The kit's CI also validates the file against the kernel's dials schema with a real validator, `scripts/check-dials-schema.py`. The YAML inside Markdown fences is not under the rule, and a consumer's file is the consumer's (decision [dec-0037-dials-file-block-style](docs/decisions/dec-0037-dials-file-block-style.md)).
- `docs/research/` — one current dated comparison per module, written by its module's own research round. It also holds one per mechanism of the kit's own tooling whose change asked for one. A superseded one is kept beside it while cited. Not a reading assignment: open one when changing a mechanism.
- `shared/GATE.md` — the code every gate shares. Read it before authoring a module with a gate.

## Laws of this repository

1. <a id="law-1"></a>**Kernel is authoritative; never restate it.** Modules and documents reference kernel definitions by name — duplication is a defect.
2. <a id="law-2"></a>**Portability ([kernel §6](docs/constitution/CONVENTIONS.md#k6)):** no file in a module references any project — no paths, names, repos, values. Project specifics enter only through the module's dials namespace. Test: the module installs and operates on an empty repository using defaults alone.
3. <a id="law-3"></a>**Sibling independence:** modules depend on the kernel and nothing else. Sibling references only as optional enhancements ("when `const-x` is installed…"). The kit's shared gate code is not a sibling: it has one source under `shared/`. A module's plugin imports it from the installed Python distribution `constitution-layer-kit` and never carries it. The module's tests reach it by links. A module never reaches another module through it (R7 and R8 of [dec-0099-shared-code-installed-as-a-pip-package](docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r7)). Test: kernel + this module + the shared package alone on a bare repo is a functioning installation. If a module seems to need a sibling, the shared concept belongs in the kernel. Raise that as a `process`-stakes decision instead of coupling.
4. <a id="law-4"></a>**A module implements exactly its matrix rows.** Its `MODULE.md` cites them. Content beyond its rows is scope creep; a missing row is incompleteness. Both are review findings.
5. <a id="law-5"></a>**Enforcement honesty:** every artifact is `gate` (deterministic, red = fix), `advisory` (judgment-shaping) or `grant` (a hook's deterministic answer of `allow` for a command the module itself ships). A grant judges nothing, blocks nothing and is never red. The kind is declared, never blurred. Nothing judgment-based is dressed as a check (decision [dec-0110-new-document-command-granted-by-a-hook](docs/decisions/dec-0110-new-document-command-granted-by-a-hook.md) for the third kind).
6. <a id="law-6"></a>**Teaching errors:** every gate's error message states what failed, why the rule exists (one clause), and the exact fix. Error messages are designed content, reviewed like code.
7. <a id="law-7"></a>**Every gate ships its red→green fixture** in `modules/<name>/tests/` — one input that fails without the check and passes with it. Every grant ships its two halves, the forms it allows and the forms it must not, as [kit-template-slot-guidance](module-template/slot-guidance.md#s2) says.
8. <a id="law-8"></a>**Sizes in characters, never tokens.**
9. <a id="law-9"></a>**Kit decisions follow the kernel's own stakes triage.** Routine → act, note in the commit. `process` (most kit changes) → decision record in `docs/decisions/`, one human yes on the change. The yes is named in the merge commit of its pull request. That merge is the decider's own, since the kit has no second human to approve. Decisions [dec-0016-yes-on-the-change](docs/decisions/dec-0016-yes-on-the-change.md) and [dec-0057-pr-flow-merge-names-the-yes](docs/decisions/dec-0057-pr-flow-merge-names-the-yes.md) say so. Kernel changes are always recorded. Record lifecycle, supersession, and deletion: [kernel §1](docs/constitution/CONVENTIONS.md#k1) and [kernel §5](docs/constitution/CONVENTIONS.md#k5) — not restated here.

## Session conduct

*Every kit session, save the escape below, loads the kit's modules as plugins from its committed `.claude/settings.json`. That file declares the clone as the marketplace `claude-constitution-layer-kit` by a relative directory source and enables each module. Nothing per clone is needed to load them, in a folder trusted once (decision [dec-0043-kit-plugins-through-project-settings](docs/decisions/dec-0043-kit-plugins-through-project-settings.md)). A module whose gate blocks its own fix is switched off for one clone, its skills and session-start text with it. The switch is `"<module>@claude-constitution-layer-kit": false` under `enabledPlugins` in that clone's `.claude/settings.local.json`. It is the one per-clone write to the plugin settings, in a file the kit's `.gitignore` keeps out of the tree. The rules the modules ship reach the model from them, and are not restated here. They reach it at session start, as skills and as hooks. A skill's description asks for it to be loaded at its moment, and a module's hooks also name it where they meet that moment. This block keeps what no module carries. Of the kit's own agents in `.claude/agents/`, the implementer is the one that writes the kit's tracked files. It lists the `Skill` tool, so that it can load a skill that its start context or a hook's red names. The others write nothing tracked and keep their tools. So a pointer to a skill that reaches them asks nothing of them (decision [dec-0079-skills-named-at-their-moment](docs/decisions/dec-0079-skills-named-at-their-moment.md)). The gates of those plugins import the shared package from the `python3` the session runs, so each clone installs it once, as [kit-install-guide](INSTALL.md) says. The sessions run that release and not the working tree, so a broken shared change cannot stop the gates that guard its fix. A module that requires a later release stops with `C16` until that release is installed. That stop blocks nothing in hook mode (R9 and R23 of [dec-0099-shared-code-installed-as-a-pip-package](docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r9)).*

- **Work starts on a branch.** Every change — one commit or many, routine or recorded — is made on its own branch `work/<name>`, cut from `main`. Its name part is a short kebab-case name of the work. The change reaches `main` as the merge commit of one pull request on the kit's public GitHub remote, `origin`. The branch is pushed, `git push -u origin work/<name>`, the pull request opened, `gh pr create`, and merged with `gh pr merge <n> --merge --subject "Work: <name>"`. A local `main` then follows by `git pull`, a fast-forward only. The branch is kept forever after the merge, in the clone and on the remote. Nothing is committed on `main` itself.
  - **Before the merge.** The range check of module [`const-task-close`](docs/requirements.md#const-task-close) is green on the branch: `PYTHONPATH="$PWD/shared" sh modules/const-task-close/plugin/scripts/check-task-close.sh --scan`. A plugin carries no shared code, so a run by hand needs the installed package or that path; `sh scripts/gate-list.sh --run task-close` sets it. The check reads the kit's `coverage` map in `constitution.yaml`. A change that touches code a current-state document describes updates that document in the same change. Or it declares no impact by a `No-Doc-Impact: <pair> — <reason>` trailer on one of its commits, in the message's last paragraph. It never declares it by the pull request's description alone, which the kit's CI does not give the check. With `--scan --change <merge>` the check audits a landed change. When `main` has moved since the branch's last CI run, the branch merges `main` and waits for CI green again before `gh pr merge`. Review holds this, since the ruleset does not ask a branch to be up to date.
  - **The gate list and CI.** Read [the gate-list page](docs/guide/gate-list-and-ci.md) before a change to the kit's tooling — the gate list, a kit check, the workflow, the eval runner. Read it also when a gate of the list or a job of CI is red. It says what the gate list and its CI run, and the one local run a change owes.
  - **The yes.** Where the change needs a yes, the merge gives it. The decider merges the pull request, or says yes in chat and has the session merge in the decider's name. The merge commit names the yes and carries the `Accepted:` and `Carry-Audit:` trailers in its last paragraph. They are written with `--body`, or into the merge message on the forge's page. It is the commit that lands the change in the sense of [kernel §4](docs/constitution/CONVENTIONS.md#k4). It also completes the change in the sense of rule 5 of [plc-0004-decision-records](docs/policies/plc-0004-decision-records.md#r5). It is the commit law 9 asks the yes to be named in. Since the merge of the kit's first pull request, every `Accepted:` and `Carry-Audit:` trailer stands on a merge commit, never on a branch commit.
  - **The local gate.** The gate is `scripts/git-hooks/prepare-commit-msg`. While `main` is checked out it refuses a commit, an amend, a cherry-pick and a revert — `--no-verify` does not skip it. It lets a merge pass whole, a detached HEAD too. The fix it teaches follows what git leaves behind. A cherry-pick, and a revert still in progress, are aborted first, since git will not switch branches in the middle of one. Its fixture is `scripts/git-hooks/tests/run.sh`. Git keeps per clone, and never versions, the three settings the gate and the pull need. They are `core.hooksPath`, `merge.ff` = `false`, and `pull.ff` = `only`; without the last, a plain `git pull` onto `main` makes a merge commit of its own. So in a fresh clone run `sh scripts/setup-clone.sh` once. Its `--check` tells whether it has run and the hook file is executable. The setup writes `core.hooksPath` as `scripts/git-hooks`. The check also takes the absolute path the Claude desktop app writes into the configuration of each worktree it makes. It is a path to `scripts/git-hooks` in the top folder of a checkout that shares the clone's git common directory. Such a checkout is the main checkout or one of its worktrees, never another clone. The check takes no other path. Git runs the hook file in the folder the value names, so with either value that file must be executable. Under the absolute path it is that checkout's copy of the hook (decision [dec-0095-setup-check-takes-the-app-hooks-path](docs/decisions/dec-0095-setup-check-takes-the-app-hooks-path.md)). The gate cannot hold whatever moves `main` without passing that hook; that is left to the rule "Work starts on a branch". Such moves are `git am`, a rebase of `main`, a fast-forward asked for on the command line (`--ff`, `--ff-only`), a push into `main`, `git reset`, `git update-ref` and `git branch -f`. A merge concluded by hand can also carry any content.
  - **The shared `main`.** On the remote, the repository's ruleset holds `main`. It asks for a pull request before every merge, with no approval required, since the kit's only human is the author. It allows no force push and no deletion, puts no one on its bypass list, and asks for the check `gates` green. GitHub asks the owner's approval before a fork's workflows run for all external contributors, its setting `all_external_contributors`. Such a pull request then runs the same CI as any other (decision [dec-0112-email-forks-and-pypi-before-the-switch](docs/decisions/dec-0112-email-forks-and-pypi-before-the-switch.md)). The repository allows merge commits only, squash and rebase off, and keeps a branch after its merge. So whatever is done to a local `main` in those ways reaches the shared one only through a pull request's merge. A local `main` stays unheld, and the hook stays as the fast local check (decision [dec-0057-pr-flow-merge-names-the-yes](docs/decisions/dec-0057-pr-flow-merge-names-the-yes.md)).
  - **Worktrees and scratch folders.** A session's worktree is a folder of `.claude/worktrees/` in the main checkout, where the Claude desktop app makes its own. The hooks of a session in a worktree run the plugins of the main checkout, the one folder user settings keep for the kit's marketplace. So such a hook can disagree with a scan run in the worktree, which runs the worktree's own scripts. The kit's `.gitignore` keeps `.claude/worktrees/` out of the tree. A session that makes a worktree itself runs `git worktree add .claude/worktrees/<name> -b work/<name> main` at the top of the main checkout. Scratch work — a copy, a clone, a message file, an agent's probe folder — goes in the session's scratch directory, outside the repository. What must outlive the session goes in `local/`, which git ignores. Before the merge, the session removes the scratch folders that it and its agents made. After the merge, once `git pull` has brought the merge into the local `main`, the session removes each worktree that it or its agents made. It removes it with `git worktree remove <path>`, never with `--force`, when `git status` there is clean and the worktree's `HEAD` is in the local `main`. The branch stays, and so does a worktree whose commits are not in the local `main`. A worktree the app made, or one another session made, is removed only with the decider's yes. Review holds this bullet; no check does (decision [dec-0111-worktrees-and-scratch-folders](docs/decisions/dec-0111-worktrees-and-scratch-folders.md)).
- <a id="references"></a>**References are clickable; handles are scoped.** The chat rule and the document rule are module [`const-referencing`](docs/requirements.md#const-referencing)'s, both taught by its skill. The chat rule makes every reference to a file, a section or a document a markdown link wherever the file exists. In chat a handle is local to its message, decision or session, and its source is named when a cite crosses that boundary. The document rule makes a bare handle local to its own document. Across documents it asks for a link to the target's anchor ([requirements A5.5–A5.7](docs/requirements.md#a5)). Only the chat rule is printed at session start. A commit message is read long after its session, by a reader who has neither the session nor a document outside the repository. So every handle in a commit message names its source. A key of a tracked document names that document in the same message. A handle of a document outside the repository names that document — "hardcode audit G4 B1", never "G4 B1" alone. A handle local to a session or a chat names the work or the decision it came from. An example is "item I3 of the ID-collision follow-up of 2026-10-11". The module's chat rule carries this for a handle local to a message, a decision or a session. The rest is the kit's own. Review holds it (decision [dec-0082-handle-migration-in-records](docs/decisions/dec-0082-handle-migration-in-records.md)). The kit's `scripts/check-handle-forms.py` holds that a citation of a decision record's ruling links the ruling's anchor, `R7 of [dec-…](…#r7)`. It holds this in the Markdown files git lists, save the comparisons, a carry list, code and HTML comments. It is another entry of the gate list, run by the kit's CI. Its fixture is `--self-test` (decision [dec-0083-handle-forms-held-by-a-kit-check](docs/decisions/dec-0083-handle-forms-held-by-a-kit-check.md)). The kit's verbose handles are "law 3 of CLAUDE.md", "dial `ns.key`", "requirement [A5.3](docs/requirements.md#a5-3)" or "[aspect A5](docs/requirements.md#a5)". The first is a form that holds while the laws are numbered. The kit's reference forms are its `lanes` in `constitution.yaml`. A bare aspect handle, "A5", is held by review and not by a lane. This is because the letter and a number collide with the message keys of the kit's documents. The gate is the scan of module [`const-referencing`](docs/requirements.md#const-referencing), `sh modules/const-referencing/plugin/scripts/check-references.sh --scan`, an entry of the gate list the kit's CI runs. Module prose is the files under `modules/` and `module-template/`, which name a module "module `const-x`". Everywhere else — every other kit document, and chat — a module is cited by a link to its specification anchor, with the plugin name as text. A kit template under `templates/` is copied into another folder, where a relative link would break. So it names the module plain, with the link's path from the copy's folder in a code span. A frozen research comparison keeps the form it was frozen with ([rule 7 of plc-0005-research](docs/policies/plc-0005-research.md#r7)). In one not yet frozen, review holds the link. A third exception is the module table of the root README, which links a module to its `README.md`, the landing page. That way a reader on GitHub lands on the plain-language page first. Outside these three places and module prose, and in chat, the specification anchor stays the citation. It also stays the module's handle (decision [dec-0077-module-readme-pages](docs/decisions/dec-0077-module-readme-pages.md)). The kit's `scripts/check-module-links.py` holds the link where a module's name stands in a code span after the word "module" or "modules", capitalized or not. It holds it in the Markdown files git lists, save module prose, the templates and the comparisons. A name standing alone, or any name after the first of a plural, is held by review. The check is another entry of the gate list, run by the kit's CI and never at write time. Its fixture is `--self-test` (decisions [dec-0049-module-links-held-by-a-kit-check](docs/decisions/dec-0049-module-links-held-by-a-kit-check.md) and [dec-0051-module-citation-rule-in-the-guide](docs/decisions/dec-0051-module-citation-rule-in-the-guide.md)).

## Developing a module

Before a module is authored or changed — its document, its plugin, its tests or its eval cases — read [the module-development page](docs/guide/developing-a-module.md). It gives the seven steps, from the copy of the template to the version bump, and the rules each step holds.

## Never in this repository

Project content or references (law 2). References to any location outside this repository other than a public URL — no local folder, no sibling repository, no absolute filesystem path. Information from such places enters only after verification, cited to the public source that verified it. In markdown files the scan of module [`const-referencing`](docs/requirements.md#const-referencing) turns red on an absolute path under a home directory or a `file:` link. Scripts and configuration are held by review. For the forms of [requirement A12.1](docs/requirements.md#a12-1), the kit's `scripts/check-portability.py` also holds a module's installed components. A placeholder path in install instructions — a consumer's clone location, the platform's own configuration directory — is not a reference. Knowledge-layer content (separate layer, separate concern). A parallel component model — Claude Code's plugins/skills/hooks/agents are the mechanical kernel; this repo adds semantics only. Machinery for failures no consumer has hit — growth is friction-earned, via consumer commit notes recurring on a theme. A count of the modules in the install guide or the README. A number word drifts without a sound when a module is added, so both name the modules without one. The lists a new module joins that `scripts/check-gate-lists.py` holds are the ones [step 1 of the module-development page](docs/guide/developing-a-module.md#s1) names. The module table of the root README is held by review.
