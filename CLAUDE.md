# Constitution Kit — Session Guide

This repository is the **constitution kit**: a portable, project-agnostic governance layer for Claude Code projects, shipped as plugins. It contains the semantic kernel, the module template, and the modules. It contains **no project content, ever**.

Read before any work:
- `INTENT.md` — what this repo is for and what it is not.
- `docs/constitution/CONVENTIONS.md` — the semantic kernel (one page). Authoritative for all vocabulary.
- `module-template/MODULE.md` — the fixed shape every module fills.
- `docs/requirements.md` — the traceability matrix and module specifications (requirement rows per module).
- `docs/rollout-plan.md` — the phases, the kit's own active task-record; not a reading assignment.
- `constitution.yaml` — the kit's own dials file; its `root_policy` key locates the policies that govern this repository's documents ([kernel §3](docs/constitution/CONVENTIONS.md#k3)). Not a reading assignment: open a policy only when working in its territory. Written in block style — one key or one `- ` item per line; flow style, `[]` or `{}`, only for an empty list or mapping — held by `python3 scripts/check-yaml-style.py`, run by the kit's CI; its `--fix` rewrites the file keeping every comment, anchor, alias and quote as written; the kit's CI also validates the file against the kernel's dials schema with a real validator, `scripts/check-dials-schema.py`; the YAML inside Markdown fences is not under the rule, and a consumer's file is the consumer's (decision [dec-0037-dials-file-block-style](docs/decisions/dec-0037-dials-file-block-style.md)).
- `docs/research/` — one current dated comparison per module, written by its module's own research round, and one per mechanism of the kit's own tooling whose change asked for one; a superseded one is kept beside it while cited. Not a reading assignment: open one when changing a mechanism.
- `shared/GATE.md` — the code every gate shares. Read it before authoring a module with a gate.

## Laws of this repository

1. <a id="law-1"></a>**Kernel is authoritative; never restate it.** Modules and documents reference kernel definitions by name — duplication is a defect.
2. <a id="law-2"></a>**Portability ([kernel §6](docs/constitution/CONVENTIONS.md#k6)):** no file in a module references any project — no paths, names, repos, values. Project specifics enter only through the module's dials namespace. Test: the module installs and operates on an empty repository using defaults alone.
3. <a id="law-3"></a>**Sibling independence:** modules depend on the kernel and nothing else. Sibling references only as optional enhancements ("when `const-x` is installed…"). The kit's shared gate code is not a sibling: it has one source under `shared/`, which a module's plugin imports from the installed Python distribution `constitution-layer-kit` and never carries, and which the module's tests reach by links — a module never reaches another module through it (R7 and R8 of [dec-0099-shared-code-installed-as-a-pip-package](docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r7)). Test: kernel + this module + the shared package alone on a bare repo is a functioning installation. If a module seems to need a sibling, the shared concept belongs in the kernel — raise that as a `process`-stakes decision instead of coupling.
4. <a id="law-4"></a>**A module implements exactly its matrix rows.** Its `MODULE.md` cites them. Content beyond its rows is scope creep; a missing row is incompleteness. Both are review findings.
5. <a id="law-5"></a>**Enforcement honesty:** every artifact is `gate` (deterministic, red = fix), `advisory` (judgment-shaping) or `grant` (a hook's deterministic answer of `allow` for a command the module itself ships, which judges nothing, blocks nothing and is never red) — declared, never blurred. Nothing judgment-based is dressed as a check (decision [dec-0110-new-document-command-granted-by-a-hook](docs/decisions/dec-0110-new-document-command-granted-by-a-hook.md) for the third kind).
6. <a id="law-6"></a>**Teaching errors:** every gate's error message states what failed, why the rule exists (one clause), and the exact fix. Error messages are designed content, reviewed like code.
7. <a id="law-7"></a>**Every gate ships its red→green fixture** in `modules/<name>/tests/` — one input that fails without the check and passes with it; every grant ships its two halves, the forms it allows and the forms it must not, as template §10 says.
8. <a id="law-8"></a>**Sizes in characters, never tokens.**
9. <a id="law-9"></a>**Kit decisions follow the kernel's own stakes triage.** Routine → act, note in the commit. `process` (most kit changes) → decision record in `docs/decisions/`, one human yes on the change, named in the merge commit of its pull request — the decider's own merge, since the kit has no second human to approve (decisions [dec-0016-yes-on-the-change](docs/decisions/dec-0016-yes-on-the-change.md) and [dec-0057-pr-flow-merge-names-the-yes](docs/decisions/dec-0057-pr-flow-merge-names-the-yes.md)). Kernel changes are always recorded. Record lifecycle, supersession, and deletion: [kernel §1](docs/constitution/CONVENTIONS.md#k1) and [kernel §5](docs/constitution/CONVENTIONS.md#k5) — not restated here.

## Session conduct

*Every kit session, save the escape below, loads the kit's modules as plugins from its committed `.claude/settings.json`, which declares the clone as the marketplace `claude-constitution-layer-kit` by a relative directory source and enables each module — nothing per clone to load them, in a folder trusted once (decision [dec-0043-kit-plugins-through-project-settings](docs/decisions/dec-0043-kit-plugins-through-project-settings.md)). A module whose gate blocks its own fix is switched off for one clone, its skills and session-start text with it, by `"<module>@claude-constitution-layer-kit": false` under `enabledPlugins` in that clone's `.claude/settings.local.json`, the one per-clone write to the plugin settings, a file the kit's `.gitignore` keeps out of the tree. The rules the modules ship reach the model from them — at session start, as skills, whose descriptions ask to be loaded at their moment and which a module's hooks also name where they meet it, and as hooks — and are not restated here; this block keeps what no module carries. Of the kit's own agents in `.claude/agents/`, the one that writes the kit's tracked files, the implementer, lists the `Skill` tool, so that it can load a skill that its start context or a hook's red names; the others write nothing tracked and keep their tools, so a pointer to a skill that reaches them asks nothing of them (decision [dec-0079-skills-named-at-their-moment](docs/decisions/dec-0079-skills-named-at-their-moment.md)). The gates of those plugins import the shared package from the `python3` the session runs, so each clone installs it once, as [kit-install-guide](INSTALL.md) says. The sessions run that release and not the working tree, so a broken shared change cannot stop the gates that guard its fix. A module that requires a later release stops with `C16`, which blocks nothing in hook mode, until that release is installed (R9 and R23 of [dec-0099-shared-code-installed-as-a-pip-package](docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r9)).*

- **Work starts on a branch.** Every change — one commit or many, routine or recorded — is made on its own branch `work/<name>`, a short kebab-case name of the work, cut from `main`, and reaches `main` as the merge commit of one pull request on the kit's public GitHub remote, `origin`: the branch pushed, `git push -u origin work/<name>`, the pull request opened, `gh pr create`, and merged with `gh pr merge <n> --merge --subject "Work: <name>"`; a local `main` then follows by `git pull`, a fast-forward only. The branch is kept forever after the merge, in the clone and on the remote. Nothing is committed on `main` itself.
  - **Before the merge.** The range check of module [`const-task-close`](docs/requirements.md#const-task-close) is green on the branch — `PYTHONPATH="$PWD/shared" sh modules/const-task-close/plugin/scripts/check-task-close.sh --scan` (a plugin carries no shared code, so a run by hand needs the installed package or that path; `sh scripts/gate-list.sh --run task-close` sets it), over the kit's `coverage` map in `constitution.yaml`: a change that touches code a current-state document describes updates that document in the same change or declares no impact by a `No-Doc-Impact: <pair> — <reason>` trailer on one of its commits, in the message's last paragraph, never by the pull request's description alone, which the kit's CI does not give the check; with `--scan --change <merge>` it audits a landed change. When `main` has moved since the branch's last CI run, the branch merges `main` and waits for CI green again before `gh pr merge`; review holds this, since the ruleset does not ask a branch to be up to date.
  - **The gate list and CI.** Before a change to the kit's tooling — the gate list, a kit check, the workflow, the eval runner — and when a gate of the list or a job of CI is red, read [the gate-list page](docs/guide/gate-list-and-ci.md): what the gate list and its CI run, and the one local run a change owes.
  - **The yes.** Where the change needs a yes, the merge gives it: the decider merges the pull request, or says yes in chat and has the session merge in the decider's name. The merge commit names the yes and carries the `Accepted:` and `Carry-Audit:` trailers in its last paragraph, written with `--body`, or into the merge message on the forge's page. It is the commit that lands the change in the sense of [kernel §4](docs/constitution/CONVENTIONS.md#k4) and completes it in the sense of rule 5 of [plc-0004-decision-records](docs/policies/plc-0004-decision-records.md#r5), the one law 9 asks the yes to be named in. Since the merge of the kit's first pull request, every `Accepted:` and `Carry-Audit:` trailer stands on a merge commit, never on a branch commit.
  - **The local gate.** The gate is `scripts/git-hooks/prepare-commit-msg`: while `main` is checked out it refuses a commit, an amend, a cherry-pick and a revert — `--no-verify` does not skip it — and lets a merge pass whole, a detached HEAD too; the fix it teaches follows what git leaves behind — a cherry-pick, and a revert still in progress, are aborted first, since git will not switch branches in the middle of one; its fixture is `scripts/git-hooks/tests/run.sh`. Git keeps the three settings the gate and the pull need per clone and never versions them — `core.hooksPath`, `merge.ff` = `false`, and `pull.ff` = `only`, without which a plain `git pull` onto `main` makes a merge commit of its own — so in a fresh clone run `sh scripts/setup-clone.sh` once; `--check` tells whether it has run and the hook file is executable. The setup writes `core.hooksPath` as `scripts/git-hooks`; the check also takes the absolute path the Claude desktop app writes into the configuration of each worktree it makes: a path to `scripts/git-hooks` in the top folder of a checkout that shares the clone's git common directory — the main checkout or one of its worktrees, never another clone — and no other. Git runs the hook file in the folder the value names, so with either value that file must be executable, and under the absolute path it is that checkout's copy of the hook (decision [dec-0095-setup-check-takes-the-app-hooks-path](docs/decisions/dec-0095-setup-check-takes-the-app-hooks-path.md)). What the gate cannot hold, left to the rule "Work starts on a branch", is whatever moves `main` without passing that hook: `git am`, a rebase of `main`, a fast-forward asked for on the command line (`--ff`, `--ff-only`), a push into `main`, `git reset`, `git update-ref`, `git branch -f`; and a merge concluded by hand can carry any content.
  - **The shared `main`.** On the remote, `main` is held by the repository's ruleset: a pull request before every merge, with no approval required, since the kit's only human is the author; no force push; no deletion; no one on its bypass list; the check `gates` green. GitHub asks the owner's approval before a fork's workflows run for all external contributors, its setting `all_external_contributors`, and such a pull request then runs the same CI as any other (decision [dec-0112-email-forks-and-pypi-before-the-switch](docs/decisions/dec-0112-email-forks-and-pypi-before-the-switch.md)). The repository allows merge commits only, squash and rebase off, and keeps a branch after its merge. So whatever is done to a local `main` in those ways reaches the shared one only through a pull request's merge; a local `main` stays unheld, and the hook stays as the fast local check (decision [dec-0057-pr-flow-merge-names-the-yes](docs/decisions/dec-0057-pr-flow-merge-names-the-yes.md)).
  - **Worktrees and scratch folders.** A session's worktree is a folder of `.claude/worktrees/` in the main checkout, where the Claude desktop app makes its own, and the kit's `.gitignore` keeps that folder out of the tree; a session that makes one itself runs `git worktree add .claude/worktrees/<name> -b work/<name> main` at the top of the main checkout. Scratch work — a copy, a clone, a message file, an agent's probe folder — goes in the session's scratch directory, outside the repository; what must outlive the session goes in `local/`, which git ignores. Before the merge, the session removes the scratch folders that it and its agents made. After the merge, once `git pull` has brought the merge into the local `main`, the session removes each worktree that it or its agents made with `git worktree remove <path>`, never with `--force`, when `git status` there is clean and the worktree's `HEAD` is in the local `main`; the branch stays, and so does a worktree whose commits are not in the local `main`. A worktree the app made, or one another session made, is removed only with the decider's yes. Review holds this bullet; no check does (decision [dec-0111-worktrees-and-scratch-folders](docs/decisions/dec-0111-worktrees-and-scratch-folders.md)).
- <a id="references"></a>**References are clickable; handles are scoped.** The chat rule — every reference to a file, a section or a document a markdown link wherever the file exists, a handle local to its message, decision or session, its source named when a cite crosses that boundary — and the document rule — a bare handle local to its own document, a link to the target's anchor across documents ([requirements A5.5–A5.7](docs/requirements.md#a5)) — are module [`const-referencing`](docs/requirements.md#const-referencing)'s, both taught by its skill; only the chat rule is printed at session start. A commit message is read long after its session, by a reader who has neither the session nor a document outside the repository. So every handle in a commit message names its source: a key of a tracked document names that document in the same message; a handle of a document outside the repository names that document — "hardcode audit G4 B1", never "G4 B1" alone; a handle local to a session or a chat names the work or the decision it came from — "item I3 of the ID-collision follow-up of 2026-10-11". The module's chat rule carries this for a handle local to a message, a decision or a session; the rest is the kit's own. Review holds it (decision [dec-0082-handle-migration-in-records](docs/decisions/dec-0082-handle-migration-in-records.md)). In the Markdown files git lists, save the comparisons, a carry list, code and HTML comments, the kit's `scripts/check-handle-forms.py` holds that a citation of a decision record's ruling links the ruling's anchor, `R7 of [dec-…](…#r7)`; it is another entry of the gate list, run by the kit's CI, with `--self-test` as its fixture (decision [dec-0083-handle-forms-held-by-a-kit-check](docs/decisions/dec-0083-handle-forms-held-by-a-kit-check.md)). The kit's verbose handles are "law 3 of CLAUDE.md" (a form that holds while the laws are numbered), "dial `ns.key`", "requirement [A5.3](docs/requirements.md#a5-3)" or "[aspect A5](docs/requirements.md#a5)"; the kit's reference forms are its `lanes` in `constitution.yaml`. A bare aspect handle, "A5", is held by review and not by a lane, since the letter and a number collide with the message keys of the kit's documents. The gate is the scan of module [`const-referencing`](docs/requirements.md#const-referencing), `sh modules/const-referencing/plugin/scripts/check-references.sh --scan`, an entry of the gate list the kit's CI runs. Module prose is the files under `modules/` and `module-template/`, which name a module "module `const-x`". Everywhere else — every other kit document, and chat — a module is cited by a link to its specification anchor, with the plugin name as text. A kit template under `templates/`, copied into another folder where a relative link would break, names the module plain, with the link's path from the copy's folder in a code span. A frozen research comparison keeps the form it was frozen with ([rule 7 of plc-0005-research](docs/policies/plc-0005-research.md#r7)); in one not yet frozen, review holds the link. A third exception is the module table of the root README, which links a module to its `README.md`, the landing page, so that a reader on GitHub lands on the plain-language page first; outside these three places and module prose, and in chat, the specification anchor stays the citation and the module's handle (decision [dec-0077-module-readme-pages](docs/decisions/dec-0077-module-readme-pages.md)). In the Markdown files git lists, save module prose, the templates and the comparisons, the kit's `scripts/check-module-links.py` holds the link where a module's name stands in a code span after the word "module" or "modules", capitalized or not; a name standing alone, or any name after the first of a plural, is held by review. The check is another entry of the gate list, run by the kit's CI and never at write time, with `--self-test` as its fixture (decisions [dec-0049-module-links-held-by-a-kit-check](docs/decisions/dec-0049-module-links-held-by-a-kit-check.md) and [dec-0051-module-citation-rule-in-the-guide](docs/decisions/dec-0051-module-citation-rule-in-the-guide.md)).

## Developing a module

Before a module is authored or changed — its document, its plugin, its tests or its eval cases — read [the module-development page](docs/guide/developing-a-module.md): its seven steps, from the copy of the template to the version bump, and the rules each step holds.

## Never in this repository

Project content or references (law 2). References to any location outside this repository other than a public URL — no local folder, no sibling repository, no absolute filesystem path; information from such places enters only after verification, cited to the public source that verified it (in markdown files the scan of module [`const-referencing`](docs/requirements.md#const-referencing) turns red on an absolute path under a home directory or a `file:` link — scripts and configuration are held by review, and a module's installed components also by the kit's `scripts/check-portability.py` for the forms of [requirement A12.1](docs/requirements.md#a12-1)). A placeholder path in install instructions — a consumer's clone location, the platform's own configuration directory — is not a reference. Knowledge-layer content (separate layer, separate concern). A parallel component model — Claude Code's plugins/skills/hooks/agents are the mechanical kernel; this repo adds semantics only. Machinery for failures no consumer has hit — growth is friction-earned, via consumer commit notes recurring on a theme. A count of the modules in the install guide or the README: a number word drifts without a sound when a module is added, so both name the modules without one. The lists a new module joins that `scripts/check-gate-lists.py` holds are the ones [step 1 of the module-development page](docs/guide/developing-a-module.md#s1) names; the module table of the root README is held by review.
