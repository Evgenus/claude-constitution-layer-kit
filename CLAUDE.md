# Constitution Kit — Session Guide

This repository is the **constitution kit**: a portable, project-agnostic governance layer for Claude Code projects, shipped as plugins. It contains the semantic kernel, the module template, and the modules. It contains **no project content, ever**.

Read before any work:
- `INTENT.md` — what this repo is for and what it is not.
- `kernel/CONVENTIONS.md` — the semantic kernel (one page). Authoritative for all vocabulary: envelope, meta-types, governance binding, stakes, decision records, dials, naming.
- `module-template/MODULE.md` — the fixed shape every module fills.
- `docs/requirements.md` — the traceability matrix and module specifications (requirement rows per module).
- `docs/rollout-plan.md` — the phases, the kit's own active task-record; not a reading assignment.
- `constitution.yaml` — the kit's own dials file; its `root_policy` key locates the policies that govern this repository's documents ([kernel §3](kernel/CONVENTIONS.md#k3)). Not a reading assignment: open a policy only when working in its territory. Written in block style — one key or one `- ` item per line; flow style, `[]` or `{}`, only where a list or a mapping is empty — held by `python3 scripts/check-yaml-style.py`, kit tooling never shipped in a module, run before every commit that touches the file until the kit's CI runs it; its `--fix` rewrites the file, keeping every comment, anchor, alias and quote as written; the YAML inside Markdown fences is not under the rule, and a consumer's file is the consumer's (decision [dec-0037-dials-file-block-style](docs/decisions/dec-0037-dials-file-block-style.md)).
- `docs/research/` — one current dated comparison per module, written by that module's own research round; a superseded one is kept beside it while cited. Not a reading assignment: open one when changing a mechanism.
- `shared/GATE.md` — the code every gate shares: what is shared, the interface a module fills, every shared message, the shared limits and acceptance items. Read it before authoring a module with a gate.

## Laws of this repository

1. <a id="law-1"></a>**Kernel is authoritative; never restate it.** Modules and documents reference kernel definitions by name — duplication is a defect.
2. <a id="law-2"></a>**Portability ([kernel §6](kernel/CONVENTIONS.md#k6)):** no file in a module references any project — no paths, names, repos, values. Project specifics enter only through the module's dials namespace. Test: the module installs and operates on an empty repository using defaults alone.
3. <a id="law-3"></a>**Sibling independence:** modules depend on the kernel and nothing else. Sibling references only as optional enhancements ("when `const-x` is installed…"). The kit's shared gate code is not a sibling: it has one source under `shared/`, a module links to it, and the installed plugin carries what the link points at — a module never reaches another module through it (decision [dec-0025-shared-gate-code-linked](docs/decisions/dec-0025-shared-gate-code-linked.md)). Test: kernel + this module alone on a bare repo is a functioning installation. If a module seems to need a sibling, the shared concept belongs in the kernel — raise that as a `process`-stakes decision instead of coupling.
4. <a id="law-4"></a>**A module implements exactly its matrix rows.** Its `MODULE.md` cites them. Content beyond its rows is scope creep; a missing row is incompleteness. Both are review findings.
5. <a id="law-5"></a>**Enforcement honesty:** every artifact is `gate` (deterministic, red = fix) or `advisory` (judgment-shaping) — declared, never blurred. Nothing judgment-based is dressed as a check.
6. <a id="law-6"></a>**Teaching errors:** every gate's error message states what failed, why the rule exists (one clause), and the exact fix. Error messages are designed content, reviewed like code.
7. <a id="law-7"></a>**Every gate ships its red→green fixture** in `modules/<name>/tests/` — one input that fails without the check and passes with it.
8. <a id="law-8"></a>**Sizes in characters, never tokens.**
9. <a id="law-9"></a>**Kit decisions follow the kernel's own stakes triage.** Routine → act, note in the commit. `process` (most kit changes) → decision record in `docs/decisions/`, one human yes on the change: named in the commit message until the kit has a PR flow, PR approval from rollout Phase D (decision [dec-0016-yes-on-the-change](docs/decisions/dec-0016-yes-on-the-change.md)). Kernel changes are always recorded. Record lifecycle, supersession, and deletion: [kernel §1](kernel/CONVENTIONS.md#k1) and [kernel §5](kernel/CONVENTIONS.md#k5) — not restated here.

## Session conduct

- One decision per message: options, pros/cons, exactly one recommendation with reasoning, named decider. Below recorded stakes: decide yourself and note it in the commit — do not ask.
- **Decision format.** Options are lettered A, B, C… (never numbered — numbers are for every other list item, so an option is never confused with a finding or a step). The full argument is written in the chat message, in this shape: each option is a bullet whose first line is the bold letter and title plus a one-sentence description; beneath it, two indented sub-bullets labeled **Pros:** and **Cons:**, each a short prose line — never inline in the description paragraph, never a table; then exactly one recommendation with reasoning, and the named decider. When there are fewer than five options, the `AskUserQuestion` tool is then used only to collect the pick: the question restates the decision in one line, each option is its letter plus a short label, and the tool's descriptions carry at most one clause each — never the pros, cons, or recommendation. Five or more options: chat only, the user answers with a letter. The argument must reach the user: chat text written between tool calls in one turn is not always rendered, so if the user reports an argument missing, every later decision in that session ends the turn on the chat message and the pick is collected by letter, without the tool.
- Derive questions from the artifact's open slots (template sections, matrix rows, missing dials), in order. Closed vocabularies are offered as the option set. Defaults are proposed as "default is X — accept or override?".
- No deferred questions: delivered work contains resolved decisions only; an absent decider becomes a named blocker.
- Lead with the answer.
- **Restate before acting.** The user's intents may be vague. Whenever a thought or wish shows any sign of ambiguity, or does not obviously fit the current context, open the reply by restating it as understood — "I read this as: …" — and, where more than one reading is plausible, name the alternatives and the one chosen. Never silently guess.
- **Assumptions are always explicit.** Every assumption made while interpreting a request or doing the work is listed in the response, in its own short line or bullet, so the user can correct it. An assumption that would change the work materially is a question, not an assumption.
- **Every list item is addressable.** Any list, table, or set of options in a reply, a document, or a module carries a stable handle per item — a number, a letter, or a short key — so the user can refer to one item without quoting it. Table rows get an id column or numbered rows. This applies to findings, options, assumptions, questions, and steps alike.
- **Honesty over agreement.** Say plainly when a request is wrong, unreasonable, or conflicts with the laws above, and say why — even when the user has already decided. Do not soften findings, hide failures, or report unverified work as done.
- **Commit before you edit.** Rollback points live in git, not in chat rewind — rewind does not track changes made through Bash, scripts, or subagents. Before starting any batch of edits, commit the current state if the tree is dirty; after finishing a coherent change, commit again. Never leave uncommitted work behind at the end of a turn — the `Stop` hook of module `const-task-close` reports a dirty tree once per turn in a session that loads the plugin, and the kit calibrates it to block. Rolling back is then `git revert` or `git checkout` of a named commit, and it works regardless of which tool made the change.
- **Work starts on a branch.** Every change — one commit or many, routine or recorded — is made on its own branch `work/<name>`, a short kebab-case name of the work, cut from `main`, and reaches `main` as one merge commit: `git merge --no-ff work/<name> -m "Work: <name>"`. Before the merge the range check of module `const-task-close` is green on the branch — `sh modules/const-task-close/scripts/check-task-close.sh --scan`, the kit's own coverage map being its `coverage` in `constitution.yaml`: a change that touches code a current-state document describes updates that document in the same change or carries a `No-Doc-Impact: <pair> — <reason>` trailer on one of its commits, in the message's last paragraph; the same check with `--change <merge>` audits a landed change. Where the change needs a yes, the merge comes after it, and the commit that names the yes stands on the branch: until the kit has a PR flow that commit is the one that lands the change in the sense of [kernel §4](kernel/CONVENTIONS.md#k4) and completes it in the sense of rule 5 of [plc-0004-decision-records](docs/policies/plc-0004-decision-records.md#r5), the one law 9 asks the yes to be named in, and carries the `Accepted:` and `Carry-Audit:` trailers, and the merge commit names no yes and carries no trailer; from rollout Phase D the yes is PR approval and the trailers move to the commit that merges the pull request. The branch is kept after the merge, with no limit of time. Nothing is committed on `main` itself. The gate is `scripts/git-hooks/prepare-commit-msg`: while `main` is checked out it refuses a commit, an amend, a cherry-pick and a revert — `--no-verify` does not skip it — and lets a merge pass whole, a detached HEAD too; the fix it teaches follows what git leaves behind — a cherry-pick, and a revert still in progress, are aborted first, since git will not switch branches in the middle of one; its fixture is `scripts/git-hooks/tests/run.sh`. Git keeps the two settings the gate needs per clone and never versions them, so in a fresh clone run `sh scripts/setup-clone.sh` once; `--check` tells whether it has been and whether the hook file is executable. What the gate cannot hold is left to this rule — whatever moves `main` without passing that hook: `git am`, a rebase of `main`, a fast-forward asked for on the command line (`--ff`, `--ff-only`), a push into `main`, `git reset`, `git update-ref`, `git branch -f`; and a merge concluded by hand can carry any content.
- **References are clickable; handles are scoped.** In chat, every reference to a file, section, requirement, law, or record is a markdown link. A numbered item resolves within its message, a lettered option within its decision, a table key within the session; across that boundary, name the message or decision. Verbose handles: "law 3 of CLAUDE.md" (a form that holds while the laws are numbered), "dial `ns.key`", "requirement [A5.3](docs/requirements.md#a5-3)" or "[aspect A5](docs/requirements.md#a5)", "module `const-x`". In documents a bare handle is local to its own document; across documents it is a link to the target's anchor ([requirements A5.5–A5.7](docs/requirements.md#a5)); the gate is the scan of module `const-referencing`, `sh modules/const-referencing/scripts/check-references.sh --scan`, run before every commit that touches a document until the kit's CI runs it — the kit's own reference forms are its `lanes` in `constitution.yaml`.
- **Refuse destructive moves without a spoken confirmation.** Before any hard-to-reverse action (deleting files or documents, rewriting history, force-pushing, dropping a kernel definition, breaking a published module's contract), state the consequence and the reversible alternative, then wait for an explicit yes in chat. An approval covers that action only. If the user repeats the request after the warning, it is their decision — proceed and note the objection in the commit.

## Developing a module

1. `cp -r module-template/ modules/const-<name>/` — kebab-case, `const-` prefix. The template's relative links gain one `../` level in the copy; the scan of module `const-referencing` turns red until they are fixed.
2. Research first: a subagent surveys how this module's matrix rows are addressed today — official Claude Code documentation for the native surface, community harnesses, applicable tools — and returns one dated comparison in kit vocabulary at `docs/research/res-<nnnn>-const-<name>.md` — the document created through the command of module `const-locations` from `templates/research-comparison.md`, the subagent filling its placeholders, numbered as rule 6 of [plc-0005-research](docs/policies/plc-0005-research.md#r6) says: candidate approaches, mechanism class, maturity, cost, one recommendation per mechanism with reasoning (decision [dec-0010-module-research-per-module](docs/decisions/dec-0010-module-research-per-module.md)). Earlier design work is a clue set, never a source: nothing enters unverified. Raw material stays in the subagent; only the comparison returns.
3. Fill `MODULE.md` top-down from the module's matrix rows, moving the plan's description into it and leaving a one-line stub under the plan's anchor, which stays the module's handle; every section filled or "none" with one line of reasoning. Before the artifacts table, confirm or overturn the matrix's recommended enforcement for each row from the comparison, naming on every step down what the native option cannot do.
4. Implement artifacts: hooks/scripts for gates (paths via `${CLAUDE_PLUGIN_ROOT}`), skills for procedures and advisory rules, `INSTALL.md` with at most one CLAUDE.md pointer line. Only `.claude-plugin/plugin.json` lives inside `.claude-plugin/`; components sit at module root. Script runtime (decision [dec-0015-pre-module-audit-rulings](docs/decisions/dec-0015-pre-module-audit-rulings.md)): a script that reads YAML — the envelope, the dials file — is Python 3 with PyYAML; one that reads none may be POSIX shell. A missing interpreter or library is a configuration failure: exit 1 with the install command in the message, never a silent pass. Every Python script follows the sixteen gate-script rules of [template §6](module-template/MODULE.md#t6) — package shape, typed message functions, exit codes, floor 3.12, declared dependencies, no fail-open, strict typing, output log, case-record fixtures, imports at the top (decisions [dec-0020-gate-script-rules](docs/decisions/dec-0020-gate-script-rules.md), [dec-0026-imports-at-the-top](docs/decisions/dec-0026-imports-at-the-top.md)). The linter, formatter and type-checker configuration — `ruff`, `mypy --strict` — is the kit's own development routine: it lives in `pyproject.toml` at the kit root with the commands to run, and no module ships tool configuration. Shared gate code (decision [dec-0025-shared-gate-code-linked](docs/decisions/dec-0025-shared-gate-code-linked.md)): what every gate needs — the hook event, the dials file, territories and resolution, the output log, the command line and its guard, the shared messages, the fixture harness — has one source under `shared/`, described in [kit-shared-gate-code](shared/GATE.md). A module links to it from its first commit (`scripts/const_gate` and three files in `tests/`, relative symbolic links; `scripts/check-shared-links.py` is the gate), fills the interface of [its §2](shared/GATE.md#g2), and writes only its own model, messages, checks and modes. Code is admitted there only when it implements a kernel section literally or a gate-script rule of the template, and two or more modules need it — a part already shared may be widened for one module where the widening keeps a rule the part carries for all and defaults to what the others pass; a fix in shared code bumps the version of every module that links it. Territory matching in the default dialect goes through `git check-ignore`, verified at authoring.
5. Prove twice: fixtures against a bare temp repo (laws 2–3 by hand until CI exists — for law 2 the [A12.1](docs/requirements.md#a12-1) grep: no path literal in the module beyond `${CLAUDE_PLUGIN_ROOT}`-relative ones, public URLs, and `constitution.yaml`), then live — in this repository for document-shaped modules — those whose objects are governed documents of a kind the kit itself holds (the kit is consumer zero), and in a consumer project: session in the project, plugin loaded from this repo's path (verify current local plugin-dir / marketplace mechanics against official docs; do not trust memory for this surface). When no consumer exists yet, the record and the yes follow the kit-live proof; the consumer-live proof is a named step of the consumer's bootstrap, and a finding there is a fix with a version bump, priced by its stakes (decision [dec-0015-pre-module-audit-rulings](docs/decisions/dec-0015-pre-module-audit-rulings.md)).
6. Validate fresh-context before the human yes, in two passes, both mandatory. First, a subagent holding only the module's files, the template, this file, and the module's matrix rows — never the authoring reasoning — reviews against laws 2–7 and every template section. Second, the carry audit of [rule 2 of plc-0004-decision-records](docs/policies/plc-0004-decision-records.md#r2), run through this repository's `carry-audit` skill: fresh readers, each round pinned to one commit, their scope computed by `scripts/check-carry-lists.py --scope` and never chosen — read in full, the records the change adds or edits and those the module's decisions section cites; read for regression, every other record that cites a file the change touched, asked only whether that file still states what the record ruled; and for each record the change adds, a reader who never sees it answers the author's questions from the current-state documents alone. Every finding of either pass is fixed or justified in the pull request, or in a commit message of the change until the kit has a PR flow (decision [dec-0009-module-routine-validation-and-inputs](docs/decisions/dec-0009-module-routine-validation-and-inputs.md)). The commit that names the yes carries the audit's receipt — which shows that an audit was declared and accounted for, not that it was run — and `scripts/check-carry-lists.py` is the gate on the records' carry lists and on that receipt; whether a ruling is carried is judgment and stays with the readers.
7. Version bump on every change once published; consumer projects update by version.

## Never in this repository

Project content or references (law 2). References to any location outside this repository other than a public URL — no local folder, no sibling repository, no absolute filesystem path; information from such places enters only after verification, cited to the public source that verified it (the scan of module `const-referencing` turns red on an absolute path under a home directory or a `file:` link, in markdown files only, code and comments included — scripts and configuration are held by review). A placeholder path in install instructions — a consumer's clone location, the platform's own configuration directory — is not a reference. Knowledge-layer content (separate layer, separate concern). A parallel component model — Claude Code's plugins/skills/hooks/agents are the mechanical kernel; this repo adds semantics only. Machinery for failures no consumer has hit — growth is friction-earned, via consumer commit notes recurring on a theme.
