# Constitution Kit — Session Guide

This repository is the **constitution kit**: a portable, project-agnostic governance layer for Claude Code projects, shipped as plugins. It contains the semantic kernel, the module template, and the modules. It contains **no project content, ever**.

Read before any work:
- `INTENT.md` — what this repo is for and what it is not.
- `kernel/CONVENTIONS.md` — the semantic kernel (one page). Authoritative for all vocabulary.
- `module-template/MODULE.md` — the fixed shape every module fills.
- `docs/requirements.md` — the traceability matrix and module specifications (requirement rows per module).
- `docs/rollout-plan.md` — the phases, the kit's own active task-record; not a reading assignment.
- `constitution.yaml` — the kit's own dials file; its `root_policy` key locates the policies that govern this repository's documents ([kernel §3](kernel/CONVENTIONS.md#k3)). Not a reading assignment: open a policy only when working in its territory. Written in block style — one key or one `- ` item per line; flow style, `[]` or `{}`, only for an empty list or mapping — held by `python3 scripts/check-yaml-style.py`, run by the kit's CI; its `--fix` rewrites the file keeping every comment, anchor, alias and quote as written; the kit's CI also validates the file against the kernel's dials schema with a real validator, `scripts/check-dials-schema.py`; the YAML inside Markdown fences is not under the rule, and a consumer's file is the consumer's (decision [dec-0037-dials-file-block-style](docs/decisions/dec-0037-dials-file-block-style.md)).
- `docs/research/` — one current dated comparison per module, written by its module's own research round; a superseded one is kept beside it while cited. Not a reading assignment: open one when changing a mechanism.
- `shared/GATE.md` — the code every gate shares. Read it before authoring a module with a gate.

## Laws of this repository

1. <a id="law-1"></a>**Kernel is authoritative; never restate it.** Modules and documents reference kernel definitions by name — duplication is a defect.
2. <a id="law-2"></a>**Portability ([kernel §6](kernel/CONVENTIONS.md#k6)):** no file in a module references any project — no paths, names, repos, values. Project specifics enter only through the module's dials namespace. Test: the module installs and operates on an empty repository using defaults alone.
3. <a id="law-3"></a>**Sibling independence:** modules depend on the kernel and nothing else. Sibling references only as optional enhancements ("when `const-x` is installed…"). The kit's shared gate code is not a sibling: it has one source under `shared/`, a module links to it, and the installed plugin carries what the link points at — a module never reaches another module through it (decision [dec-0025-shared-gate-code-linked](docs/decisions/dec-0025-shared-gate-code-linked.md)). Test: kernel + this module alone on a bare repo is a functioning installation. If a module seems to need a sibling, the shared concept belongs in the kernel — raise that as a `process`-stakes decision instead of coupling.
4. <a id="law-4"></a>**A module implements exactly its matrix rows.** Its `MODULE.md` cites them. Content beyond its rows is scope creep; a missing row is incompleteness. Both are review findings.
5. <a id="law-5"></a>**Enforcement honesty:** every artifact is `gate` (deterministic, red = fix) or `advisory` (judgment-shaping) — declared, never blurred. Nothing judgment-based is dressed as a check.
6. <a id="law-6"></a>**Teaching errors:** every gate's error message states what failed, why the rule exists (one clause), and the exact fix. Error messages are designed content, reviewed like code.
7. <a id="law-7"></a>**Every gate ships its red→green fixture** in `modules/<name>/tests/` — one input that fails without the check and passes with it.
8. <a id="law-8"></a>**Sizes in characters, never tokens.**
9. <a id="law-9"></a>**Kit decisions follow the kernel's own stakes triage.** Routine → act, note in the commit. `process` (most kit changes) → decision record in `docs/decisions/`, one human yes on the change, named in the merge commit of its pull request — the decider's own merge, since the kit has no second human to approve (decisions [dec-0016-yes-on-the-change](docs/decisions/dec-0016-yes-on-the-change.md) and [dec-0057-pr-flow-merge-names-the-yes](docs/decisions/dec-0057-pr-flow-merge-names-the-yes.md)). Kernel changes are always recorded. Record lifecycle, supersession, and deletion: [kernel §1](kernel/CONVENTIONS.md#k1) and [kernel §5](kernel/CONVENTIONS.md#k5) — not restated here.

## Session conduct

*Every kit session, save the escape below, loads the kit's modules as plugins from its committed `.claude/settings.json`, which declares the clone as the marketplace `constitution-kit` by a relative directory source and enables each module — nothing per clone to load them, in a folder trusted once (decision [dec-0043-kit-plugins-through-project-settings](docs/decisions/dec-0043-kit-plugins-through-project-settings.md)). A module whose gate blocks its own fix is switched off for one clone, its skills and session-start text with it, by `"<module>@constitution-kit": false` under `enabledPlugins` in that clone's `.claude/settings.local.json`, the one per-clone write to the plugin settings, a file the kit's `.gitignore` keeps out of the tree. The rules the modules ship reach the model from them — at session start, as skills, whose descriptions ask to be loaded at their moment and which a module's hooks also name where they meet it, and as hooks — and are not restated here; this block keeps what no module carries. Of the kit's own agents in `.claude/agents/`, the one that writes the kit's tracked files, the implementer, lists the `Skill` tool, so that it can load a skill that its start context or a hook's red names; the others write nothing tracked and keep their tools, so a pointer to a skill that reaches them asks nothing of them (decision [dec-0079-skills-named-at-their-moment](docs/decisions/dec-0079-skills-named-at-their-moment.md)).*

- **Work starts on a branch.** Every change — one commit or many, routine or recorded — is made on its own branch `work/<name>`, a short kebab-case name of the work, cut from `main`, and reaches `main` as the merge commit of one pull request on the kit's private GitHub remote, `origin`: the branch pushed, `git push -u origin work/<name>`, the pull request opened, `gh pr create`, and merged with `gh pr merge <n> --merge --subject "Work: <name>"`; a local `main` then follows by `git pull`, a fast-forward only. The branch is kept forever after the merge, in the clone and on the remote. Nothing is committed on `main` itself.
  - **Before the merge.** The range check of module [`const-task-close`](docs/requirements.md#const-task-close) is green on the branch — `sh modules/const-task-close/scripts/check-task-close.sh --scan`, over the kit's `coverage` map in `constitution.yaml`: a change that touches code a current-state document describes updates that document in the same change or declares no impact by a `No-Doc-Impact: <pair> — <reason>` trailer on one of its commits, in the message's last paragraph, never by the pull request's description alone, which the kit's CI does not give the check; with `--scan --change <merge>` it audits a landed change. When `main` has moved since the branch's last CI run, the branch merges `main` and waits for CI green again before `gh pr merge`; review holds this, since the ruleset does not ask a branch to be up to date.
  - **The gate list and CI.** The whole gate list — the scans of the modules, the kit's own checks each with its `--self-test` where it has one, and the range check — is the gate group of `scripts/gate-list.sh`, the kit's one list; its extra group holds each module's fixtures, lint and types, the branch gate's fixture, the fixture of `scripts/setup-claude.sh`, and the kit's lint and types. A module's fixtures run through `python3 scripts/check-aspects.py --run --module <module>`, which runs its runner once, prints the runner's own output whenever it exits other than 0, and holds the runner's items against the module's acceptance table both ways (decision [dec-0080-fixtures-run-through-check-aspects](docs/decisions/dec-0080-fixtures-run-through-check-aspects.md)). Every script under the kit's `scripts/` is kit tooling, never shipped in a module. The kit's CI runs the whole list, `.github/workflows/gates.yml`, on every pull request and on `main` after each merge: one job per module holding its entries, one job `install-guide` running the commands of `INSTALL.md` through `scripts/check-install-guide.py` (decision [dec-0062-install-guide-governed-kind](docs/decisions/dec-0062-install-guide-governed-kind.md)), and one job `kit` for the rest, in parallel, from the list's `--json`; and a job `gates`, green only when every other job is. No local run is required; for a red before a push, the `gate-list-runner` agent of `.claude/agents/` runs the gate group, the extra group on request, and returns every red line verbatim. The install entries and the guide run on the Claude Code that `scripts/claude-code.version` pins; `sh scripts/setup-claude.sh` installs it once per clone, and again after the pin moves, into `.claude-code-pinned/` beside git's common directory, which git ignores, and the list puts it first on `PATH` for those entries alone, when it is there. The kit's `scripts/check-gate-lists.py`, an entry of that list with `--self-test` as its fixture, holds the form of each module's enforcement table, and that every scan a module declares there stands in the list's gate group and in its module's job, every `scripts/check-*.py` git tracks at the top of `scripts/` is run by an entry of the gate group, `MODULES` names exactly the module folders, the workflow's steps, comments aside, call the list's `--json` and `--run`, and neither passes a runner's `--item`, never a full pass. It also holds each module folder named `const-<aspect>`, its manifest naming it, listed once in the marketplace at `./modules/<name>` and enabled, `true`, in the kit's settings, which declare the marketplace as a directory at `.`; neither file names a plugin of that marketplace that is no module folder. It holds each marketplace `description` equal to its manifest's, every top-level `const-<aspect>` key of `constitution.yaml` naming a module folder, and the `types` entry putting on `MYPYPATH` exactly the module folders `scripts/check-schema-mirror.py` imports from.
  - **The yes.** Where the change needs a yes, the merge gives it: the decider merges the pull request, or says yes in chat and has the session merge in the decider's name. The merge commit names the yes and carries the `Accepted:` and `Carry-Audit:` trailers in its last paragraph, written with `--body`, or into the merge message on the forge's page. It is the commit that lands the change in the sense of [kernel §4](kernel/CONVENTIONS.md#k4) and completes it in the sense of rule 5 of [plc-0004-decision-records](docs/policies/plc-0004-decision-records.md#r5), the one law 9 asks the yes to be named in. Since the merge of the kit's first pull request, every `Accepted:` and `Carry-Audit:` trailer stands on a merge commit, never on a branch commit.
  - **The local gate.** The gate is `scripts/git-hooks/prepare-commit-msg`: while `main` is checked out it refuses a commit, an amend, a cherry-pick and a revert — `--no-verify` does not skip it — and lets a merge pass whole, a detached HEAD too; the fix it teaches follows what git leaves behind — a cherry-pick, and a revert still in progress, are aborted first, since git will not switch branches in the middle of one; its fixture is `scripts/git-hooks/tests/run.sh`. Git keeps the three settings the gate and the pull need per clone and never versions them — `core.hooksPath`, `merge.ff` = `false`, and `pull.ff` = `only`, without which a plain `git pull` onto `main` makes a merge commit of its own — so in a fresh clone run `sh scripts/setup-clone.sh` once; `--check` tells whether it has run and the hook file is executable. What the gate cannot hold, left to the rule "Work starts on a branch", is whatever moves `main` without passing that hook: `git am`, a rebase of `main`, a fast-forward asked for on the command line (`--ff`, `--ff-only`), a push into `main`, `git reset`, `git update-ref`, `git branch -f`; and a merge concluded by hand can carry any content.
  - **The shared `main`.** On the remote, `main` is held by the repository's ruleset: a pull request before every merge, with no approval required, since the kit's only human is the author; no force push; no deletion; no one on its bypass list; the check `gates` green. The repository allows merge commits only, squash and rebase off, and keeps a branch after its merge. So whatever is done to a local `main` in those ways reaches the shared one only through a pull request's merge; a local `main` stays unheld, and the hook stays as the fast local check (decision [dec-0057-pr-flow-merge-names-the-yes](docs/decisions/dec-0057-pr-flow-merge-names-the-yes.md)).
- <a id="references"></a>**References are clickable; handles are scoped.** The chat rule — every reference to a file, a section or a document a markdown link wherever the file exists, a handle local to its message, decision or session, its source named when a cite crosses that boundary — and the document rule — a bare handle local to its own document, a link to the target's anchor across documents ([requirements A5.5–A5.7](docs/requirements.md#a5)) — are module [`const-referencing`](docs/requirements.md#const-referencing)'s, both taught by its skill; only the chat rule is printed at session start. The kit's verbose handles are "law 3 of CLAUDE.md" (a form that holds while the laws are numbered), "dial `ns.key`", "requirement [A5.3](docs/requirements.md#a5-3)" or "[aspect A5](docs/requirements.md#a5)"; the kit's reference forms are its `lanes` in `constitution.yaml`. A bare aspect handle, "A5", is held by review and not by a lane, since the letter and a number collide with the message keys of the kit's documents. The gate is the scan of module [`const-referencing`](docs/requirements.md#const-referencing), `sh modules/const-referencing/scripts/check-references.sh --scan`, an entry of the gate list the kit's CI runs. Module prose is the files under `modules/` and `module-template/`, which name a module "module `const-x`". Everywhere else — every other kit document, and chat — a module is cited by a link to its specification anchor, with the plugin name as text. A kit template under `templates/`, copied into another folder where a relative link would break, names the module plain, with the link's path from the copy's folder in a code span. A frozen research comparison keeps the form it was frozen with ([rule 7 of plc-0005-research](docs/policies/plc-0005-research.md#r7)); in one not yet frozen, review holds the link. A third exception is the module table of the root README, which links a module to its `README.md`, the landing page, so that a reader on GitHub lands on the plain-language page first; outside these three places and module prose, and in chat, the specification anchor stays the citation and the module's handle (decision [dec-0077-module-readme-pages](docs/decisions/dec-0077-module-readme-pages.md)). In the Markdown files git lists, save module prose, the templates and the comparisons, the kit's `scripts/check-module-links.py` holds the link where a module's name stands in a code span after the word "module" or "modules", capitalized or not; a name standing alone, or any name after the first of a plural, is held by review. The check is another entry of the gate list, run by the kit's CI and never at write time, with `--self-test` as its fixture (decisions [dec-0049-module-links-held-by-a-kit-check](docs/decisions/dec-0049-module-links-held-by-a-kit-check.md) and [dec-0051-module-citation-rule-in-the-guide](docs/decisions/dec-0051-module-citation-rule-in-the-guide.md)).

## Developing a module

1. `cp -r module-template/ modules/const-<name>/` — kebab-case, `const-` prefix; name it in its manifest, in `MODULES` of `scripts/gate-list.sh` (a scan also in `GATES`, `job()` and `commands()`), in `.claude-plugin/marketplace.json` and, as `const-<name>@<marketplace name>`, in `.claude/settings.json`, all held by `scripts/check-gate-lists.py`. The template's relative links gain one `../` level in the copy; the scan of module [`const-referencing`](docs/requirements.md#const-referencing) turns red until they are fixed.
2. Research first: a subagent surveys how this module's matrix rows are addressed today — official Claude Code documentation for the native surface, community harnesses, applicable tools — and returns one dated comparison in kit vocabulary at `docs/research/res-<nnnn>-const-<name>.md` — created through the command of module [`const-locations`](docs/requirements.md#const-locations) from `templates/research-comparison.md`, the subagent filling its placeholders, numbered as rule 6 of [plc-0005-research](docs/policies/plc-0005-research.md#r6) says: candidate approaches, mechanism class, maturity, cost, one recommendation per mechanism with reasoning (decision [dec-0010-module-research-per-module](docs/decisions/dec-0010-module-research-per-module.md)). Earlier design work is a clue set, never a source: nothing enters unverified, and its vocabulary — its aspects numbered one to ten, its D-numbers, its register rulings — does not enter at all. Raw material stays in the subagent; only the comparison returns.
3. Fill `MODULE.md` top-down from the module's matrix rows, moving the module's specification from the requirements document into it and leaving a one-line stub under its anchor there, which stays the module's handle; every section filled or "none" with one line of reasoning. Before the artifacts table, confirm or overturn the matrix's recommended enforcement for each row from the comparison, naming on every step down what the native option cannot do.
4. Implement artifacts: hooks/scripts for gates (paths via `${CLAUDE_PLUGIN_ROOT}`), skills for procedures and advisory rules, `INSTALL.md` with at most one CLAUDE.md pointer line, and `README.md`, the module's landing page for a reader on GitHub, filled from the template's `README.md`. That page is of the root README's kind — user-facing, informational, in no policy's territory, with no envelope, binding nothing. Its first section opens with the manifest's `description` as written and says the rest in plain words; its second states the problem and how the module resolves it; its implementation is told at a high level, one paragraph per tool; its links are the module's own `INSTALL.md` and `MODULE.md` alone, never a requirement row, a record or a comparison. Law 2 holds for it by review, since the kit's portability check reads a module's installed components alone. A change to it is routine, like one to the root README (decision [dec-0077-module-readme-pages](docs/decisions/dec-0077-module-readme-pages.md)). Only `.claude-plugin/plugin.json` lives inside `.claude-plugin/`; components sit at module root. Each manifest names `Apache-2.0` in `license`; in `author`, a module's names the author `NOTICE` names and the template's keeps a placeholder. The Apache License 2.0 is the kit's one license for the whole tree, documents and code alike: `LICENSE` at the kit root is its text, `NOTICE` beside it its credit, which holds no email address, and no file takes a license header (decision [dec-0063-apache-license-with-notice](docs/decisions/dec-0063-apache-license-with-notice.md)). Script runtime (decision [dec-0015-pre-module-audit-rulings](docs/decisions/dec-0015-pre-module-audit-rulings.md)): a script that reads YAML — the envelope, the dials file — is Python 3 with PyYAML; one that reads none may be POSIX shell. A missing interpreter or library is a configuration failure: exit 1 with the install command in the message, never a silent pass. The Python floor has one source, `FLOOR` in `shared/const_gate/preflight.py`; every copy of it, records and comparisons aside, and each entry's [`C1`, `C14` and `C15`](shared/GATE.md#g3) clause are held by the kit's `scripts/check-copies.py`, an entry of the gate list with `--self-test` as its fixture. Every Python script follows the sixteen gate-script rules of [template §6](module-template/MODULE.md#t6) (decisions [dec-0020-gate-script-rules](docs/decisions/dec-0020-gate-script-rules.md), [dec-0026-imports-at-the-top](docs/decisions/dec-0026-imports-at-the-top.md)). The configuration of the linter, formatter and type checker — `ruff`, `mypy --strict` — is the kit's own development routine, in `pyproject.toml` at the kit root with the commands to run; no module ships tool configuration. Shared gate code: what every gate needs has one source under `shared/`, described in [kit-shared-gate-code](shared/GATE.md). A module links to it from its first commit (`scripts/const_gate`, and in `tests/` the same package, the shared test files and the module's own packages, relative symbolic links; `scripts/check-shared-links.py` is the gate), fills the interface of [its §2](shared/GATE.md#g2), and writes only its own model, messages, checks and modes. What may be admitted there, and when a shared part may be widened for one module, is rule 2 of [plc-0009-shared-code](docs/policies/plc-0009-shared-code.md#r2); a change to the shared code bumps the version of every published module that links it. Territory matching in the default dialect goes through `git check-ignore`, verified at authoring.
5. Prove twice: fixtures against a bare temp repo (the parts of laws 2–3 a run can test, in the kit's CI: the [A12.1](docs/requirements.md#a12-1) grep of law 2, `scripts/check-portability.py`, and each module's bare-repo install alone, from the change's GitHub repository and branch — a pull request's head, or `main` on a push — `scripts/check-bare-install.py`, entries of the gate list each with its `--self-test` as its fixture; the rest of law 3, sibling references only as optional enhancements, by review), then live. The live proof is in this repository for modules whose objects the kit holds: governed documents of a kind it holds, the code territories its own current-state documents describe, its own session conduct, both the rules its guide keeps and those its modules carry (the kit is consumer zero) — and in a consumer project: session in the project, plugin loaded from this repo's path (check current plugin-dir and marketplace mechanics against the official docs, never memory). When no consumer exists yet, the record and the yes follow the kit-live proof; the consumer-live proof is a named step of the consumer's bootstrap, and a finding there is a fix — with a version bump once the module is published — priced by its stakes. Each acceptance item names the matrix rows it proves ([template §10](module-template/MODULE.md#t10)). The kit's `scripts/check-aspects.py` holds those tags, one entry of the gate list; with `--run` it runs the runners and gives each matrix row the result of its own items — a status derived on each run and stored nowhere, never a green for a row no run examined. `--module <name>` narrows the run, `--self-test` is its fixture (decision [dec-0054-acceptance-items-name-their-rows](docs/decisions/dec-0054-acceptance-items-name-their-rows.md)).
6. Validate fresh-context before the human yes, in two passes, both mandatory. First, a subagent holding only the module's files, the template, this file, and the module's matrix rows — never the authoring reasoning — reviews against laws 2–7 and every template section. Its mutation probes run through the `mutation-probe-runner` agent of `.claude/agents/`, and the live items of step 5 through the `live-proof-runner` agent there, each on a copy or a clone in the scratch directory, the kit read-only to both. A headless run in a clone or copy the platform has not been told to trust silently loads no plugin through settings, so the runners pass `--plugin-dir` per module. Second, the carry audit of [rule 2 of plc-0004-decision-records](docs/policies/plc-0004-decision-records.md#r2), run through the kit's `carry-audit` skill — its regression and confirming readers the `regression-reader` and `confirming-reader` agents of `.claude/agents/`: fresh readers, each round pinned to one commit, their scope computed by `scripts/check-carry-lists.py --scope` and never chosen. Full readers read in full the records the change adds or edits and those the module's decisions section cites; regression readers, every other record that cites a file the change touched, asked only whether that file still states what the record ruled. For each added record, a blind reader who never sees it answers the author's questions from the current-state documents alone. Where the change makes wording edits in accepted records or frozen comparisons, one more reader reads each against the kinds their policies list. Every finding of either pass is fixed or justified in a commit message of the change, the merge commit included — never only in the pull request's description, which git does not keep (decision [dec-0009-module-routine-validation-and-inputs](docs/decisions/dec-0009-module-routine-validation-and-inputs.md)). The commit that names the yes carries the audit's receipt of [rule 5 of plc-0004-decision-records](docs/policies/plc-0004-decision-records.md#r5); `scripts/check-carry-lists.py` gates the carry lists, every ruling's anchor and the receipt — which shows that an audit was declared and accounted for, not that it was run — and whether a ruling is carried stays the readers' judgment.
7. Version bump on every change once published; consumer projects update by version. A draft, at `0.0.x`, need not be bumped — for a change of its own, a change to the shared code or a consumer-live finding alike — and may still be bumped within `0.0.x` (decision [dec-0053-drafts-keep-their-versions](docs/decisions/dec-0053-drafts-keep-their-versions.md)).

## Never in this repository

Project content or references (law 2). References to any location outside this repository other than a public URL — no local folder, no sibling repository, no absolute filesystem path; information from such places enters only after verification, cited to the public source that verified it (in markdown files the scan of module [`const-referencing`](docs/requirements.md#const-referencing) turns red on an absolute path under a home directory or a `file:` link — scripts and configuration are held by review, and a module's installed components also by the kit's `scripts/check-portability.py` for the forms of [requirement A12.1](docs/requirements.md#a12-1)). A placeholder path in install instructions — a consumer's clone location, the platform's own configuration directory — is not a reference. Knowledge-layer content (separate layer, separate concern). A parallel component model — Claude Code's plugins/skills/hooks/agents are the mechanical kernel; this repo adds semantics only. Machinery for failures no consumer has hit — growth is friction-earned, via consumer commit notes recurring on a theme.
