# The code every gate shares

*One source for what every gate of the kit must have: `constitution_layer_kit/` for the gates, and its subpackage `constitution_layer_kit/testing/` for their fixtures. A plugin holds none of it. Its entry files import the Python package that pip installed for `python3`, in every project, the kit's own sessions included. [§1](#g1) tells how the package is built and released. A module's `tests/` reach the working tree's copy through one relative symbolic link to the package, the shared test files inside it. That link stands beside its links to its own packages. The harness puts `shared/` on the `PYTHONPATH` of every gate it starts. So a fixture tests the module and the shared code of one commit together. It never tests an installed release (R7 and R8 of [dec-0099-shared-code-installed-as-a-pip-package](../docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r7)). R2 of [dec-0107-shared-test-files-in-the-distribution](../docs/decisions/dec-0107-shared-test-files-in-the-distribution.md#r2) rules the one link. This page and its two companions are the home of every shared text. This page holds the interface and the limits. The messages are on [the page of shared messages](MESSAGES.md#g3), and the acceptance items on [the page of shared items](ITEMS.md#g5). A module's document writes out its own messages and links to the page of shared messages for the rest. Every list and table row carries a handle.*

## 1. What is shared, and why it may be

What may be admitted here, and when a part already admitted may be widened for one module, is [rule 2 of plc-0009-shared-code](../docs/policies/plc-0009-shared-code.md#r2). The table's class says which kind of code each part is. Class K implements a kernel section literally. Class R implements a rule of [kit-gate-script-rules](../module-template/gate-script-rules.md). Class T implements a section of the module template that every module fills. Today that is the section "Effect" of [template §13](../module-template/MODULE.md#t13) (R7 of [dec-0114-module-effect-report-design](../docs/decisions/dec-0114-module-effect-report-design.md#r7)).

| part | class | carries |
|---|---|---|
| `identity` | R | which gate this run is. It holds the namespace, the gate name, the plugin root and the name of the dials file the gate reads. It holds any library the module needs beyond the shared ones. It holds the two clauses that close `C2` and `C12.11`, and what stands until the failure is fixed, a gate's by default. By mode, it also holds the skill of the plugin that teaches the rule and its fix. The dials file's name is the required field `dials_file`, relative to the repository's top. It has no default (R1 of [dec-0100-gate-declaration-scoped-to-one-guarded-run](../docs/decisions/dec-0100-gate-declaration-scoped-to-one-guarded-run.md#r1)). The top-level keys of that file that are no namespace are the kernel-owned keys of its layer. They are the required field `kernel_keys`, with no default either. In every gate of this kit they are `KERNEL_KEYS`, the constitution's three. In a gate of another layer they are its own layer's list, with `module_prefix` always among them. A list without `module_prefix` is a defect of the entry point. It is a `RuntimeError` raised as the scope opens, which declares nothing (R3 of [dec-0106-two-dials-files-and-kernel-keys](../docs/decisions/dec-0106-two-dials-files-and-kernel-keys.md#r3)). The constitution's own calibration stays in the one file [kernel §6](../docs/constitution/CONVENTIONS.md#k6) names; another layer's file holds that layer's keys and modules alone. A gate of another layer reads the constitution part of a second file in a scope of `reading(dials_file, kernel_keys)`, opened inside its run's scope. That scope shadows the file's name and its kernel keys and nothing else. So every message names the file being read, while the identity's other fields, the mode and the hook's deadline stay the run's. Outside every scope, it is the caller's defect, raised as it opens. So is an empty name, or one empty once stripped, or a list without `module_prefix` (R1 of [dec-0106-two-dials-files-and-kernel-keys](../docs/decisions/dec-0106-two-dials-files-and-kernel-keys.md#r1)). The identity is declared for the length of one guarded run. The mode of the run is declared with it: hook, scan or act. The git budget of `repository` and the hook's deadline read that mode (limit 16 of [§4](#g4)). It also carries `hook_seconds`, the seconds one hook run of the gate may take in all: `HOOK_SECONDS`, 25 s, unless the module sets another. In hook mode the opening of the run's scope starts the run's one deadline, `hook_seconds` from that moment. `remaining`, `ran_out` and `left_of`, which never raises, serve the waits of the run, as limit 16 of [§4](#g4) says. `LEFT_FOR_THE_REST`, 5 s, is the margin that a handler's timeout keeps over `hook_seconds`. The declaration is held in one context variable of the package, with no default. Only a scope sets that variable. No other module-level name holds the declaration. No code assigns or patches it otherwise (R2 of [dec-0100-gate-declaration-scoped-to-one-guarded-run](../docs/decisions/dec-0100-gate-declaration-scoped-to-one-guarded-run.md#r2)). The context manager `declared(identity, mode)` sets the variable when the scope opens. It resets it when the scope closes, normally or by an exception (R3 of [dec-0100-gate-declaration-scoped-to-one-guarded-run](../docs/decisions/dec-0100-gate-declaration-scoped-to-one-guarded-run.md#r3)). Outside every scope, a read of the identity or of the dials file's name is a defect of the caller. It is a `RuntimeError` and never a failure of the repository. The mode then reads as none, and no wait has a deadline. So does a scope opened with no mode, as a test runner opens one. An identity whose `dials_file` is empty, or empty once stripped of whitespace, names no file. That is the same kind of defect, raised as the scope opens, and it declares nothing. A scope opened inside another shadows the outer declaration until it closes, and the outer one holds again after it. A second declaration is no defect, whether it differs or not (R5 of [dec-0100-gate-declaration-scoped-to-one-guarded-run](../docs/decisions/dec-0100-gate-declaration-scoped-to-one-guarded-run.md#r5)). Every module of this kit names `constitution.yaml` in `dials_file`, the file [kernel §6](../docs/constitution/CONVENTIONS.md#k6) names. A module of another layer names its layer's own file (R10 of [dec-0099-shared-code-installed-as-a-pip-package](../docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r10)) |

It carries the keys of the shared configuration failures and the exit codes |

| `repository`, `territory` | K | git for the root and the file list. `is_markdown` is the one test of what Markdown is, by the name's ending, in any case, a file named just `.md` included (limit 7 of [§4](#g4)). | `dials` | K, R | the dials file, the one the declared identity names, read and validated for the keys every gate reads. Those keys are the kernel-owned keys the identity lists in `kernel_keys`. It is a kebab-case word that ends in `-`, else `C5.11`, which the reading module's namespace starts with, else `C5.12`, another layer's file. One that holds no mapping is passed over, save the reading module's own, which is `C5.5`. One that holds a mapping is read as the last read of this row says. Any other top-level key, the kernel-owned ones aside, must hold a mapping, else `C5.4`, and is read as a candidate policy namespace, its `territory` strictly (`C5.6`). A module that declares territories in its own dials calls it for them too, naming the dial by its whole path. The second is of a key of the module's namespace that the module does not read (`C5.10`). Every module calls it — class R, [rule 8 of kit-gate-script-rules](../module-template/gate-script-rules.md#r8). A dial ignored in silence is a silent pass. A module that blocks nothing lists `LOG_DIR_KEY` alone. `texts` gives the non-empty strings of a list. `relative_path` gives a repository-relative path as the file system reads it. It is used for `root_policy` and `log_dir` and by the modules that read paths (limit 15 of [§4](#g4)). One read crosses the kernel's "reads no other module's namespace". A prefixed key that holds a mapping is also kept as a candidate policy namespace. Its `territory` is kept when it is a list of non-empty strings, and is silently empty otherwise. ## 2. The interface a module fills

1. **Identity.** The module's `start` builds one `Identity(namespace, gate, plugin_root, dials_file, kernel_keys, libraries, until_installed, until_fixed, skills, hook_seconds)` and calls `cli.run(argv, identity, load_modes)`. Its `dials_file` is `"constitution.yaml"`, the file [kernel §6](../docs/constitution/CONVENTIONS.md#k6) names, and its `kernel_keys` `KERNEL_KEYS`. This is so in every module of this kit and in each of its entry points, as review holds. A module of another layer names its layer's own file and that file's kernel keys (the `identity` row of [§1](#g1)). There is no separate declaration. That call, and `cli.guarded` below, open one scope of `identity.declared` before anything else. That scope declares the identity and the mode of the run together (limit 16 of [§4](#g4)). The scope covers all the guard does. It covers the output, the parse of the arguments, the preflight and the import of the module's modes. It covers the run, the failure lines and the flush. It closes before the guard returns the exit code (R4 of [dec-0100-gate-declaration-scoped-to-one-guarded-run](../docs/decisions/dec-0100-gate-declaration-scoped-to-one-guarded-run.md#r4)). The `namespace` contains a `-`. The fix of `C5.11` writes the part of it up to and including its first `-` as the `module_prefix` of the file. A namespace without one would get a fix that is no valid prefix. The identity carries the hook's budget, `hook_seconds`, so the opening of a hook run's scope also starts its deadline. `until_installed` and `until_fixed`, the clauses that close `C2` and `C12.11`, default to a write gate's — writes pass unchecked, the check does not run. Those defaults fit a gate whose hook runs on a Markdown write, and `until_fixed`'s fits every gate. Any other gate names `until_installed` with what its failure leaves unchecked, since no Markdown write passes through it. Such a gate is a scan alone, a hook on the shell or a hook at a turn's end. Its entry files carry the same clause in `C1`, `C14`, `C15`, `C16` and `C17`, and its module's document writes it out. An item of its runner holds it in `C2` and in the entry files. A second entry point of a module is a generator that changes files, with a command line of its own, never a gate. It builds an identity of its own. It calls `cli.guarded(identity, Mode.ACT, body, could_not_run)`, whose second argument is the mode of its scope: an act, so its git calls have no clock. That is the same single guard, exit codes and log, around a body. The body parses its own arguments with a parser whose usage error is a configuration failure. It runs `preflight.check`, and only then imports what needs the declared libraries. `could_not_run` is its own closing line, since "0 documents examined" is a gate's. Its two clauses say what it leaves undone or what not to do with it — nothing is created, do not move documents with it. They are true in every state the failure can find, since no write passes through a generator. A session-start printer — an advisory hook that reads the dials and prints to the model's context, blocking nothing — is a third kind. It builds its own identity and calls `cli.guarded(identity, Mode.HOOK, body, could_not_run)`, so that its git calls have the hook's clock and its deadline. The guard is around a body that takes no arguments, turning any into the shared misinvocation by hand. The body runs `preflight.check`, and only then imports the pipeline and its dials. Its closing line says that the gate's state is not said. Its `until_installed` is `until then the gate's state is not said at session start`. Its module's document writes it out, and an item of its runner holds it in `C2` and `C1`. The shared code never imports a module. A library beyond PyYAML goes into `libraries` and `requirements.txt`; S137 holds the two lists equal. `skills` maps a mode to the skill of the plugin that teaches that mode's rule and its fix, by the skill's own name. The pipeline names it in the line after a red verdict of that mode, `F10`. A mode the map leaves out gets no line. A gate whose module has no skill, a generator and a session-start printer give none.
2. **Two modes.** `load_modes` returns `cli.Modes(hook, scan)`, each returning an exit code. A module whose scan takes flags of its own hands `cli.run` a list of `cli.Argument` and gives `Modes` a `scan_with`, called in `scan`'s place with the values by flag. A flag given without `--scan` is a misinvocation, and the usage line names the flags. `load_modes` is called after the preflight, because the module's code needs the declared libraries. This makes the import inside `load_modes` an explicitly necessary exception to [rule 16 of kit-gate-script-rules](../module-template/gate-script-rules.md#r16). In an entry point of another kind, so is the import of a generator's acts, or of a printer's pipeline and dials. So is the import of the effect report's rules after its preflight, with the dials and the pipeline of the report's runner. Each is marked and reasoned where it stands.
3. **The middle of a run is the module's.** A mode calls `pipeline.locate_write` or `locate_scan` and gets a target or a `Skip`. The skip carries `reason`, the shared text, and `kind` and `where`, the same facts typed. A module that says a skip in its own words switches on `kind` and takes `where` whole. It never parses `reason`. A gate that resolves policies then returns `pipeline.no_root_policy(output)` when `target.dials.root_policy` is absent. The type of `build_index` does not let it forget. A gate that resolves policies only under a dial of its own raises its own `C5` there instead. It does so since a skip would let a write through with nothing examined. A gate that reads only its own dials matches its own territories with the `Matcher` and builds no index. The first kind builds the index by `build_index` inside `with Matcher() as matcher`, with the pending document in hook mode only. Building it raises the shared failure `C12.10` in both modes for a file in the root policy's territory nobody can read. Such a file is a policy by the kernel's rule whose own territory nobody can know, never a policy with no id. It then examines documents with its own checks, in a scan through `index.documents()`, which raises the same failure. It hands findings and notes to `pipeline.report_hook`, `report_scan`, `green_hook` or `skip`. `report_hook` takes the event's name, which the `warn` channel must repeat. It also takes a count line of the module's own where "1 document examined" would not be true. It takes `ask` too, true for a gate whose block is the user's yes at the platform's prompt — the shell gate. All three default to what a gate before the write needs. `WriteTarget.event_name` tells a module wired to both events which one it is answering. `green_hook` takes what the examined document is: `messages.governed_by(policy)`, or the module's own words where no policy is involved. It also takes the event's name, which a run with notes must repeat (`G2`). `skip` takes the event's name in a hook run that has notes to hand on, and none in a scan. A gate wired to an event that names no file — `Stop` — calls `pipeline.locate_event` for an `EventTarget` or a `Skip`. A clean examination ends in `green_event`. Its findings go through `report_hook` with `event_name=STOP` and a `count` of its own, and the warn there is the `systemMessage` alone. Nothing in the pipeline calls back into the module.
4. **Own dials.** `Dials.own` is the module's namespace as YAML read it. The module parses it once into its own dataclass. It raises the shared `ConfigurationFailure` with its own `C5` text when it is malformed. It first calls `dials.refuse_unknown_keys(own, known)`, `known` being the keys it reads in the order its failure lists them. The shared `C5.10` is the first key outside them, in sorted order. 5. **Own messages.** A module's findings, skip reasons, notes and dial failures live in the module's `messages`, written like the shared ones. Its finding keys are its own enum. A message may take a value from a document, a dial, the envelope, the command line, the hook payload, the environment or a tool. Such a value goes through one of two shared functions of `messages` ([§1](#g1)), never raw and never through `shown` alone. `escaped` shows the backslash, the line feed and the carriage return escaped and never cuts. It is for a value the reader must open, copy or type into a fix, or that a later step reads. That is a repository path, an id or an anchor typed into a fix, or the text of a dial that teaches. It is also a tool's one-line diagnosis, or a generator's output line. `echoed` is `escaped(shown(value))`: cut at 80 characters, then escaped. It is for a value that only points at something the reader can already see in the file or the command. That is a dial key, a pattern, a phrase, a command word, a match from a document, or an event or tool name. A value is left alone in three cases only. The code or a check has fixed its shape before the message. Examples are a name matched whole by a kebab pattern, an integer, a hash, an enum, a code literal. Or the system's own error text already escapes it: an OS error that quotes the path with `repr`. Or it stands inside a command the reader pastes. A pattern that checks an id is applied with `fullmatch`, so that no id ends in a line break. A field read as a string goes through the shared `envelope.string_field`. A message that names the dials file asks `identity.dials_file()` and holds the name in no string of its own (S178).

## 4. Shared honest limits

Every module has these limits and states its own beside them.

1. **Shell writes and other actors.** The gates judge `Write` and `Edit`, the members of `FileTool`. Survey of 2026-10-11, Claude Code 2.1.286: the tools reference lists `NotebookEdit` and the shells `Bash` and `PowerShell` beside them, and `MultiEdit` is in neither page. A matcher of only letters, digits, `_`, `-`, spaces, `,` and `|` is read as an exact string or a list of them. So the matcher `Write|Edit` of a gate that judges writes sends it no other tool. An event for another tool that does reach such a gate is a visible skip, `G1.1`. A shell, `Bash` or `PowerShell`, a heredoc, `sed -i`, a human's editor, a merge, another server's file tool: none is a `Write` or `Edit`, and the hook never sees it. The hooks documentation adds `tool_response.bashEditDiff` to a `PostToolUse` of `Bash` (Claude Code 2.1.269 or later) and calls the list best effort and in public beta. Backstop: the module's scan, on demand and in CI.
2. **A configuration failure, a timeout, and a hook that cannot start are non-blocking in hook mode.** Exit 1 shows the user the first stderr line and the write proceeds. The platform treats a late hook or a missing script alike (Claude Code 2.1.251, read 2026-09-18 to 2026-09-23). Backstop: the scan exits 1 with the same line, so CI turns red. The line lands in the output log.
3. **The package may be missing, too old or too new.** A plugin holds no shared code. So a gate cannot run in a project that has not installed the package for the `python3` its hooks run. Nor can it run where the project has a release the plugin was not written for. The failure is `C15` when the package cannot be imported, and `C16` when the release is below the one the plugin requires. It is `C17` when the plugin is older than the installed major. Each is an exit 1 that names the plugin's own `INSTALL.md`, where the command stands, and none blocks in hook mode (limit 2). In the kit's own sessions the plugins run from the working tree with the release the developer installed. So a module that requires a later release stops with `C16` until that release is installed. The other way out is that the developer installs `shared/` from the clone with pip. Between the merge of a change that raises `REQUIRES` and the push of its release's tag, the install notes name a tag not yet made. Then installing `shared/` from the clone is the way (R9 of [dec-0099-shared-code-installed-as-a-pip-package](../docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r9)). Backstop: those lines, loud like a missing library's, with an absence fixture in every module (S115, S184–S186). S112, S115, S184 and S185 run every entry file the module's `Subject` names. The scan backs them, exiting 1 with the same line. `scripts/check-copies.py` holds each `REQUIRES`, the text of `C15` whole, and the code of each entry that prints `C16` and `C17`. It does not hold their texts, which come from the shared code and which S184 and S185 run. It holds the install note's command too, and the tag of each such command in the install guide. Beside it stand `scripts/check-bare-install.py`, red for anything at `plugin/scripts/constitution_layer_kit` in the copy it installs. So do the install, session and guide checks, which run every hook and scan in a throwaway virtual environment. Its `.pth` file names the change's `shared/`. `scripts/check-shared-package.py` stands beside `scripts/check-copies.py` too (R17 and R19 of [dec-0099-shared-code-installed-as-a-pip-package](../docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r17)). Fallback: none. The earlier one, links replaced by copies, has no object. The reason is that no plugin holds a link or a copy (R7 of [dec-0099-shared-code-installed-as-a-pip-package](../docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r7)). Platform facts, seen while plugins carried a link and kept because the install check rests on them. A marketplace install copies a plugin into the plugin cache. It dereferences a link whose target lies elsewhere within the same marketplace — "the target's content is copied into the cache in its place". It skips one leading outside it (re-read 2026-09-23 against the documentation, Claude Code 2.1.251). The marketplace root is the directory holding `.claude-plugin/`. A plugin loaded in place — `--plugin-dir`, or a relative-path entry of a marketplace added from a local directory — runs from its source. Its hook processes receive a plugin root that points there (observed on 2.1.282, 2026-10-01). Installing such an entry writes a copy into the cache all the same, which the session does not run (research [res-0008-const-interaction](../docs/research/res-0008-const-interaction.md), p14). In that copy, on 2.1.282, a link to the shared code arrived as a real directory. File links were recorded dereferenced on 2026-09-25, and a directory link seen on 2026-10-01. One a level deeper in `plugin/scripts/` was seen on 2026-10-21. An install from the marketplace's git remote, the copy a consumer's install writes, carries it the same way. A link that stays inside the plugin stays a link. This was seen on 2026-10-07 in the kit's CI on 2.1.282. It was seen the same day on 2.1.286 too, in an install from the working folder. No plugin holds one, since a module's runner links stand in `tests/`, outside the plugin, and no install copies them. A project that registers a clone as its marketplace runs that clone in place, as a relative-path entry of a local folder does. This was seen on 2.1.286 on 2026-10-07. One registered from the kit's GitHub repository runs the cache copy. The install guide's check holds this on every run of the kit's CI. The documentation says that under `--plugin-dir` only symlinks that resolve within the plugin's own directory are preserved. That sentence describes what a copy into the cache keeps. The kit reads it as a rule for a component path. A script's own import through a link is none (on 2.1.251 a plugin loaded with `--plugin-dir` resolved it, observed 2026-09-19).
4. **`Edit` is reconstructed, not observed.** The edit is applied to the file on disk and the result judged. An absent `old_string` is a visible skip. An `old_string` occurring twice without `replace_all` is judged on its first occurrence though the tool will refuse the edit. An `Edit` of a missing file with an empty `old_string` is judged on what it creates. One with an empty `old_string` on a file that exists is a visible skip, since it matches everywhere. Backstop: the tool's own refusal comes after the hook (Claude Code 2.1.251, read 2026-09-18 to 2026-09-23). The next real write is judged again.
5. **Symbolic links in the consumer.** The written path is resolved before it is matched, so a territory that names only a link does not claim what is written through it. Backstop: territories over real paths; the scan lists files under the paths git records.
6. **A key given twice in an envelope.** YAML keeps the last one. Backstop: review.
7. **Markdown means `.md` — the name's ending, in any case, a file named just `.md` included, in the hook and in the scan alike. Git-ignored files are invisible to the scan,** which lists tracked files and untracked ones git does not ignore. A tracked file deleted from the working tree is left out. A path holding a line break is examined, and every message shows the break escaped, `\n`, so each line stays one line. Backstop: the hook still judges such a file when it is written through the file tools. A module whose hook follows its dial skips a new file git ignores before the write too, as [`const-referencing`](../docs/requirements.md#const-referencing) does. A file git lists stays covered, whatever the ignore rules say of it.
8. **The envelope opens when the first line is `---`, leading byte-order marks aside. It ends at the first later line that is `---`. Trailing whitespace is ignored on both lines**. A line ends only at `\n`, `\r\n` or a lone `\r`. Whitespace is what Python's `str.rstrip` strips. So a form feed or another break character after `---` is whitespace, while one before `---`, or one after it with text, makes no delimiter. A block scalar containing such a line truncates it. Backstop: the module reports the truncated envelope as invalid.
9. **Patterns match case-sensitively on every platform,** so one repository gets one verdict everywhere. Backstop: the scan sees a file under the case git records.
10. **The output log is best-effort evidence, not a gate.** A logging failure never changes a verdict, and neither does a failure of an advisory memo a module keeps beside the log. The module swallows that memo's read and write errors the same way, each said so at its place ([rule 12 of kit-gate-script-rules](../module-template/gate-script-rules.md#r12)). A configuration failure is two records — its BROKEN line and the closing line. An unexpected one is three, the traceback last, because the guard prints each apart. Should that trouble a reader, the remedy is a guard that prints once, never another unit of record. `C1`, `C14`, `C15`, `C16` and `C17` are printed and not logged, since the entry file prints them before the shared code that logs has run. Backstop: stdout and stderr remain the record.
11. **No `--help`,** and no abbreviated flags: `argparse`'s own help exits past the guard and the log. Backstop: any unknown argument is a misinvocation whose fix line is the usage.
12. **With two gates installed, the model sees one block message at a time** when both exit 2. This was observed on Claude Code 2.1.251 on 2026-09-19, and the documentation is silent. Backstop: the next write is judged again; both findings are in the output logs.
13. **A negated pattern takes a file out of a territory only where git can re-include it:** not under a directory an earlier pattern excluded. `<dir>/**` followed by `!<dir>/README.md` works, since the file lies directly in the named directory. `!<dir>/sub/README.md` does not, and the file stays inside. Backstop: a territory of file patterns — `<dir>/**/*.md` — from which any file can be taken out. The shared item S148 shows the half that works, and the third module's own fixture shows both.
14. **A hook's text over 10,000 characters is replaced by a preview.** Read 2026-10-03 on the platform's hooks documentation, Claude Code 2.1.286 installed. The `additionalContext`, `systemMessage` and `initialUserMessage` strings of a hook, and its plain stdout, are capped at 10,000 characters, each string measured alone. Over it the platform saves the whole text to a file and shows its path and a preview of the first 2,000 characters. The cap has no setting. The two modules that can print many findings after a write, [`const-language`](../docs/requirements.md#const-language) and [`const-referencing`](../docs/requirements.md#const-referencing), show those that fit in `SHOWN_CHARACTERS`, 8,000. They do so through `pipeline.within_the_cap`, so that the whole text stays under the platform's 10,000 and is not replaced by a preview. The count line and the closing note stand last and would be lost with it. The findings shown fit the 8,000, except the first, which is always shown. The notes and the count line are not counted in the 8,000. A value that only points is cut at 80 characters ([`echoed`](#g1)). But a value escaped whole is bounded by its source, not by 80. Such a value is a path, an id typed into a fix, or the text of a dial that teaches. A dial's text or a document's text is bounded by nothing the gate holds. Examples are the plain word of [`const-language`](../docs/requirements.md#const-language) kept whole in the fix of its pair rule, or a link's fragment in R6 of [`const-referencing`](../docs/requirements.md#const-referencing). Such values reach `within_the_cap`, which runs after a write only. **Breaks:** one such first finding can alone pass the platform's 10,000, and `within_the_cap` still shows it, since it shows the first. The platform then replaces the whole text with a file path and a preview of its first 2,000 characters. The count line and the closing note are lost with it. Before a write, [`const-referencing`](../docs/requirements.md#const-referencing) prints its R1 to R4 findings with no cut at all. So many of them, or a lane's `fix` kept whole, can pass the 10,000 there as well. Backstop: the count line says how many findings there are, and the scan lists them all. A dial's text stays as short as it teaches. That covers a dial's text and not a link's fragment, whose length is the document's. Fallback: none needed.
15. **A dial's path is read with the platform's separator.** `root_policy`, `log_dir` and the paths a module reads — the `docs` paths of the `coverage` dial of [`const-task-close`](../docs/requirements.md#const-task-close), which trims each first, and the `template` paths of [`const-locations`](../docs/requirements.md#const-locations) — go through `dials.relative_path`. Blank and absolute paths are refused, and so are those leaving the repository by `..`. `./` and `//` are normalised, and `.` is accepted, the repository itself. A leading or trailing space is kept as part of the name for `root_policy`, `log_dir` and a `template` path of [`const-locations`](../docs/requirements.md#const-locations). A backslash separates only where the platform says so. So `..\x` leaves the repository on Windows and is one file name on macOS and Linux. That is one dials file, two verdicts on two machines — unlike a pattern, limit 9, which is read the same everywhere. Backstop: a path written with `/` reads alike everywhere.
16. **A hook run has one deadline, and every wait in it takes the smaller of its own cap and what is left.** The identity carries `hook_seconds`, 25 s by default (`HOOK_SECONDS`), which each module's gate, session-start printer or generator names in its identity. In hook mode the guard starts one deadline for the run. It does so when it opens its scope (item 1 of [§2](#g2); R3 of [dec-0100-gate-declaration-scoped-to-one-guarded-run](../docs/decisions/dec-0100-gate-declaration-scoped-to-one-guarded-run.md#r3)). A scan, an act and a scope opened with no mode have none, and neither has a wait made outside every scope. Every shared git call and every wait a module makes takes the smaller of its cap and what is left of the deadline. The shared git calls have a cap of `GIT_SECONDS`, 3 s each: `rev-parse --show-toplevel`, `ls-files`, `check-ignore`, the `Matcher`'s `init` and `check-ignore --no-index`, and every call a module makes through the function. The modules' own caps come next. The history read of [`const-catalogs`](../docs/requirements.md#const-catalogs) has a cap of 5 s. For the prose linter of [`const-language`](../docs/requirements.md#const-language), the version probe has 5 s and the run 10 s. For the link checker of [`const-referencing`](../docs/requirements.md#const-referencing), the version probe has 5 s. The one budget for its reading, its masking and its run is 20 s. Where nothing is left when a wait is asked, the wait does not start. The run ends in the configuration failure `C12.14`, which names the budget and the wait it ended. It is non-blocking, as limit 2 says, and the count line follows it. So the user reads the gate's line and not the platform's notice for a hook cut at its timeout. A call that runs past its own 3 s is still `C12.12` for a call in the person's repository. It is `C12.13` for one in the `Matcher`'s scratch repository. A wait that the deadline shortened, given less than its cap, and that then runs out ends in `C12.14` too. Such a wait is a shared git call, or the version probe and the run of the prose linter and of the link checker. The link checker's budget is one too. The tool's own line stands only for a wait given its whole cap. The history read of [`const-catalogs`](../docs/requirements.md#const-catalogs) is the exception: it is a git call outside the function, and an advisory wait, asked only after a verdict. It takes the smaller of its 5 s and what is left, by `left_of`, which never raises, with a clock of its own inside that number. A read that clock cuts ends in the working tree's answer. So does a read asked when nothing is left, which starts no git. Neither is a failure, so that no verdict falls with its advice. In scan mode and in act mode the function gives git no clock. So a slow scan or a slow move is waited for as long as it takes. The scan checks the tree a hook gave up on. The version probes of the two tools keep their cap of 5 s in every mode, and their runs have no limit in a scan. A scope opened with no mode, as a test runner opens one, has no clock and no deadline. **What the deadline does not hold:** the interpreter's start and the reads before the scope opens, and the reading of the event on standard input. Nor does it hold a wait that takes no number from the clock, of which there is none in hook mode today. A healthy git slower than 3 s in a hook, as on a very large repository, gives the `C12.12` line in place of a late verdict. A process git started, a `core.fsmonitor` hook, may outlive the git the timeout kills. Two ties hold the numbers. The first tie binds every handler of a module's hooks file whose `command` names `python3`, or whose script names it. It binds a gate's, a session-start printer's, a grant's or any other entry point's. Each such handler has a timeout of at least the `hook_seconds` its own entry point declares plus `LEFT_FOR_THE_REST`, 5 s. That margin is for the interpreter's start, which the deadline does not count, and for the reads after the last wait. So a run that spends its deadline ends with the shared line before the platform cuts the hook. The tie reads the declared number whatever mode the scope opens in. An entry point whose run has no deadline, an act, is held to it all the same. S165 holds it, in every module. It starts each such handler as the platform does, on empty input in a fresh consumer. A patch logs the budget the entry point declares itself with, and ends the process there, before the scope opens. So nothing of the run happens. So a printer whose identity names another budget than its gate's is held at its own. A handler whose entry point never declares itself, opening no scope of `identity.declared`, is red, since the tie has no number to hold it to. So is one that cannot be started, or that does not reach its declaration within the 20 s the item gives it. An identity that names no `hook_seconds` declares the default. A gate with a hook run must have at least one handler to hold. So there a hooks file that is missing, or that holds no handler that names `python3`, is red. Any other module owes none: with no hooks file, or with handlers that all name no `python3`, it is green. A handler's script is each `args` entry that is no option, an option being an entry that starts with `-`. It is also each word of its `command` that lies under the plugin's folder or is an existing file. A script that cannot be read counts as one that names `python3`. A handler that names no `python3` is not held to the timeout. The other tie: each module's own waits in one hook run fit its `hook_seconds`. The module's own item holds it: item 77 of [`const-catalogs`](../docs/requirements.md#const-catalogs), item 16 of [`const-language`](../docs/requirements.md#const-language) and item 70 of [`const-referencing`](../docs/requirements.md#const-referencing). Facts, read 2026-10-08 with git 2.54.0, Python 3.12.4 and Python 3.14.8, follow. A `core.fsmonitor` hook ran on `ls-files`, `check-ignore -q` and `status --porcelain`, never on `rev-parse --show-toplevel` or on the `Matcher`'s `init` and `check-ignore --no-index`. A hung hook of that kind, set in a repository's or a person's configuration, therefore hangs the call that lists the files. A stalled file system can hang any call. A `subprocess.run` timeout of 1 s raised `TimeoutExpired` at 1.01 s on both interpreters while the hook still ran. The hook ended by itself and no process was left. Backstop: the scan; the lines name the scan, the setting to find and, for `C12.12`, the call to run by hand; S165 and S167.

17. **The transcript's format is the platform's, and Claude Code does not document it.** The window of `--since` opens at the day's first second. For git it opens in the machine's own time, since git reads a bare date as that day at the clock time of the run. For a transcript, whose times are UTC, it opens by the date as written. The headline counts the sessions with an event in the window. On Claude Code 2.1.317, read 2026-11-07, a run that let its call through was recorded with the command `command hook <n>`. Earlier sessions recorded the script's path in its place. The reader then takes the module from the run's green line. A gate whose green line does not open `GREEN: <module>:` is matched by script alone. The effect report reads it as it was observed on Claude Code 2.1.286 on 2026-11-07, the fields `history` names. A line it cannot read is counted, and the count stands in `U1`. So a changed format shows as unread lines and never as a quiet count of nothing. A field that moved shows as moments no longer found. A hook's input names the transcript's path, `transcript_path`, as the [hooks reference](https://code.claude.com/docs/en/hooks) documents it. The plugin list's `projectPath` is compared with the repository of the current folder. So a report run in a worktree of a project whose plugins are enabled for its main checkout finds none of them. Backstop: the shared items of the effect report, which build their transcripts by hand, and the log's own fields, which the kit writes.

18. **The ways read by pattern, and the escape check scans an older tree with the new plugin.** `shell_changes` reads a command's text. So a `>` inside a quote, a path built in a variable and a path with a space are misread, in either direction. So is a file changed by a program the pattern does not know. `skill_before` counts a load earlier in the same session for every later moment. A skill stays in the context until the session is compacted. Yet a load before a compaction also counts after it. `escape` scans at most the last 50 commits of the window and says so in `U7.5`. It runs the plugin as it is installed now over the tree of each older commit. So a rule added since flags a commit that was green when it landed. `switch_off` reads the plugin list as of the time of the report, not as of the session. A report run in a worktree finds the plugin list entries of the main checkout only, limit 17. Backstop: the report is advisory and blocks nothing. The counts say how many moments each helper found, and the fixture of `scripts/layered-fixture/` shows each helper's reading on a hand-made input.
