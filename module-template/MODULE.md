# MODULE.md — `const-<aspect>`

*Template. Every constitution module is a folder whose `plugin/` subfolder is a Claude Code plugin, with this document at the folder's top beside it, and this document is the module's **description** from the first draft on — there is no separate specification kind (decision [dec-0003-module-spec-kind](../docs/decisions/dec-0003-module-spec-kind.md)). A draft module carries manifest version `0.0.x`; it is published at `0.1.0` or higher, once every gate has its fixture and no open marker is left. Open slots in a draft are written inline as `[decide: <slot> — default <X> — stakes <level> — decider <who>]`; an authoring session derives its questions from these markers in document order, and a published module carries none.*

*Fill every section; a section that does not apply says "none" with one line of reasoning. The module depends on the kernel (`CONVENTIONS.md` + schemas) and on nothing else — if it seems to need a sibling module, the shared concept belongs in the kernel; raise that instead of coupling. **No file in the module references a project directly** (paths, names, values): project specifics arrive only through the dials namespace, and the module must install and operate on an empty repository using its defaults ([kernel §6](../kernel/CONVENTIONS.md#k6), portability rule). References to sibling modules are permitted **only as optional enhancements** ("when module `const-x` is installed, ..."); every rule must be executable with the kernel alone — the test: **kernel + this module on an empty repository is a functioning installation.** Every list and table row carries a handle so one item can be cited without quoting it.*

*In a module's copy, the two paragraphs above give way to one status line in italics, three sentences: "Draft at manifest version `0.0.x`, no open slots.", then "This document is the module's description", with the word *template* linked to this file, then "Every list and table row carries a handle.". Once the module is published, its first sentence reads "Published at manifest version `x.y.z`."; a draft names its open `[decide:]` markers in place of "no open slots". It names no phase of the rollout plan, a task-record whose state changes apart from this document. A bold label in this template is followed by one of two marks: *(slot)*, where the module writes its own text, and *(template rule)*, which binds the module and is not copied into it.*

<a id="t1"></a>
## 1. Purpose

One paragraph: the failure pattern this module prevents, stated concretely — in terms someone has observed, not a category name. If the failure pattern cannot be named, the module is not ready to exist.

<a id="t2"></a>
## 2. Failure class

`accumulating` or `self-limiting`, with one line of reasoning; a module may be split honestly — name the accumulating slice and the self-limiting remainder. Then the **entry trigger**: accumulating modules belong in every project's day-one install set; a self-limiting module names the observed friction signal that earns its installation, stated so a consumer can recognize it.

<a id="t3"></a>
## 3. Rows

The requirement set, and nothing else ([law 4 of CLAUDE.md](../CLAUDE.md#law-4)): every matrix row homed in this module, by handle. The row's text lives in the matrix and is not repeated; the table carries the *reading* the row needs beyond its text — interpretation, boundary rulings, the part of a shared row this module owns. A row under a boundary test (marked † in the matrix) states which of the three tests is open — *one invariant? one enforcement moment? one lifecycle trigger?* — and which sibling takes the row if the boundary moves.

| row | this module's reading |
|---|---|
| `[A<n>.<m>](../../docs/requirements.md#a<n>-<m>)` | … |

Optional, one line after the table: each row of the module's aspect that another place homes, with that home and how this module meets it — the kernel's, a definition enforced through one of this module's rows, a binding row this module only gives dials to.

<a id="t4"></a>
## 4. Decisions

Provenance of this module's rules: the records whose rulings it applies, each cited by its record id while the record exists. When a record is deleted its entry goes with it and nothing replaces it; a ruling below recorded stakes has no entry. The rule itself is stated in the section where it acts ([§5](#t5)–[§9](#t9)); a record is cited for where and why it was decided, never in place of the rule ([kernel §5](../kernel/CONVENTIONS.md#k5)). The record holds the options and reasoning, which are not restated here.

One record per entry, one line each, the record and the row linked in the form the placeholders show:

1. `[<record-id>](../../docs/decisions/<record-id>.md)` — one line naming what it fixes here.

<a id="t5"></a>
## 5. Invariant

The one rule the module guarantees, stated in a single testable sentence built only from kernel vocabulary and this module's own definitions. An advisory-only module claims no invariant; in its place stands the numbered rule list, each rule labeled `advisory` in its own text. A module with an invariant and advisory rules states the invariant, then its advisory rules as a numbered list under the handles `<L>-a`, `<L>-b` and so on, the letter `<L>` one that none of its message keys uses, each rule labeled `advisory` in its own text.

Four fixed sub-slots follow the table:

- **Always-on content** *(slot)*: the exact lines the module's `SessionStart` and `SubagentStart` hooks print, and each skill's `description`, with its `when_to_use` if any, as the skill listing carries it, each with its size in characters; or "none". This is the module's whole always-on budget, since the platform loads the skill listing into every session. A line that holds a value, such as a path, is written with the value's placeholder, `{root}`, and sized as its fixed text, the placeholder named. A pointer line given to subagents too is counted again here, as the cost of each subagent's start. Then the pointer line of the skill row, or `Pointer line: none` with one line of reasoning: no skill applies before a write or at a moment no gate meets, or sessions were found to load it at its moment.
- **Platform facts relied on** *(slot)*: each fact with its source — a link to the page of the official documentation, this module's research comparison with the fact's handle there, or `observed on Claude Code <version>` with what was run — the date it was verified, one date per fact, and what breaks if it changes. Nothing in this slot comes from memory.
- **Cost and budget** *(slot)*: the hook budget each hook run declares, each wait's cap, each handler's `timeout`, and each cost measured, with its date and the platform's version; or "none". [§9](#t9) and [§10](#t10) cite this slot and never restate its figures.
- **Research** *(slot)*: a link to this module's own dated comparison in `docs/research/` — written at authoring, in kit vocabulary, from a survey of the official documentation, community harnesses, and applicable tools for exactly this module's rows — and, per row, whether the matrix's recommended enforcement was confirmed or overturned by it (decision [dec-0010-module-research-per-module](../docs/decisions/dec-0010-module-research-per-module.md)). Nothing from earlier design work enters unverified. Where a later survey covered some mechanisms only, the line names which comparison each mechanism cites ([rule 2 of plc-0005-research](../docs/policies/plc-0005-research.md#r2)).

**Gate-script rules** *(template rule)* (decision [dec-0020-gate-script-rules](../docs/decisions/dec-0020-gate-script-rules.md)) — every Python script a module ships follows all sixteen; the fresh-context validation checks them:

1. **Shape.** The entry point is a thin file. Past about 300 lines of logic, or with a second entry point, the code is a package directory beside it, imported with no path manipulation — Python puts the script's directory on the import path. What every gate shares is not written again: it is the Python package `constitution_layer_kit`, which pip installs from the distribution `constitution-layer-kit` and the plugin never carries, the module fills the interface of [kit-shared-gate-code §2](../shared/GATE.md#g2), and the Python entry file states `REQUIRES`, the release of the package it needs, turns a package it cannot import into its designed configuration failure, `C15`, and calls `cli.version_failure` right after it imports `cli` (R5 and R7 of [dec-0099-shared-code-installed-as-a-pip-package](../docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r5)). Never a sibling-script import and never a `sys.path` edit of the script's own process, the fixtures included: the tests import the shared package and the module's own packages through links in `tests/` (item 7 of [kit-shared-gate-code §2](../shared/GATE.md#g2)), and a child process a test starts may be given its own path (item 8 there). A package or shared test file the tests import this way uses `__file__` only as `Path(__file__).resolve()` and derives every path from that, since through a link `__file__` is the link's path, not the file's; the kit's `scripts/check-resolved-paths.py` holds it. Package and module names are snake_case because the language requires identifiers; entry-point files stay kebab-case.
2. **Messages.** One messages module per package: the shared package's, and the module's own for its findings, skip reasons, notes and dial failures. Each message is a function with typed parameters returning its three parts — what failed, why the rule exists, the exact fix — under the key it carries in this section's error-message table.
3. **One exit.** `main(argv) -> int`, a single `sys.exit`, and one guard that maps the configuration exception to exit 1. The entry file's exits before the module's own package can be imported — the interpreter floor, a shared package that cannot be imported (`C15`) or whose release does not serve the module (`C16` and `C17`, found right after `cli` is imported) — are the only others, each printing its designed line and the count line; a generator's entry file prints its own closing line in the count line's place, and its variants of those lines drop the clause about unchecked writes.
4. **Exit codes.** Named constants: 0 green, 2 finding, 1 configuration failure. Parameters are parsed with `argparse`, whose exit-2 default on bad usage is overridden to 1.
5. **Separation.** Parsing, checking, and reporting are separate functions; a check is a function of typed inputs.
6. **Runtime.** Plain `python3` through the POSIX entry point, never `uv run`. Floor: Python 3.12, the value of `FLOOR` in the shared preflight. The interpreter version and every declared library are preflighted on each invocation, before any verdict is printed.
7. **Dependencies.** Unrestricted, but declared in `requirements.txt` at the plugin root; the configuration-failure message prints the one install command for that file. The shared package is the one exception: it is no entry of that file, and its failure names the module's `INSTALL.md`, which gives the pip command at the tag of `REQUIRES` (R15 and R16 of [dec-0099-shared-code-installed-as-a-pip-package](../docs/decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r15)). `yaml.safe_load` only.
8. **No fail-open.** An unexpected exception exits 1 with its traceback; unparseable hook input is a configuration failure; nothing exits 0 on error. An advisory script may fail open and says so in its docstring.
9. **Types.** Every parameter and return is annotated. Untyped data — JSON, YAML — is parsed once into dataclasses; no bare `dict`, `list` or `Any` crosses a function boundary; closed vocabularies are enums. `mypy --strict` is clean.
10. **Docstring contract.** The entry point's docstring states the hook events, the modes, the input fields read, the exit codes, the output channels, and the dial keys read.
11. **Hook wiring.** `hooks.json` uses the exec form (`command` plus `args`) wherever a path placeholder appears, with an explicit `timeout`.
12. **Output log.** Everything a gate prints is also appended to a log, one JSON line per print: timestamp, module, gate, mode, session, stream, text — a text of several lines, a verdict or a traceback, stays one record, never a line apiece, its newlines escaped by JSON. The records of a run whose log is written, each text followed by a newline, rebuild what was printed on each stream exactly, save a character the stream could not encode, which the stream shows escaped and the record keeps (decision [dec-0038-log-record-per-print](../docs/decisions/dec-0038-log-record-per-print.md)). Location: the fixed dial `log_dir` ([§7](#t7)) when set — repository-relative and verified git-ignored, otherwise a configuration failure; else `${CLAUDE_PLUGIN_DATA}`; else nowhere, and stdout is the record. The log rotates at a fixed size, holds only what was printed, and a logging failure never changes the verdict — the one error a gate swallows, and the code says so, save that a gate keeping an advisory memo beside its log, which no verdict reads, swallows that memo's read and write failures the same way, each said so at its place. It is built on the standard library's `logging`, not a hand-made tee (decision [dec-0022-output-log-through-logging](../docs/decisions/dec-0022-output-log-through-logging.md)): a `RotatingFileHandler` behind a `MemoryHandler` that holds records until the location is known, with three cautions — the logger is named and does not propagate, so no other library's line reaches stdout or stderr, which in hook mode are a protocol; the stream is the caller's choice and the level only carries it; `logging.raiseExceptions` is switched off, because its default prints a traceback to stderr, whose first line is what the user sees.
13. **Paths.** The target path comes from the tool input, resolved against the event's `cwd`; a path escaping the repository is a visible skip.
14. **Fixtures.** pytest tests in `tests/test_<name>.py`, each an item `@item(<number>, <title>)`, numbered as in [§10](#t10), the module's own from 1 and the shared acceptance items, linked into `tests/` and run through the module's own entry point, from 101, one number per item, a number two tests carry stopping the run before any test. A case record — number, title, red, green, the message red must teach — drives the real entry point with real hook events and fails when red does not fire or does not teach the expected message, or green still fails. A property with no failing half is a plain test. Every message the module's code can print stands, in the fixtures that run it, at least once as a line typed by hand — its fixed text written out, a value the test computes filled in — since an expectation built by the message's own function cannot catch a defect in that function's text; a shared message stands so in the shared items or in the fixtures of a module that runs it. The fresh-context review holds this, with the kit's `scripts/list-message-literals.py`, never shipped in a module, as its aid: it reads the messages modules, where rule 2 puts every message, lists each message function with no piece of its fixed text, 15 characters or more, typed in a fixture that runs it — for a shared message, the shared harness included — and lists apart those whose text is too short to find — a list for the review to judge and never a verdict. YAML fixture documents are rendered by the dumper, never typed as strings, unless malformed text is the point.
15. **Absence fixtures.** Every external tool or library the gate needs has a fixture simulating its absence; the shared items cover the interpreter, git, PyYAML and the shared package itself, and a module adds one for anything more it needs.
16. **Imports at the top.** Every import stands at the top of its module, where a reader, the type checker and the preflight see the dependency; none inside a function or a method, unless it is explicitly necessary — and then the reason is written at the import, beside the marker that silences the check, `# noqa: PLC0415`. Today there are three such cases, of one kind: a module's two modes, a generator's acts, and a session-start printer's pipeline and dials, are imported after the preflight, because only then does a missing library become its designed message instead of a traceback. An entry file imports `cli` of the shared package at module level after the floor check, inside the guard that prints `C15`, and the module's own package after the version check that `cli` makes (item 6 of [kit-shared-gate-code §2](../shared/GATE.md#g2)), for the same reason; each of these imports carries the marker `# noqa: E402`. A call of `importlib.import_module` made on purpose — the preflight's own — is one the tool does not see; review holds it. The kit's tooling holds the rule: `ruff` rule `PLC0415` (decision [dec-0026-imports-at-the-top](../docs/decisions/dec-0026-imports-at-the-top.md)).

**Error messages** *(slot)*. Every check's error message is written here as part of the design — the module's own; the shared texts are written out once, in [kit-shared-gate-code §3](../shared/GATE.md#g3), and the module's table links there — it is the highest-bandwidth channel for teaching an agent mid-session: state what failed, why the rule exists (one clause), and the exact fix. Reviewed like code; copied verbatim into the script. The table is `| key | first line | why | fix |`, one row per key of the module's messages module. A text that is no finding — a skip reason, the count line's tail, a session-start line, a note, a dial failure — fills the cells it has and writes `—` in the others.

**Installed components reference nothing in the kit** *(template rule)*. A skill, hook, script, command, agent, error text, or install note never cites the requirements document, the rollout plan, a matrix row, a decision record, a research comparison, or this document: consumers install the module without the kit, so every such reference dangles there. Rules are stated in those components in plain words; the reasoning lives here and in [§4](#t4).

<a id="t7"></a>
## 7. Dials

The module's calibration surface. Namespace = plugin name in the project's `constitution.yaml`; every dial has a default; the module works with zero configuration. A module with a hook gate — at write time, at a turn's end, or on a shell call — carries the fixed dial `severity` — `block` (default) or `warn` — as its first row; its repository-scan mode ignores the dial and always reports. Every gate also carries the fixed dial `log_dir` — absent by default — naming a repository-relative, git-ignored directory for its output log ([§6](#t6), gate-script rule 12).

| dial | default | read by | meaning |
|---|---|---|---|
| `<dial>` | `<value>` | the gate, the scan, a printer or a skill | one line |

The `read by` cell names each part that reads the dial: only a dial a script reads is validated.

<a id="t8"></a>
## 8. Boundary examples

For every judgment-based boundary the module introduces (including its slice of the routine/product stakes line, if any): at least three contrastive pairs, numbered straight through the section. A pair sets one side against the other, each with its verdict: violates / complies, or, where both sides are allowed, the two outcomes, such as → routine / → recorded. Where the module has several advisory rules, the pairs stand in one group per rule, headed by the rule's handle in bold. The examples are the definition; no abstract criteria. The project's own pairs arrive through dials.

<a id="t9"></a>
## 9. Enforcement honesty

For each artifact of [§6](#t6) that runs or prints, the session-start printers included: `gate` (deterministic — hook or script, red means fix) or `advisory` (judgment-shaping — skill prose, a line printed at session start, suggestions in review), one artifact per row. Nothing advisory is dressed as a gate. A scan over the tree is written in its row as a code span that reads exactly `<entry> --scan`, or `<entry>.py --scan` for an entry named by its Python file, nothing after the flag, so that the kit's `scripts/check-gate-lists.py` finds it and holds it in the kit's gate list, its CI list and the install guide's scan block. That check reads the table row by row, whatever a row's indent, each row opening `E<n>`, bold or not. A mode that is no tree scan is written `<entry> --scan --<flag> …` with the words `not a tree scan` in the same cell, outside a code span, and declares no scan. Any other code span in a row that holds `--scan`, and a span in the declared form in this section's prose, is a finding of that check. A deterministic check whose blocking is a dial is a `gate` with its severity dial named — the check is still deterministic. For a hook gate that dial is `severity` ([§7](#t7)): `warn` reports the finding and lets the write, or the turn's end, through — the adoption path onto a repository with legacy documents, or the path for a session that must not be asked to commit; the default `block` keeps the gate a gate. The table:

| # | artifact | kind |
|---|---|---|
| E1 | the hook on `<event>` and `<entry>.sh`: what it checks | `gate`, its dial `severity` |
| E2 | the scan: the code span of its `--scan` form | `gate` |
| E3 | the skill `<name>` | `advisory` |
| E4 | the hook on `SessionStart` and `<printer>.sh`: the line it prints | `advisory` |

Then the **honest limits** *(slot)*: first one line that cites the limits every gate shares, [kit-shared-gate-code §4](../shared/GATE.md#g4), and restates none; then the module's own, numbered, each a path the gate does not see (a tool that bypasses the hook's event, a moment outside its trigger) with its backstop, or `none — accepted` with the reason the gap is accepted.

**Exit-code contract** *(template rule)* for every check: a finding (the repository is wrong) and a configuration failure (the checker is broken, a pinned tool is missing, the invocation is malformed) are distinct exit codes with distinct messages, so a reader never mistakes one for the other. A missing tool is loud, never a silent pass; a check that could not run reports that it could not run.

<a id="t10"></a>
## 10. Acceptance

For each gate: the red→green fixture proving it (a fixture that fails without the check, passes with it), under `tests/` ([law 7 of CLAUDE.md](../CLAUDE.md#law-7)), plus one fixture showing the exit-code split of [§9](#t9) (a missing tool or malformed invocation exits differently from a finding). For each advisory rule: the boundary examples above stand as its acceptance. Each item labeled by verification kind: `fixture` (bare temp repo), `live` (the kit as consumer zero, or a consumer project, the plugin loaded from this repository), `eval` (a run of one of the module's eval cases on the pinned model, its result read from the kit's receipt, whose date, platform version and model are its evidence; one item per case, its "what it proves" cell naming the case as `` `evals/<case>/` ``), `review` (the human, at the one yes), `kit check` (a check the kit runs on the module from outside it, never shipped). A `live` item that proves a session's behaviour alone, and whose proof does not run in a consumer project, becomes an `eval` item where a case covers it whole: the `eval` item replaces it, and the proof it asks for is owed no more. Every other `live` item stays `live`, and the proof it asks for stays owed: one that no case covers whole, one that proves a scan over the kit's tree, and one whose proof runs in a consumer project, deferred or not. A scan item and a consumer-project item stay `live` because an eval runs in an empty folder, which a scaffold seeds where a case needs a project: it proves no scan over the kit's tree, and it runs in no consumer project.

**Runner line** *(slot)*. A line at column 0 that opens `Runner:`, outside code fences, names the command that runs the fixtures from the module's folder, `python3 -m pytest tests`, the run the kit makes through `scripts/check-aspects.py --run --module <name>`, and the item ranges the table holds; it may hold `<digits> items green`, a count that the kit's `scripts/check-aspects.py` holds against the runner's total under `--run`.

**Handles** *(template rule)*. As [rule 8 of plc-0006-module-documents](../docs/policies/plc-0006-module-documents.md#r8) states them, one prefix per kind. A number once used is never used again: a removed item leaves a gap, and a shared item the module does not claim is left out of the shared line.

**Rows** *(template rule)*. The acceptance table is `| item | kind | rows | what it proves |`. The `rows` cell links every matrix row the item proves, each to its anchor in the requirements document, or says `none` for an item that proves no row of the module — the hooks file's shape, the manifest, the install note. An item names a row only where it proves what the module's reading of that row in [§3](#t3) says the module ships. A fixture that checks an advisory row's carrier — a line a hook prints, a skill's description — names the row: it proves that the carrier is shipped and reads as written, never that the rule is followed, whose judgment is proved by the boundary examples at the review item. An `eval` item names each row whose reading names the skill, the pointer line or the start rule its case checks. The line of the shared items carries every row that a fixture item of the module, run through the same entry point — the script its hook or its scan calls — names, and no other row. Every row [§3](#t3) holds is named by at least one item. The item cell is handles and closed ranges, `T1–T4, T7`, a fixture item's handle being its test's number, bare or under `T` or `S`; the kind opens with `fixture` — `fixture, red→green` for a case record, `fixture, assertion` for a plain test — or `kit check`, `live`, `live, deferred`, `eval` or `review`. An `eval` item is one item for one case: its "what it proves" cell names the case as the code span `` `evals/<case>/` ``, the folder's name of lowercase letters, digits and hyphens, every case folder of the module has an item, and no case has two. The kit's `scripts/check-aspects.py` holds this as a line of the gate list; with `--run` it runs the tests and gives each row the result of its items, a row's status derived on each run and stored nowhere (decision [dec-0054-acceptance-items-name-their-rows](../docs/decisions/dec-0054-acceptance-items-name-their-rows.md)); it reads an `eval` item's result from the module's receipt, and gives none where the receipt is not current; an `eval` item whose receipt is current counts as run, green when its last attempt passes and red when it does not, a run declared and not one the kit sees (decision [dec-0093-module-evals-with-local-receipts](../docs/decisions/dec-0093-module-evals-with-local-receipts.md)).

**Examined count** *(template rule)*. Every check reports how many items it examined in its green and red output alike. Zero is a visible count, never a failure and never a silent green: a check that inspected nothing must say so, because a vacuous green read as permission is the failure this rule exists for.

<a id="t11"></a>
## 11. Siblings

**Depends on:** the kernel sections used, each external tool a gate preflights, such as git or a pinned third-party tool, and the Python distribution `constitution-layer-kit`, which pip installs as it installs PyYAML for a module that reads YAML: the kit's shared gate code is no sibling ([law 3 of CLAUDE.md](../CLAUDE.md#law-3)) — nothing else. Then the kernel-alone statement, with that package installed: what the module does on a bare repository with the kernel only, and what runs without each external tool. Then each optional enhancement as "when module `const-<x>` is installed, …". A concept this module needs from a sibling is a kernel candidate, raised as a `process` decision, never coupled.

<a id="t12"></a>
## 12. Deferred

What this module deliberately does not ship yet, each with the friction signal that would earn it. The deferrals every gate shares stand once in [kit-shared-gate-code §1](../shared/GATE.md#g1), the deferred parts, and are cited, never restated; this list holds the module's own. Nothing here is a hidden requirement: a deferred item has no matrix row, or its row is marked deferred there.

## Plugin skeleton

```text
const-<aspect-name>/
├── MODULE.md                # this document, filled in; never installed
├── README.md                # the landing page for a reader, from the template's README.md; of the root README's kind, binds nothing; never installed
├── plugin/                  # the plugin root, the only folder a project installs; its marketplace source ./modules/const-<aspect-name>/plugin
│   ├── .claude-plugin/
│   │   └── plugin.json      # manifest — the ONLY file inside .claude-plugin/; version 0.0.x while draft
│   ├── INSTALL.md           # install/uninstall notes; the pip command of the shared package at the tag of REQUIRES; the one CLAUDE.md pointer line if any
│   ├── requirements.txt     # optional; the libraries its scripts need, installed by one command
│   ├── skills/
│   │   └── <name>/          # optional; SKILL.md, and any file it names through ${CLAUDE_SKILL_DIR}
│   ├── commands/<name>.md   # optional
│   ├── agents/<name>.md     # optional
│   ├── hooks/hooks.json     # optional
│   └── scripts/             # optional; reference via ${CLAUDE_PLUGIN_ROOT}
│       ├── <entry>.sh       # the POSIX entry point each hook and the scan call; finds python3, then exec
│       ├── <entry>.py       # a Python entry file: FLOOR and REQUIRES, then C14, C15 and the version call, then its own package
│       ├── session-start.sh # optional, with session-start.py: the line of a gate whose dial leaves it examining nothing
│       ├── print-skill-pointer.sh  # optional: the pointer line, at session start and, with --subagent, at a subagent's start
│       └── <module>_gate/   # the module's own package: model, messages, checks, modes, start, dials, session
├── evals/<case>/case.yaml   # the eval cases, each naming its plugin (plugins: ../../plugin), scaffold.sh beside one that needs a project; evals/results/ ignored by git; never installed
└── tests/                   # conftest.py, test_<name>.py; constitution_layer_kit and the shared test files linked from shared/; <module>_gate from ../plugin/scripts/; one red→green fixture per gate ([law 7 of CLAUDE.md](../CLAUDE.md#law-7)); never installed
```

The template takes the same split: `module-template/plugin/` holds its parts that install, and `MODULE.md` and `README.md` stand beside it; it has no `tests/` and no `evals/`, which a module adds with its first gate and its first case. Kebab-case everywhere. Only plugin.json lives inside `.claude-plugin/`; every component directory sits at plugin root. Verify the manifest fields against the current plugin reference at authoring time. A module carries no license file: its manifest names the license, and the kit's `LICENSE` and `NOTICE` stand at the kit root alone. Linking both into each module is reopened as a decision once a module is mirrored or vendored outside the kit's marketplace.
