# Shared-code policy

Governs the document kind *shared-code description*: the three pages beside the kit's shared gate code. [`shared/GATE.md`](../../shared/GATE.md) states what the code is for, the interface a module fills and the shared limits. [`shared/MESSAGES.md`](../../shared/MESSAGES.md) holds every shared message, and [`shared/ITEMS.md`](../../shared/ITEMS.md) the shared acceptance items (decision [dec-0025-shared-gate-code-linked](../decisions/dec-0025-shared-gate-code-linked.md)). Territory under this policy's id in `constitution.yaml`.

## Rules

1. <a id="r1"></a>**One home for shared texts.** Every message the shared code prints is written out, word for word, on the page of shared messages, [`shared/MESSAGES.md`](../../shared/MESSAGES.md), as the code returns it. A module's document writes out its own messages and links there for the rest ([law 6 of CLAUDE.md](../../CLAUDE.md#law-6)).
2. <a id="r2"></a>**Admission.** Code is shared only when two conditions hold (R7 of [dec-0114-module-effect-report-design](../decisions/dec-0114-module-effect-report-design.md#r7)). The first is that it implements a kernel section literally or a rule of [kit-gate-script-rules](../../module-template/gate-script-rules.md). A section of the module template that every module fills also counts. The one such section today is the section "Effect" of [template §13](../../module-template/MODULE.md#t13). The second is that two or more modules need it. The document names the class of each part. A part already shared may be widened for one module where the widening keeps a rule the part carries for all. Such a rule is one guard, one pipeline or one fixture subject. The widening must also default to what the other modules pass, so they change nothing.
3. <a id="r3"></a>**Portability.** The pages and the code carry no project reference ([law 2 of CLAUDE.md](../../CLAUDE.md#law-2)) and no module's name. A module is `{module}` in every text. The one exception is a page that must point at one module's fixture or code. There the module is its ordinal in the order of authoring — "the third module". The rollout plan resolves that ordinal, and it never changes. A shared message about a module's namespace names the key and never shows an example of that module's dials. An example that replaces the namespace drops the module's own keys. The example is the module's to give.
4. <a id="r4"></a>**Handles.** Every list and table row carries a handle. An acceptance item's number is never reissued: an item a subject leaves out keeps its number free, and a new item takes the next.
5. <a id="r5"></a>**Anchors.** Every section carries an explicit anchor `g<n>`. A new section takes the next number, and an anchor is never renumbered.
6. <a id="r6"></a>**Platform facts.** An observed fact about the platform names the platform's version and the date it was observed, its backstop and, where one exists, its fallback. A re-read is dated inline.
7. <a id="r7"></a>**Change.** A change to the shared code updates the pages of this kind in the same change — the pair `shared-gate-code` of the kit's coverage map. Where rule 11 says so, it also raises `__version__` of the package. It bumps no module's version by itself. A module's version is bumped when the module stops being consistent with the earlier shared code and raises the version it requires. The bump is an explicit act of the change. A draft's need not be bumped (steps [4](../guide/developing-a-module.md#s4) and [7](../guide/developing-a-module.md#s7) of the module-development page).
8. <a id="r8"></a>**Deferred.** A part not built is listed with the signal that would build it, as [template §12](../../module-template/MODULE.md#t12) asks of a module.
9. <a id="r9"></a>**Enforcement.** The envelope is held by module [`const-meta-types`](../requirements.md#const-meta-types), and links and anchors by module [`const-referencing`](../requirements.md#const-referencing). Module [`const-task-close`](../requirements.md#const-task-close) holds the pairing with the code in its scan alone — the range check, run before a merge and on the trunk after it. Rule 11 is held by two checks of the kit, never shipped in a module. Each is an entry of the gate list with `--self-test` as its fixture. `scripts/check-copies.py` holds every version a module requires at or below `__version__`, in the same major. `scripts/check-shared-package.py` builds the package, installs it into a fresh virtual environment and imports it there. It holds the installed version and `__version__` equal. That a change raised `__version__` and that a release is a go-ahead's tag are review. A check on the raise waits for a release that missed it. That the messages table equals the code word for word, and rules 2 and 3, are review. A check on the equality waits for a friction that earns it. The twelve traces of the style defaults are held by module [`const-styling`](../requirements.md#const-styling) in its scan alone, which runs no hook. The grade, the sentence length and the constructions of the prose are held by module [`const-language`](../requirements.md#const-language), after a write and in its scan. The length in characters is held by module [`const-doc-budgets`](../requirements.md#const-doc-budgets), after a write and in its scan. The module checks it against the ceiling its dial `ceilings` in `constitution.yaml` sets for documents of this kind.
10. <a id="r10"></a>**Style.** Documents of this kind follow the style guides that the dial `guides` of module [`const-styling`](../requirements.md#const-styling) names in `constitution.yaml`, the dials file. They depart from a default only where that module's dial `departures` names one for their territory, with its reason ([rule 9 of plc-0001-root-policy](plc-0001-root-policy.md#r9)). The traces of the defaults are held as the enforcement rule says, and the rest is review.
11. <a id="r11"></a>**Versions.** The package follows semantic versioning, major.minor.patch, from its first release, `1.0.0`. Before that tag nothing is promised. From it on, a release keeps every module written for an earlier release of the same major working, because it only adds. Such an addition is a module, a function, an optional parameter or field whose default keeps the behaviour, or a message key. A message's wording may change, its key and its parameters may not, and a name that starts with `_` is no part of the promise. A change that breaks the promise is a new major and a `process`-stakes decision of its own, made only when nothing else serves. A change to `shared/constitution_layer_kit/` or `shared/pyproject.toml` after a release raises `__version__` in the same change, unless the version already stands above the last tag. It raises the minor number for an addition and the patch number for any other change that keeps the promise. A change to `shared/GATE.md` alone raises nothing. The subpackage `testing`, the shared test files, is part of the package and of its promise. A module of another kit builds its `Subject` and its `Harness` from it (R5 of [dec-0107-shared-test-files-in-the-distribution](../decisions/dec-0107-shared-test-files-in-the-distribution.md#r5)). A release is the tag `constitution-layer-kit-v<version>` on a commit of `main` whose `__version__` is that version. It is pushed only on the decider's go-ahead, since a tag is an outward act. A release, once tagged, is never moved or made again. A module requires the first release of the package's current major until it uses a name that a later release of that major added. The change that makes it use one raises the version it requires to that release (decision [dec-0099-shared-code-installed-as-a-pip-package](../decisions/dec-0099-shared-code-installed-as-a-pip-package.md)). A new major raises every module's to its first release (R5 of [dec-0106-two-dials-files-and-kernel-keys](../decisions/dec-0106-two-dials-files-and-kernel-keys.md#r5)). It does so in the change that makes it.
