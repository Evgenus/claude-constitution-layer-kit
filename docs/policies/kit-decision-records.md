# Decision-record policy

Governs the document kind *decision record* as [kernel §5](../../kernel/CONVENTIONS.md#k5) defines it, for the kit's own rulings. Territory under this policy's id in `constitution.yaml`.

## Rules

1. **When.** A record is written for every `process`, `product`, or `architecture` ruling of the kit ([law 9 of CLAUDE.md](../../CLAUDE.md#law-9)); routine calls leave a commit note, never a record. Carrying an already-ruled item into a policy or into `CLAUDE.md`, its ruling unchanged, is a repair and routine — the ruling's own record and yes cover it, and the commit note names that record. A matrix row is not covered by this: amending one stays under rule 2 of [kit-requirements](kit-requirements.md).
2. **Shape.** The kernel's record schema and body shape; a record applied in the commit that creates it is born `inactive`. A record's last section is titled "Carry list". Every ruling item opens with a bold handle, written `**R1.**`, `**R2.**` and so on; a deferred trigger, a fallback and an exception are items too, wherever in the record they stand and though they change no file on the day. The list pairs each handle, once, with one of three things. First, links to the text that now states the item: an item that binds today is always carried so, and such a link may lead only where a rule can live — an `active` `current-state` document, `CLAUDE.md`, a skill of the kit, a module's or the template's own file, a file that is not markdown — never to the rollout plan, a research comparison, another record or the README. Second, "history only", for an item that binds nothing: a one-time act, a finding of the day. Third, "pending" with a link to the active task-record that holds it, for intent that is not yet real ([kernel §2](../../kernel/CONVENTIONS.md#k2)); once the intent is real the entry is rewritten to link the text that states it — a reference-form migration, the ruling untouched. **The carry audit** is mandatory before the yes and is run through this repository's `carry-audit` skill, by fresh readers of three kinds. One reads the record: checks that the listed text states each item in full, hunts for binding sentences the list leaves out, and sorts every mention of the record elsewhere into provenance and reliance. One reads older records for regression — whether a file the change touched still states what they ruled. One never sees the record: holding the current-state documents alone, that reader answers the questions the author puts, one per ruling item, and an item it cannot answer is a finding. Every finding is fixed, or justified in the message of the commit that names the yes — in the pull request once the kit has one. The audit is run in full, over every record, on any change to the kernel and once before publication. **Enforcement, declared:** the shape of the list and the receipt of rule 5 are a gate, `scripts/check-carry-lists.py`, for records numbered `0030` and above; whether a ruling is carried is judgment, held by the audit's readers and by review, and the gate cannot see an item that was given no handle. Records `0027` to `0029` carry a list in an earlier form and are not edited to fit, since renaming a section is no reference-form migration; records below `0027` carry none.
3. **Number.** Records are a numbered kind: id and filename stem are one name, `dec-<nnnn>-<slug>`; prefix, width and territory are an entry of `const-catalogs.catalogs` in `constitution.yaml`, its territory this policy's own by a YAML alias. A new record takes one more than the highest number the catalog has held, deleted records included, provisional until it lands on main ([requirement A13.1](../requirements.md#a13-1), [A13.3](../requirements.md#a13-3)).
4. **Reversal.** A ruling is reversed by a new record, never by editing the old one ([kernel §5](../../kernel/CONVENTIONS.md#k5)).
5. **Yes.** Until the kit publishes (rollout Phase D) the yes is given in chat and named in the message of the commit that lands the change ([kernel §4](../../kernel/CONVENTIONS.md#k4)) — its last commit, which for an audited record comes after the audit, since the readers are pinned to a commit that already holds the record; from then on it is PR approval on a protected main. The commit that names the yes carries two trailers in its last paragraph: `Accepted:` with the record's id — one trailer per record, or several ids separated by commas — and `Carry-Audit: at <commit>; <n> records; <f> findings, <x> fixed, <j> justified`, the receipt of the carry audit: the commit the readers were pinned to, an ancestor at which the record already existed; the records read, above zero; the findings, each fixed or justified. The newest acceptance of a record is the one that counts, so a wrong receipt is mended by accepting again. A record that no commit accepts yet awaits its yes: the gate reports a note and never a finding, since a gate is not red for waiting on a person. The receipt shows that an audit was declared and accounted for, not that it was run.
6. **Enforcement.** Module `const-decision-records` guards `type`, `stakes` and `decider` of every document in this territory — this policy's id is named in its dial `record_policies` in `constitution.yaml` — at write time when a session loads the plugin, and by its scan; the rest of the envelope is module `const-meta-types`'. Module `const-catalogs` guards the name, the id and the number's uniqueness the same two ways.
7. **Deletion.** No record has to be deleted. An `inactive` record whose ruling is carried binds nothing, and no rule depends on it ([kernel §5](../../kernel/CONVENTIONS.md#k5)); it is kept as evidence of the options and reasoning. Whether anything should still reference it ([kernel §1](../../kernel/CONVENTIONS.md#k1)) is the decider's judgment, not a count of links. Deleting one is routine and is one commit: every link to it is removed, the record is removed, and the commit message names the record and calls the change a deletion. Inside another record the link becomes the deleted record's title in plain words — never its id, so nothing in the tree points at what is gone — which is a reference-form migration in the kernel's sense, the ruling untouched, and the commit names it one. An `active` record is never deleted.
