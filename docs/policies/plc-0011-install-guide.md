# Install-guide policy

Governs the document kind *install guide*: the one document that tells a reader how to install the kit into a project — load its modules, copy its kernel, write the first policies, the dials file and the first record — and how to update and remove it, introduced by decision [dec-0062-install-guide-governed-kind](../decisions/dec-0062-install-guide-governed-kind.md). Territory under this policy's id in `constitution.yaml`.

## Rules

1. <a id="r1"></a>**Type.** `current-state`, superseded in place ([kernel §1](../../kernel/CONVENTIONS.md#k1)).
2. <a id="r2"></a>**Content.** The guide holds the kit's install procedure whole: the prerequisites; a walkthrough that bootstraps a new project, the modules loaded before any governed document is written; the ways to load one module, its calibration, its `CLAUDE.md` pointer and its verification; update; uninstall; and what the kit's own tooling does not ship. It restates no rule of the kernel. It gives the commands a bootstrap runs across the modules — their prerequisites, their install, their scans — and leaves each module's dials, its findings and its own calibration to the module's `INSTALL.md`, which it links. A command of the install procedure stands in the guide, where the check of rule 4 runs it; another document of the kit links to the guide instead of copying the command. A module's own `INSTALL.md` is the one exception: it ships inside the plugin, where no link to the kit's root resolves, and gives the commands of its own module — its load, the tools it needs, its scan and its fixtures.
3. <a id="r3"></a>**Present tense.** The guide states what works today. A mechanism not yet built is named as planned, with a link to the step of the rollout plan that builds it, or left out ([kernel §2](../../kernel/CONVENTIONS.md#k2)).
4. <a id="r4"></a>**Commands are run.** Every `bash` fence of the guide names, after its language in the info string, the word `check=<name>`. The name is one of the closed set the kit's `scripts/check-install-guide.py` knows, each standing in the guide exactly once, for a block the check runs, or `none`, as often as needed, for a block it does not run — an interactive session, a system package manager, or the module fixtures, which each module's own CI job runs. The dials example is a `yaml` fence named `check=dials`. A fence that opens with `check=<name>` where its language should stand is red too. A block runs in a fresh `bash -eu`, in the folder the block before it ended in, so no block relies on a variable another block set: such a variable is unset there, and the block fails. The guide writes the kit's clone as `~/dev/constitution-kit` and the project as `~/dev/my-project`, and the check makes both real under a home folder of its own. What the check holds at each name — beside the exit of every block it runs — is that script's docstring. A change that adds, renames or removes a named block, or that changes what the guide says a named block does, changes the check in the same change.
5. <a id="r5"></a>**Anchors.** Every section carries an explicit anchor `s<n>`, never renumbered ([requirement A5.5](../requirements.md#a5-5)).
6. <a id="r6"></a>**Change.** An edit of the guide is routine, noted in the commit, once the check of rule 4 is green on it. A change to a rule of this policy is a `process`-stakes decision ([rule 3 of plc-0001-root-policy](plc-0001-root-policy.md#r3)).
7. <a id="r7"></a>**Enforcement.** The envelope by module [`const-meta-types`](../requirements.md#const-meta-types); links and anchors by module [`const-referencing`](../requirements.md#const-referencing). The commands by the kit's `scripts/check-install-guide.py`, never shipped in a module, with `--self-test` as its fixture, an entry of the gate list in a CI job of its own, `install-guide`, on every pull request and on `main` after each merge: the marks of rule 4, the exit of every block it runs under `bash -eu`, and what its docstring holds at each name. The blocks named `none`, the steps the reader writes by hand, and whether the guide is whole and clear are review. The twelve traces of the style defaults are held by module [`const-styling`](../requirements.md#const-styling) in its scan alone, which runs no hook. The grade, the sentence length and the constructions of the prose are held by module [`const-language`](../requirements.md#const-language), after a write and in its scan. The length in characters is held by module [`const-doc-budgets`](../requirements.md#const-doc-budgets), after a write and in its scan, against the ceiling its dial `ceilings` in `constitution.yaml` sets for documents of this kind.
8. <a id="r8"></a>**Style.** Documents of this kind follow the style guides the dial `guides` of module [`const-styling`](../requirements.md#const-styling) names in `constitution.yaml`, and depart from a default only where that module's dial `departures` names a departure for their territory, with its reason ([rule 9 of plc-0001-root-policy](plc-0001-root-policy.md#r9)); the traces of the defaults are held as the enforcement rule says, the rest is review.
