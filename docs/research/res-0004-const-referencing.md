## 1. Broken-reference gate ([requirement A5.3](../requirements.md#a5-3))

The check: every local link of a Markdown document names a file that exists and, where it carries a fragment, an anchor that exists in that file — explicit `id` anchors on their own line and inside the first cell of a table row included ([requirement A5.5](../requirements.md#a5-5)). The kit's interim check runs t1 with `--offline --include-fragments` over every Markdown file git lists.

What t1 does, by experiment with 0.24.2 (E2–E7, E11); the documented parts are from its [readme at the release tag](https://github.com/lycheeverse/lychee/blob/lychee-v0.24.2/README.md) and its [example configuration](https://github.com/lycheeverse/lychee/blob/lychee-v0.24.2/lychee.example.toml):

- a1. **Link forms found.** Inline links, images, reference-style links, raw `<a href>`, autolinks. A reference-style link is reported at the line where it is used, not where it is defined (E2).
- a2. **Link forms skipped.** Inline code, fenced blocks, indented blocks and HTML comments yield no link by default; `--include-verbatim` ("Find links in verbatim sections like `pre`- and `code` blocks") turns that off (E2).
- a3. **Anchors resolved in the target file, one file given.** With a single input, fragments are verified inside every target file the input links to — the targets need not be inputs (E2). Resolved: `<a id>`, an `id` inside a table cell, an `id` on any element (`<span id>`), `<a name>`, a heading's generated name, the `-1` suffix of a repeated heading, a heading with non-ASCII letters.
- a4. **A missing file and a missing fragment are told apart**: "File not found. Check if file exists and path is correct" against "Cannot find fragment", each with `(at line:column)` (E2). A link to a directory that exists passes; a fragment on a target that is not Markdown or HTML passes unchecked (E2, items 14 and 15).
- a5. **Output formats.** `--format` takes `compact`, `detailed`, `json`, `junit`, `markdown`. The JSON report holds an `error_map` keyed by input path; each entry carries `url`, `status.text` and `span.line`, `span.column` (E3) — enough to build a finding that names file, line, destination and the kind of break. The `url` is an absolute `file:` URL, so a teaching message must turn it back into the link as written.
- a6. **Exit codes.** Documented: "0 Success", "1 Missing inputs or any unexpected runtime failures or configuration errors", "2 Link check failures", "3 Encountered errors in the config file". Observed (E3): an input that does not exist → 1; a malformed configuration file → 3; at least one broken link → 2; **an unknown flag, or no input at all → 2 as well**, with a usage text on stderr and nothing on stdout. Exit 2 alone therefore does not prove a finding: a caller must require the JSON report on stdout, and treat exit 2 without one as a configuration failure.
- a7. **The consumer's own files steer it silently.** A `lychee.toml` in the working directory is loaded without being asked for ("[default: lychee.toml]"), and an `exclude` entry there took three broken links out of the verdict (E4). `--config` pointed at an empty file stops that. A `.lycheeignore` in the working directory is honoured even then; it stopped being read only when lychee was started from another directory with absolute inputs (E4). And `include_fragments = true` — a boolean, as older configurations wrote it — is a parse error in 0.24.2, exit 3: the key takes a string such as `"anchor-only"` (E4).
- a8. **Root-relative links** (`/docs/x.md`) are an error — "To resolve root-relative links in local files, provide a root dir" — until `--root-dir` is given (E2, E3).
- a9. **Fragments are compared in lower case for Markdown targets**: `#K1` passes against `id="k1"` (E7; the source lowercases the fragment when the target is Markdown — [fragment checker](https://github.com/lycheeverse/lychee/blob/lychee-v0.24.2/lychee-lib/src/utils/fragment_checker/mod.rs)). On GitHub the rendered attribute is `id="user-content-k1"` (E10), and an HTML `id` is case-sensitive.
- a10. **Heading attributes pass.** `## Heading {#custom}` makes `#custom` resolve (E11; the [extractor](https://github.com/lycheeverse/lychee/blob/lychee-v0.24.2/lychee-lib/src/extract/markdown.rs) adds a heading attribute "alongside" the generated name), while GitHub renders `{#custom}` as literal text and creates no such anchor (E10). `#top` passes too; GitHub's line fragment `#L20` does not.
- a11. **File-name case** follows the file system: `B.md` resolved to `b.md` on the survey machine (E7) and would not on a case-sensitive CI runner.
- a12. **Standard input** is read as plain text — relative links are not extracted at all — unless `--default-extension md` is given; with it and `--base-url`, cross-file links resolve, but a same-document link `#x` is resolved against the base and reported broken (E5). A document that is not yet on disk cannot be handed to lychee faithfully.
- a13. **Speed** — section 2's table: 52 ms for the kit's whole tree, 35 ms for one file, 371 ms for 1,000 documents.

The alternatives, each run on the same fixture (E9) or read in its documentation:

| key | tool | local files | cross-file fragments | explicit `id` anchors | finding on the fixture |
|---|---|---|---|---|---|
| b1 | t1 lychee 0.24.2 | yes | yes | yes, table cells included | 8 of 8 deliberate breaks, no false alarm |
| b2 | t3 markdownlint MD051 | not its subject | no — one issue, the same-document `#nowhere` | yes, documented: "any HTML tag with an `id` attribute or an `a` tag with a `name` attribute" | 1 of 8; MD052 covers undefined reference labels only |
| b3 | t4 remark-validate-links 13.1.0 | yes | headings only | **no** — `#k1`, `#a5-3`, `#span-id`, `#named` each reported "Cannot find heading" | false alarms on every explicit anchor; missed the raw `<a href>`; exit 0 unless `--frail`; refuses a repository with no `origin` remote until `repository: false` is set |
| b4 | t2 markdown-link-check 3.15.0 | yes | no — `b.md#nope` passed | not applicable | 5 of 8, every miss a fragment in another file; it also queried the network, and exits 1 on findings |
| b5 | t5 mlc v1.2.0 | yes | no — "[Support anchor link targets](https://github.com/becheran/mlc/issues/31)" is an open issue | no | not run |
| b6 | t6 linkcheckmd v1.4.0 | yes | not documented | not documented | not run; last release 2021; exits 22 on findings |
| b7 | t7 linkinator v8.1.0 | through a served or converted page | `--check-fragments`: "exist on the target HTML page" | as rendered HTML | not run; a crawler of HTML, Node |
| b8 | a Python resolver of the module's own (E12) | yes | yes | yes — and it alone can say which kind of anchor resolved (section 4) | agrees with b1 on the kit: 983 local links, none broken; a 40-line prototype disagreed with b1 on one non-ASCII heading and found a link inside an HTML comment |

The matrix's words — "the only offline checker covering file links and all anchor forms with GitHub-slug parity" — hold on the survey date against every tool run or read here: b2 stays inside one document, b3 rejects the kit's own anchor form, b4–b6 check no fragment across files. Two corrections to the claim of parity: t1 is *more* permissive than GitHub in two places (a9, a10), so green is not always clickable; and [dec-0005-reference-forms](../decisions/dec-0005-reference-forms.md) recorded heading attributes as "not parsed by lychee", which 0.24.2 no longer bears out (a10).

Step down from the native option: the platform has no link checker — no component of a plugin resolves a Markdown link — so the first step is a script, and the script calls a third-party binary because b8 would re-implement GitHub's heading-name algorithm, which the prototype already got wrong once (E12).

**Recommendation: t1, lychee at 0.24.2 or newer, confirmed — called by the module's Python script, never by the consumer directly: `--offline --include-fragments --no-progress --format json`, `--config` pointed at the module's own file, `--root-dir` at the repository root, started outside the consumer's working directory (a7), inputs taken from git's file list filtered by territory.** The script owns the verdict: exit 2 only with a parsed report (a6), each finding rebuilt as what failed, why, and the fix ([law 6 of CLAUDE.md](../../CLAUDE.md#law-6)) from `span` and `status.text`, with the two kinds of break as two messages (a4). lychee's absence is a configuration failure with the install command and an absence fixture (rule 15 of [template §6](../../module-template/MODULE.md#t6)); a version below the floor, read from `lychee --version` (14 ms, E1), is another. The matrix's dial "lychee config" is overturned as a free-form pass-through: a consumer-supplied configuration can exclude links silently (a7) and its keys change between releases (a7, third sentence); what a project may need — extra excluded paths — is better a dial of the module's own namespace, translated by the script. For the decider.

## 2. Where it runs

Measured on the survey machine, each figure the median wall time of a whole process (E1, E8, E12):

| key | what ran | median | runs |
|---|---|---|---|
| m1 | t1 over the kit's whole tree: 68 documents, about 628,000 characters, 1,206 links of which 983 local | 51.8 ms (50.4–53.2) | 20 |
| m2 | t1 over one document of the kit (53 links), targets' fragments verified | 34.8 ms (33.7–35.7) | 20 |
| m3 | t1 over one document with one link, JSON report | 31.0 ms | 10 |
| m4 | `lychee --version` | 14.2 ms | 20 |
| m5 | t1 over a synthetic tree: 1,000 documents, about 6,590,000 characters, 20,000 links with fragments | 370.9 ms (363.1–374.6) | 10 |
| m6 | t1 over one document of that tree | 32.6 ms | 10 |
| m7 | the Python prototype b8 over the kit's tree / over the synthetic tree | 96.8 ms / 614.8 ms | 10 / 5 |
| m8 | `python3 -c "import yaml, json, argparse, logging"` — the floor of any gate process | 52.5 ms | 20 |

What a one-file check sees and misses (E8): after one explicit anchor of one document in the synthetic tree was renamed, t1 on that document alone was green — its outgoing links still resolve — and t1 on the whole tree reported the two inbound links that the edit broke. Inbound breaks — an anchor removed or renamed, a file moved or deleted — exist only in *other* files, so only the whole tree shows them. At m1 and m5 the whole tree costs less than, or a few times, the interpreter start every gate already pays (m8): the reason to check one file at write time is gone.

- **A. `PreToolUse` on `Write|Edit`, exit 2.** Blocks before the file exists. Two costs special to references. The document to judge is not on disk, and t1 cannot be handed a pending document faithfully (a12) — so resolution at this moment means the module's own resolver (b8). And a forward reference is normal authoring: a document that links to a sibling written in the next tool call would be refused, and the write order dictated by the gate. Fits the syntax lint of section 3, which needs nothing but the pending text and the envelope ids.
- **B. `PostToolUse` on `Write|Edit`, exit 2.** "Shows stderr to Claude; the tool already ran" ([hooks reference](https://code.claude.com/docs/en/hooks)); the file is on disk, so t1 runs over the whole tree as it would in CI. Exercised live on 2.1.251 (E17): the hook's stderr reached the model word for word, and the model rewrote the link in its next call. Cannot prevent the write — and a broken link, unlike a malformed envelope, damages nothing by existing for one turn. Cannot see a shell move: "Claude Code doesn't run a `PostToolUse` hook matching `Edit|Write` when a `Bash` command or a process outside Claude Code rewrites the same file" (same page).
- **C. `PostToolBatch`.** "Runs once after every tool call in a batch has resolved, before Claude Code sends the next request to the model"; "There is no matcher for this event" — so it fires after a `Bash` batch too, which is where `git mv` and `rm` happen; fired on 2.1.251 (E17). Its only gentle channel is `additionalContext`; exit 2 or `decision: "block"` "stops the agentic loop before the next model call" — a stop, not feedback. A whole-tree check here would run after *every* batch of any tools, 52 ms plus a Python start each time, mostly for nothing.
- **D. The scan in CI on the pull request.** The matrix's gate. On the merge commit the whole tree is present, shell moves included. One line of the consumer's workflow calling the module's script, stated in `INSTALL.md` — a plugin ships nothing a forge executes (section 9, p8). Needs t1 installed on the runner: one more install step than the three shipped gates ask for.
- **E. git `pre-commit`.** A per-clone install no plugin can perform; `--no-verify` skips it.
- **F. `FileChanged`.** Sees any writer, but its matcher registers "a literal filename in the working directory" — it cannot watch a territory.

**Recommendation: D confirmed as the gate — the scan, whole tree, exit 2 — and B as the write-time half: one `PostToolUse` handler on `Write|Edit` running the same whole-tree check, so that an inbound break is reported in the turn that causes it; the syntax lint of section 3 stays at A, where the three shipped gates run.** Step down from A for resolution, named: `PreToolUse` cannot show lychee the document (a12) and would refuse forward references. What B cannot do is block, and [law 5 of CLAUDE.md](../../CLAUDE.md#law-5) asks that this be said: at write time the broken-reference check is deterministic *feedback*; the blocking gate is the scan on the pull request. C is recorded as the candidate for shell moves and not recommended: no gentle blocking channel, and a cost on every batch. For the decider: whether B's exit 2 under `severity: block` and the JSON `additionalContext` under `warn` keep the shared meaning of the dial when neither can stop the write.

## 3. Reference-syntax lint with a project-blind vocabulary ([requirement A5.1](../requirements.md#a5-1), [requirement A5.6](../requirements.md#a5-6))

The interim check greps for the kit's retired bare forms — a module number, a requirement row, a kernel section, a numbered law — each exempt in its home document, plus a backticked governed id and an absolute local path. The four bare forms, their home documents and the fix texts that name kit paths are project content ([kernel §6](../../kernel/CONVENTIONS.md#k6)): a portable module receives them through its dials namespace or not at all.

Universal without any dial, because the vocabulary comes from the repository's own envelopes and from the file system's nature:

- u1. **A backticked governed id that is not a link** — every `id` read from an envelope in claimed territory, the document's own id excepted. Deterministic; on the kit 54 ids (E16).
- u2. **A link whose text is a governed id and whose target is not the document carrying that id.** On the kit 205 of 987 local links are id links; every one outside a code span points at its owner (E16). This is [requirement A5.6](../requirements.md#a5-6)'s `[id](current path)` made checkable, and it is the key section 5's repair works from.
- u3. **An absolute local path or a `file:` URL** in a governed document: resolves on one machine only. The patterns for a home directory are operating-system facts, not project facts.

How existing linters take a user-defined pattern with a message, and what each skips:

| key | tool | the shape of a rule | code, link text, frontmatter | cannot |
|---|---|---|---|---|
| c1 | t8 Vale | a YAML file per rule: `extends: existence`, `message` with `%s`, `level` ("Only errors set a non-zero exit code"), `link` ("the guidance the rule enforces, shown with every alert"), `scope`, `tokens` or `raw` patterns, `exceptions` ([styles](https://docs.vale.sh/topics/styles.md), [existence](https://docs.vale.sh/checks/existence.md)) | "By default, Vale ignores" indented blocks, fenced blocks, code spans and URLs ([Markdown format](https://docs.vale.sh/formats/markdown.md)); link text is its own scope and `scope: ~heading & ~link` excludes it ([scopes](https://docs.vale.sh/topics/scopes.md)) | read an envelope id list (u1, u2); exempt a rule per file except through `.vale.ini` sections the consumer owns; a Go binary plus a styles directory in the consumer's tree. Not run here |
| c2 | t10 for t3 | JSON entries: `name`, `message`, `information`, `search` or `searchPattern`, `replace`, `searchScope` — `all`, `code`, or `text`: "Search only in Markdown text, skip code" ([readme](https://github.com/OnkarRuikar/markdownlint-rule-search-replace)) | code yes; link text no — a linked handle would match | tell a bare handle from the same handle as link text; Node |
| c3 | t3 custom rules | a JavaScript module: `names`, `description`, `tags`, `function(params, onError)` with `lineNumber`, `detail`, `fixInfo` ([custom rules](https://github.com/DavidAnson/markdownlint/blob/main/doc/CustomRules.md)) | whatever the rule's code does with the parsed tokens | be configuration: each lane is code; Node |
| c4 | t9 with prh | a YAML dictionary of `expected` and `pattern` entries; `checkLink` "(default: `false`)" so link nodes are skipped, code blocks are not checked unless asked ([readme](https://github.com/textlint-rule/textlint-rule-prh)) | both skipped by default | carry a why or a fix beyond the expected spelling; Node |
| c5 | t11 Semgrep generic | YAML rule with `message`, `pattern-regex`, path includes and excludes | none: generic mode does not know Markdown, and its page lists "Caveats and limitations of generic mode" | skip code fences or link text |
| c6 | t12 `pygrep` | "Specify the regex as the entry"; the hook's `name` is the only message; `files`, `exclude` | none | carry a message, skip anything inside a file; needs the pre-commit framework per clone |

c1 is the only surveyed tool whose rule shape already carries what–why–fix and excludes both code and link text. The step down to the module's own code is still warranted: none reads envelope ids (u1, u2), none reads a territory, and each is a second runtime the consumer installs.

The dial shape those rule files suggest, in the module's own namespace — one entry per lane:

- d1. `pattern`: a regular expression for the bare form, matched on text outside the masked regions below.
- d2. `names`: what the form cites, in the project's words — it opens the finding's first line.
- d3. `fix`: the link form to write instead, as a literal template the message prints.
- d4. `home`: territory patterns of the documents where the bare form is the local alias and the lane is silent ([requirement A5.5](../requirements.md#a5-5): "a bare handle is a local alias inside its own document").
- d5. No `why` per lane: the reason — a bare handle resolves only inside its home document — is the same for every lane and is the module's fixed text; a lane may not rewrite it.

Defaults: no lanes — on an empty repository the lint checks u1–u3 alone, which satisfies the portability test. The patterns are validated at each read; an expression Python's `re` cannot compile is a configuration failure.

Masking, from the experiments (E2, E12, E16): frontmatter, fenced blocks, indented blocks and code spans are blanked, then every `[text](destination)` is removed whole, so a handle survives only where it is bare. The interim script removes links and frontmatter but not code, which is why the kit's documents cannot show a retired form even inside backticks; the prototype's one false alarm on the kit was the opposite slip — an id link quoted inside a code span (E16). Whether code is masked is therefore a design choice with a visible consequence, for the decider: masking code lets a document *show* a retired form as an example; not masking keeps the kit's present strictness.

**Recommendation: confirmed as a gate, in the module's own Python, at `PreToolUse` and in the scan: u1–u3 always, project lanes through a `lanes` list of d1–d4 entries, each finding in three parts with d2 and d3 filled in.** The preference half of [requirement A5.1](../requirements.md#a5-1) — an id where one exists — stays advisory: whether a path link *should* have been an id link is decidable only when the target carries an envelope, and that slice (a path link to a governed document whose text is not its id) can be offered to the decider as a fourth universal check, not assumed.

## 4. Anchors: a deterministic slice ([requirement A5.2](../requirements.md#a5-2), [requirement A5.5](../requirements.md#a5-5))

The matrix holds both rows advisory, with breakage left to the broken-reference gate of [requirement A5.3](../requirements.md#a5-3) after the fact. The question: can "this link resolves only through a heading-derived name" be detected when it is written?

- f1. **t1 cannot tell the two apart.** In E2 the link to `id="k1"` and the link to the generated name of the heading beneath it are both OK, in every output format; the JSON `success_map` is empty by default and carries no reason when filled. t3's MD051 accepts both alike, by its own documentation. t4 is the mirror image — it accepts only heading names (b3) — so it cannot serve either.
- f2. **A Python detector needs little** (E12): per target file, the set of explicit anchors — every `id="…"` and `name="…"` attribute outside code — and the set of generated heading names; a fragment found in the first set is explicit; found only in the second, heading-derived; in neither, broken. On the kit: 706 local links carry a fragment, none is heading-derived — the slice would be green on the day it ships. On the E2 fixture it named all eight heading-derived links.
- f3. **It does not need the heading algorithm to be right.** The finding is "the fragment is not among the target's explicit anchors" — a set lookup. GitHub's rules ([section links](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#section-links): lower case, spaces to hyphens, punctuation removed, a counter for repeats) matter only for wording the message — "resolves through a heading" against "resolves nowhere" — and the second is lychee's to report anyway.
- f4. **It closes the two parity gaps of section 1.** A wrong-case fragment (a9) and a heading attribute (a10) are both absent from the explicit set, so both are findings here though lychee passes them.
- f5. **False positives, and their bounds.** A target outside governed territory — a vendored readme, a generated file — has headings and no anchors: the check must be limited to links whose *target* lies in the territories the gate covers, the dial the matrix already names. A link to an external URL is never examined. GitHub's `#L20` line fragments point into code files, not Markdown. `#top` is a browser convention with no anchor behind it: a finding under this rule, correctly.
- f6. **Which explicit forms render on GitHub** (E10, GitHub's Markdown API on the survey date): `<a id>`, `<a name>`, `<span id>` and an `<a id>` inside a table cell all survive, each with the prefix `user-content-`; `{#custom}` comes out as literal heading text. GitHub documents only the `name` form — "You can use standard HTML anchor tags (`<a name="unique-anchor-name"></a>`) to create navigation anchor points for any location in the document" ([custom anchors](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#custom-anchors)) — and the readme of [github/markup](https://github.com/github/markup) still says the sanitizer removes "`class` or `id` attributes", which E10 contradicts. The kit's `id` form works and is undocumented; the `name` form is the documented one. Attribute syntax (`{#id}`, as Pandoc and kramdown write it) is accepted by lychee and by MD051 and rendered by neither GitHub nor a plain CommonMark reader — [dec-0005-reference-forms](../decisions/dec-0005-reference-forms.md) rejected it, and E10 confirms the ground.

Step down, named: no platform component and no surveyed tool separates the two kinds of anchor (f1).

**Recommendation: overturn "advisory only" for one slice — a gate, in the same Python pass as section 3: a link whose target lies in covered territory and whose fragment is not among the target's explicit anchors is a finding that teaches the anchor line to add.** Whether a *citable unit* has an anchor at all stays advisory — what counts as citable is judgment — carried by the authoring skill. For the decider: the finding belongs to the document that holds the link, though the fix is usually in the target; and the documented `name` form against the kit's working `id` form (f6) is a ruling already made, reported here only because its public ground is thinner than the record says.

## 5. Move and rename repair ([requirement A5.6](../requirements.md#a5-6): "repaired by tooling on a move")

What exists, verified today:

| key | tool | a command line? | rewrites inbound Markdown links | rewrites the moved file's own links | verdict |
|---|---|---|---|---|---|
| g1 | t13 VS Code setting | no — an editor feature: "`never` (the default)", `prompt`, `always`; "detects renames of Markdown files, images, and directories" | yes, inside the editor | not stated | unreachable from a hook or a script |
| g2 | t14 the library behind g1 | no — "Generate an edit that updates all links when a file/directory in the workspace is renamed or moved", for a host that implements its workspace interface | yes, as edits the host applies | yes, as edits | usable only by writing a Node host; no release of such a host was found |
| g3 | t15 | no — a VS Code extension | yes | not stated | editor only; last push 2024 |
| g4 | t16 foam-cli 0.46.2 | yes: `foam rename note <identifier> <new-name> --target-path <dir>` | **no** — "update every wikilink"; in E14 three standard links to the moved file were left as they were | **no** — E14: the moved file's two relative links and its image were left pointing at the old neighbourhood | five broken links after one move (E14); it also prints "Foam telemetry is on" |
| g5 | t17 Dendron | — | — | — | maintenance only |
| g6 | t18 marksman | no — a language server; its feature list has "Rename refactor" for headings and link labels, nothing on a file move | — | — | not a mover |
| g7 | t19 mdmv | yes | no — "Retains correct links to attachments" only | attachments only | one release, 2021 |
| g8 | t20 Obsidian | no — "can automatically update internal links in your vault when you rename a file", a desktop setting | inside the application | — | unreachable |

| g10 | registries | the names `mdmv`, `md-mv`, `markdown-link-updater`, `markdown-rename`, `markdown-mv`, `md-refactor` return 404 on both npm and PyPI; three GitHub repository searches for a mover with link rewriting found none with a release | — | — | nothing to adopt |

So the requirement's "tooling" does not exist as a scriptable tool on the survey date; the working movers all live inside an editor.

Building it, by experiment:

- h1. **The arithmetic is small.** For every other document: a destination that resolves to the old path becomes `relpath(new, dirname(document))`, fragment kept. For the moved document: every relative destination is re-resolved from the old directory and re-expressed from the new one. A 60-line prototype moved one document across directories and rewrote 7 destinations in 3 files — inline links, a reference definition with a title, a raw `<a href>`, an image — left the link inside a code span and the one inside a fence untouched, and t1 was green over the result (E15).
- h2. **Rewriting in place needs source positions, and the Python parsers do not give them** (E13). t21 markdown-it-py: block tokens carry `map` (a line range), inline tokens `map=None`; the `href` is normalised (`sp ace.md` came back `sp%20ace.md`), so it is not even the source text; reference definitions do carry their line range. t22 mistune, t23 marko, t24 commonmark, t25 mistletoe: no position on any inline node; t24 and t25 give block start lines only. None can say *where* in a line a destination stands; all would force re-rendering the document, which rewrites what the author did not touch.
- h3. **t26 does give byte ranges** for `link_destination` in inline links, reference definitions, images and table cells (E13) — through two compiled wheels of about 140,000 and 150,000 characters of binary each, and its readme warns: "it is not recommended to use this parser where correctness is important."
- h4. **Hence masked regular expressions**: blank frontmatter, fences, indented blocks and code spans — the masking sections 3 and 4 already need — and match the three destination forms on what is left, replacing by offset so that every other character of the file stays as it was. A parser is then at most an oracle in the fixtures (the destinations t21 finds equal the ones the expressions find), never a runtime dependency.
- h5. **Knowing what moved.** After `git mv` alone, `git diff --cached -M --name-status` answers `R100 old new`. After the moved file's own links are rewritten and staged, the same command answers `D` and `A` for a short document — similarity fell under git's threshold; a plain `mv` shows no rename until the new path is staged or added with `--intent-to-add` (E15). Detecting the move after the fact is unreliable exactly when the repair has begun; the mover should *perform* the move, or be told both paths.
- h6. **The id link repairs without knowing the move** (E16, u2): where the link text is a governed id, the current path is whatever file carries that id. A `--repair` pass needs no old path, no git history, and fixes id links after *any* kind of move, shell moves included. On the kit that is 205 of 987 local links; the other links — path plus anchor, 706 with a fragment — need h1 and the pair of paths.

Step down, named: the platform's file tools move nothing — a move is `Bash` — and no component rewrites links; no third-party tool does it from a command line (g1–g10).

**Recommendation: build it — a generator, advisory, proven by the gate: the module's script gains a move mode that performs `git mv`, applies h1 with h4, and then runs the scan, whose green is the proof; and the repair of id links (h6) is offered from the same code for moves made any other way.** It is an assist that a skill tells the agent to use instead of a bare `git mv`; nothing blocks a bare move, and the scan catches what it breaks. Declared limits to write down at authoring: links inside code are never rewritten; a root-relative destination is left alone; a directory move is a loop over its files.

## 6. Files that are not Markdown

- i1. **What t1 accepts** (E6). `--extensions` defaults to "md,mkd,mdx,mdown,mdwn,mkdn,mkdown,markdown,html,htm,css,txt,xml"; a directory input yielded the `.md` and `.txt` files under it and skipped a symbolic link to a Markdown file; a symbolic link named as an input is followed; a link *to* a symbolic link resolves through it, fragments included. From a Python or YAML file given by name it extracted only strings that are URLs with a scheme — a `file:` URL, `https:` — and none of: a relative path, a Markdown-style link in a comment, a path in a YAML value. HTML is read properly: `href` and `id` both. So for scripts and configuration t1 sees nothing that matters here, as the module's specification already says.
- i2. **A project-blind form of the interim check.** The interim script looks for the kit's record stems in every file that is not Markdown and reports one that names no existing record. Without a pattern, a *dangling* mention cannot be recognised at all: an id that exists is known from its envelope, an id that does not exist is just a kebab-case word. So the mention pattern must be a dial — d1's shape: `pattern`, `names`, and `resolves_in`, the territory whose stems or ids a match must equal. The module may not take the pattern from the catalogs module's namespace ([kernel §6](../../kernel/CONVENTIONS.md#k6): it "reads no other module's namespace"); a consumer states it twice.
- i3. **False-positive profile on the kit** (E16): 91 files that are not Markdown, 4 mentions of 4 distinct record stems, none dangling; symbolic links (16 tracked) and binary files are skipped as the interim script skips them. The risk is in fixtures — a test that *means* a record that does not exist — so the dial needs the same `home`-style exemption as d4.
- i4. **Without the dial** the universal residue is the reverse direction only: nothing. There is no dial-free check of files that are not Markdown.

**Recommendation: confirmed as feasible, as an optional lane kind in the same `lanes` dial, scan mode only** — a write to a script is no Markdown write, and the hook's matcher need not widen. Default: no such lane, nothing examined. For the decider: whether this belongs to the module's rows at all — the matrix rows speak of references between documents; the interim script added the check after a record's name dangled in a script — or waits for a consumer's friction signal.

## 8. Chat references ([requirement A5.7](../requirements.md#a5-7))

The rule shapes what the model *says*: a file that exists is cited as a clickable link; a local handle is scoped, and the scope named when a cite crosses it. Surfaces that can carry it:

Cannot judge the scoping half at all; the path half is noisy — code blocks, shell transcripts and quoted output all name files legitimately — and each finding costs a forced extra turn. Step down, named: there is no native surface that *checks* chat output against a rule without either a model in the loop or j5's noise; among the surfaces that *shape* it, the always-on ones are j2 and j3, and j3 is a shared single slot.

**Recommendation: advisory, confirmed — carried by j2, a `SessionStart` hook printing the chat-reference rule as the module's always-on content, a few lines whose size in characters is stated in the module's document; the skill (j1) carries the authoring procedure, not the chat rule.** The matrix says "skill (chat half)": overturned for the carrier, not for the class — a skill's body is absent from exactly the turns the rule governs. j5 is recorded as the available deterministic slice and not recommended until a consumer reports the advisory rule failing.

## Recommendations summary

1. [Requirement A5.3](../requirements.md#a5-3), the checker — **CONFIRMED**: lychee 0.24.2 or newer; no other surveyed tool resolves explicit anchors across files (remark-validate-links rejects them, markdownlint stays inside one document). Called by the module's script with the JSON report, `--config` and `--root-dir` of the script's choosing, from outside the consumer's working directory; exit 2 counts only with a parsed report; absence and an old version are configuration failures. The dial "lychee config" as a pass-through — **OVERTURNED**: a consumer's file silently excludes links, and its keys break between releases.
2. Where it runs — the scan in CI **CONFIRMED** as the gate; **extended** by a `PostToolUse` handler running the same whole-tree check (52 ms on the kit, 371 ms at 1,000 documents), because inbound breaks exist only in other files and a pending document cannot be shown to lychee. It gives feedback and cannot block; the lint stays at `PreToolUse`.
3. [Requirement A5.1](../requirements.md#a5-1), [requirement A5.6](../requirements.md#a5-6), syntax — **CONFIRMED** as a gate in the module's Python: three universal checks from envelopes and the file system (a backticked id, an id link pointing elsewhere, a local absolute path), project lanes through a `lanes` dial of pattern, what it names, the fix form and home territories; the why is the module's fixed text. Preference stays advisory.
4. [Requirement A5.2](../requirements.md#a5-2), [requirement A5.5](../requirements.md#a5-5) — "advisory only" **OVERTURNED for one slice**: a fragment not among the target's explicit anchors, target inside covered territory, is a deterministic finding; green on the kit today; it also closes lychee's two permissive cases (case, heading attributes). Which units deserve an anchor stays advisory.
5. Move repair — nothing scriptable exists (editor features, a library without a host, foam-cli leaving five broken links); **build**: a move mode of the module's script — `git mv`, relative-path arithmetic over masked text, by offset — proven by the scan; id links repairable with no knowledge of the move. No Markdown parser as a dependency: none of five gives inline positions, and the one that does warns against itself.
6. Files that are not Markdown — lychee extracts only URLs with a scheme from them; a project-blind check is feasible only as an optional lane with a pattern, scan mode only; no dial-free form exists. Whether it belongs to this module's rows is the decider's.
7. Shared code — reuses everything but the hook event parser's wording and the two-mode command line; strains: module-defined modes (second module to ask), an external binary with a version floor, a `PostToolUse` event, two handlers, a whole-tree verdict in hook mode, `severity: block` where nothing blocks. Described only.
8. [Requirement A5.7](../requirements.md#a5-7) — advisory **CONFIRMED**, carrier **OVERTURNED**: a `SessionStart` hook prints the rule as always-on content; the skill carries the authoring procedure. An output style is stronger and is a single slot that overrides the user; a `Stop` hook on `last_assistant_message` is the available deterministic slice, noisy, not recommended yet.
9. Platform facts — p1 to p10 confirmed; twelve items (a–l) missing, imprecise or newly relevant in the earlier comparisons, one of which changes a design: `PostToolUse` exit 2 reaches the model and the file is on disk, which is what makes a whole-tree reference check possible at write time; `PostToolBatch`, `MessageDisplay` and `FileChanged` are new to the kit's record and none is recommended.
