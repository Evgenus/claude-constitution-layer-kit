## 1. The carrier of the asking rules ([requirement A6.1](../requirements.md#a6-1) to [requirement A6.6](../requirements.md#a6-6), [requirement A6.9](../requirements.md#a6-9))

Four carriers exist for a rule that must be in force at the moment a decision arises mid-dialog. From the [skills](https://code.claude.com/docs/en/skills), [hooks](https://code.claude.com/docs/en/hooks) and [memory](https://code.claude.com/docs/en/memory) pages, and the live runs:

- a1. **A model-invocable skill, its description in the listing.** The default invocation control — no `disable-model-invocation`, no `user-invocable: false` — is "Description always in context, full skill loads when invoked". `description` is the field that decides invocation: "What the skill does and when to use it. Claude uses this to decide when to apply the skill … Put the key use case first: the combined `description` and `when_to_use` text is truncated at 1,536 characters in the skill listing". `when_to_use` is "Appended to `description` in the skill listing and counts toward the 1,536-character cap". The listing's budget "scales at 1% of the model's context window". When it overflows the platform "drops descriptions starting with the skills you invoke least"; `skillListingBudgetFraction` and `skillListingMaxDescChars` exist on the [settings reference](https://code.claude.com/docs/en/settings-reference) (default cap 1,536, example `2048`). Cost: the description's characters in every turn, the body's on invocation.
- a2. **The skill's body after invocation.** Content re-invoked unchanged gets "a short note that the skill is already loaded rather than a second copy". On compaction the platform "re-attaches the most recent invocation of each skill after the summary, keeping the first 5,000 tokens of each. Re-attached skills share a combined budget of 25,000 tokens" — a rule set stated in a few thousand characters survives a compaction whole. The page's own advice for a rule the model stops following: "Strengthen the skill's `description` and instructions so the model keeps preferring it, or use hooks to enforce behavior deterministically" — the second half is what [law 5 of CLAUDE.md](../../CLAUDE.md#law-5) forbids dressing a judgment rule as.
- a3. **A `SessionStart` hook printing the rules.** Plain stdout becomes context; matchers `startup`, `resume`, `clear`, `compact`, `fork`; capped at 10,000 characters. The page itself says "For static context that doesn't require a script, use CLAUDE.md instead", and "SessionStart runs on every session, so keep these hooks fast". Cost: the rules' characters in every session and after every compaction, whether or not a decision arises; [res-0004-const-referencing](res-0004-const-referencing.md) recommended one for a rule about every chat message, which nothing triggers — a decision has a trigger.
- a4. **A `CLAUDE.md` pointer, or the consumer's own copy.** `CLAUDE.md` files are read "at the start of every session"; user, project and `CLAUDE.local.md` scopes; `@path/to/import` imports; an `AGENTS.md` is read when no `CLAUDE.md` is present. A module ships at most one pointer line in `INSTALL.md` (step 4 of "Developing a module" in [CLAUDE.md](../../CLAUDE.md)). A consumer's own copy of the rules is what the kit does today. The six commits of 2026-09-14 and 2026-09-15 are that copy being corrected in place, which is the friction the module exists to absorb.
- a5. **Live, the skill alone (E1, E2, E4).** A plugin holding one skill and nothing else — description 364 characters, phrased by activity ("Use when a choice is the user's to make, when a request has more than one plausible reading, when about to ask the user anything, or when a decision surfaces mid-task"), body 2,450 characters carrying the threshold and the shape — on a two-file scratch repository, no `CLAUDE.md`, `--setting-sources project`. The decision prompt ("Decide where our decision records should live, docs/decisions or docs/adr, and whether they get numbered; I am the decider (Eugene).") in two headless runs and one interactive one: in all three the model's first tool call was `Skill` on `q-plugin:decide-with-the-user`, before listing the repository; every reply then held **one** decision (the directory; numbering announced as next), lettered options with a one-sentence description, indented **Pros:** and **Cons:** sub-bullets of one prose line each, one recommendation with reasoning, and the line "Decider: Eugene." Headless, where the platform offers no question tool (section 2), the reply ended "Reply with a letter" — the fallback of [requirement A6.9](../requirements.md#a6-9) reached for on its own.
- a6. **Live, below the threshold (E2).** The prompt "Add a short "Running locally" section to the README saying how to start the service." on the same repository: the model read the tree without invoking the skill, found no source, no manifest, no start command, and only then invoked the skill with the argument "Repo has no source code — cannot determine how to start the service; need the actual start command from the user"; its reply asked for the start command in plain words with no options — the skill's exemption for a factual clarification, at a genuine blocker, as [requirement A6.1](../requirements.md#a6-1) reads it. The description reached the model at the moment of asking, not before.
- a7. **Live, the control (E3).** The same decision prompt with no plugin: one message carrying both decisions (directory and numbering) and two more "worth settling in the same breath" (a status field, a deciders field); no lettered options, no pros and cons, the recommendation stated first and argued as "Why … over …"; "for your call" in place of a named decider. Four turns. The failure pattern of the specification, reproduced on demand.
- a8. **What no carrier reaches.** A model that decides without noticing a decision arose invokes nothing — E2 shows the skill reached only when the model itself judged something open. The listing cannot make a session see a choice it took for routine. That is the honestly ungateable half of [requirement A6.1](../requirements.md#a6-1), and the consumer's boundary examples (section 4) are the only lever.

Mechanism class: a1 and a2 are skill prose, judgment-shaping; a3 is a hook used as a carrier of prose; a4 is memory. Maturity: all four documented and stable across the six earlier surveys. Cost: a1 the cheapest that has a trigger.

**Recommendation: one skill, model-invocable and user-invocable (the default), its description phrased by the activities that precede a question — a choice that is the user's, a request with two readings, being about to ask — and its body carrying the threshold, the one-decision rule, the shape word for word, the derivation, enum-first and defaults-with-override rules, the restatement rule and the fallback; no `SessionStart` line, no `paths`, no `context: fork`, since the decision lives in the dialog that raised it; CONFIRMED as advisory for every row of this section.** The sizes stated in the module's document in characters ([law 8 of CLAUDE.md](../../CLAUDE.md#law-8)): the throwaway's 364 and 2,450 are the measured reference. For the decider: whether `INSTALL.md`'s one pointer line names the skill for consumers whose `CLAUDE.md` already carries a copy of the rules, as the kit's does.

## 2. The platform's question tool ([requirement A6.2](../requirements.md#a6-2), [requirement A6.9](../requirements.md#a6-9))

`AskUserQuestion`, from the [hooks](https://code.claude.com/docs/en/hooks), [tools reference](https://code.claude.com/docs/en/tools-reference), [headless](https://code.claude.com/docs/en/headless), [permissions](https://code.claude.com/docs/en/permissions) and [settings reference](https://code.claude.com/docs/en/settings-reference) pages, the two changelogs, and the runs:

- b1. **The documented input.** The hooks page, in its table of tool inputs: "Asks the user one to four multiple-choice questions." Field `questions`, an array — "Questions to present, each with a `question` string, short `header`, `options` array, and optional `multiSelect` flag" — with the example `[{"question": "Which framework?", "header": "Framework", "options": [{"label": "React"}], "multiSelect": false}]`; and `answers`, an object "Maps question text to the selected option label. Multi-select answers join labels with commas. Claude doesn't set this field; supply it via `updatedInput` to answer programmatically". No page read today states a limit on the number of options, a length limit on a label or a description, or that an option carries a `description` at all.
- b2. **The observed input (E4).** The interactive session's tool call, from its transcript on disk: `{"questions": [{"question": "Where should decision records live?", "header": "Directory", "multiSelect": false, "options": [{"label": "A — docs/decisions", "description": "Generic name, MADR v3 default layout."}, {"label": "B — docs/adr", "description": "Conventional ADR directory name."}]}]}` — an option carries a `description` beside its `label`, undocumented on the pages read; the model wrote the letter into the label and one clause into the description, as the skill asked. Whether a `description` is required, and what length the dialog truncates at, was not observed.
- b3. **How it renders and answers.** The tools reference: "Claude uses `AskUserQuestion` to ask you multiple-choice questions when it needs a decision or a clarification. Answer by picking an option, or type your own text through the `Other` row or the notes field." Free text is relayed "with neutral wording so Claude follows what you wrote, including a request to wait or explain first" (the changelog's 2.1.216 fix). Observed in E4: the dialog was answered through its clarify path, and the model received a tool result opening "The user doesn't want to proceed with this tool use. The tool use was rejected … The user wants to clarify these questions. … Start by asking them what they would like to clarify." followed by the question text and "(No answer provided)"; the model then asked what to clarify. The dialog's own rendering of the labels and descriptions was not legible in the terminal scrape and is not described here.
- b4. **Whether the argument before the call is shown.** In the interactive terminal of 2.1.251, the scrape taken while the dialog was open carried the argument's lines — "A — docs/decisions", "Pros: matches MADR's own default layout since v3", "Cons: less immediately recognisable", "B — docs/adr" — above the dialog (E4): in the CLI, on this version, the chat text written in the same turn as the tool call was on screen. The specification records the observation of 2026-09-15 by date and count ("two of three arguments lost"). The brief for this survey places it in the desktop app, which this survey did not run. Neither changelog carries an entry about text before a tool call in the desktop app. The one entry on the theme is 2.1.38, "Fixed text between tool uses disappearing when not using streaming" — a different surface. The rule of [requirement A6.9](../requirements.md#a6-9) is therefore neither confirmed nor contradicted by the documentation: it stands on the field observation, and the skill states it as a fallback the user triggers.
- b5. **Headless.** "In non-interactive mode with the `-p` flag, Claude Code offers `AskUserQuestion` and `ExitPlanMode` only when the run has a permission host to receive the prompt, such as an Agent SDK `canUseTool` callback." Observed: the `init` message of every `-p` run listed 27 tools and `AskUserQuestion` was not among them (E1–E3); the model never attempted the call and collected the pick by letter (a5). A hook can answer it: "Returning `permissionDecision: "allow"` together with `updatedInput` satisfies that requirement … For `AskUserQuestion`, echo back the original `questions` array and add an `answers` object" (the changelog: 2.1.85); a `-p` integration can `defer` the call and resume the session with the answer. Under `dontAsk`, "`AskUserQuestion` … are denied even when an allow rule matches"; `--permission-prompts none` "removes the tools that need an answer from a person, such as `AskUserQuestion`", a flag that "requires Claude Code v2.1.259 or later", above the local version.
- b6. **The wait.** `askUserQuestionTimeout`: "With the default, questions wait until you answer them", values `60s`, `5m`, `10m`, `never`, default `never`, "Requires Claude Code v2.1.200 or later"; the changelog at 2.1.200: "Changed `AskUserQuestion` dialogs to no longer auto-continue by default". On timeout the dialog "submits any options you'd already selected and tells Claude you may be away from your keyboard, so Claude proceeds on its own judgment and can re-ask later" — a decision left in a dialog can be made by nobody, which is the case for [requirement A6.7](../requirements.md#a6-7)'s named blocker.
- b7. **Skill interplay.** A skill's `disallowed-tools` example is "`AskUserQuestion` for a background loop". 2.1.69 fixed "interactive tools (e.g., `AskUserQuestion`) being silently auto-allowed when listed in a skill's allowed-tools, bypassing the permission prompt and running with empty answers". 2.1.147 fixed "auto mode suppressing `AskUserQuestion` when the user or a skill explicitly relies on it". A skill that names the tool is a documented pattern; it does not pre-approve it.

Mechanism class: a platform tool, its shape the platform's; maturity: present since before 2.0.55 (the earliest changelog entry read), still receiving fixes at 2.1.274. Cost: none to ship; the dialog's wait in every session that uses it.

**Recommendation: the tool follows the chat message when fewer than five options stand, carrying one question, a `header` naming the slot, and one option per letter whose `label` opens with the letter and whose `description` holds at most one clause — the observed shape of b2; the pros, cons and recommendation never inside it; five or more options, or a headless session, or a session where the user has reported an argument lost: the pick by letter in chat; CONFIRMED against the row.** For the decider (the draft's third marker): whether the letter-only fallback becomes the default from the first decision — the tool then never used — or stays the row as written, triggered by a reported loss; and whether that preference is per decider (section 4) rather than per session.

## 3. Structured elicitation elsewhere ([requirement A6.3](../requirements.md#a6-3), [requirement A6.4](../requirements.md#a6-4), [requirement A6.5](../requirements.md#a6-5))

How a standard and seven harnesses shape a question with options, each read and not run, against five points: one question at a time, options as a closed set, a default, a recommendation, a free-text escape.

- c1. **t2, MCP elicitation (2026-07-28).** Form mode "MUST … include" a `message` and a schema "limited to flat objects with primitive properties only"; enums single- or multi-select, with titles through `oneOf` of `{const, title}`; "All primitive types support optional default values … Clients that support defaults SHOULD pre-populate form fields with these values"; the response is a "three-action model", `accept`, `decline`, `cancel`. Several fields per request; no recommendation slot; free text only where the schema has a string field. The one candidate with a first-class default — the shape of [requirement A6.5](../requirements.md#a6-5).
- c2. **t3, Cline.** The SDK schema: `question`, "The single question to ask the user", and `options`, "Array of 2-5 user-selectable answer options for the single question", strings. One question, a closed set of two to five plain labels, no descriptions, no default, no recommendation; free text is the UI's. Its CLI lists `ask_followup_question` among `SAFE_AUTO_APPROVE_TOOL_NAMES`.
- c3. **t4, Roo Code.** `question` required and `follow_up`, "A list of 2-4 suggested answers"; "Limited to asking one specific question per tool use"; "Cannot force structured responses – users can still respond freely"; "Suggested answers must be complete, with no placeholders requiring user edits". One question, suggestions rather than a closed set, no default, no recommendation.
- c4. **t5, Codex CLI.** `request_user_input`: "Questions to show the user. Prefer 1 and do not exceed 3"; each with `id`, `header` ("12 or fewer chars"), `question` ("Single-sentence prompt"), and `options`, "Provide 2-3 mutually exclusive choices. Put the recommended option first and suffix its label with "(Recommended)". Do not include an "Other" option in this list; the client will add a free-form "Other" option automatically" — the handler sets `is_other` true on every question and refuses a question with no options. An option is `label` ("1-5 words") plus `description` ("One short sentence explaining impact/tradeoff if selected"). The tool is "unavailable in {mode} mode" outside the modes that allow it. The recommendation is a label convention; the trade-off is one sentence per option.
- c5. **t6, Gemini CLI.** `ask_user`: "1 to 4 questions", each `question`, `header` ("max 16 chars"), a `type` of `choice`, `text` or `yesno`, `options` of "2-4 selectable options" with `label` ("1-5 words") and `description` ("Brief explanation"), `multiSelect` (which "Automatically adds an "All the above" option"). Answers "indexed by question position". No default, no recommendation; free text is a question type.
- c6. **t8, OpenCode.** `question`: "When `custom` is enabled (default), a "Type your own answer" option is added automatically; don't include "Other" or catch-all options"; "If you recommend a specific option, make that the first option in the list and add "(Recommended)" at the end of the label"; "Answers are returned as arrays of labels". The same convention as t5.
- c7. **t9, Kiro; t10, Cursor.** Kiro's spec workflow is a document sequence — `requirements.md`, `design.md`, `tasks.md`, "All specs follow a three-phase workflow" — the open slots being the files' sections. No per-question shape is documented on the page read. Cursor's agent "Ask questions" feature: "Ask clarifying questions during a task. While waiting for your response, the agent continues reading files, making edits, or running commands" — a question that does not block; its plan mode "asks clarifying questions to understand your requirements". No option shape is documented on the pages read.
- c8. **Convergence.** Every harness offers a free-text escape and most add it themselves (t5, t6, t8). Options are `label` plus one-sentence `description` in the three newest tools (t5, t6, t8) and plain strings in the two older (t3, t4). One question is preferred or enforced everywhere except t2 and t6. A recommendation exists only as a label convention, "(Recommended)" first (t5, t8); a default exists only in t2. ## 5. The open-question-marker scan ([requirement A6.7](../requirements.md#a6-7), the optional gate-lite)

What tools flag markers in text, which vocabulary to scan for, whether the check runs at write time or as a scan, and what territory it reads; the kit's own tree measured in E5.

- e1. **The tools.** t12 ships no `TODO` hook. t13 parses "TODOs and FIXMEs from comments" — "Must be in a comment (line or block) in its own line", "Supported default types are `TODO` and `FIXME` - case-insensitive", extra tags by option — a reporter, never a gate. t14 scans `NOTE, OPTIMIZE, TODO, HACK, XXX, FIXME, and BUG comments` line by line, unmaintained. t15 raises "a `TodoOrDie::OverdueError` whenever a `TODO` is overdue", a marker with a `by:` date or an `if:` condition, at load time in Ruby code. t16 allows "Only `TODO`s with valid, open issues" — a `TODO` with a closed issue or none is an error, "Malformed todo" — the one gate among them, tied to an issue tracker. t17 custom rules are "a name (or multiple names), a description … and a function" over the parsed Markdown, reported through `onError`. t18's `existence` check "looks for the "existence" of particular tokens" in prose with a `level` of `warning` or `error`. t19's `git diff --check` warns "if changes introduce conflict markers or whitespace errors". A leftover `<<<<<<< HEAD` is caught, a `TODO` is not (E6: exit 2 with a conflict marker, exit 0 with a `TODO` line alone). Every code tool scans comments. The two prose tools (t17, t18) need a rule written; none knows a decider or a stakes level, and only t16 blocks.
- e2. **The vocabulary, measured (E5).** On the kit's 94 Markdown files at `3384631`: `[decide:` 8 lines — the three real markers in the draft module's document, and five mentions of the syntax itself (the template's own definition in [module-template/MODULE.md](../../module-template/MODULE.md), rule 4 of [plc-0006-module-documents](../policies/plc-0006-module-documents.md), [dec-0003-module-spec-kind](../decisions/dec-0003-module-spec-kind.md), [dec-0009-module-routine-validation-and-inputs](../decisions/dec-0009-module-routine-validation-and-inputs.md), and the draft's own row for [requirement A6.3](../requirements.md#a6-3)); `TODO`, `TBD`, `FIXME`, `XXX`, `HACK`, `[open]`: 0; `???`: 1, a glob `pep-????.rst` quoted in [res-0003-const-catalogs](res-0003-const-catalogs.md); "open question": 5, all prose describing the rule; the prose deferrals tried ("to be decided", "decide later", "pending decision"): 0. A literal marker set on this tree yields five false positives and one out of nine hits. The false positives are the documents that *define* the marker — the full-shape pattern (`[decide: … — default … — stakes … — decider …]`) still matches the template's own placeholder line. One real marker (the second, on the dial's shape) holds a `]` inside its brackets. A pattern that ends at the first `]` cuts it short: the marker's own grammar is not regular.
- e3. **What a scan cannot see.** A deferred question written as prose — "we can settle the numbering later", a heading with nothing under it, a decider named nowhere — carries no marker. E5's zero for every prose phrase says nothing about tomorrow's phrasing. [Requirement A6.7](../requirements.md#a6-7)'s rule is about resolved decisions and a named blocker, which no token proves. A marker scan proves that nobody left a marker, and that is all its message may claim ([law 5 of CLAUDE.md](../../CLAUDE.md#law-5)).
- e4. **Write time or scan.** The shared code gives every module a `PreToolUse` hook on `Write|Edit` plus `--scan` ([kit-shared-gate-code §2](../../shared/GATE.md#g2)). A write-time block on a marker blocks the kit's own routine: the draft module's document was written *with* three markers at `3384631`, as [plc-0006-module-documents](../policies/plc-0006-module-documents.md) rule 4 asks of a `0.0.x` module, and the authoring session derives its questions from them. Exempting drafts means reading the manifest beside the document — a rule of the kit's module documents, portable to no consumer ([kernel §6](../constitution/CONVENTIONS.md#k6)). The moment the rule speaks of is delivery, not the keystroke: a scan on demand and in CI, over a territory the consumer names, is the only shape that fits both the draft and the deliverable — and [`const-task-close`](../requirements.md#const-task-close)'s range check is where a consumer would run it, as an enhancement never a dependency.
- e5. **Territory.** A territory dial of the module's own — the pattern of `const-referencing.territories`, gitignore syntax, negated patterns taking files out — with the consumer excluding its templates, its draft documents and the documents that define its markers; on the kit, three negations for `templates/**`, `module-template/**` and `modules/*/MODULE.md`, plus the two records and the policy of e2, would leave zero hits today — a scan that is green by construction until a marker escapes into a document nobody exempted.
- e6. **The friction test.** No consumer has hit a marker in a delivered document: the kit's zero counts are the measurement, and "growth is friction-earned" ([CLAUDE.md](../../CLAUDE.md), "Never in this repository"). The failure the row names in the field — questions deferred into delivered plans — was prose, not markers, in the specification's own wording.

Mechanism class: a deterministic scan, gate-lite; maturity: trivial to build on the shared code; cost: a module document that must state, beside the check, that prose deferrals are invisible — and a territory that exempts more than it covers.

**Recommendation: the rule stays advisory in the skill — resolved decisions only, an absent decider a named blocker with the name — CONFIRMED; the optional scan is not shipped at this version: its shape is recorded here (a `--scan`-only check over an own `territories` dial with a `markers` list defaulting to `[decide:`, `TODO`, `TBD`, `FIXME`, reporting file and line and claiming no more than "no marker left"), and its signal is a consumer's commit note about a marker that landed in a delivered document.** For the decider (the draft's first marker): ship now with the shape above, or record and wait; if now, the marker set — the four above, with or without `???` and `[open]` — and whether the territory's exemptions are the consumer's negated patterns or a second dial.
