## 1. The grant of the create command ([requirement A2.4](../requirements.md#a2-4))

The skill tells the model to run the command. In a session that can ask, an ungranted command costs one prompt. In a session that cannot ask — `claude -p` in Manual mode or `acceptEdits`, `dontAsk` — it is denied, and the model then writes the document by hand or stops (E1, E9). What the platform says, and what the runs showed:

- a1. **The page's promise.** The [skills](https://code.claude.com/docs/en/skills) page says `allowed-tools` "grants permission for the listed tools during the turn that invokes the skill". In a plugin skill, `${CLAUDE_PLUGIN_ROOT}` is substituted in the skill's content and in Bash rules of `allowed-tools`: "Using the same variable in both places lets a skill run a bundled script without a permission prompt." The page names no difference between a load the user types and a load the model makes.
- a2. **A typed load gets the grant.** `/exp:v1` and `/exp:v2` ran their scripts with no rule (E6), and so did the module's `/const-locations:new-document notes nightly-backups` (E9, E16). The rule form is sound: the variable is expanded, and both `sh <root>/… *` and `<root>/… *` match.
- a3. **A model load approved at a prompt gets the grant.** In the interactive interface, default mode, the model's `Skill` call raised the prompt "Use skill …?"; after its first option, "Yes", the command ran with no second prompt (E16).
- a4. **A model load approved by a rule loses the grant.** With `Skill(<name>)` allowed by `--allowedTools`, the skill loaded and its command was denied, "This command requires approval" (E2). The same held for a rule with the literal path and for `Bash(sh *)` (E3), and for a project skill outside any plugin (E4). It held for the module as shipped (E9), in the interactive interface (E16), and in the live proof on the first consumer project (E1). The same command ran under the same rule given on the command line (E5). The skill prompt's second option, "Yes, and don't ask again", names a rule for the skill (E16): by a4, a later load approved by that saved rule would lose the grant. This is inferred and was not run.
- a5. **A changelog entry newer than the pin.** Release 2.1.295 of 2026-10-08 says: "Fixed a skill's `allowed-tools` and `effort` being dropped when the Skill tool finished before the response stream ended, which denied the skill's Bash commands in `-p` runs". A load approved by a rule finishes at once; a load approved at a prompt waits for the person. That fits a3 and a4, but it was not tested: no release from 2.1.295 on was run.
- a6. **The field makes the load itself need approval.** With no rule, the skill `v0`, which has no `allowed-tools`, loaded ("Launching skill"), and `v4`, which has one, was denied ("Execute skill") (E7). The module as shipped, with no rule, had its `Skill` call denied, and the model then wrote the note by hand with `Write` (E9). The variants without the field loaded with no rule (E10, E11, E14), and so did the hook variant in the interactive interface, with no skill prompt (E16).
- a7. **Managed settings withhold the field.** Under an organization's `allowManagedPermissionRulesOnly`, the skills page says Claude Code ignores `allowed-tools` in project and personal skills. The changelog of 2.1.284 extends this to plugins from marketplaces, claude.ai and npm: "only plugins from an official Anthropic source or a source that managed settings vouch for keep that pre-approval". Read, not run.
- a8. **Auto mode asks nothing.** In auto mode the model loaded the skill and ran the command with no prompt at all (E16). The screen does not show which mechanism allowed the command.

The candidates:

- a9. **Candidate (i): the skill's own `allowed-tools`, as shipped.** Class: a platform field. Maturity: documented. On 2.1.282 it holds for a typed load and for a load approved at a prompt (a2, a3). It fails for a load approved by a rule (a4), the only form a session that cannot ask has. Cost: the field itself makes the load need a rule (a6). So a consumer whose session cannot ask writes a `Skill` rule per skill and a `Bash` rule for the command: the rules of step 3 of the [install note](../../modules/const-locations/plugin/INSTALL.md). Should a5 cure a4, the `Skill` rules would still be owed, and managed settings can withhold the grant (a7).
- a10. **Candidate (ii): consumer allow rules on the install path.** `Bash(sh <root>/scripts/new-document.sh *)` with the skill rules created the note (E9). The [plugin components](https://code.claude.com/docs/en/plugins/components) page says each version has its own cache directory, "so the path changes when the plugin updates". With the plugin moved from a `0.0.1` folder to a `0.0.2` folder under the same rule, the command was denied (E9, E10). A rule with `*` in place of the varying folders, `Bash(sh */const-locations/*/scripts/new-document.sh *)`, survived the move (E10). It also ran a planted script at `vendor/const-locations/x/scripts/new-document.sh` of the repository, which created its marker file (E10). The [permissions](https://code.claude.com/docs/en/permissions) page says a `*` "matches any text, including spaces", so the wildcard grants any file of that name at any depth. Class: consumer configuration. Maturity: documented. Cost: a rule rewritten at every published version, or a wildcard that grants a planted script.
- a11. **Candidate (iii): a plugin `bin/` command and one path-free rule.** The components page says the files of `bin/` are on the `PATH` of the Bash tool's shell while the plugin is enabled. A program `bin/const-new-document` that runs the script, with no `allowed-tools`, under `Bash(const-new-document *)`, created the note, and kept working after the version move (E11). Without the rule it was denied, and the typed form needs the rule too (E11). The page says plugin `bin/` folders "come after the user's own `PATH` entries"; a program of the same name earlier on `PATH` ran in its place under the same rule (E11). Under `claude plugin eval`, the bare name did not resolve in any of six runs (E13). The model then called the program by its full path or put the folder on `PATH` itself: forms the consumer's rule would not match. Plain `-p` and sandboxed `-p` in the same image put the folder on `PATH`, and so did macOS sandbox mode (E12). The page also says claude.ai and Cowork "don't install a plugin that has a top-level `bin/` directory". Class: a platform component and consumer configuration. Maturity: documented; observed. Cost: still one consumer rule; a name another program can take; evals that cannot see the command by name.
- a12. **Candidate (iv): a `PreToolUse` hook that answers `allow` for exactly the plugin's own command.** The [hooks](https://code.claude.com/docs/en/hooks) page says `"allow"` "skips the permission prompt", with named exceptions. A prototype hook answered `allow` when the command was `sh <root>/scripts/new-document.sh` followed only by arguments written plain or in single quotes, and said nothing otherwise; the skills had no `allowed-tools`. With no rule, the model's load and its command created the note, in `-p` and in the interactive interface; the typed form did too (E14, E16). Class: deterministic hook code that the plugin ships. Maturity: the decision field is documented; the behaviour was run. Cost: one hook entry, one process for each Bash call the handler's filter lets through, and a grammar that must stay strict (a13).
- a13. **An `allow` answer skips the split of a compound command.** The permissions page says a compound command runs without a prompt only when "every subcommand" is allowed. A prototype that allowed any command starting with the plugin's command allowed `…new-document.sh …; touch PWNED`, and the whole call ran (E14). `touch` is one the `acceptEdits` mode approves anyway, by the [headless](https://code.claude.com/docs/en/headless) page. So the run was repeated with a tail that needs approval on its own, `python3 -c "open('PWNED','w').close()"`: the hook's `allow` ran both parts (E15). The strict prototype stayed silent on the compound form, and the platform then asked for its first part (E14, E15). Neither the hooks page nor the permissions page says that an `allow` covers every part of a compound call. Read with E15, a loose match grants whatever follows a separator.
- a14. **The consumer keeps the last word.** The permissions page says "Claude Code evaluates deny and ask rules regardless of what a PreToolUse hook returns". A `--disallowedTools "Bash(sh *)"` rule denied the command the hook allowed (E14). In plan mode, the same page says a hook's `"allow"` "has no effect on a file edit or another call that isn't read-only". Under `allowManagedHooksOnly`, the hooks page says plugin hooks are blocked, except those of plugins force-enabled in managed settings. In both cases the command falls back to the platform's own flow.
- a15. **The `if` field narrows the spawn, not the grant.** Read, not run. The hooks page gives each handler an optional `if` in permission-rule syntax, evaluated on tool events alone. For Bash it checks "each subcommand", and it is "best-effort": "When Claude Code can't determine which commands the Bash input runs, it runs your hook regardless of the pattern." The page does not say that `${CLAUDE_PLUGIN_ROOT}` is substituted in `if`. So `"if": "Bash(sh *)"` can spare a process on most Bash calls, and the hook must still check the whole command itself.
- a16. **Candidate (v): a `PermissionRequest` hook.** Read, not run. The headless page names it as one way to approve a call in a Manual-mode `-p` run, and the hooks page lists the event "When a tool call needs a permission decision". It would fire only where the platform was about to ask, so it would not spawn on calls that need no approval. No run tested how it meets a skill's load, a compound command or auto mode, so it is not weighed beside (iv).
- a17. **Cost of the prototype.** The strict prototype took 56 ms at the median and 93 ms at most over twenty spawns, and importing the shared modules a hook entry would load took 47 ms at the median (E17). Its pattern stayed silent on six near-miss forms: double quotes, `$( )`, a redirection, a second line, a quoted path, a longer file name (E17).
- a18. **`claude plugin eval` grants only its own tools; a hook's `allow` does not approve a call there.** In the eval of the module as built on R1 of [dec-0110-new-document-command-granted-by-a-hook](../decisions/dec-0110-new-document-command-granted-by-a-hook.md) ran the create command, and the hook answered `allow`. The call was still refused for the session's mode, `dontAsk`, in every run (E18). Outside the eval, `-p` in `dontAsk` with no rule ran the same command under the same answer (E18). The [plugin evals](https://code.claude.com/docs/en/plugin-evals) page says "Runs never stop to ask for permission", and that a case's `allowed_tools` and a skill's own `allowed-tools` "can't widen" the grants of the run. It has no sentence on a `PreToolUse` hook's answer in a run. So on 2.1.282 the kit's eval cannot prove the grant; a `-p` run outside it can.

Mechanism class: (i) is a platform field, (ii) and (iii) are consumer rules, (iii) with a platform component, (iv) and (v) are plugin hooks. Maturity: (i), (ii), (iii) and (iv) were run; (v) was read only. Cost: (iv) is the only candidate that needs no consumer rule and survives a version change (E14, E11, E9).

**Recommendation: candidate (iv), the `PreToolUse` hook that answers `allow` for the plugin's own command and nothing else, with `allowed-tools` dropped from both skills; OVERTURNED against the skill's own grant as shipped.** The hook needs no consumer rule in any session that runs plugin hooks, survives every version change, and leaves the consumer's deny and ask rules in force (a12, a14). Dropping the field lets the model load the skill with no rule (a6). The strict grammar is the safety of the design: by a13, nothing short of an exact match may be answered. The row's enforcement is unchanged: [requirement A2.4](../requirements.md#a2-4) stays advisory, since the grant changes how the command is reached and judges nothing; how [law 5 of CLAUDE.md](../../CLAUDE.md#law-5) classes such a hook is ruled in [dec-0110-new-document-command-granted-by-a-hook](../decisions/dec-0110-new-document-command-granted-by-a-hook.md). The decider chose (iv) in chat on 2026-11-02, as that record says. Left open: a run on a release from 2.1.295 on would show whether a5 cures a4; either way (i) keeps its `Skill` rules and (iv) needs none, so the choice does not rest on it.

## 2. Fit with the shared gate code

Described, not decided; part names as in [kit-shared-gate-code §1](../../shared/GATE.md#g1). The hook is a second entry point of the module beside the generator, in hook mode.

- f1. **The guard.** `cli.guarded` in [`cli.py`](../../shared/constitution_layer_kit/cli.py) takes an identity, a mode and a body, and is the one place a failure's exit code is decided: 1, with a closing line the entry gives. A hook entry calls it with `Mode.HOOK`, as a session-start printer does, and its own closing line, which says nothing was granted. The hooks page says an exit code other than 0 or 2 is an error "even if it printed JSON that allows the action". So every failure of the hook grants nothing, and the platform's own flow decides the call: the failure is safe by construction.
- f2. **The event.** `read_event` in [`events.py`](../../shared/constitution_layer_kit/events.py) reads `tool_input.command` when the tool is `SHELL`, `"Bash"` in [`model.py`](../../shared/constitution_layer_kit/model.py), and refuses an event without it. `ToolEvent` carries `event_name`, `tool_name`, `session_id` and `command`: all the hook reads. No widening is needed.
- f3. **A strain: the shared input text names a scan.** `c12_input` in [`messages.py`](../../shared/constitution_layer_kit/messages.py) closes its fix with "to check a repository by hand run it with --scan [<dir>]". A hook with no scan must replace that fix with its own, by building its own failure from the shared key and headline. That is module code, and it touches no shared file. A parameter in the shared text would serve a second such hook; one module does not earn it.
- f4. **The answer.** The shared pipeline writes one permission answer, `ask`, for module [`const-interaction`](../requirements.md#const-interaction), through `report_hook` with `ask=True` in [`pipeline.py`](../../shared/constitution_layer_kit/pipeline.py). No shared function writes `allow`. The hook prints its one JSON object through the shared `Output.out`, which also logs it. Whether an `allow` answer belongs in the shared pipeline is a question for [rule 2 of plc-0009-shared-code](../policies/plc-0009-shared-code.md#r2); with one module, nothing asks for it.
- f5. **The log.** `Output` in [`output.py`](../../shared/constitution_layer_kit/output.py) writes one JSON line per print to the plugin's data directory, which the platform gives every plugin hook. A hook that prints nothing on a call that is no match leaves no line for it, so the log holds the grants and the failures alone.
- f6. **The preflight and the identity.** `cli.guarded` runs no preflight; `preflight.check` imports the declared libraries, PyYAML among them. The hook reads no YAML, so it may run the preflight on a match alone; a missing library then fails that one call with exit 1, which grants nothing (f1), and the command would fail the same way. The `Identity` fields `dials_file` and `kernel_keys` have no default, so the hook names them although it reads no dials file, as the generator does. A missing or wrong shared release stops the entry with `C15`, `C16` or `C17`, exit 1, which again grants nothing.
- f7. **The deadline.** In hook mode the guard opens the run's deadline, `hook_seconds` of the identity. The hook makes no git call and waits on nothing, so the deadline is never spent by its own work.

No change to `shared/constitution_layer_kit` is needed (f2, f4); the one strain is the text of f3, met in the module.

## 3. Platform facts, re-verified, and discrepancies

Read again on the survey date:

- p1. **`allowed-tools` and the path variable.** The field grants "during the turn that invokes the skill"; `${CLAUDE_PLUGIN_ROOT}` is substituted in a plugin skill's content and in Bash rules of the field (skills; a1). Breaks: the typed form's grant, should the field stay in a skill.
- p2. **Skill rules.** "`Skill(name)` for exact match, `Skill(name *)` for prefix match with any arguments"; an allow rule is matched "only against the skill's own name and the name in Claude's invocation" (skills). Breaks: the `Skill` rules of the install note's step 3.
- p3. **Bash rule matching.** A `*` "matches any text, including spaces"; the words before the first `*` are matched as written; the separators are `&&`, `||`, `;`, `|`, `|&`, `&` and newlines, and every subcommand must be allowed (permissions; a10, a13). Breaks: the reading of (ii)'s wildcard and of the hook's silence on a compound command.
- p4. **The `PreToolUse` decision.** `permissionDecision` is `allow`, `deny`, `ask` or `defer`; `"allow"` "skips the permission prompt", except for actions no mode approves and reads from network paths; "precedence is `deny` > `defer` > `ask` > `allow`" (hooks; a12). Breaks: the grant itself.
- p5. **Rules over hooks.** Deny and ask rules apply "regardless of what a PreToolUse hook returns" (permissions; a14). Breaks: the consumer's way to refuse the command, which E14 relied on.
- p6. **Plan mode.** A hook's `"allow"` "has no effect on a file edit or another call that isn't read-only" there (permissions; a14). Breaks: nothing; in plan mode the command asks as it did before.
- p7. **A failed hook allows nothing.** An exit code other than 0 or 2 is an error "even if it printed JSON that allows the action" (hooks; f1). Breaks: the safety of every failure of the hook.
- p8. **The hook's environment.** Hooks receive `CLAUDE_PLUGIN_ROOT` in their environment, and the path placeholders are substituted in `command` and `args` (hooks, plugin components). Breaks: the root the hook compares the command with.
- p9. **The `if` field.** Permission-rule syntax, tool events only, each subcommand checked, best-effort (hooks; a15). Breaks: only how many calls spawn the hook.
- p10. **`bin/` on `PATH`.** On the Bash tool's `PATH` while the plugin is enabled, after the user's own entries; claude.ai and Cowork do not install a plugin with a top-level `bin/` (plugin components; a11). Breaks: candidate (iii) only.
- p11. **A version has its own folder.** "Each version has its own cache directory, so the path changes when the plugin updates" (plugin components; a10). Breaks: every consumer rule that names the install path.
- p12. **Managed limits.** `allowManagedPermissionRulesOnly` withholds `allowed-tools` from marketplace plugins (skills, changelog 2.1.284; a7); `allowManagedHooksOnly` blocks plugin hooks not force-enabled (hooks; a14). Breaks: in such an organization the command asks, whatever the plugin ships.
- p13. **Headless modes.** In a Manual-mode `-p` run, "a call that needs approval is denied unless something approves it"; `acceptEdits` approves "common filesystem commands such as `mkdir`, `touch`, `mv`, and `cp`" (headless; a13). Breaks: the reading of the experiments' denials, and why E15 repeated E14's tail.
- p14. **The grants of an eval run.** "Runs never stop to ask for permission"; tools beyond the read-only set run only when the run grants them with `--allow-tools`, and "A case's `allowed_tools` and a skill's own `allowed-tools` frontmatter can't widen any of them" ([plugin evals](https://code.claude.com/docs/en/plugin-evals)). The page says nothing on a hook's `allow`, which E18 found not honoured (a18). Breaks: whether the kit's eval cases can show the grant, should a later release honour the hook there.

Stale, imprecise or missing in [res-0005-const-locations](res-0005-const-locations.md), and in the module document, which took its facts from there:

- a. **Its p11 and E6 said the grant held for a human-typed load and not for the model's own.** On 2.1.282 the line runs elsewhere: a model load approved at a prompt keeps the grant, and a load approved by a rule loses it (a3, a4). Platform fact 7 and limit 10 of the module document carry the earlier reading. This changes a design: the grant (section 1).
- b. **Its p11 quoted the page as applying a project skill's `allowed-tools` "whenever you or Claude invoke the skill, including in a `-p` run".** The page today says instead that Claude Code applies it "even in a `-p` run in a folder you've never trusted", in a paragraph on workspace trust. No design changes from the wording alone.
- c. **Missing: the field makes the load itself need approval (a6).** It changes a design: the field is dropped.
- d. **Missing: the install note's `Bash` rule names the version folder** and so breaks at every published version (a10, p11). It changes a design: no consumer rule is asked for.
- e. **Missing: plugin `bin/` and the `if` field of a hook handler.** Neither was surveyed; section 1 weighs both. No design changes from them.
- f. **Newer than the pin: the changelog fix of 2.1.295 (a5).** Not tested. If it cures a4, finding a reads differently on later releases; the recommendation stands either way.
- g. **Its section 2 rejected a hook that only teaches as advisory content on a gate's channel.** A hook that answers `allow` neither teaches nor blocks; its class under [law 5 of CLAUDE.md](../../CLAUDE.md#law-5) is ruled in [dec-0110-new-document-command-granted-by-a-hook](../decisions/dec-0110-new-document-command-granted-by-a-hook.md), not here.

## Experiments

Each in a scratch directory outside any repository of the kit. Versions: Claude Code 2.1.282, git 2.56.0, Python 3.12.15, PyYAML 6.0.2, `constitution-layer-kit` 2.0.0, tmux 3.4, Docker 28.5.2, macOS 27.0.1 on arm64. Every headless run used `claude -p … --permission-mode acceptEdits --output-format stream-json --verbose`, the plugin by `--plugin-dir`, and was read from the stream's tool calls, tool results and `permission_denials`, and from the tree after the run. `<root>` stands for the plugin folder of the run. Runs on t3 used `--model sonnet` and a fresh `git init` folder. Runs on t2 used `--model claude-opus-5-5`, `--include-hook-events` and `--max-turns 20`. Their folder was seeded by the scaffold of the module's eval case `new-document`: a small inventory project whose `constitution.yaml` declares a root policy, a decision-records policy and a notes policy over `docs/notes/**`. Their task prompt, called Q below, was the eval case's own: add a note on the nightly backup of the stock database, with its facts. The typed form, called T, was `/const-locations:new-document notes nightly-backups`. A rule named "the skill rules" is `Skill(const-locations:new-document),Skill(const-locations:new-kind)`.

- E1. **The live proof that started this survey.** A clone of the first consumer project, its eleven modules loaded by `--plugin-dir`, `-p` with `acceptEdits` on `claude-opus-5-5`, Claude Code 2.1.282, asked to create one document per policy kind. ## Recommendations summary

All six serve [requirement A2.4](../requirements.md#a2-4).

1. [Requirement A2.4](../requirements.md#a2-4), its enforcement — **CONFIRMED**: advisory, as the matrix recommends; the grant changes how the command is reached and judges nothing.
2. [Requirement A2.4](../requirements.md#a2-4), the skill's own `allowed-tools` — **OVERTURNED**: on 2.1.282 it drops when a rule approves the load, the only load a session that cannot ask has (a4). The field itself makes the load need a rule (a6).
3. [Requirement A2.4](../requirements.md#a2-4), consumer allow rules on the install path — **OVERTURNED** as the install note's backstop: a path rule breaks at every published version, and a wildcard over it grants a planted script (a10).
4. [Requirement A2.4](../requirements.md#a2-4), a plugin `bin/` command — **not needed**: it still asks a consumer rule, a program earlier on `PATH` takes its name, and `claude plugin eval` does not see it (a11).
5. [Requirement A2.4](../requirements.md#a2-4), a `PreToolUse` hook that answers `allow` for exactly the plugin's own command — **build**: no consumer rule, every version, and the consumer's deny and ask rules kept (a12, a14). Its grammar stays strict, since an `allow` skips the platform's split (a13). It fits the shared code with no shared change (section 2). The kit's eval cannot show the grant on 2.1.282, since an eval run does not honour a hook's `allow` (a18); a `-p` run outside it does. Chosen in [dec-0110-new-document-command-granted-by-a-hook](../decisions/dec-0110-new-document-command-granted-by-a-hook.md).
6. [Requirement A2.4](../requirements.md#a2-4), a `PermissionRequest` hook — **not needed** at this version: read and not run, and (iv) closes the gap (a16).
