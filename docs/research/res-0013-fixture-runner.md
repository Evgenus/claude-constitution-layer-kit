## 1. The runner (what runs a module's items and gives the verdict)

The question: which program runs a module's items, reports each one, and gives `scripts/check-aspects.py --run` a result it can trust.

- a1. **The kit's runner before the branch.** At `fb30e75` each of the eleven modules had a `tests/run.py` that called `Harness.run_all` of the shared harness. An item was a function that returned a pair, a flag and an evidence text, or a red→green case. `run_all` sorted the items by number, refused a number held twice before any item ran (exit 1, `BROKEN:` lines), took one option, `--item <n>[,<n>…]`, and ran the items one after another in one process. It printed `[ok]` or `[FAIL]`, the number, the kind and the title for each item, the evidence on the next line, and a last line `N/T acceptance items green — …`; exit 0 green, 2 red. `scripts/check-aspects.py` read those lines by regular expressions (`ITEM_LINE`, `LAST_LINE` in its source). Source: `git show fb30e75:shared/tests/harness.py`, `git show fb30e75:modules/const-questions/tests/run.py`, `git show fb30e75:scripts/check-aspects.py`. E7 ran the runner of `const-questions`: 77/77 items green in 47 s; `--item 1,2` printed `2/2 selected items green — 2 of 77 items run, not a full pass`.
- a2. **The harness improved in place.** One candidate keeps the harness and adds a thread pool to `run_all`. It was not built and not run in this survey. What the tree shows about it: each red→green case already builds its own throwaway consumer repository (`Harness.fresh_consumer`, in both commits), and the gate runs as a child process, so threads would mostly wait on children. Two facts of the tree speak against threads in one process. First, `const-task-close` sets `GIT_DEFAULT_REF_FORMAT` in `os.environ` around one consumer's build and deletes it after (`modules/const-task-close/tests/test_task_close.py` at `5a4e01f`, the same lines in `run.py` at `fb30e75`). Threads share one environment, so a second thread's `git init` could read it. Second, at `fb30e75` `const-locations` kept a module-level set `COMPARED` that the other items filled and the last item read (`modules/const-locations/tests/run.py`, line 335). Any parallel run breaks such an order. That set is gone at `5a4e01f`. A thread pool would also leave the custom output format, its reader and its fixtures in place.
- a3. **pytest.** pytest collects test functions, runs them, and reports each with a node id (the file path and the function name, `tests/test_x.py::test_one`). Its exit codes are a public interface: 0 all passed, 1 some failed, 2 interrupted, 3 internal error, 4 usage error, 5 no tests collected, 6 too many warnings ([exit codes](https://docs.pytest.org/en/stable/reference/exit-codes.html)). It writes a JUnit XML report with `--junitxml` (section 3), selects tests by node id, `-k` or `-m` (E4b), and has a plugin interface that pytest-xdist and coverage tools use. Its assertion rewriting shows the values of a failing `assert` in a test module (E2d). At `5a4e01f` every module's fixtures are pytest tests: 1,174 tests collected over the eleven modules' folders, from 86 (`const-locations`) to 166 (`const-referencing`), each module's folder collected alone.
- a4. **unittest.** The standard library's runner needs no install. Its command-line options are `-b`, `-c`, `-f`, `-k`, `--locals`, `--durations`, `-v`, `-s`, `-p` and `-t`; the page names no option to run tests in parallel and no XML report. It says that shared fixtures "do not play well with [potential] features like test parallelization" ([unittest](https://docs.python.org/3.12/library/unittest.html), read). An XML report needs a package such as t6; parallel runs need another runner. pytest runs `unittest.TestCase` tests as they are ([unittest-based tests](https://docs.pytest.org/en/stable/how-to/unittest.html)), so unittest is no step away from pytest.
- a5. **nose2.** nose2 runs unittest tests and lists a multiprocess plugin, `mp`, and a `junitxml` plugin ([plugins](https://docs.nose2.io/en/latest/plugins.html), read). Its PyPI classifier is "Development Status :: 4 - Beta". It was not run.
- a6. **Speed of one module, serial.** E7 and E6 measured `const-questions` on the same machine: the old runner alone took 47 s; `check-aspects.py --run --module const-questions` at `5a4e01f`, serial, took 47 s, collection and the report reading included. pytest itself adds no visible cost; the time is the gates' child processes.

Mechanism class: a deterministic program run in CI, a gate entry. The custom harness: the kit's own, two output formats and a reader of its lines to keep. The thread pool: the same, plus thread-safety to prove. pytest: a mature, widely used runner with a documented exit-code interface; cost one pinned package (two with xdist) in CI and in the consumer's verify step. unittest: no install, no parallel runs, no report. nose2: beta, smaller.

**Recommendation: pytest, run one module's folder per run by `scripts/check-aspects.py --run`; OVERTURNED against the kit's custom harness and runners.** It gives a stable exit-code interface, a structured report, selection, and a parallel plugin. It takes away the custom output format and its reader. The cost is a dependency the consumer must install to verify a module, and the old `--item` flag goes (section 3 and the summary).

## 2. Parallel runs (how a module's items run side by side)

The question: how a module's items can run at the same time without one item changing another's result, and what a failure looks like when they do.

- b1. **None before the branch.** At `fb30e75` `run_all` ran items one by one (a1). CI ran the modules in parallel, one job per module, as it still does (`.github/workflows/gates.yml`); within a module nothing ran side by side.
- b2. **pytest-xdist.** `-n <number>` starts that many worker processes; `-n auto` starts "as many processes as your computer has physical CPU cores"; `-n 0` runs in the main process ([distribution](https://pytest-xdist.readthedocs.io/en/stable/distribution.html)). The modes of `--dist` are `load`, the default ("Sends pending tests to any worker that is available, without any guaranteed order"), `loadscope` (by module or class), `loadfile` (by file), `loadgroup` (by the `xdist_group` mark), `worksteal`, and `no`. The kit uses the default.
- b3. **Collection in each worker.** The controller "spawns one or more workers". Each worker performs "a full test collection", and the controller checks that all workers "collected the same tests" ([how it works](https://github.com/pytest-dev/pytest-xdist/blob/v3.8.0/docs/how-it-works.rst)). Tests may not "differ in order or their amount across workers" ([known limitations](https://github.com/pytest-dev/pytest-xdist/blob/v3.8.0/docs/known-limitations.rst)). A session-scoped fixture runs once per worker ([how-to](https://github.com/pytest-dev/pytest-xdist/blob/v3.8.0/docs/how-to.rst)). E4 confirmed it: with `-n 2` the conftest's `pytest_configure` ran three times, in the controller and in workers `gw0` and `gw1`, each in its own process. The kit's session fixture `subject` returns a module constant, so running it per worker costs nothing.
- b4. **A collection stop under xdist.** A conftest that raises `pytest.UsageError` from `pytest_collection_modifyitems` stops a serial run with exit 4 and prints the error's text as an `ERROR:` line; so does `--collect-only` (E4). With `-n 2` the same conftest gave exit 3, 35 `INTERNALERROR>` lines ending in an assertion of xdist's `dsession.py` (`assert not crashitem`), and not one line of the error's own text, three times out of three; `-n auto` also gave exit 3 (E4). The xdist pages read say nothing of this case. So a stop that must teach its fix cannot rely on a parallel run to show it.
- b5. **The kit's answer to b4.** `run_runner` of `scripts/check-aspects.py` at `5a4e01f` first runs `python3 -m pytest modules/<m>/tests -p no:cacheprovider -W error -q --collect-only` serially and reads its exit; only then does it run the tests, adding `-n <value>` when the environment's `CONSTITUTION_KIT_JOBS` names one. The serial collection of `const-questions` took 1 s (E6). The workflow at `5a4e01f` sets no `CONSTITUTION_KIT_JOBS`, so CI still runs each module's tests in one process.
- b6. **What makes items safe side by side.** Each worker is a process of its own. Process-wide state — the environment (a2), the gate identity that `identity.declare` sets once per test file, module-level sets — is never shared between two running items. What stays shared is the file system: each case builds its own consumer under a fresh temporary folder (`Harness.scratch_dir`, `tempfile.mkdtemp` under a per-process folder), so two workers never write one path. An item that reads what other items left behind fails under `load`, which promises no order; the `COMPARED` set of a2 was such an item at `fb30e75`.
- b7. **Speed.** E6 measured `const-questions` through `check-aspects.py --run` at `5a4e01f`: serial 47 s, `CONSTITUTION_KIT_JOBS=4` 18 s, `CONSTITUTION_KIT_JOBS=auto` (14 workers here) 13 s, every run green.
- b8. **The worker count of `-n auto`.** The page says physical cores. The code of `auto_detect_cpus` in `src/xdist/plugin.py` at v3.8.0 uses `psutil.cpu_count(logical=False)` only when psutil is installed. Without it, it counts `len(os.sched_getaffinity(0))` where Python has that call (Linux), and `os.cpu_count()` otherwise. Without psutil, then, `auto` counts logical CPUs. `PYTEST_XDIST_AUTO_NUM_WORKERS` overrides it. On the survey machine both counts are 14, and E4 printed `created: 14/14 workers`.

Mechanism class: process-level parallelism through a pytest plugin, deterministic in its results when the items are independent. Maturity: xdist is a pytest-dev project, its last release fifteen months before the survey. Cost: one pinned package, the independence of every item to keep, and the collection run before (b5). The thread pool of a2: not built; its cost is a proof of thread-safety the processes do not need.

**Recommendation: pytest-xdist with the default `--dist load`, asked for by `CONSTITUTION_KIT_JOBS`, after a serial collection; build, since the kit had no parallel run within a module.** Processes isolate the process-wide state that threads would share (a2, b6), and the serial collection keeps the stop's teaching text (b4). For the decider: whether CI sets `CONSTITUTION_KIT_JOBS`, and to what; the decider chose in chat on 2026-10-14 that CI sets it to `auto` once the shuffled runs are green for every module. The decider reversed that in chat on 2026-10-16, after an audit of the branch found items with time limits failing on a loaded machine: CI sets none, and runs each module's tests one by one. The per-module jobs already run side by side, and the CI machine's CPU count was not measured here.

## 3. Numbering and reporting an item (how an item's number reaches the verdict)

The question: how each test carries its fixed item number, and how `scripts/check-aspects.py` reads each number's result.

- c1. **Before the branch.** The number was a field of the item, printed on its `[ok]`/`[FAIL]` line. The reader matched the line's form, counted the lines, and compared the count with the last line (a1).
- c2. **A marker carries the number.** At `5a4e01f` `acceptance.item(number, title)` returns `pytest.mark.item(number, title)`; `acceptance.configure` registers the marker in `pytest_configure`. An unregistered marker gives `PytestUnknownMarkWarning`, which `-W error` makes a collection error, exit 2 (E2a).
- c3. **The one-number rule at collection.** `acceptance.collected`, called from each conftest's `pytest_collection_modifyitems`, adds a line for each test without an `item(…)` marker and for each number two tests carry. Then it raises `pytest.UsageError` with all the lines, before any test runs. Serially that is exit 4 with the lines on the terminal (E4); [GATE.md §3](../../shared/GATE.md#g3) states the lines.
- c4. **The number in the JUnit report.** The same hook appends `("item", "<number>")` to each test's `user_properties`. The JUnit writer emits every entry of `user_properties` as a `<property>` of the test's `<testcase>`, whatever the report's family (`src/_pytest/junitxml.py` at 9.1.1, the loop over `report.user_properties`). pytest's own page shows this pattern: a conftest that reads a marker in `pytest_collection_modifyitems` and appends to `item.user_properties` ([output](https://docs.pytest.org/en/stable/how-to/output.html), section `record_property`). E3 confirmed it under `-W error`: every testcase held its `<property name="item" value="…"/>`, with no warning. Under `-n 2` the one report held all four tests, each with its property once (E4).
- c5. **`record_property` against it.** The fixture `record_property` also appends to `user_properties`, but it calls `_warn_incompatibility_with_xunit2`, which warns "record_property is incompatible with junit_family 'xunit2' (use 'legacy' or 'xunit1')" whenever a JUnit report is written and the family is not `xunit1` or `legacy` (source). The default `junit_family` is `xunit2` since pytest 6.1 ([reference](https://docs.pytest.org/en/stable/reference/reference.html), `junit_family`). E3: the default run passed with that warning; under `-W error` the test failed, exit 1; with `-o junit_family=legacy` it passed. The page says only that the feature "will break schema verifications for the latest JUnitXML schema". A property added at collection avoids the fixture, and so the warning; the same schema remark applies to the `<properties>` it writes.
- c6. **A skipped test in the report.** A test that calls `pytest.skip(…)` and a test marked `skipif` both become `<skipped type="pytest.skip" message="…">`, the message the reason, the text `<file>:<line>: <reason>`; the testcase keeps its `<properties>` (E3). The line is the call's for `pytest.skip()` and the test's definition for `skipif` (E3: lines 9 and 11 of the file). The suite's `skipped` attribute counts them. At `5a4e01f` a shared item the module's subject leaves out calls `pytest.skip(f"not this gate's: {reason}")` (`shared/tests/test_shared_items.py`).
- c7. **The reader.** `read_report` of `scripts/check-aspects.py` at `5a4e01f` parses the report, takes the one `item` property of each testcase, leaves a skipped one out, counts a `failure` or `error` child as red, and is BROKEN when a testcase has no number or two, when a number repeats, or when the counts disagree with the suite's `tests` and `skipped` attributes. It also holds pytest's exit (0 or 1) against the report.
- c8. **Parsing pytest's terminal output.** The terminal lines carry the node id and the outcome, not the marker (E4b; `-q` prints dots, `-v` one line per test). A reader of them would need a second map from node id to number, built from the source or a collection. It would depend on the verbosity chosen. pytest's documentation offers the report as the machine-readable output and names no stable terminal format in the pages read.
- c9. **Selecting one item.** `-m "item(number=1)"` selected nothing, exit 5, since `-m` matches a marker's keyword arguments and the kit's marker takes positional ones ([markers](https://docs.pytest.org/en/stable/example/markers.html); E4b). A node id or `-k` on the test's name selects one test (E4b). At `5a4e01f` `scripts/check-gate-lists.py` holds that no line of the gate list or the workflow selects some tests only, the old `--item` included.

Mechanism class: a marker and a collection hook, deterministic; the report is pytest's documented XML. Maturity: `user_properties` and the JUnit writer are part of pytest's public interface; the marker-to-property pattern is pytest's own example. Cost: the kit's reader of the XML and its consistency checks; nothing new to install.

**Recommendation: the number as an `item(<number>, <title>)` marker, checked and copied to `user_properties` at collection, read from the JUnit report; OVERTURNED against the printed lines of the old runner.** The report is structured and holds a skip as a skip; the collection hook warns nothing under the default family, where `record_property` does (c5).

## 4. Wiring the shared code into each module's folder (how the tests reach the shared files)

The question: how the one source of the shared test files, under `shared/tests/`, reaches each module's `tests/` folder and is loaded there by pytest.

- d1. **Links, before and after.** At both commits each module's `tests/` holds relative symbolic links to the shared files and to its own packages; `scripts/check-shared-links.py` derives the links it wants from the folders ([GATE.md item 7 of §2](../../shared/GATE.md#g2)). At `fb30e75` Python put the folder of `run.py` first on the import path as it does for a script; at `5a4e01f` pytest does it.
- d2. **Import modes.** `prepend`, the default: "The directory path containing each module will be inserted into the *beginning* of `sys.path` if not already there". `importlib`: "pytest will not change `sys.path` at all", and among its drawbacks "Test modules can't import each other" and test utility modules "are not importable" ([pythonpath](https://docs.pytest.org/en/stable/explanation/pythonpath.html)). The page says the default "will remain `prepend` for the foreseeable future". `python -m pytest` also adds the current directory to `sys.path` (same page). E1: a linked `helper.py`, imported by plain name from a test and from a linked test file, passed under `prepend` and gave `ModuleNotFoundError: No module named 'helper'` at collection under `--import-mode=importlib`, exit 2.
- d3. **Links in collection.** Since 6.0.0rc1 "symlinks are no longer resolved during collection and matching `conftest.py` files with test file paths" (#5965). 6.2.0 fixed "symlinked directories not being followed during collection" (#7981). 7.1.0 stopped resolving link components in conftest paths (#9493) ([changelog](https://docs.pytest.org/en/stable/changelog.html)). E1: a linked test file kept the link's path in its node id, in the JUnit `classname` (`mod.tests.test_common`) and in `__file__`.
- d4. **One module's folder per run.** E1b ran two folders that link the same shared test file in one run. Both passed, and the second folder's test printed the first folder's `__file__`: under `prepend` the second link imports by the same name, and pytest's mismatch check compares the files with `os.path.samefile` (`_is_same` in `src/_pytest/pathlib.py` at 9.1.1), so it reuses the first module object without a word. The kit's shared items also repeat their numbers in every module. `acceptance.py` at `5a4e01f` states the rule: one module's folder is one run; `check-aspects.py` runs one module per run.
- d5. **`pytest_plugins` in a conftest below the root.** The plugin page calls it deprecated and says it "will raise a warning"; the deprecations page lists it as removed in 4.0 ([writing plugins](https://docs.pytest.org/en/stable/how-to/writing_plugins.html), [deprecations](https://docs.pytest.org/en/stable/deprecations.html)). The source fails only for a conftest loaded after pytest has configured (`_check_non_top_pytest_plugins`). E2b and E2e: `pytest mod/tests` with `pytest_plugins = ["acceptance"]` in `mod/tests/conftest.py` passed, as did a run from inside `mod/tests`; a bare `pytest` from the folder above found the conftest during collection and stopped, "Defining 'pytest_plugins' in a non-top-level conftest is no longer supported", exit 2.
- d6. **The built-in plugin name `fixtures`.** `fixtures` is one of pytest's essential built-in plugins, and `import_plugin` imports a built-in name as `_pytest.<name>` (`src/_pytest/config/__init__.py` at 9.1.1). E2a: a shared file named `fixtures.py` named in `pytest_plugins` was never loaded; the plugin manager's `fixtures` was `_pytest.fixtures`, the file's marker was unregistered, and `-W error` stopped collection with `PytestUnknownMarkWarning`, exit 2. The kit's file is named `acceptance.py`.
- d7. **Assertion rewriting.** pytest rewrites asserts in test modules and in plugin modules; another module must be marked with `pytest.register_assert_rewrite` "before it gets imported" ([writing plugins](https://docs.pytest.org/en/stable/how-to/writing_plugins.html), section "Assertion Rewriting"). A plugin module already imported when pytest marks it gives `PytestAssertRewriteWarning`, "Module already imported so cannot be rewritten" (`src/_pytest/assertion/rewrite.py`). E2c: a conftest that imports its test module, which imports `acceptance`, and then names `acceptance` in `pytest_plugins`, gave that warning; under `-W error` the run ended with a Python traceback and exit 1. Each kit conftest imports its test module, to hand the module's `SUBJECT` to the session fixture `subject`.
- d8. **A conftest with its own hooks.** At `5a4e01f` each conftest names no plugin; it defines `pytest_configure` and `pytest_collection_modifyitems`, one line each calling `acceptance.configure` and `acceptance.collected`, and the fixture `subject`. E2d: this form ran under `-W error` with no warning. A failing `assert` in the test module showed its values (`assert [1, 2] == [1, 3]`, with the index of the difference). A failing `assert` inside the imported shared file showed only `AssertionError`, since that file is not rewritten. The kit's checks in `acceptance.py` carry their own messages for that reason (`expect`, `broken_first_line`, `check_case`).
- d9. **The rootdir.** From the kit root, pytest 9.1.1 takes the kit's `pyproject.toml` as its config file although it has no pytest table, and the kit root as rootdir (E6's collection header); the page says a `pyproject.toml` counts "even if it does not contain a `[tool.pytest]` table (since version `9.0`)" when no other file matches ([customize](https://docs.pytest.org/en/stable/reference/customize.html)). The rootdir shapes node ids, not `sys.path` (same page).

Mechanism class: file-system links checked by a kit gate, and pytest's default import mode. Maturity: `prepend` is the documented default; the link behaviour is in the changelog since 6.0. Cost: the one-module-per-run rule (d4), a conftest of a few lines per module, and the explicit messages of d8.

**Recommendation: keep the links and the plain-name imports under the default `prepend` mode, and let each conftest define the two hooks that call `acceptance`; CONFIRMED against the kit's links of [dec-0025-shared-gate-code-linked](../decisions/dec-0025-shared-gate-code-linked.md).** `importlib` breaks the imports (d2); `pytest_plugins` breaks under `-W error` once the conftest imports its test module (d7), and under the name `fixtures` it loads pytest's own module (d6).

## 5. Coverage (how a run is measured)

The question: how the lines and branches that a module's fixtures reach are measured, when the gates run as child processes, serially and in parallel.

- e1. **Before the branch.** At `fb30e75` `scripts/kit_coverage.py` ran the module's `tests/run.py` under `python3 -m coverage run` with `branch = true`, `parallel = true` and `patch = subprocess`, put a `python3` shim first on the runner's PATH, and combined the data. At `5a4e01f` the same module runs pytest instead: `python3 -m coverage run --rcfile … -m pytest …`, its docstring saying "never pytest-cov".
- e2. **`patch = subprocess`.** It configures Python "to start coverage automatically" in processes created with `subprocess`, `os.system`, or the `execv` and `spawnv` families. It "sets `parallel = True` and will require combining data files before reporting"; added in 7.10 ([config](https://coverage.readthedocs.io/en/7.16.2/config.html), `[run] patch`; [changes](https://coverage.readthedocs.io/en/7.16.2/changes.html), version 7.10.0 of 2025-07-24). The [processes page](https://coverage.readthedocs.io/en/7.16.2/subprocess.html) says the parallel option and `coverage combine` are needed with it.
- e3. **Serial against `-n 2`, in a scratch package.** E5: a test file ran a small gate script as a child process three times. Serially, under `coverage run -m pytest` with the patch, four data files appeared (pytest and three children); with `-n 2`, six (the controller, two workers, three children). After `coverage combine`, both runs gave the same executed lines (9 of 9) and the same five executed branches. Without the patch, the child's lines were all missed, 0 of 9.
- e4. **Serial against four workers, on the kit.** E8 ran `check-aspects.py --run --module const-questions` with `CONSTITUTION_KIT_COVERAGE` set, at `5a4e01f`: serially in 71 s, and with `CONSTITUTION_KIT_JOBS=4` in 26 s. The two JSON files measured the same 24 files. Per file, the executed lines (1,117 in all), missed lines (179), executed branches (213) and missed branches (85) were equal.
- e5. **pytest-cov.** Its xdist page says that under `load` it reports "the combined coverage of all workers", and "Each worker will have its subprocesses measured" ([xdist](https://pytest-cov.readthedocs.io/en/latest/xdist.html)). Its 7.0.0 release "Dropped support for subprocesses measurement", which relied on a `.pth` file, and tells users to enable coverage's `patch = subprocess` instead ([changelog](https://github.com/pytest-dev/pytest-cov/blob/v7.1.0/CHANGELOG.rst)). Read, not run. It adds a plugin and options for what `coverage run -m pytest` already gives (e3, e4).

Mechanism class: coverage.py's own tracer and its subprocess patch, a report and never a gate ([dec-0089-module-coverage-report](../decisions/dec-0089-module-coverage-report.md)). Maturity: the patch is fifteen months old and fixed in later releases. Cost: none new; the same rc file and shim as before.

**Recommendation: `python3 -m coverage run -m pytest` with `patch = subprocess`, as `scripts/kit_coverage.py` runs it, and no pytest-cov; CONFIRMED against the kit's coverage mode before the branch.** It measures the gates' child processes serially and under workers alike (e3, e4); pytest-cov would add a dependency and now relies on the same patch (e5).

## 7. Platform facts, re-verified, and discrepancies

The platform here is pytest, pytest-xdist and coverage.py at their pinned versions; each fact was read or run on 2026-10-15.

- p1. **`prepend` is the default import mode.** The pythonpath page and the `--import-mode` option of the reference, at 9.1.1; E1. Breaks: the plain-name imports of every module's tests, which then need the folder on `sys.path` by other means.
- p2. **Links are not resolved in collection.** Changelog entries #5965 (6.0.0rc1), #7981 (6.2.0) and #9493 (7.1.0); E1. Breaks: node ids and the JUnit `classname` would name `shared/tests` in place of the module's folder.
- p3. **The mismatch check uses `os.path.samefile`.** `_is_same` in `src/_pytest/pathlib.py` at 9.1.1; E1b. Breaks: a two-module run would then fail loudly instead of reusing one module; the one-module rule stands either way.
- p4. **`pytest_plugins` fails only in a conftest loaded after configuration.** `_check_non_top_pytest_plugins` at 9.1.1; E2b, E2e. Breaks: nothing in the kit, whose conftests name no plugin.
- p5. **`fixtures` is a built-in plugin name.** `essential_plugins` and `import_plugin` at 9.1.1; E2a. Breaks: nothing while the shared file keeps its name `acceptance.py`; a new built-in name could shadow a shared file the same way.
- p6. **Only test and plugin modules are rewritten; an already-imported plugin warns.** The plugin page, section "Assertion Rewriting", and `rewrite.py` at 9.1.1; E2c, E2d. Breaks: the explicit messages of `acceptance.py` would become redundant if helpers were rewritten; a plugin form of the wiring stays fatal under `-W error`.
- p7. **`junit_family` defaults to `xunit2`; `record_property` warns there; `user_properties` reach the XML in any family.** The reference (`junit_family`, changed in 6.1) and `junitxml.py` at 9.1.1; E3. Breaks: `read_report`, which finds no number when properties stop reaching the XML.
- p8. **A skip is `<skipped type="pytest.skip">` and keeps its properties.** `append_skipped` in `junitxml.py` at 9.1.1; E3. Breaks: the skip count `read_report` holds against the suite.
- p9. **Exit codes 0–6 are public; a usage error is 4.** The exit-codes page at 9.1.1; E4. Breaks: `run_runner`, which reads 0 as green and 1 as red and every other exit as BROKEN.
- p10. **Each xdist worker collects in full; the collections must agree; session fixtures run per worker.** The xdist pages at v3.8.0; E4. Breaks: a module whose collection varied by process would stop under `-n`.
- p11. **A `UsageError` from the collection hook is exit 3 without its text under xdist.** Observed only (E4); the pages read say nothing. Breaks: the serial collection of b5 would become needless if xdist passed the error through.
- p12. **`-n auto` counts physical cores with psutil, logical CPUs without it.** `auto_detect_cpus` in `plugin.py` at v3.8.0; the page says physical. Breaks: the worker count on any machine where the two differ.
- p13. **`patch = subprocess` measures child processes, sets `parallel`, needs `combine`.** coverage.py's config page and changelog at 7.16.2; E5, E8. Breaks: the coverage report, whose gate lines would count as missed.
- p14. **pytest-cov no longer measures subprocesses on its own.** Its changelog, 7.0.0. Breaks: nothing in the kit, which does not use it.

No earlier comparison covers this mechanism, so none is stale. Where a tool's page and its code disagree:

- a. **The worker count.** The xdist page says physical cores; without psutil the code counts logical CPUs (p12). It changes no design while CI does not set the variable.
- b. **`pytest_plugins` below the root.** The plugin page says it raises a warning. The deprecations page says it was removed. The code fails only for a conftest loaded late (p4). It changes no design, since the kit names no plugin for another reason (d7).
- c. **The `record_property` warning.** The pages do not state it; the source and E3 do (c5). It is one reason the property is added at collection.
- d. **A stop under xdist.** The pages are silent; E4 shows the text lost. This one changed a design: the serial collection before a parallel run (b5).

## Recommendations summary

1. The runner — **OVERTURNED**: pytest, one module's folder per run through `scripts/check-aspects.py --run`, in place of the custom harness and its eleven `run.py`; a stable exit-code interface and a structured report, at the cost of one install (a3, a6).
2. Parallel runs — **build**: pytest-xdist with `--dist load`, asked for by `CONSTITUTION_KIT_JOBS` after a serial collection; processes isolate what threads would share, and the serial collection keeps the stop's text (b4–b7). CI sets none and runs each module's tests one by one, the decider's ruling of 2026-10-16, which reversed the choice of 2026-10-14 to set `auto`.
3. Numbering and reporting an item — **OVERTURNED**: an `item(<number>, <title>)` marker, checked and copied to `user_properties` at collection, read from the JUnit report, in place of printed lines and their parser; `record_property` is not used, since it warns under the default family (c4, c5).
4. Wiring the shared code — **CONFIRMED**: the relative links and plain-name imports stand under pytest's default `prepend` mode, with each conftest defining the two hooks that call `acceptance` and naming no plugin (d2, d6–d8).
5. Coverage — **CONFIRMED**: `python3 -m coverage run -m pytest` with `patch = subprocess`, the same lines and branches serially and under workers; pytest-cov is not needed (e3–e5).
6. Selecting some items — **not needed**: the old `--item` flag goes; a node id or `-k` serves a person, and the gate list and CI select nothing (c9).
