# Research comparison — const-change-cost (2026-11-08)

Surveyed 2026-11-08; local `claude --version` prints `2.1.286 (Claude Code)`. The kit's pin, `scripts/claude-code.version`, names 2.1.282, and the changelog's newest entry is 2.1.319 of 2026-11-06. Experiments ran with ccusage 20.0.48 (its npm launcher and its native binary for macOS on arm64), Node 25.2.1, npm 11.6.2, git 2.56.0 and Python 3.12.15, on macOS 27.0.1 (build 26A434, Darwin 27.0.0, arm64), in a scratch directory outside any repository of the kit. Four live runs were `claude -p` on 2.1.286 with `--model sonnet`, which the transcripts name `claude-sonnet-5-5`, a probe plugin loaded by `--plugin-dir`, and `--output-format stream-json --verbose`, in a scratch git repository. Two experiments read the transcripts of the kit's own sessions on this machine, wrote nothing there, and report counts only. ccusage's Rust source was read at its tag `v20.0.48` through the GitHub API; a statement taken from the source says so. Official Claude Code pages were read in their Markdown form (`curl -sL https://code.claude.com/docs/en/<page>.md`), and every quotation below was checked against that text. A statement about a tool's behaviour is written only where the experiment that showed it is named, with the version tried; a tool read but not run is marked so.

Scope: the six rows of [aspect A15](../requirements.md#a15), [A15.1](../requirements.md#a15-1) to [A15.6](../requirements.md#a15-6), and [the specification](../requirements.md#const-change-cost). Sources by authority: official Claude Code documentation, Anthropic's API pages and price page, git's manuals and release notes, ccusage's package and source, then the experiments reported here. ## 1. The counter ([A15.2](../requirements.md#a15-2))

Claude Code writes each reply of the model into the session's transcript with its token counts. The platform gives no count per commit. The candidates differ in who reads those records and which records they read.

- a1. **What the session command gives.** In the source, `ccusage claude session --id <id> --json` keeps every entry, after its deduplication, whose recorded `sessionId` or whose session taken from the file's path equals the id. It sorts them by time and prints, per entry, `timestamp`, the four counts, `model` and `costUSD`, then `totalTokens` and `totalCost`. No message id, request id or agent id stands in the output (E3). So the output cannot be split into commit windows afterwards: the cut is made before ccusage runs (section 2).
- a2. **The cost.** Per entry, `costUSD` is the record's own stored field, or 0 when it is absent (source). None of the 136,388 usage records in the kit's own transcripts has that field (E11). `totalCost` is computed from the four counts and a price table built into the release when `--offline` is given (source). On a fixture it matched Anthropic's [price page](https://platform.claude.com/docs/en/about-claude/pricing) by hand to the last digit (E3). On a live session it matched the page too, while the platform's own cost record priced cache reads at twice the page's rate (E18).
- a3. **One reply, several records.** The key of a reply is its message id and request id, over every file ccusage reads. Of two records under one key, a main-thread record replaces a sidechain one; else the record with the larger total wins; on a tie the first file in path order wins, the files of every folder sorted together (source; E4, E5). A record with no request id is keyed by its message id and its session instead (source); 6 records in the kit's transcripts have none (E11).
- a4. **Subagents and workflow agents.** Their records carry the parent session's id (E11). `--id` gathers them through that field. Without `--id`, ccusage takes a workflow agent's session from its path and lists its replies in a row of their own, named after the workflow's folder (E9).
- a5. **The advisor model.** Of a record's `usage.iterations`, each item of type `advisor_message` becomes an entry of its own, priced at the advisor model's rate (source; E3). The API's [advisor tool page](https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool) says: "Advisor tokens are not rolled into the top-level totals because they are billed at a different rate." No advisor iteration stands in the kit's transcripts (E11), so this was proven on a fixture alone.
- a6. **The walk follows no link.** The walk keeps a path only when its entry's own type is a file or a folder, which a symbolic link is not (source). A linked file and a linked folder were both left out (E6).
- a7. **A configuration file changes the output.** ccusage reads the first JSON object it finds at `.ccusage/ccusage.json` under its working folder, then at `ccusage.json` in each folder of `CLAUDE_CONFIG_DIR` (source). Its schema lets such a file set, for the session command, `mode`, `since`, `until`, `pricingOverrides`, `jq` and `noCost`. One file in the working folder set the cost to 0, another emptied the output; `--config` naming a file that holds `{}` restored the count (E7).
- a8. **An unknown model costs nothing, silently.** A reply whose model the table lacks adds its tokens and no cost, and the `--id` output says nothing about it (E8). The same report without `--id` marks the model `missingPricing: true` (E8).
- a9. **Prices fetched online.** Without `--offline`, ccusage fetches LiteLLM's price file from its main branch (source). Two runs of one release could then give two costs; `--offline` ties the table to the release.
- a10. **Equal to a count made apart, and fast.** On three of the kit's own sessions, each copied alone, ccusage and the count made apart agreed reply for reply, and each run took at most 0.10 s on folders of up to 248 MB (E10).
- a11. **The package.** The npm package ships a Node launcher and one native binary per platform, and no library; the Rust workspace sets `publish = false` (source). The repository lists 20 releases from v20.0.29 of 2026-10-10 to v20.0.48 of 2026-11-02. Nothing read for this survey promises the JSON shape; the module's fixtures hold it (section 9). The launcher needs Node; the native binary ran with no Node on the `PATH` and gave the same count (E1). The package states no `engines` field.

The candidates:

- a12. **Candidate (i): the pinned ccusage over a folder that holds one session alone, R1 and R2.** Class: a third-party tool run by the module's script. Maturity: 19,363 stars on GitHub on the survey date, and a release every day or two (a11). Cost: a copy of the session's records for each count, Node and npm in the project, a pin, and one flag more than [R1](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r1) names (a7). The native option and what it cannot do: the platform's own `cost-state` record, an undocumented line of the transcript, holds a running total per session. It stood once at the end of each run, not at a commit, and a fork's total carried the parent's (E16, E17).
- a13. **Candidate (ii): a parser of the module's own.** Class: module code. It would copy and follow every rule of a3 to a5. The count made apart for this survey holds those rules in about 50 lines and agrees today (E10); each later change of the format would be the kit's to follow.
- a14. **Candidate (iii): ccusage over all the transcripts.** It fails the rule of [A15.1](../requirements.md#a15-1): with a fork and its parent read together, the parent's count fell from 5,737 to 990 when the fork's path sorted first (E4).
- a15. **Candidate (iv): OpenTelemetry.** Class: a documented platform export. The event `claude_code.api_request` carries, per request, the four counts, a cost, `request_id`, `session.id` and `query_source`, whose values include `compact` ([monitoring usage](https://code.claude.com/docs/en/monitoring-usage)). Cost: a collector must run from a session's first request, and no past session can be counted. Read, not run.
- a16. **Candidate (v): tools that tie spend to git.** git-ai records line-level attribution in git notes; its README lists "Tokens and cost per commit and PR", which "Aggregates token usage and cost across the sessions behind each commit/PR", and ties token spend to pull requests in its paid teams version. The Langfuse hooks of t6 replay transcripts as traces grouped by session. Claude Code's analytics count lines and pull requests, and the page points to OpenTelemetry for token counts. None counts one session's spend between two of its own commits, apart from other sessions. All read, none run.

How a project gets the pinned ccusage:

- a17. **Install (i): Claude Code's own dependency install.** The [plugin loading](https://code.claude.com/docs/en/plugins/loading) page says Claude Code "installs the dependencies into the copied version directory each time it creates one", when a plugin root holds a `package.json` and a supported lockfile. It needs registry packages pinned to exact versions, `https` downloads and no overrides, runs no lifecycle scripts, stops after 60 seconds, and runs npm from the person's `PATH`. "You can't turn the automatic install off." For a plugin loaded in place from a marketplace on a local path, which is how the kit loads its own modules, "Claude Code doesn't install the dependencies into the source directory". ccusage's lockfile meets those limits (E1). Not run: no marketplace install was made.
- a18. **Install (ii): a `SessionStart` hook that installs into `${CLAUDE_PLUGIN_DATA}`.** The [plugin components](https://code.claude.com/docs/en/plugins/components) page gives this hook as an example: it runs `npm install` when the plugin's `package.json` differs from the copy in the data folder. That folder survives updates and is deleted with the plugin ([plugins reference](https://code.claude.com/docs/en/plugins-reference)). The first session needs the network, and the hooks page asks that `SessionStart` hooks stay fast. Read, not run.
- a19. **Install (iii): `npx` with an exact version.** It fetches the package into npm's cache at the first count, so a count needs the network then. Read, not run.

**Recommendation: candidate (i), the pinned ccusage run as [R1](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r1) and [R2](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r2) say, with `--config` naming an empty file of the module, and the pin held as an exact version in a `package.json` with its `package-lock.json` at the plugin root; CONFIRMED against the row's advisory enforcement.** It is the only candidate that keeps the reading and the prices outside the kit and keeps every other session out (a12, a14). The flag shields the count from a configuration file of the project (a7). The lockfile is "a file of its plugin", as [A15.2](../requirements.md#a15-2) asks, and both installs read it: (i) where the plugin is copied, (ii) where it loads in place. For the decider: whether the module calls the native binary directly, so that no Node is needed at count time (a11). The binary's place inside `node_modules` is ccusage's own layout, not a promise.

## 2. Ownership and windows ([A15.3](../requirements.md#a15-3))

- b1. **A fork copies; a resume appends.** A fork made with `--resume <id> --fork-session` got a new id. Its transcript copied the parent's main-thread records with their message ids, request ids, times and uuids, every one with the fork's session id written in. Every copy was dated before the fork's `SessionStart` hook ran, and the parent's subagent transcript was not copied (E16). A plain `--resume <id>` kept the id and appended to the same file, with no copy (E17).
- b2. **One id, several starts.** A resumed session's hook gave `source` `resume`, a compaction's gave `compact`, both under the session's own id (E17, E18). A start log then holds several starts for one id. The start that owns, under [R3](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r3), is the earliest; a later one would cut away the session's own earlier work.
- b3. **A compaction stands in no transcript.** `/compact` wrote a summary of 3,350 characters and no record with a token count. The platform's own total for the session rose by 2,436 input, 1,456 output, 89 cache-write and 36,384 cache-read tokens, and by $0.027 (E18). A count read from transcripts misses this work, which [A15.1](../requirements.md#a15-1) counts as the session's. OpenTelemetry reports such a request with `query_source` `compact` (a15).
- b4. **`/clear` and the desktop app's forks.** The [environment variables](https://code.claude.com/docs/en/env-vars) page says the session variable "is updated on `/clear`"; the hooks page gives `/clear` its own `source`, `clear`, and its own `SessionEnd` reason. The `fork` source covers `--fork-session`, `/fork`, `/branch` and a conversation moved to the background (hooks page). Neither was run.
- b5. **A reply that spans a commit.** On a fixture, a reply whose first record came before a commit and whose full record came after it was counted once, in the earlier window, when the cutter grouped records by message id and request id. Cut record by record, it was counted in both windows (E5).
- b6. **A commit's time needs milliseconds.** Git writes a commit's date in whole seconds. In E15, the reply that called `git commit` was dated 0.177 s into the second that git wrote as the commit's date. A cut at that date would move the reply into the next window. The commit log's time is therefore the hook's own clock, with milliseconds.
- b7. **No reply of a session comes before its start hook.** The hooks page says "Claude's first response still waits for the hooks to finish". The first record of each run came after the hook's time, by 0.23 s at a start and 0.02 s at a fork (E15, E16). So a cut at the hook's time keeps all of the session's own replies and none of the copies.

**Recommendation: [R3](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r3) and [R4](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r4) as written, with three readings made explicit: the start that owns is the earliest one logged for the id (b2), the commit's time is the hook's clock in milliseconds (b6), and the cutter groups records with ccusage's own key (a3); CONFIRMED against the row's advisory enforcement.** The cut at the start log kept the fork's count apart from the parent's in every run (E4, E16). For the decider: the compaction's work cannot reach a transcript-based count (b3). The rulings record can name it as a limit of the count, or take OpenTelemetry for that one kind of request.

## 3. The start log ([A15.5](../requirements.md#a15-5))

- c1. **The hook's input.** The hooks page gives every event `session_id`, `transcript_path` and `cwd`, and `SessionStart` a `source` of `startup`, `resume`, `clear`, `compact` or `fork`. The changelog of 2.1.214 records that a session that begins as a fork reports `fork`, where it reported `resume` before. The probe saw `startup`, `fork`, `resume` and `compact` (E15 to E18).
- c2. **The transcript does not exist yet.** At a start, the hook found no line in the file that `transcript_path` names (E15). The path is still given, so a log can keep it.
- c3. **The hook knows its session twice.** The variable `CLAUDE_CODE_SESSION_ID` of the hook's environment equalled its input's `session_id` in every run (E15 to E18).
- c4. **Place (i): the clone's git common directory.** `git rev-parse --git-common-dir` named the same folder from the main checkout and from a linked worktree (E12). A file there is shared by every worktree, never committed or pushed, and kept when the plugin is removed. It is lost with the clone.
- c5. **Place (ii): the plugin's data folder.** It is one folder per person and plugin, across all projects, kept across updates and deleted at uninstall unless `--keep-data` is given ([plugins reference](https://code.claude.com/docs/en/plugins-reference)). A log there is lost at uninstall, the very loss [R11](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r11) names. The Bash tool's environment does not name it (d7).
- c6. **Place (iii): beside the gate logs.** The dial `log_dir` names a folder in each worktree's top, so each worktree, the desktop app's ones included, would keep a log of its own.
- c7. **A session that starts outside the clone.** `git -C <clone> commit` from another folder fired the clone's hook (E12). Under place (i), the start of such a session stands in no log of that clone; section 8 meets that case.

**Recommendation: build the hook as [R7](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r7) says, logging the id, the hook's time in milliseconds, the `source`, and also `transcript_path`, appended to a file in the clone's git common directory (c4).** The common directory is the one place every worktree shares and an uninstall leaves alone. The transcript's path spares the count a search of the platform's folders. The row's advisory enforcement stands: the hook blocks nothing and judges nothing. For the decider: a second copy of the start log in the plugin's data folder, for sessions that start outside the clone (c7).

## 4. The commit log ([A15.5](../requirements.md#a15-5))

- d1. **The variable is documented.** The environment variables page says `CLAUDE_CODE_SESSION_ID` is set to the current session's id in the Bash tool's processes, in hook commands and in stdio MCP servers. For Bash and hooks "this matches the `session_id` field in the hook JSON input and is updated on `/clear`". The changelog brought it to the Bash tool in 2.1.132.
- d2. **It names the session in every Bash call.** A value inherited from the launching shell was replaced by the session's id. A subagent's commit carried the main session's id, as the main thread's did (E15). In the desktop app session that ran this survey, a subagent's Bash calls carried the variable too (E12).
- d3. **Git runs hooks named in its configuration.** Git 2.54's release notes: "Hook commands are now allowed to be defined (possibly centrally) in the configuration files". A hook is `hook.<name>.command` with one or more `hook.<name>.event`. The `git hook` manual says "The default <hook-name> from the hookdir is run last." Both ran in E12, with `core.hooksPath` set as the kit sets it.
- d4. **Which operations fire which hook.** The table holds what E12 observed:

| git operation | `post-commit` | `post-merge` | a new commit |
|---|---|---|---|
| `git commit`, with `--no-verify` or `-C`, or in a linked worktree | yes | no | yes |
| `git cherry-pick`, `git commit --amend` | yes | no | yes |
| `git rebase`, once per commit it replays | yes | no | yes |
| `git commit` that concludes a conflicted merge | yes | no | yes |
| `git merge --no-ff` with no conflict | no | yes | yes |
| `git merge --ff-only`, `git pull --ff-only` | no | yes | no |

- d5. **An inherited variable outlives its session.** The variables page describes an inherited `CLAUDE_CODE_CHILD_SESSION` "from a `screen` session or a background launcher first started by Claude Code's Bash tool". A process like that keeps the session's variables, so a commit typed later in it, even by a person, would be logged with the session. Read, not run.
- d6. **A nested session may keep no transcript.** The same page says a nested interactive `claude` started from the Bash tool is left out of `--resume`, and offers `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE` "to force transcript persistence". Its commits could name a session that no transcript holds, which then gets no count. Read, not run.
- d7. **A git hook cannot reach the plugin.** The Bash tool's environment in the session that ran this survey held no variable whose name starts with `CLAUDE_PLUGIN_` (E12). A copied plugin also changes folders at each version: the version "names the plugin's cache directory", and an old one is removed 14 days after an update ([plugin loading](https://code.claude.com/docs/en/plugins/loading)). So the command written into git's configuration must be a whole command of its own that appends to the log in the git common directory, not a path into the plugin.
- d8. **A plugin installs no git hook.** The plugin components page lists no git hook among its components. Hooks in git's configuration need one step per clone, or a `SessionStart` hook that writes the keys into the clone's configuration with no step by a person.

The candidates:

- d9. **Candidate (i): a hook in git's configuration reading the variable.** Class: git's own configuration, with a documented platform variable. Maturity: git 2.54 or later, and a variable documented since 2.1.132. It sees every commit the session's processes make, in any worktree of the clone and through `-C` (d4). Cost: a step per clone, and a `post-merge` entry that logs `HEAD` only when it is a new merge commit whose first parent is `ORIG_HEAD`, since a fast-forward and a pull also fire it (d4). A git older than 2.54 lacks the keys; no older git was run.
- d10. **Candidate (ii): a `PostToolUse` hook that lists the commits a tool call made.** Class: a plugin hook. It needs no step per clone, and it knows the agent, since tool hooks inside a subagent carry `agent_id` (E15). It cannot tell two sessions apart in one checkout: from one snapshot, both lists named both commits (E13). It sees only the Bash calls of sessions that load the plugin.
- d11. **Candidate (iii): OpenTelemetry's `tool_result` event.** With `OTEL_LOG_TOOL_DETAILS=1`, `git_commit_id` "is the full commit SHA when the commit is the HEAD of the session's working directory, and git's abbreviated SHA otherwise" (monitoring usage). The closed issue [anthropics/claude-code#77237](https://github.com/anthropics/claude-code/issues/77237) says the value is scraped from git's output. The open [anthropics/claude-code#95934](https://github.com/anthropics/claude-code/issues/95934) reports it dropped for `git -C <path> commit` and for quiet or redirected commits on 2.1.278. It needs a collector. Read, not run.
- d12. **Candidate (iv): commits matched to sessions afterwards.** The main transcript's tool result held an undocumented `gitOperation.commit` with a 7-character SHA for each main-thread commit, and the subagent's transcript held none for its commit (E15). A fork's copies carry the parent's (E16). Beyond that field, the match would read git's own output text, which issue #77237 shows to be fragile.
- d13. **Merges on the forge.** No local hook runs; the commit is logged with no session and gets no count, as [R7](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r7) says. A squash or rebase merge lands commits that differ from the session's own (section 5).

**Recommendation: candidate (i), git's `post-commit` and `post-merge` hooks from its configuration, each a whole command that appends the SHA, the clock in milliseconds and `CLAUDE_CODE_SESSION_ID` to the log in the git common directory; build, with the row's advisory enforcement unchanged.** It is the only route that names each commit's session with no guess when sessions share a checkout (d10). It also covers subagents, other worktrees and `-C` (d2, d4). The native options fall short: the platform's own commit facts reach only a collector (d11) or an undocumented field that misses subagents (d12). For the decider: the step per clone is either a line of the install note run once, as `sh scripts/setup-clone.sh` is in the kit, or a `SessionStart` hook that writes the keys itself (d8).

## 5. Where the counts are kept ([A15.4](../requirements.md#a15-4))

- e1. **Git notes.** Notes on two commits were seen from a linked worktree. A plain push sent no notes ref, and a push that named the ref sent it. A rebase lost the notes unless `notes.rewriteRef` named their ref (E14). A squash or rebase merge on a forge makes new commits that no note names. A pushed ref publishes every count and every cost; the kit's own repository is public.
- e2. **A file in the repository.** A count exists only after its window closes, so it would ride a later commit, which itself must be counted, and it would publish the costs on every push.
- e3. **Commit trailers.** A trailer changes the commit's SHA, and the count is made after the commit ([R5](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r5)). No commit can carry its own count.
- e4. **Beside the gate logs.** One folder per worktree (c6).
- e5. **The clone's git common directory.** Shared by every worktree, never published, kept at uninstall, lost with the clone (c4).
- e6. **After a squash or rebase merge.** The counts are keyed by the session's own SHAs, which the landed commit does not carry. A report per pull request can sum the pull request's own commits; a rewritten commit could be matched to its original by `git patch-id`. Not run.

**Recommendation: one file of JSON lines in the clone's git common directory, beside the two logs, one line per counted commit (e5); build, with the row's advisory enforcement unchanged.** It is shared, local and never published, and it needs no ref the person must remember not to push (e1). For the decider: git notes as an export a person runs on purpose, never by default.

## 6. When the count runs ([A15.4](../requirements.md#a15-4))

- f1. **The transcript lags.** The hooks page: "The transcript file is written asynchronously and may lag the in-memory conversation". At `PostToolUse` of a commit, the transcript did not yet hold the call's result. At `Stop` it held 31 of its final 34 lines. At `SessionEnd` it held all 34 (E15).
- f2. **`SessionEnd` is short.** The hooks page: "SessionEnd hooks have a default timeout of 1.5 seconds", and "Timeouts set on plugin-provided hooks don't raise the budget." It fired in every `-p` run with reason `other` (E15 to E18). No crash or kill was tried.
- f3. **An async hook does not wait.** The hooks page: with `"async": true` a command hook runs in the background, and "Claude Code doesn't enforce `timeout` on it."
- f4. **The cleanup.** The [settings reference](https://code.claude.com/docs/en/settings-reference): `cleanupPeriodDays` defaults to 30, its minimum is 1, and the sweep runs after a session starts; it "deletes transcripts without showing a message". Desktop app transcripts are kept at any age unless `desktopSessionCleanupPeriodDays` is set (from 2.1.248), and then deleted only once older than both limits. A subagent's transcripts are removed with the parent's ([the `.claude` directory](https://code.claude.com/docs/en/claude-directory)).
- f5. **A count is cheap.** A ccusage run took at most 0.10 s (E10); the copy of the records is the larger part.
- f6. **A git `pre-push` hook.** It would need a hook in git's configuration too, and a project may push rarely, or from another clone.
- f7. **An own copy of each window.** A count written at completion is never made again ([R5](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r5)), so a copy would serve no recount. It would keep the session's prompts and tool output in a second place.

**Recommendation: an async `Stop` hook that counts every complete window of its session not yet counted, the same pass at `SessionStart` over every session in the clone's logs, and a command a person can run; no own copy of a window; build, with the row's advisory enforcement unchanged.** `Stop` runs at the end of every turn, by which time each earlier commit's window already holds a later record (f1), and async keeps the turn from waiting (f3). The pass at `SessionStart` catches a window that no later `Stop` saw complete, at the clone's next start, normally long before the sweep's 30 days (f4). `SessionEnd` alone is too short for a large session, and no crash was tried (f2).

## 7. Parallel agents inside one session ([A15.3](../requirements.md#a15-3))

- g1. **What the transcript gives.** A subagent writes its own file under the session's `subagents` folder, with a metadata file naming its `agentType` and the `toolUseId` that started it (E15). Its records carry `agentId`, `isSidechain` and the parent's session id; a workflow agent's file stands one folder deeper, under `subagents/workflows/` (E11).
- g2. **What the hooks give.** Tool hooks inside a subagent carry `agent_id` and `agent_type`, and `SubagentStart` and `SubagentStop` fire with them (hooks page; E15).
- g3. **What the commit log gives.** The variable names the session, not the agent (d2); no agent variable stands on the environment variables page.
- g4. **Windows split by agent.** They need each commit's agent, which only candidate (ii) of section 4 knows. They still leave the main thread's work, and that of agents that never commit, to be shared by time.

**Recommendation: time windows over the whole session, every agent's replies included, as [R4](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r4) cuts them; a split by agent is not needed.** Time is the one key every reply carries (a1). A split by agent would trade the commit log's certainty (d9) for an agent name, and would still fall back on time (g4).

## 8. Sessions from before the start log ([A15.3](../requirements.md#a15-3), [A15.5](../requirements.md#a15-5))

- h1. **When the case arises.** Under candidate (i) of section 4, a commit can name a session whose `SessionStart` hook never ran in this clone. That session started before the plugin was enabled, or in another folder (c7).
- h2. **A stand-in start.** Take the earliest record of the session's transcript whose uuid, or whose message id and request id, stands in no other session's transcript. On the live fork it fell 20 ms after the logged start, and the count was the same (E19).
- h3. **When the stand-in fails.** Once the parent's transcript has been swept (f4), the fork's copies stand in no other transcript and look like its own. It also needs every other transcript of the project's folders to be read.
- h4. **Skip.** The commit gets no count, and the report names it with its reason, as it names a commit with no session ([R7](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r7)).

**Recommendation: skip such a session and name each of its commits in the report (h4); build.** The case is narrow under [R13](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r13), which installs the module from a project's first session. The stand-in could claim a parent's work once the sweep has run (h3). For the decider: the stand-in, for a project that enables the module after weeks of sessions.

## 9. The pin's known-count test ([A15.6](../requirements.md#a15-6))

- i1. **The fixture's form.** ccusage reads only compact JSON lines: with a space after each colon, it found the files and no entry (E2). The fixture keeps fixed ids and times under `projects/<folder>/`.
- i2. **What it holds.** A reply written twice, first in part, a subagent, a workflow agent, an advisor iteration, and a fork whose copies keep the parent's ids and times (E3). Each case is one ccusage rule the count relies on (a3 to a5).
- i3. **The known values.** The four counts and the total are held exactly: 5,737 tokens for the parent, and 2,360, 3,375 and 2 for its three windows (E3, E5). The cost is held against the public price page, for models whose prices the page lists (E3). A price change then fails the test by design, for a person to read.
- i4. **How the fixtures reach the pinned version.** A test needs the pinned ccusage, installed from the module's lockfile into a scratch folder, which needs npm and the network. A missing ccusage is a configuration failure, never a silent pass, as step 4 of "Developing a module" in [CLAUDE.md](../../CLAUDE.md) asks.

**Recommendation: build the fixture of i2 and hold i3 in the module's tests at the pinned version, through the module's own cutter and the pinned ccusage; CONFIRMED against the row's review enforcement.** The same run proves the cutter's windows (E5) and the counter's rules (E3, E4). Before the pin moves, the same test runs on the new version, as [R8](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r8) says.

## 10. Fit with the shared gate code

Described, not decided; part names as in [kit-shared-gate-code](../../shared/GATE.md#g1). The module would have four entry points: the start hook, the git hook's command, the count, and the report.

- s1. **The transcript reader.** `read_transcript` in [`history.py`](../../shared/constitution_layer_kit/history.py) reads human turns, tool calls and hook runs, each with its time. It keeps no message id, request id or uuid, which the cutter needs (b5, h2). Widening it for one module is a question for [rule 2 of plc-0009-shared-code](../policies/plc-0009-shared-code.md#r2); a reader of the module's own needs only a record's time, session id and ids, as [R1](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r1) allows.
- s2. **The modes.** `Mode` in [`model.py`](../../shared/constitution_layer_kit/model.py) has `hook`, `scan`, `act` and `report`. The start hook fits `hook`, through `cli.guarded`, and the report fits `report`, which "reads and counts, and changes and judges no file". The count appends its lines of counts, so it fits `act`, the mode of an entry point that changes files, more than `report`.
- s3. **The git hook's command is no entry of the shared code.** Git runs it outside Claude Code's hooks, so it gets no payload and no `CLAUDE_PLUGIN_*` variable, and it cannot name a script in the plugin's folder (d7). It stays a whole command of its own, outside the shared code.
- s4. **The output log.** `Output` in [`output.py`](../../shared/constitution_layer_kit/output.py) writes to the folder `CLAUDE_PLUGIN_DATA` names. That suits the hook and the count's own log of runs, not the module's records, which belong in the git common directory (c4, e5).
- s5. **The preflight.** It imports the declared Python libraries. Node, npm and ccusage stand outside it, so a missing ccusage is the module's own configuration failure, with its install command, as module [`const-referencing`](../requirements.md#const-referencing) names lychee's.
- s6. **The effect report.** The count is no rule of a module, so it is no effect rule; its report is an entry of its own, named outside `check-`, as [A15.1](../requirements.md#a15-1) keeps it advisory.

No change to `shared/constitution_layer_kit` is needed for any of these; the one strain is the transcript reader of s1, met in the module.

## Recommendations summary

1. [A15.1](../requirements.md#a15-1), the count's reach — **CONFIRMED** as advisory, with one gap: a compaction's tokens reach no transcript, so the row or the module's limits must name them (b3).
2. [A15.2](../requirements.md#a15-2), the counter — **CONFIRMED**: the pinned ccusage over a folder of one session's plain copies, as [R1](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r1) and [R2](../decisions/dec-0115-tokens-per-commit-counted-by-ccusage.md#r2) say, plus `--config` naming an empty file (a7). The pin is an exact version in a lockfile at the plugin root, installed by the platform where the plugin is copied and by a start hook where it loads in place (a17, a18).
3. [A15.3](../requirements.md#a15-3), ownership and windows — **CONFIRMED**: the earliest logged start owns, a commit's time is the hook's clock in milliseconds, and the cutter groups records by ccusage's own key (b2, b6, a3). Parallel agents share the session's windows by time; a split by agent is **not needed** (g4). A session from before the start log is skipped and named — **build** (h4).
4. [A15.4](../requirements.md#a15-4), the count and its keeping — **build**: an async `Stop` hook and a pass at `SessionStart` count each complete window once (f1, f3), into JSON lines in the clone's git common directory (e5). Git notes, a file in the tree, trailers and an own copy of each window are **not needed** (e1 to e3, f7).
5. [A15.5](../requirements.md#a15-5), the logs — **build**: the start hook logs the id, the time in milliseconds, the `source` and the transcript's path (c1, c2). The commit log is git's `post-commit` and `post-merge` hooks from its configuration, each a whole command reading `CLAUDE_CODE_SESSION_ID` (d9). The step per clone is left to the decider (d8).
6. [A15.6](../requirements.md#a15-6), the pin's test — **build**: a compact fixture with a reply written twice, a subagent, a workflow agent, an advisor iteration and a fork's copies, whose four counts and total are held exactly and whose cost is held against the price page (i2, i3).
