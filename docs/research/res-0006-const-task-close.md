## 1. The `Stop` hook ([requirement A4.7](../requirements.md#a4-7))

From the [hooks reference](https://code.claude.com/docs/en/hooks) unless another page is named, field by field, and the live runs E1:

- a1. **When it fires.** "Runs when the main Claude Code agent has finished responding. Does not run if the stoppage occurred due to a user interrupt. API errors fire StopFailure instead." It fires at the end of a `claude -p` run (E1, every run). It did not fire when a `claude -p` run was ended with SIGINT after seven seconds — no payload was written and the stream ended with `[Request interrupted by user]` (E5). It fires "whenever Claude finishes responding, not only at task completion" ([hooks guide](https://code.claude.com/docs/en/hooks-guide)).
- a2. **No matcher.** `Stop` is in the row "no matcher support — always fires on every occurrence". "If you add a `matcher` field to an event without matcher support, it is silently ignored." The `if` field on a handler is "Only evaluated on tool events … On other events, a hook with `if` set never runs". Neither narrows a Stop hook. The script decides.
- a3. **The payload, observed** (E1a, nine payloads, every one the same shape): `session_id`, `transcript_path`, `cwd`, `prompt_id`, `permission_mode`, `effort` (an object, `{level: high}`), `hook_event_name` (`Stop`), `stop_hook_active` (a boolean), `last_assistant_message` (a string), `background_tasks` (a list, empty), `session_crons` (a list, empty). No `tool_name`, no `tool_input`, no `scratchpad_dir` — the page says that field "Requires Claude Code v2.1.257 or later", above the local version — and no `agent_id`. The two arrays "let hooks distinguish 'session is done' from 'session is paused waiting for background work'".
- a4. **`cwd` is the session's directory.** In every payload of E1 it equalled the scratch repository the session was started in (E1a); nothing else in the payload names a file. A Stop hook that judges the working tree starts from `cwd` and asks git for the root.
- a5. **What a Stop hook may return.** Exit 2: "Prevents Claude from stopping, continues the conversation"; "A hook that blocks by exiting 2 routes the same way as `reason`: Claude receives the stderr message as the explanation for why it should continue." JSON, exit 0:
  - `decision: "block"` with `reason` ("Required when `decision` is `"block"`");
  - `hookSpecificOutput.additionalContext`, "Non-error feedback for Claude. The conversation continues so Claude can act on it";
  - `continue: false` with `stopReason`, which "Takes precedence over any event-specific decision fields";
  - `systemMessage`, a "Warning message shown to the user".

  Any other exit code is "a non-blocking error … the transcript shows a `<hook name> hook error` notice followed by the first line of stderr".
- a6. **`additionalContext` on `Stop` is a continuation, not a warning.** The page says so — "It keeps the conversation going through the same loop protections as `decision: "block"`, namely the `stop_hook_active` input and the 8-consecutive-continuation cap" — and E1a shows what that means for the shared warn channel: a hook returning exit 0 with `hookSpecificOutput.additionalContext` and a `systemMessage` fired nine times in one `claude -p` run of a one-word prompt; the model answered the context eight times ("I'll leave that alone", "Same answer", "Holding." three times) before the platform ended the turn; the run's result was `num_turns: 1` and the last reply. The same hook returning `systemMessage` alone (E1b) fired once, the turn ended, the stream carried an `informational` notice `Stop says: <the message>` for the user, and the model saw nothing. The shared `W1` channel of [kit-shared-gate-code §3](../../shared/GATE.md#g3) — `additionalContext` plus `systemMessage` — is therefore the wrong warn for this event (section 8, s3).
- a7. **The loop guard and the cap.** "`stop_hook_active` … is `true` when Claude Code is already continuing as a result of a stop hook. Check this value or process the transcript to avoid blocking on a condition that will never resolve. Claude Code overrides the hook and ends the turn after 8 consecutive blocks." Observed:
  - `false` on the first firing of every run and `true` on every later one (E1a, E1c, E1d);
  - **a hook that exits 2** unconditionally fired nine times — one plus eight — after which the run ended with `stop_reason: end_turn`, an empty `result`, `num_turns: 10` and exit 0 from `claude -p` (E1c).

  The cap is `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` ([environment variables](https://code.claude.com/docs/en/env-vars)), "default: 8", "Set to `0` to disable the cap". The guide's own pattern is to "exit early if it's `true`".
- a8. **Exit 2 made the model commit — when nothing told it not to.** E1d:
  - **the prompt asked** for one file edit and one sentence;
  - **at turn end** the hook exited 2 with a three-part message (what failed, why, `git add -A && git commit -m '<what changed>'`);
  - **the model ran** `git status --porcelain`, then `git add -A && git commit` with a message of its own, replied "Committed … so the working tree is clean", and the second firing found the tree clean and exited 0: six turns, the tree committed.

  E1c′: the same hook, the prompt ending "Do not commit unless you are told to" — the model refused ("An explicit instruction from you outranks a generic end-of-turn policy nudge"), and the second firing, `stop_hook_active` true, let the turn end. E1c, a fix that could not clean the tree: the model refused seven times ("No."). A block on `Stop` is a request the model weighs against its instructions. Every standoff ends at the cap — an honest limit to state in the module's document, not a defect of the design.
- a9. **What the user sees, what the model sees.** On exit 2 the stream carries a `notification` with key `stop-hook-error` and the text `Stop hook error occurred · ctrl+o to see`; the model receives a user-role message opening `Stop hook feedback: [<the hook's command line>]:` followed by the stderr text (E1c, E1d). On exit 0 with `systemMessage` the user gets the `Stop says:` notice and the model nothing (E1b). Stderr of a hook that exits 0 "goes to the debug log only, never the transcript, and Claude never sees it."
- a10. **Timeouts and channels.** A command hook's default timeout is 600 seconds; the page lowers it for four other events and not for `Stop`. Hooks "run in their own session without a controlling terminal". "Your hook's stdout must contain only the JSON object." A `systemMessage` in `-p` mode "can arrive as an `SDKInformationalMessage`" — the `informational` line of E1b. Rule 11 of [template §6](../../module-template/MODULE.md#t6), the exec form with `args`, applies: "Set `args` whenever the hook references a path placeholder".
- a11. **`SubagentStop`.** The same decision control, with `agent_id`, `agent_type`, `agent_transcript_path` added; "Not every SubagentStop event comes from a subagent Claude spawned" — internal agents fire it too. A `Stop` hook written in a subagent's frontmatter is converted to `SubagentStop`. A plugin's `Stop` handler fires for the main agent only (a1). Whether a dirty tree at a subagent's end deserves the same message is a design question; not exercised live.
- a12. **`SessionEnd` cannot carry the rule.** Matchers `clear`, `resume`, `logout`, `prompt_input_exit`, `other`; "SessionEnd hooks have no decision control. They can't block session termination"; "Claude Code discards their JSON output fields, such as `systemMessage`"; exit 2 "Shows stderr to user only". The hooks "share a 1.5-second budget". There is no model left to read a teaching message: at most a log line.
- a13. **Skill-registered hooks.** A skill's frontmatter may declare hooks that Claude Code "registers … when you or Claude invoke the skill and keeps running them for the rest of the session", with `once: true` to drop one "after its first successful run". "A run that fails, blocks with exit code 2, or times out leaves the hook in place". The close skill could register the turn-end check for the session that invoked it. That hides a gate inside a skill, the blur [law 5 of CLAUDE.md](../../CLAUDE.md#law-5) forbids. Recorded, not recommended.
- a14. **Prompt-based Stop hooks and `/goal`.** A `prompt` hook lets a model judge "whether all requested tasks are complete", with `impossible: true` to let the turn end. `/goal` is "a session-scoped prompt-based Stop hook". Judgment on a gate's channel: out under [law 5 of CLAUDE.md](../../CLAUDE.md#law-5).
- a15. **The platform's own framing.** The guide, on hooks that match `Edit|Write`: "Claude can also create or modify files by running shell commands. If your hook must see every file change … add a `Stop` hook that scans the working tree once per turn." The row's hook is the documented remedy for shared honest limit 1 of [kit-shared-gate-code §4](../../shared/GATE.md#g4).
- a16. **Cost.** `git status --porcelain` on the kit: 24 ms median (E4); with `--untracked-files=all`, the same. The model's `git status --porcelain` in E1d showed an untracked file as `??` — untracked files that git does not ignore are part of "dirty". The kit's `local/` is ignored and invisible.

**Recommendation: the `Stop` hook confirmed as gate-lite, with one correction to how its two severities are carried — `warn` is exit 0 with `systemMessage` alone, never `additionalContext` (a6); `block` is exit 2 with the three-part message on the first firing and exit 0 when `stop_hook_active` is true (a7), so a block costs one continuation and never a standoff; the check is `git status --porcelain` from the event's `cwd`, dirty meaning any line, tracked or untracked; `SessionEnd` is no carrier (a12), `SubagentStop` is not wired (a11). CONFIRMED.** For the decider:

- **the default of the dial** the specification names, "dirty-tree-at-turn-end: warn or block" — the matrix says warn;
- **whether the block message** names the commit-before-edit skill of section 7 by name;
- **and whether the hook**, once it has read the tree, also runs the range check of section 2 and reports its finding through the same `systemMessage` (about 22 ms more, E4).

## 2. The close gate over a commit range ([requirement A4.4](../requirements.md#a4-4), [requirement A4.2](../requirements.md#a4-2))

The matrix says "PR check, red = fix". A pull request is one place a range of commits is examined. The check itself is a diff over a range against the coverage map of section 3, plus a search of that range's messages for the declaration of section 4.

- b1. **The range on GitHub.** For `pull_request`, "GITHUB_SHA … is the last merge commit of the pull request merge branch", and the head is `github.event.pull_request.head.sha` (t6); the base is `github.event.pull_request.base.sha` in the payload, which carries `base.sha`, `base.ref` and `body` (E8, on a public repository through `gh api`). GitHub's own path filters use "Three-dot diffs … between the most recent version of the topic branch and the commit where the topic branch was last synced with the base branch" for pull requests and two-dot diffs for pushes (t6). `git diff A...B` "is equivalent to git diff $(git merge-base A B) B" (t11). A checkout needs the base's history: t1's readme documents `initial-fetch-depth`, t7 asks for `fetch-depth: 0`; a clone of depth 1 cannot name `HEAD~1` at all (E3).
- b2. **How the base is known without a pull request** — the candidates and their failure modes, each tried in E3 on a repository with no remote, a fresh clone, a branch without upstream, a detached head, a shallow clone, and the kit itself:

| key | candidate | fresh clone | no remote (the kit) | detached head | shallow clone |
|---|---|---|---|---|---|
| b2.1 | an argument, `--since <ref>` | works | works | works | works to the depth fetched; past it `fatal: Not a valid object name` |
| b2.2 | `@{upstream}`, then the merge-base | works on the default branch (`origin/main`); on a new branch "fatal: no upstream configured" | "fatal: no upstream configured for branch 'work/task-close'" | no branch, so no upstream | as b2.1 |
| b2.3 | `git symbolic-ref refs/remotes/origin/HEAD` | `refs/remotes/origin/main` | "fatal: ref refs/remotes/origin/HEAD is not a symbolic ref" | works | works |
| b2.4 | `git merge-base --fork-point <trunk> <branch>` | found the fork point | needs a branch name; the kit has one | none | as b2.1 |
| b2.5 | a dial naming the trunk, default `main` | works when the name exists | works: the kit's `main` is local | works | works |

The page for b2.4 warns that "older reflog entries in your repository may be expired by git gc. If B0 no longer appears in the reflog … the --fork-point mode obviously cannot find it and fails" (t11). The kit today: no remote, `init.defaultBranch` is `main`, `main...HEAD` from this branch is one commit and eleven files (E4). On the trunk itself the range is empty — the moment for section 5's scan or a `--since HEAD~1`.

- b3. **The merge is the change.** After `git merge --no-ff`, `main...work/locations` is empty — the merge-base is the branch's tip (E4). The change that landed is the merge commit's first-parent diff: `git diff --name-only M^1 M` for the locations merge lists 34 paths, `modules/const-locations/MODULE.md` among them beside `modules/const-locations/scripts/locations_gate/*.py` — covered and updated in one range (E4). A range gate therefore takes either a base or a merge commit, and reads the merge's messages with `git log M^1..M`.
- b4. **Per commit or per change — the kit's own history decides** (E6, read-only): eight non-merge commits touched `shared/const_gate/**`, one of them without `shared/GATE.md` in the same commit — the extraction commit, whose message announced "documents and the record follow in the next commit"; of the commits touching a module's `scripts/` or `hooks/`, seven of eight for `const-catalogs`, five of fifteen for `const-meta-types`, four of eight for `const-decision-records`, two of sixteen for `const-referencing`, none of three for `const-locations` lacked that module's `MODULE.md`. At the granularity of a change — 23 merge commits on `main`, 24 covered (merge, pair) cases — 22 carried the document and two did not, both the `tooling-first-run` merge, a linter and type-checker pass over `const-meta-types`' scripts and the kit's own scripts with no document touched. A per-commit gate would have been red nineteen times on work the kit accepted; a per-change gate once, on a change that is either a real finding or a one-line no-impact declaration. The unit of the gate is the change: the kit's branch merged `--no-ff` under [dec-0032-work-starts-on-a-branch](../decisions/dec-0032-work-starts-on-a-branch.md), a pull request elsewhere.
- b5. **What a tool event could see.** A `PreToolUse` hook on `Bash` receives `tool_input.command`, "The shell command to execute", a string (the reference's example: `npm test`); nothing of the diff. The `if` field narrows it — `"Bash(git *)"` — "best-effort", since "When Claude Code can't determine which commands the Bash input runs, it runs your hook regardless". The commit E1d made was a `git add -A && git commit -m "$(cat <<'EOF' …)"` heredoc, which the table says is matched subcommand by subcommand. Such a hook could run the range check itself before the commit lands, from `cwd`, over `base...HEAD` plus the index. It would not see a commit made by a script, an editor or a human. It would fire on every `git` command of the session. A `PostToolUse` after the commit "Shows stderr to Claude; the tool already ran" — a report, no gate. Neither is the enforcement moment: the section 1 hook already meets the model at turn end, and the range check belongs where the range is complete.
- b6. **Git's own hooks, and what `--no-verify` skips** (t11, and E2 with a logging hook installed for each): a plain commit runs `pre-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit`; with `--no-verify` only `prepare-commit-msg` and `post-commit` — the page: `pre-commit` "can be bypassed with the --no-verify option", `commit-msg` likewise, `pre-merge-commit` likewise; `pre-push` "can be used to prevent a push", and `git push --no-verify` will "Toggle the pre-push hook" off ([git-push](https://git-scm.com/docs/git-push)); `prepare-commit-msg` "is not suppressed by the --no-verify option" but "should not be used as a replacement for the pre-commit hook"; `post-commit` "cannot affect the outcome of git commit". A `--no-ff` merge runs `pre-merge-commit`, then `prepare-commit-msg` and `commit-msg`; with `--no-verify`, `prepare-commit-msg` alone (E2). The kit relies on exactly this for its branch gate, `scripts/git-hooks/prepare-commit-msg`. But git hooks live in a clone's `.git/hooks`, never in a plugin — the kit needs `sh scripts/setup-clone.sh` per clone — so a module cannot ship one without a setup step of the consumer's. A check that reads YAML in `prepare-commit-msg` puts a Python start in front of every commit.
- b7. **Where the check runs, then.** Three moments, honestly priced:
  - (i) on demand and before the merge, by hand — `--since main` on the branch, the kit's practice for the referencing scan;
  - (ii) in CI on the pull request, `fetch-depth: 0`, `--since ${{ github.event.pull_request.base.sha }}`, exit 2 red;
  - (iii) at turn end, as a note of section 1's hook.

  A change merged by hand into `main` with neither is the backstop's gap, the same as every scan's.

**Recommendation: a Python script with a range mode — `--since <ref>` for a base, `--change <commit>` for a merge's first-parent diff — the base defaulting, when neither is given, through a chain whose every failure is a configuration failure naming the next step: the merge-base with `@{upstream}`, then with `origin/HEAD`, then with the trunk a dial names (`main` by default); run before the merge and in CI on a pull request; no `PreToolUse` hook on `Bash` (b5), no git hook shipped (b6); per change, never per commit (b4). CONFIRMED as a gate; the matrix's "PR check" is one place it runs, not its shape.** The scan mode of section 5 is the same check with the base derived. For the decider:

- **the order** of the default chain;
- **whether a** `--since` that names a ref the repository does not have is a configuration failure or a skip;
- **and whether the kit's own CI**, when it exists, runs it on `main` with `--change HEAD`.

## 3. The coverage map ([requirement A4.6](../requirements.md#a4-6), [requirement A4.4](../requirements.md#a4-4))

A dial in the module's own namespace mapping code territories to the current-state documents that describe them. The kernel's `current-state` row says such documents are "kept aligned with code at every task close" ([kernel §2](../constitution/CONVENTIONS.md#k2)). The map says which document is aligned with which code.

- c1. **How the surveyed tools state "if X changed, Y must too".** t5: one line per pattern, "a pattern that follows most of the same rules used in gitignore files", minus three — escaping `#`, `!` negation and `[ ]` ranges "do not work" — and "the last matching pattern takes the most precedence": a path resolves to one owner set. t6: `paths` and `paths-ignore` lists with `*` and `**`; "You cannot use both … for the same event"; with `!` "The order that you define paths patterns matters". t1: named filters, each a list of globs "evaluated using picomatch", `dot` set to true, an output per filter and a `${name}_files` list. t2: rules as JavaScript over `modified_files` — the shape of the rule is the author's. t3: no pattern at all — a file per change in `.changeset/`, and a bot that asks for it. t4: rules over the message's `footer`, none over files. t9: reviews in git notes; no file rules; dormant since 2023. No tool read pairs a code pattern with a document that must move with it: t2 lets one write such a rule, the rest gate on the presence of a file or a footer.
- c2. **The kit's dialect is already there.** Territories are gitignore patterns "evaluated against paths relative to the repository root" ([kernel §6](../constitution/CONVENTIONS.md#k6)). The shared `territory.Matcher` evaluates them with `git check-ignore` in a null repository and reports the deciding pattern per path. The `dials` part "offers the refusal of a pattern git would misread (`C5.7`), which a module that declares territories in its own dials calls for them too" ([kit-shared-gate-code §1](../../shared/GATE.md#g1)). The map's `code` side is a list of such patterns, matched against the range's paths. The paths need not exist, which is what the null repository is for. A deleted file in the diff still matches.
- c3. **`docs`: exact paths, not patterns.** With a path, "updated" is "this path is among the range's paths" and existence is checkable against the range's tip. With a pattern, "updated" would be "some path matching it changed" and there would be nothing to check the map against. The kit's documents have stable paths by the supersession rule of [kernel §1](../constitution/CONVENTIONS.md#k1). A document path that is also inside the pair's `code` patterns is excluded from the code side of that pair. A documentation-only change is never its own trigger.
- c4. **A `docs` path that does not exist** at the range's tip and is not among the range's paths is a configuration failure, not a finding: the map is wrong, not the change, and a finding would recur on every change and blame its author — the precedent is `C6`, "names root_policy … but no such file exists" ([kit-shared-gate-code §3](../../shared/GATE.md#g3)). A path the range deletes or renames counts as touched: the diff names it.
- c5. **Overlap is allowed, and is the point.** A policy territory must resolve a document to exactly one policy ([kernel §3](../constitution/CONVENTIONS.md#k3)); a coverage pair asks a different question — is this code described here? — and one file may be described in two places: the shared gate code by `shared/GATE.md` and, in its fit section, by a module's document; a module's scripts by its `MODULE.md` and by `CLAUDE.md`'s development routine. Two pairs claiming one path both apply; order carries no meaning, unlike t5's last match.
- c6. **Semantics, settled.** A change is *covered by a pair* when at least one of the range's paths matches the pair's `code`. It *updates the pair* when at least one of the pair's `docs` is among the range's paths. A covered pair that is not updated needs a declaration naming it (section 4), else it is a finding: what failed (the pair, the code paths that matched, the documents that did not move), why (the kernel's single act), the fix (update one of the documents, or declare no impact with the exact trailer). A change touching no `code` of any pair is green with the count of pairs examined.
- c7. **The kit's own map, as a proof of shape** (E7, the pairs a prototype used):
  - `shared/const_gate/**` → `shared/GATE.md`;
  - **for each module**, `modules/<name>/scripts/**`, `hooks/**`, `skills/**` → `modules/<name>/MODULE.md` — one entry per module, since a pattern has no capture;
  - `scripts/**` → `CLAUDE.md`;
  - `kernel/**` needs no pair, the kernel is the document.

  Six or seven entries. A per-pair `name` — kebab-case, unique — gives the declaration something to name and the count line something to list.
- c8. **Absent map.** No namespace, or an empty list: zero pairs examined, said so on the count line; install-and-run on an empty repository holds ([kernel §6](../constitution/CONVENTIONS.md#k6)).

**Recommendation: a list of named pairs, `coverage: [{name: <kebab>, code: [<gitignore patterns>], docs: [<repository-relative paths>]}]`, absent by default; `code` through the shared `Matcher` with the `C5.7` refusal, `docs` exact paths whose absence is a configuration failure; overlapping pairs allowed, order meaningless. Binding, validated at each read: CONFIRMED.** For the decider: whether `name` is required or defaults to the first document's path, and whether a pair may be declared `docs`-empty as a way to say "this code is described nowhere, and that is a finding on every change" — a sharper form of the defect rule than the kit needs today.

## 4. The no-impact declaration ([requirement A4.6](../requirements.md#a4-6); the open design decision)

- d1. **Trailer mechanics** (t11, E2). Trailers are "a group of one or more lines that (i) is all trailers, or (ii) contains at least one Git-generated or user-configured trailer and consists of at least 25% trailers", "preceded by one or more empty (or whitespace-only) lines", at the end of the message; "there can be no whitespace before or inside the `<key>`". A value "may be split over multiple lines with each subsequent line starting with at least one whitespace". Observed:
  - **a paragraph of** `No-Doc-Impact:` and `Co-Authored-By:` parses, both keys read;
  - **the same paragraph** with one colon-less line in it yields *nothing* — `Co-Authored-By` is not a Git-generated trailer, so clause (ii) does not rescue the block and clause (i) fails;
  - **a trailer above a later paragraph** is not read;
  - **a one-line message** has none;
  - **a folded value** comes back whole with `unfold`;
  - `%(trailers:key=No-Doc-Impact,valueonly,separator=%x1f)` returns every value of a repeated key, the key matched case-insensitively;
  - `git commit --trailer "No-Doc-Impact: …"` writes it;
  - **a** `trailer.<alias>.key` configuration shortens typing.

  A merge made with `-m` carries no trailer (E2). None of the kit's merges do, by [dec-0032-work-starts-on-a-branch](../decisions/dec-0032-work-starts-on-a-branch.md): the trailers stand on the branch's commits.
- d2. **Squash and rebase.** A rebase keeps each message. GitHub's squash writes "the commit title and message if the pull request contains only 1 commit, or the pull request title and list of commits if the pull request contains 2 or more commits", configurable to "just the pull request title, the pull request title and commit details, or the pull request title and description" (t10). E2 on the two-or-more shape: a trailer that ends up after the last bullet is read; one that sits between bullets is not — a per-commit trailer survives a squash only when its commit is the last, or when the setting keeps commit details and the trailer happens to close the message. A consumer that squashes needs the declaration where the squash keeps it.
- d3. **The pull request body.** `pull_request.body` is a string of the event payload (E8); `gh pr view --json body` returns it (t12); a `pull_request_template.md` "will fill the pull request body" (t10) — a checkbox line is the usual marker. In CI the body is at hand through `github.event`. Locally it is reachable only through the network and `gh`, and only once a pull request exists. Before it, and in the kit until rollout Phase D, there is no body.
- d4. **Scope: per change.** b4 of section 2 is the argument: the kit writes its documents in the commit after the code as a matter of course, and the range is what the gate examines. A declaration is one trailer anywhere in the range's commits — the shape of `Accepted:`, which `scripts/check-carry-lists.py` reads with `git log --format=%(trailers:key=Accepted,valueonly)` over the history and takes "The newest acceptance". Per commit would require the declaration on the very commit that touches the code, which the extraction commit of E6 shows is not how the kit works.
- d5. **What it carries.** The precedents: `Signed-off-by` (an identity), `Reviewed-by` (an identity), `Change-Id` (an opaque id), Conventional Commits' `BREAKING CHANGE: <description>` — a footer whose key holds a space and so is not a git trailer, which t4's rule set reads with its own parser; the specification says footers "follow a convention similar to git trailer format". A no-impact declaration has to name *what* is declared unaffected and *why*: `No-Doc-Impact: <pair name> — <reason>`, one trailer per pair, the name checked against the map (a name that is no pair's is a finding, not a declaration), the reason a free clause the gate requires non-empty and never judges. A path in place of the name would work too, and is what a consumer without names would write. The name is shorter and survives a document's rename. A wildcard — every covered pair at once — is what a lazy declaration would use; whether to allow it is the decider's.
- d6. **The honesty limit.** A declaration is a judgment the gate accepts on its face: the gate makes it explicit, searchable — `git log --format=%(trailers:key=No-Doc-Impact)` lists every one ever made — and reviewable in the pull request; it does not make it true. That is the class boundary of [law 5 of CLAUDE.md](../../CLAUDE.md#law-5): the presence and shape of the declaration is deterministic, its truth is review.
- d7. **What the kit needs today.** No pull request flow until Phase D ([rollout plan](../rollout-plan.md)); commits on `work/*` branches merged `--no-ff`; trailers already read by one kit gate. A trailer costs nothing new; a body marker has no body to live in.

**Recommendation: the commit trailer, per change — `No-Doc-Impact: <pair name> — <reason>`, one per pair, searched over the range's commits (`base..HEAD`, or `M^1..M`) with `%(trailers:key=…)`; the pull request body marker deferred, with its signal (a consumer that squashes, or a review that wants the declaration where the reviewer reads) and its precedence settled now: when both exist, either satisfies the gate, and the trailer is what the local run can see.** The decision itself is the decider's — the matrix names it so — and this is the recommendation with the reasoning. Left open with it: the key's exact spelling, and whether a wildcard value is allowed.

## 5. Doc↔code drift detection as a scan ([requirement A4.2](../requirements.md#a4-2))

The matrix: "detected by … scan — gate as flag; blocking is a dial". With no diff, what can a whole-repository scan see?

- e1. **Three candidates.** (i) The last-commit comparison per pair: the newest commit touching the pair's `code` is newer than the newest touching its `docs` and no declaration names the pair since — flag. (ii) A window, `git log --since=<date>`, the same comparison inside it. (iii) Nothing of its own: the scan is section 2's range check with the base derived (b2), and on the trunk with `--change HEAD`.
- e2. **What the timestamp heuristic gets wrong**, by construction and by E7 on the kit:
  - **it compares commits, not content** — a typo fix in the document resets the clock while the drift stays;
  - **"newer" needs an order**, and commit dates are not one (the prototype used `git merge-base --is-ancestor`, which two branches' commits may not satisfy either way — "unordered");
  - **a shallow clone has no history to compare (E3);**
  - **a rename of the document splits its history;**
  - **and the flag is not a finding of the change at hand but of the repository's past**, so it has no author to teach and no fix but "read both and decide".

  On the kit today every pair's document is newer than its code (E7: seven pairs, seven "docs newer"), which says only that the last thing anyone did was write. t7 shows the same signal used for display — "the date of the last git modification of a page", needing `fetch-depth: 0` — and t8 stamps the build time. Neither compares two things.
- e3. **What the range check already gives a scan.** With the base derived, a scan on a branch examines the branch's change; on the trunk, `--change HEAD` examines the last change landed — the merge, in the kit — and a loop over `--first-parent` merges audits a history change by change (E6 did exactly this: 23 merges, two covered pairs not updated, both in one merge). That is the defect rule as an audit: each merge either updated its documents, declared no impact, or is a finding with a commit to name.
- e4. **The count line.** `N pair(s) examined over M commit(s), <base>..<tip>` — the module's own tail for the shared `G1` and `F9` scan forms; with no pairs, `0 pair(s) examined — coverage is empty`.
- e5. **"Blocking is a dial."** In hook mode `severity` decides; the shared scan "ignores it and always blocks" (the kit's dials file, on `severity`). For a flag that is a real finding of the change at hand, exit 2 in CI is right. A timestamp flag would have needed a softer channel, which is one more reason not to build it.

**Recommendation: the scan is the range check with a derived base and, on the trunk, the last landed change — candidate (iii); the last-commit comparison (i) is deferred, its signal a consumer commit note that drift was found which no range had shown; count line as e4. CONFIRMED as a gate, with the flag being a finding of a change, never of a timestamp.** For the decider: whether the scan offers `--history <n>` to audit the last n merges as e3 describes, which the kit would use once, on its own history.

## 6. The stalled-drift assist ([requirement A4.3](../requirements.md#a4-3), [requirement A4.5](../requirements.md#a4-5))

"An active task-record whose scope sees no commits is stalled drift" ([kernel §2](../constitution/CONVENTIONS.md#k2)); the specification's dial: "active-task age alarm (optional)".

- f1. **What "scope" could mean where a record declares no files.** The kit's records declare none. The rollout plan is the one active task-record. Its policy says "a stretch with no commits in its scope is stalled drift" ([plc-0008-rollout-plan](../policies/plc-0008-rollout-plan.md), rule 1) without saying what the scope is. Candidates:
  - (i) commits touching the record file itself — for the plan, ticking a step is such a commit;
  - (ii) commits whose message names the record's id — the kit's messages name records often (E6: `dec-0033` in 24 messages on `main`, `dec-0030` in 17), but the plan's id appears in none;
  - (iii) a dial naming the record's territory in files — a second coverage map;
  - (iv) nothing.
- f2. **The kit's state** (E6): 35 decision records, all `inactive` — records are born `inactive` when applied in their own commit ([kernel §5](../constitution/CONVENTIONS.md#k5)); one active task-record, the plan, last touched today. An alarm would have nothing to say on the kit on the survey date, and no consumer exists to say it to.
- f3. **Its shape, if built.** A note of the scan, never a finding: `note: <record> is active and its file saw no commit in <n> days` — with (i) as the scope, an `active_age_days` dial, absent by default; a shallow clone cannot answer it (E3), so the note is skipped there and says so.

**Recommendation: deferred, with the signal named — a consumer commit note about a task-record left active, or a stretch of the kit's own plan with no commits — and the shape of f3 recorded so that it ships as a note in the scan when the signal comes. The matrix's "optional assist script" is thus honoured as optional; advisory CONFIRMED.** For the decider: whether the dial's key is reserved now in the module's namespace inventory, at its absent default.

## 7. The close skill ([requirement A4.5](../requirements.md#a4-5), [requirement A4.1](../requirements.md#a4-1), [requirement A4.3](../requirements.md#a4-3), [requirement A4.7](../requirements.md#a4-7))

- g1. **The procedure, from the kernel.** "Task close is a single act: changes are applied to code and to the affected current-state documents together; then the record is set `inactive` and its working files are deleted (git remembers)" ([kernel §2](../constitution/CONVENTIONS.md#k2)). "A document that nothing should reference is deleted" ([kernel §1](../constitution/CONVENTIONS.md#k1)). Skill prose in that order:
  - **read the coverage map** and the change's range, and name the documents the change owes;
  - **merge the deltas** into them;
  - **run the range check** of section 2 and read its verdict;
  - **delete** the working files;
  - **set** the record `inactive`;
  - **commit as one change**, the commit message naming the close.
- g2. **The boundary with the record skill.** The record skill of `const-decision-records` already says when a record is `inactive` — "`inactive` once it is applied. A record whose ruling is applied in the same commit that creates it is born `inactive`" ([record-decision](../../modules/const-decision-records/plugin/skills/record-decision/SKILL.md), step 3, item 5) — and its module reserves the moment: "When module `const-task-close` is installed, setting a record `inactive` at task close is its moment" ([const-decision-records MODULE.md §11](../../modules/const-decision-records/MODULE.md#t11), item 4). The close skill therefore *performs* the status change at close and the record skill *defines* it. Neither restates the other. With the kernel alone the close skill still works, since the status field is the kernel's ([kernel §1](../constitution/CONVENTIONS.md#k1)).
- g3. **Working files.** In the kit nothing tracked is a working file — `local/` is git-ignored (E4) and scratch work lives outside the repository — so the deletion step is empty here. A consumer's working files are a dial of patterns in the module's namespace, `working_files: [<gitignore patterns>]`, absent by default. The leftover check is then a line of the scan — `note: <n> working file(s) match working_files and are tracked` — a note, because whether a file is leftover is the closer's judgment, which is what the matrix's "gate-lite at close" concedes. With the dial absent, the skill asks the closer to name them.
- g4. **Commit before you edit** ([requirement A4.7](../requirements.md#a4-7)). The session rule of `CLAUDE.md` in skill prose:
  - **commit a dirty tree** before a batch of edits, commit again after a coherent change, never end a turn dirty;
  - **the reason** (rewind does not track edits made through Bash, scripts or subagents);
  - **and the exact** commands.

  One skill with two sections, or two skills: the close procedure is invoked at a task's end, the commit rule at every turn — a skill's description is always in context ([res-0005](res-0005-const-locations.md), section 1), so two short descriptions cost about what one long one does. The hook's block message of section 1 names the skill. A model that meets the hook for the first time finds the rule. The message itself carries the fix, as [law 6 of CLAUDE.md](../../CLAUDE.md#law-6) asks, and does not depend on the skill being read.
- g5. **What no skill can do.** Decide that a change had no impact (section 4, d6), or that a file is leftover (g3): judgment, labelled as such in the module's enforcement-honesty section.

**Recommendation: two skills, both advisory — `close-task` with the sequence of g1 and the boundary of g2, and `commit-before-edit` with g4 — plus a `working_files` dial read by the scan for the note of g3; no hook beyond section 1's. CONFIRMED as advisory, the leftover check as a note of the gate's scan rather than a gate of its own.** For the decider: one skill or two.

## 8. Fit with the shared gate code

Described, not decided; part names as in [kit-shared-gate-code §1](../../shared/GATE.md#g1), the interface as in [§2](../../shared/GATE.md#g2). The module would ship one gate with two faces: a `Stop` hook (section 1) and a range check with a scan (sections 2 and 5). What each part gives and what it lacks:

- h1. **`identity`, `cli`, `errors`, `preflight`, `output`.** As every gate: one `Identity`, `cli.run(argv, identity, load_modes)`, the single guard, the log. Nothing new — except the command line (s1).
- h2. **`events.read_event`.** Parses any hook payload into a `ToolEvent`; for a `Stop` payload `tool` is `None`, `tool_name` empty, `event_name` `Stop`, `cwd` and `session_id` filled (a3). It drops `stop_hook_active`, which the loop guard needs (a7). `pipeline.locate_write` would then return the skip "tool '' carries no file to examine" — right for a tool gate, wrong here.
- h3. **`pipeline.locate_scan`.** Takes a directory, finds the root, loads the dials, routes the log, returns `ScanTarget(root, dials)`: everything a range check needs before its own `git diff --name-only` and `git log --format=%(trailers…)`, which are the module's, as `const-catalogs`' history reads are its own.
- h4. **`dials`.** `Dials.own` hands the namespace over as read. `coverage`, `trunk`, `working_files` are parsed by the module into its own dataclass, with the `C5.7` refusal called for every `code` pattern ([kit-shared-gate-code §1](../../shared/GATE.md#g1), the `dials` row). `severity` and `log_dir` come validated. A gate that reads only its own dials builds no index and never asks for a root policy — `const-catalogs`' shape, `resolves_policies=False` in its `Subject`.
- h5. **`territory.Matcher`.** `match(patterns, paths)` over the range's paths per pair — the exact reuse c2 names; nothing to widen.
- h6. **`pipeline.report_hook`, `green_hook`, `report_scan`.** The scan forms fit with a count tail (e4). The hook forms assume a document: `f9_count_hook(n, rel)` says "1 document examined ({path})" — the `count` parameter already lets a module replace it — and `green_hook(what)` says "1 document examined, {what}", which no parameter replaces. The warn branch emits `additionalContext` (s3).
- h7. **`tests/harness`, `tests/shared_items`.** The `Subject` describes a gate driven by a `Write` it passes and one it blocks. The items S117–S131 and S142–S150 send tool events and read a document's verdict. A `Stop`-driven gate passes or blocks no write.

The strains, each with the rule of [plc-0009-shared-code](../policies/plc-0009-shared-code.md), rule 2, it must satisfy — "keeps a rule the part carries for all … and defaults to what the other modules pass":

- s1. **A second argument on the command line.** `cli.make_parser` knows `--scan [DIR]` only; the range check needs `--since <ref>` and `--change <commit>`. Two ways: a dial names the trunk and the scan derives everything (zero shared change; the explicit base of b2.1 is lost); or `cli.run` takes an optional list of module arguments added to the one parser, defaulting to none, so the guard, the misinvocation message and the one exit stay shared — the widening keeps "one guard" and defaults to what the others pass. A second entry point is not the answer: the interface reserves it for "a generator that changes files … never a gate".
- s2. **A locate for an event without a file.** A `pipeline.locate_event(output, stdin)` returning the root found from the event's `cwd`, the dials and the event's name — a sibling of `locate_scan` that reads the payload — keeps "one pipeline under a second event" ([kit-shared-gate-code §1](../../shared/GATE.md#g1)). `locate_write` is untouched. `ToolEvent` gains `stop_hook_active: bool | None`, `None` for every tool event, so the three gates change nothing.
- s3. **The warn channel on `Stop`.** `report_hook`'s warn branch writes `additionalContext`, which on `Stop` continues the conversation up to the cap (a6). The smallest widening: `report_hook` takes the event's name already; when it is `Stop`, the warn object carries `systemMessage` alone — one branch, the tool events unchanged. The alternative, a module-side JSON writer, duplicates the channel the shared code exists to hold.
- s4. **The green and count lines of a hook without a document.** `green_hook` and `f9_count_hook` need a form for "the working tree examined, clean" and "RED: 1 finding — the working tree examined ({n} path(s) dirty)". The `count` parameter covers the red form, and a `what` string that is a whole line — or a second function — the green one. A rule kept: `G1` stays the one green line; a default kept: the document form for every tool gate.
- s5. **The fixture `Subject`.** The twenty event-shaped items do not describe this gate. `event_driven=False` drops them at no shared cost and leaves the module to prove its `Stop` cases — clean tree green, dirty tree red, `stop_hook_active` lets go, warn as `systemMessage` only, `--since`, `--change`, a missing `docs` path, a declaration that names no pair — in its own items. It also drops S131, the warn channel, and the scan items S145–S146, which this gate has. The smallest new option is a `Subject.event` naming the hook event, default `PreToolUse`: when `Stop`, the harness feeds a `Stop` payload built from a `cwd` in place of a `Write`, and the paths-and-skips items give way to three of their own. A widening for "one fixture subject for a gate shaped differently", the phrase [kit-shared-gate-code §1](../../shared/GATE.md#g1) already has.
- s6. **A gate with two hook events?** No: one hook event, `Stop`; the range check is the scan face. `hooks.json` wires `Stop` alone, in the exec form with `args`.
- s7. **Timeouts.** The shared code was sized for a write. A `Stop` hook running `git status` (24 ms) and, if the decider adds it, the range check (22 ms) stays far under any timeout.

None of s1–s5 lets one module reach another; each keeps the rule it touches and defaults to today's behaviour. The order of size:

- **s2 and s3** are one function each;
- **s4** two lines;
- **s1 and s5** are interface widenings the kit gate `scripts/check-shared-links.py` does not see and the acceptance list would have to state.
