# Research comparison — the mutation score of each module (2026-11-11)

Surveyed 2026-11-11; local `claude --version` prints `2.1.286 (Claude Code)`. The survey reads no Claude Code page, since the mechanism is the kit's own tooling and no platform feature takes part in it. Experiments ran with Python 3.12.15, pytest 9.1.1, pluggy 1.7.0, pytest-xdist 3.8.0, execnet 2.1.2, coverage.py 7.16.2, PyYAML 6.0.2 and git 2.56.0, on macOS 27.0.1 (build 26A434) with 14 physical and 14 logical CPU cores. Other sessions used the machine: its load average stood between 3 and 8 before the runs. No live run with a model was made. The tools' pages were read in their source form (`curl -sfL https://raw.githubusercontent.com/<owner>/<repo>/<tag>/<path>`), GitHub's pages as Markdown (`https://docs.github.com/api/article/body?pathname=<path>`), and release dates from `https://pypi.org/pypi/<package>/json`. Every quotation below was checked against that text. A statement about a tool's behaviour is written only where the experiment that showed it is named, with the version tried. A tool read but not run is marked so.

Scope: one mechanism of the kit's own tooling, not a module's rows — how the mutation score of each module is measured. A mutant is a copy of a module's code with one small change. A test run kills it when a test fails, and it survives when every test passes. The score is the share of mutants killed. The survey answers four questions, one per section: which engine makes and applies the mutants, which tests run for each mutant, where and when the run happens, and whether a score turns anything red. It informs [item 9.27 of the rollout plan](../rollout-plan.md#s9-27), the work that R6 of [dec-0087-module-metrics-report](../decisions/dec-0087-module-metrics-report.md#r6) and R2 of [dec-0089-module-coverage-report](../decisions/dec-0089-module-coverage-report.md#r2) left open. Records that bind the shape: [dec-0091-module-fixtures-run-as-pytest](../decisions/dec-0091-module-fixtures-run-as-pytest.md) for how a module's tests run, and the two records above for the reports. Vocabulary: a gate and an advisory artifact in the sense of [law 5 of CLAUDE.md](../../CLAUDE.md#law-5). The kit's tooling is surveyed for fit in section 5. Sources by authority: the tools' documentation and source, PyPI, GitHub's documentation, experiments E1–E11. No earlier comparison covers this mechanism; every fact relied on here was read or run on the survey date.

## 1. The mutation engine (what makes and applies the mutants)

The question: which program makes the mutants of a module's own Python under `modules/<module>/plugin/scripts`, and applies each so that the module's tests meet it.

- a1. **The layout decides.** A module's tests reach its code two ways. They import the gate package in the pytest process, through the link `tests/<name>_gate`. And they run the gate as a child process: an `sh` entry that calls `python3 <entry>.py`. In [`const-questions`](../requirements.md#const-questions) the pytest process itself runs 51 of the 298 statements of the module's code. With the child processes counted, the tests run 287 (E1). So 236 statements, four in five, run only in a child. An engine whose mutant does not reach a child `python3` measures one fifth of the code.
- a2. **Two import routes, both ahead of `PYTHONPATH`.** The tests' folder goes first on the import path of the pytest process: pytest's default mode, `prepend`, inserts it at the beginning ([pytest's page](https://docs.pytest.org/en/stable/explanation/pythonpath.html)). A child puts its script's folder first, before the entries of `PYTHONPATH`, as Python does for a script ([sys.path](https://docs.python.org/3.12/library/sys.html#sys.path)). A changed copy of the package that is offered through `PYTHONPATH` is therefore never imported: with a copy on `PYTHONPATH` whose `checks.py` raises at import, five tests that run the gate passed (E5).
- a3. **cosmic-ray (t1).** Class: it rewrites the file on disk in place, runs one fixed shell command, and restores the file (`use_mutation` in its `mutating.py`, read; E2). A session is a SQLite file, which holds each mutant, its outcome and its diff. Since the file on disk changes, a child process meets the mutant: of a sample of 30, 29 were in code only a child runs, and 17 of those were killed (E2). It mutates module-level code. It made 451 mutants for `const-questions`. Its operator list holds 16 kinds: 132 replacements of one binary operator by another, 56 of a comparison, numbers, `not` added, `and` and `or` swapped, `break` and `continue` swapped, a loop of zero turns, a decorator removed, and more. It mutates no string, so it made none in `messages.py`. Each `+` becomes eleven mutants, one per other operator: 88 of the 451 come from eight `+` signs (E2). It reports through `cr-report`, `cr-html`, `cr-rate` and `cr-badge`. Its test command is one string for the whole session, so it cannot run other tests for another mutant. Parallel work needs its HTTP workers, each in a clone of a git repository ([its concepts page](https://github.com/sixty-north/cosmic-ray/blob/master/docs/source/concepts.rst), read, not run). Maintenance: 665 stars, last push 2026-11-10, two releases in the three days before the survey. It depends on 13 packages directly, among them aiohttp, SQLAlchemy and GitPython.
- a4. **mutmut (t2).** Class: it copies the code into a folder `mutants/`, where each function holds all its mutants behind a switch, a trampoline, that an environment variable sets. It runs pytest in its own process and forks once per mutant ([its README](https://github.com/boxed/mutmut/blob/3.8.0/README.rst): "Mutmut must be run on a system with `fork` support"). It mutates functions only: "If you want to mutate code outside of functions, you can try using mutmut 2". On the kit it made 550 mutants, none in the two entry files and none in `model.py`, whose code is all at module level (E3). Its copy turned the links of the tests' folder into real folders with no trampoline in them, so the pytest process would import unmutated code. The run then stopped before any mutant ran: the trampoline in a gate's child process loads mutmut's configuration from the child's working folder, a throwaway repository, and fails there; the run ended with `failed to collect stats. runner returned 1` (E3). Maintenance: 1,534 stars, last push 2026-11-07. It depends on six packages directly, among them libcst and textual.
- a5. **pytest-gremlins (t3).** Class: mutation switching inside pytest. It instruments the code once and an environment variable picks the active mutant ([its README](https://github.com/mikelane/pytest-gremlins/blob/v1.12.2/README.md): "Instrument once, toggle mutations via environment variable"). A `sitecustomize` file that it puts first on `PYTHONPATH` serves the instrumented code to a child interpreter (the docstring of its `spawn_hook.py`, read). It reached a child: all five mutants of `dials.py`, a file only a child runs, were killed (E4). It has five operator groups and made 107 mutants. Its coverage step returned no data for such a file and warned so; under the kit's `-W error` that warning ends the run with exit 1 (E4). A run over the whole module with four workers had printed no report when it was stopped, after 530 s in one run and 570 s in the next (E4). Maintenance: alpha by its classifier, 63 stars; its last five releases fall between 2026-10-17 and 2026-10-30.
- a6. **poodle (t4).** Class: it copies the source folder into a work folder, changes the copy, and runs a command with the copy first on `PYTHONPATH` (`runners/command_line.py`, read). With the module's script folder as the source, a2 applies: the copy is never imported. With the kit's root as the source, its copy left out the folder links of the tests, and its clean run failed with `ModuleNotFoundError: No module named 'constitution_layer_kit'` (E5). It has twelve mutators, strings among them, and made 89 mutants for `checks.py` alone. Maintenance: 6 stars; three releases in 2026 after none since 2024-02.
- a7. **mutatest (t5) and MutPy (t6).** Both fail to start on Python 3.12.15 (E6). mutatest changes only the bytecode cache ([its README](https://github.com/EvanKepner/mutatest/blob/master/README.rst): "only the ``__pycache__`` is changed"). Its last release is of 2022 and MutPy's of 2019.
- a8. **pytest-leela (t7).** Class: import hooks in the pytest process ([its README](https://github.com/markng/pytest-leela/blob/main/README.md)). On a scratch package its results were wrong both ways: three mutants of a tested function all survived, and three mutants of a module that only a child imports were all reported killed in 0.1 s, also when the child's test could not fail (E6). It was not run on the kit.
- a9. **The others of t13.** universalmutator rewrites source by regular expressions for any language. mutahunter asks a language model for mutants, under the AGPL. mutpy-pynguin, pytest-mutagen and xmutant have no release since 2021. None was run.
- a10. **A script of the kit's own (t8).** Class: it parses each file with `ast`, replaces the source text of one node, keeps the file's line count, and compiles the result; a mutant that does not compile is dropped (E7). It writes the mutant over the file in a copy of the kit, so a child meets it. Module-level code is mutated like any other. Fourteen operators made 329 mutants for `const-questions`, 125 of them strings (E7). It keeps each mutant under a stable name, `<file>:<line>:<column>:<operator>`, and each result as one line of JSON, so a stopped run goes on where it stopped. It needs nothing the kit's CI does not already pin: coverage.py and pytest.
- a11. **The engines disagree on the count.** For the same 650 lines the engines made 107, 329, 451 and 550 mutants (a3, a4, a5, a10). A score is a property of the operator set as much as of the tests.
- a12. **The bytecode cache.** Python loads cached bytecode when the source's "last-modified timestamp and size" equal those stored in the cache ([the import system](https://docs.python.org/3.12/reference/import.html#cached-bytecode-invalidation)). A mutant often has the size of the original, so an engine that rewrites a file twice within one second can meet the wrong bytecode. The prototype gives each text of a file a modification time of its own (E7). cosmic-ray's `mutating.py` sets none (read); its runs here took more than a second each, so the case did not arise.

Mechanism class: all are deterministic programs that report; none judges. cosmic-ray: mature, in beta by its classifier, and the one outside engine that ran whole on this layout; cost one pin with 13 packages behind it, and no choice of tests per mutant. mutmut and poodle: maintained, and stopped by the layout. pytest-gremlins: reaches a child, alpha, fast-moving, and it fails under `-W error`. mutatest, MutPy: dead on Python 3.12. The kit's own script: about 700 lines to own, with their operators, and nothing new to pin.

**Recommendation: a script of the kit's own on `ast`, which writes each mutant to the file in a copy of the kit; build, since the kit has no mutation engine.** Only two candidates reached the code a child runs and finished: cosmic-ray and the prototype (a3, a10). cosmic-ray cannot pick tests per mutant, which section 2 shows is worth a factor of five or more. It brings 13 packages for what 240 lines of `ast` do. The cost is real: the kit owns the operators, and a11 says that choice shapes the score. For the decider: whether to own that script or to pin cosmic-ray 8.7.0 and accept a whole pass per mutant, and which operators the script keeps; the string operator made 38% of the mutants.

## 2. Which tests run for a mutant, and how fast

The question: which tests run against each mutant, how the run is made fast, and what each shortcut costs in the score's truth.

- b1. **The whole module per mutant.** One pass of the tests of `const-questions` took 45 s (E1). With the whole module run for each mutant, stopped at the first failure, cosmic-ray took 25.5 s per mutant and the prototype 16.0 s, each on its own sample of 30 (E2, E7). The twelve modules hold 9,848 mutants by the prototype's operators (E10). At 16 s that is 44 hours of one process.
- b2. **Stop at the first failure.** Every run above already used `-x`. A killed mutant then costs the time up to the killing test. A survivor still costs the whole pass: 41 to 46 s each in E7. So the survivors set the cost.
- b3. **A per-test line map.** One run of the module's tests under coverage.py gives, for each line, the tests that run it, child processes included (E8). The pytest process switches coverage's context to each test's node id, through a plugin of 41 lines. A child takes its context from the environment variable `PYTEST_CURRENT_TEST`, which pytest sets to the running test ([pytest's page](https://docs.pytest.org/en/stable/example/simple.html#pytest-current-test-environment-variable)) and a child inherits. The rc file says `context = ${PYTEST_CURRENT_TEST-}`, and coverage.py expands environment variables there ([its config page](https://coverage.readthedocs.io/en/7.16.2/config.html)). The child must read the rc file itself. The run sets `COVERAGE_PROCESS_START` and does not use `patch = subprocess`: that patch hands the child the parent's settings already expanded (`_patch_subprocess` in coverage's `patch.py`, read). The map of `const-questions` took 67.0 s to build and held 355 lines.
- b4. **Only the tests that reach the mutant.** With the map, a mutant runs against the tests whose coverage reaches one of its lines, the quickest first, stopped at the first failure. The same 30 mutants took 82.8 s in place of 480.7 s, and each of the 30 had the same outcome (E7). A mutant of `const-questions` reaches 14 tests of 117 at the median, one of [`const-change-cost`](../requirements.md#const-change-cost) 6 of 77 (E8, E10). A survivor still runs every test that reaches it: 17.8 s on average in `const-questions`, 65 s in `const-referencing` (E9, E10).
- b5. **Lines that run outside any test.** Module-level code runs at import, during collection, in no test's context. A test can depend on such a line and never run it. The prototype runs every test for a mutant on such a line, the reaching tests first: 29 of the 329 mutants of `const-questions`, 135 of the 1,626 of `const-change-cost` (E8, E10).
- b6. **Mutants no test reaches.** A mutant on a line no test runs cannot be killed. It is counted as not covered with no run: 30 of 329 in `const-questions`, 178 of 1,626 in `const-change-cost` (E9, E10). The count can be too high where a child escapes coverage: one started with an environment of its own, as R1 of [dec-0089-module-coverage-report](../decisions/dec-0089-module-coverage-report.md#r1) says. The score is then too low, never too high.
- b7. **What the selection can cost.** A test that depends on a line through a value cached in another test's run would be missed. That error also lowers the score only. In E9 every one of the 53 survivors was run again against the whole module, and all 53 survived: the selection missed no kill.
- b8. **Copies side by side.** Each worker owns a copy of the kit and takes mutants from one queue. With eight copies, the unmutated tests ran in all eight at once, three times: 24 runs green, each in 46.6 to 50.7 s against 45 s alone (E9). All 246 mutants killed under that load were run again alone on a quiet copy: 246 stayed killed, 245 by the same test (E9). So the load made no false kill here. This is shown for one module on one machine; the shared items set a time limit in two places (`bounded` in `items.py` of the shared test code), which is where [dec-0091-module-fixtures-run-as-pytest](../decisions/dec-0091-module-fixtures-run-as-pytest.md) met failures under load.
- b9. **pytest-xdist inside one mutant's run.** A whole pass with `-n auto` took 8.7 s against 45 s (E1). It would add its workers' load to each run. That is the load which made CI run the tests one by one, the decider's reversal in the Choice of that record. It was not tried under mutation.
- b10. **A seeded sample with a time budget.** The prototype takes a sample size, a seed and a budget in seconds (E7). A sampled score is an estimate. Its standard error is `sqrt(p * (1 - p) / n)`: 6 points for 50 mutants at a score of 72%, 2.2 points for 400. A budget that stops the run early makes a sample too, of the mutants that came first.
- b11. **Shards over CI jobs.** One job per module is the natural shard, twelve jobs. A module can be cut further by the mutant's place in the list. GitHub allows 256 jobs in a matrix and, on the Free plan, 20 at once (p2).

Mechanism class: all are run-time choices of one deterministic runner. The whole module per mutant: simple, exact, and days of machine time. The line map: one more run per module, a plugin, and an error that can only lower the score. Worker copies: a proof per module that the unmutated tests stay green under the run's load. xdist inside a run: untried, against a ruling's reason. A sample: cheap, and a score with an error bar.

**Recommendation: the tests that reach the mutant's lines, from a per-test line map built once per run, stopped at the first failure; mutants no test reaches counted without a run; worker copies side by side, after three green rounds of the unmutated tests in every copy; build.** It measured `const-questions` whole in 3.8 minutes with eight copies, with no false kill and no missed kill (E9). No pytest-xdist inside a mutant's run (b9). A sample is the fallback for a module that does not fit its job, reported with its size and its error (b10). For the decider: how many copies a CI job runs; the load proof holds for one module on this machine, and a hosted runner has four cores.

## 3. Where and when the run happens, and where the score is read

The question: which workflow runs the measure, how often, how it is sized, and where a person reads the score.

- c1. **What the records say.** R5 of [dec-0087-module-metrics-report](../decisions/dec-0087-module-metrics-report.md#r5) keeps the mutation score out of a step that runs on every change. R6 names a scheduled workflow. R4 of [dec-0089-module-coverage-report](../decisions/dec-0089-module-coverage-report.md#r4) put the coverage report into the workflow `gates`, on every change, and narrowed that R5 to the mutation score.
- c2. **The size of the work.** `const-questions` took 3.8 minutes with eight copies here, and its runs summed to 1,521 s (E9). For `const-change-cost`, the largest module, a sample of 50 gives 5.2 s per mutant and so 141 minutes of one process for its 1,626 mutants; two standard errors either way give 62 to 219 minutes (E10). For [`const-referencing`](../requirements.md#const-referencing), whose tests are the slowest, a sample of 40 gives 13.4 s per mutant and so 286 minutes for its 1,278 mutants, 81 to 490 at two standard errors (E10). The survivors set that cost: seven of the 40 took 455 of the 537 seconds. On the kit's CI the tests of a module, one by one under coverage.py, took 61 to 171 s, against 65 to 157 s for three like runs here (E11, E8, E10). So a hosted runner is not much slower per process. It has four cores (p1).
- c3. **A job per module, and the limit.** A job on a hosted runner may run six hours (p2). By the samples, one process needs about two and a half hours for the largest module and nearly five for the slowest, whose upper estimate passes eight. So one process per job does not hold every module. Two or three copies in a job do, and so do two jobs for the slowest module (b11). Twelve jobs, one per module, fit under the 20 jobs a Free plan runs at once.
- c4. **Cost.** The kit's repository is public, and "Use of the standard GitHub-hosted runners is free and unlimited on public repositories" (p1).
- c5. **A schedule's limits.** A scheduled workflow runs on the default branch only, can start late, and is switched off after 60 days without repository activity (p3). `workflow_dispatch` starts it by hand and is not bound to the schedule.
- c6. **Where the score is read.** A step can write a table to the run's summary, at most 1 MiB per step (p5). An artifact holds the JSON; artifacts and logs are kept 90 days by default, and a public repository can set 1 to 90 (p4). The coverage report of [dec-0089-module-coverage-report](../decisions/dec-0089-module-coverage-report.md) is read the same two ways, in the job `gates` of each run.
- c7. **A file in the tree.** A committed score file needs a pull request for each run, since the ruleset of `main` asks one of every change and has no one on its bypass list ([CLAUDE.md](../../CLAUDE.md), the bullet "The shared `main`"). The file would also be stale after the next change to the module.
- c8. **On every change.** The measure of the smallest module took minutes with eight cores. On every pull request it would cost each of the twelve module jobs from minutes to hours. The records of c1 rule that out.

Mechanism class: a GitHub Actions workflow, a report. A schedule of its own with `workflow_dispatch`: no pull request waits for it, numbers trail the changes by the schedule's period, one more workflow to keep. The workflow `gates`: ruled out by c1 and c8. A committed file: a pull request per run.

**Recommendation: a workflow of its own, on a weekly schedule and on `workflow_dispatch`, one job per module with two or more worker copies, each job writing its table to the run's summary and its JSON as an artifact; CONFIRMED against R6 of [dec-0087-module-metrics-report](../decisions/dec-0087-module-metrics-report.md#r6) and R2 of [dec-0089-module-coverage-report](../decisions/dec-0089-module-coverage-report.md#r2).** The limits leave room where a job runs two or more copies (c3 to c6), and nothing waits for the run. The report stands apart from the coverage report, which belongs to each change's own run. For the decider:

- **the period;**
- **whether a job that finds its unmutated tests red under load reports no score or fails;**
- **whether the slowest module is split over two jobs;**
- **and the count of copies per job, which no experiment here ran on a hosted runner.**

## 4. Whether a score turns anything red

The question: what a threshold on the score would need to be honest. Facts only; the choice is the decider's.

- d1. **Equivalent mutants.** Some mutants change no behaviour, and no test can kill them ([Mutation testing](https://en.wikipedia.org/wiki/Mutation_testing), section on equivalent mutants). Of the 53 survivors of `const-questions`, a reading of the code finds 13 equivalent: 4% of all its mutants (E9). The best score any tests could reach there is about 96%, and the number differs per module.
- d2. **Text built on both sides.** The tests build many expected lines with the gate's own functions and its identity. A mutant of such a value changes both sides alike and survives: 3 of the 53 (E9). The tests also type each message by hand once, by R8 of [dec-0091-module-fixtures-run-as-pytest](../decisions/dec-0091-module-fixtures-run-as-pytest.md#r8). That is what killed the other string mutants: 86 of the 125.
- d3. **Real gaps.** 36 of the 53 survivors point at something no test holds (E9). That list, not the percentage, is what a person can act on.
- d4. **Sampling noise.** A sampled score moves by its standard error from run to run with no change in the code: 6 points at 50 mutants (b10).
- d5. **Flaky kills.** A test that fails under load would count as a kill. None was found in 246 (E9), on one module and one machine.
- d6. **The operator set.** Engines made from 107 to 550 mutants for the same code (a11). A change of the operators moves the score with no change in the tests.
- d7. **What other projects do.** Stryker's `thresholds` default to `{ high: 80, low: 60, break: null }`, and its page says: "Set `break` to `null` (default) to never let your build fail." PIT has a `mutationThreshold` and warns beside it: "Please bear in mind that your build may contain equivalent mutations. Careful thought must therefore be given when selecting a threshold." cosmic-ray's `cr-rate` takes `--fail-over` and can test it against a confidence interval (its `--help`, read in E2's environment). poodle takes `--fail_under` ([its README](https://github.com/WiredNerd/poodle/blob/main/README.md)). mutmut's README names no threshold. Google reports mutants on changed lines at code review, leaving out lines without coverage, and no score ([State of Mutation Testing at Google](https://research.google/pubs/state-of-mutation-testing-at-google/), abstract).
- d8. **What the kit's law asks.** A report that judges nothing is never dressed as a gate ([law 5 of CLAUDE.md](../../CLAUDE.md#law-5)). R1 of [dec-0089-module-coverage-report](../decisions/dec-0089-module-coverage-report.md#r1) says "No number is a threshold, and no check holds one". R1 of [dec-0087-module-metrics-report](../decisions/dec-0087-module-metrics-report.md#r1) says the same of the metrics.

Mechanism class: a threshold is a gate on a number; a report is advisory. An honest threshold would need the equivalent mutants named and left out per module, a whole run and no sample, the operator set frozen, and the load proof of section 2 for every module.

**Recommendation: the score is a report and turns nothing red; a threshold is not needed.** Each of d1 to d6 moves the number for a reason other than the tests' strength. The survivors' list carries what a person can use (d3). For the decider: whether the report lists survivors by name, which the prototype does, and whether a survivor judged equivalent is marked so in the tree or left in the list.

## 5. Fit with the kit's tooling

How the measure would sit beside what the kit already runs, part by part, and each strain; described, not decided.

- f1. **`run_runner` of `scripts/check-aspects.py`.** It builds the pytest command of a module and runs the tests whole. A mutation runner needs its own command: the same flags, `-x`, and a plugin that keeps the chosen tests. R9 of [dec-0091-module-fixtures-run-as-pytest](../decisions/dec-0091-module-fixtures-run-as-pytest.md#r9) says the gate list and CI run a module's tests only through `scripts/check-aspects.py --run --module`, which selects none. A report that runs chosen tests in a workflow strains those words.
- f2. **`scripts/check-gate-lists.py`.** It holds that `scripts/gate-list.sh` and the workflow name pytest only in an exact pin (its docstring at `c35438a8`). A new workflow that calls a kit script, which builds the command itself, names pytest nowhere. Whether the check reads a second workflow file was not tested.
- f3. **[`scripts/kit_coverage.py`](../../scripts/kit_coverage.py).** It runs coverage with `patch = subprocess` and a `python3` shim first on `PATH`. The line map needs the other route, `COVERAGE_PROCESS_START` (b3), and the same shim idea where the runner's `python3` is not the first on `PATH`. The two rc files differ, so the map is a run of its own, not the coverage run of the job `gates`.
- f4. **The shared harness.** `Harness.environment` hands a gate's child the runner's environment, so `PYTEST_CURRENT_TEST` and `COVERAGE_PROCESS_START` reach it (E8). It puts a `sitecustomize` of its own last on `PYTHONPATH`. The map uses coverage's `.pth` file and no `sitecustomize`, so the two do not meet. pytest-gremlins would shadow that file with its own and chain to it (a5).
- f5. **The kit's rules for a report.** R1 and R3 of [dec-0087-module-metrics-report](../decisions/dec-0087-module-metrics-report.md#r1) shape a report script: named for what it reports and never `check-`, no entry of the gate list, exit 0 whenever it can read its inputs. A mutation runner writes files in copies, so it needs a scratch folder outside the tree, as the kit's worktree rule asks.
- f6. **The probe runner.** The agent `mutation-probe-runner` of `.claude/agents/` runs hand-picked mutations at a module's review. The measure here is the mechanical half of that work and replaces none of it: a reviewer's probes aim at the change under review.
- f7. **The pins.** The workflow pins coverage.py 7.16.2 and pytest 9.1.1 ([gates.yml](../../.github/workflows/gates.yml)). The prototype ran on exactly those and adds no package.

## 6. Platform facts, re-verified, and discrepancies

The platform here is GitHub Actions, coverage.py, pytest and Python; each fact was read or run on 2026-11-11.

- p1. **A hosted Linux runner of a public repository has 4 CPUs, 16 GB of memory and 14 GB of disk, and is free.** [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), the table for public repositories and the sentence quoted in c4; [billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions). Breaks: the sizing of section 3, and its cost of nothing.
- p2. **A job runs at most 6 hours; a matrix makes at most 256 jobs; a Free plan runs 20 jobs at once.** [Actions limits](https://docs.github.com/en/actions/reference/limits): "Each job in a workflow can run for up to 6 hours of execution time." Breaks: one job per module, if the largest module outgrows the limit.
- p3. **A schedule runs on the default branch, may be late, and stops after 60 days without activity.** [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule): "Scheduled workflows will only run on the default branch", and "In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days." Breaks: a weekly score, silently, in a quiet repository.
- p4. **Artifacts and logs are kept 90 days by default; a public repository can set 1 to 90.** [Managing GitHub Actions settings for a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository). Breaks: how far back a score can be read.
- p5. **A step's summary holds at most 1 MiB.** [Workflow commands](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands): "each step is restricted to a maximum size of 1MiB". Breaks: a survivors' list of a large module, which then belongs in the artifact.
- p6. **pytest sets `PYTEST_CURRENT_TEST` to the node id and the stage.** pytest's page at 9.1.1; E8. Breaks: the child half of the line map.
- p7. **coverage.py expands environment variables in its rc file, `${WORD-default}` included.** Its config page at 7.16.2; E8. Breaks: the same.
- p8. **`coverage.process_startup()` starts coverage in a process when `COVERAGE_PROCESS_START` names an rc file.** [Its page on subprocesses](https://coverage.readthedocs.io/en/7.16.2/subprocess.html). Breaks: the same.
- p9. **`patch = subprocess` passes the parent's settings, already expanded.** `_patch_subprocess` and `CoverageConfig.serialize` in the installed 7.16.2, read. Breaks: nothing while the map avoids the patch; were the patch to pass the file's name, the map could use it.
- p10. **Another tool may set coverage's context through `Coverage.switch_context`.** [Its contexts page](https://coverage.readthedocs.io/en/7.16.2/contexts.html); E8. Breaks: the pytest-process half of the map.
- p11. **Python validates cached bytecode by the source's time and size.** The page quoted in a12. Breaks: nothing in the prototype, which changes the time with each text.
- p12. **The tests' folder and a script's folder come before `PYTHONPATH`.** E5. Breaks: were it otherwise, poodle's copy would reach the gate.

No earlier comparison covers this mechanism, so none is stale. Where a page and what was seen differ:

- a. **The `.pth` file.** coverage's page tells the reader to create a `.pth` file that calls `process_startup`. The installed 7.16.2 already holds one, `a1_coverage.pth`, in the environment's package folder, and the child processes of E8 were measured with no file added. It changes no design; the build should not write a second file.
- b. **cosmic-ray's `Lt_Is` and its like.** Its operator list replaces `<` by `is`, and `%` on a format string by `//`. Such mutants were made and run (E2). Nothing in its pages says so; it is one reason its count differs.
- c. **pytest-gremlins and warnings.** Its README names no clash with `-W error`. E4 met one.

## Recommendations summary

1. The mutation engine — **build**: a script of the kit's own on `ast` that writes each mutant to the file in a copy of the kit. Of the seven outside tools, only cosmic-ray ran whole on the kit's layout, and it cannot pick tests per mutant (a3 to a10).
2. Which tests run for a mutant — **build**: the tests that reach the mutant's lines, from a per-test line map that holds the child processes, stopped at the first failure, in worker copies side by side after three green rounds; 3.8 minutes for `const-questions`, no false kill, no missed kill (b3 to b8, E9).
3. Where and when — **CONFIRMED**: a workflow of its own, weekly and on request, one job per module, the table in the run's summary and the JSON as an artifact. A job's six hours hold every module only with two or more copies in the job, or with the slowest module split (c2 to c6).
4. A red on the score — **not needed**: the score is a report. Equivalent mutants, text built on both sides, sampling, load and the operator set each move it for a reason other than the tests (d1 to d8).
