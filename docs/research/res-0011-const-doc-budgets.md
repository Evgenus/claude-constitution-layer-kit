## 1. The length check, its moment and its ladder ([requirement A11.2](../requirements.md#a11-2), [requirement A11.3](../requirements.md#a11-3))

- a1. **What the check is.** A document's length is one number per file, computed from the file alone. The check compares it with a ceiling. It needs no parser and no external binary: the whole scan of the kit's 128 Markdown files took 0.19 to 0.21 s in three runs of a 5-line Python script (E11). The kit's scan-only style gate, which reads the same files, took 0.57 s (E11). The check is deterministic by construction, so the matrix's class "gate" fits it.
- a2. **Candidate A: a scan alone,** as module [`const-styling`](../requirements.md#const-styling) is built. Mechanism class: a repository script run by hand or in CI. Maturity: the kit's own pattern, shipped. Cost: the least code, and no hook entry. What it cannot do: tell the model at the moment it makes a document longer. The model learns of the excess only when someone runs the scan. A document the model writes in one session may cross its ceiling several times before then.
- a3. **Candidate B: a `PostToolUse` hook after `Write` and `Edit`,** as module [`const-language`](../requirements.md#const-language) is built. Mechanism class: a platform hook plus a repository script. Maturity: the kit's own pattern, shipped. The platform runs the hook "After a tool call succeeds", and its exit 2 "Shows stderr to Claude; the tool already ran" (t1, hooks page). This is post-hoc in the specification's sense: the write stands, and the model is told the length at once. What it cannot do alone: see a file written by a shell command, a human's editor or a merge (limit 1 of [kit-shared-gate-code §4](../../shared/GATE.md#g4)). The scan is the backstop, so B never stands alone.
- a4. **Candidate C: both,** the hook for the moment and the scan as its backstop and as "in CI". Cost: one more mode over the same check; the shared code already carries both modes (section 7). This is the shape of module [`const-language`](../requirements.md#const-language).
- a5. **Candidate D: a pre-write gate** on `PreToolUse`, blocking a write that leaves a document over its ceiling. Rejected. The specification says "post-hoc". A whole-document ceiling blocks every partial fix: an edit that shortens an over-long document by half its excess would be refused. A variant blocks only a write that makes an over-long document longer, a ratchet. It is deterministic, but it depends on the reconstruction of an `Edit` (limit 4 of [kit-shared-gate-code §4](../../shared/GATE.md#g4)). Nothing in the rows asks for it.
- a6. **The ladder and the shared `severity` dial do not map one to one.** [Template §7](../../module-template/MODULE.md#t7) gives every hook gate the dial `severity`, `block` or `warn`, and says the scan "ignores the dial and always reports". With `severity: warn` alone as the warn rung, the scan would still be red on every ceiling during the first month. CI would then block before a month of data exists, which the amended [requirement A11.3](../requirements.md#a11-3) forbids. The ladder therefore needs a level per ceiling, as module [`const-language`](../requirements.md#const-language) has a level per rule in its `levels` dial. There, `error` is a finding and red, and `warning` is a note that is never red. The two dials then do two jobs. The per-ceiling level says whether an excess is a finding at all. The shared `severity` says how a finding travels after a write: exit 2 under `block`, `additionalContext` under `warn`.
- a7. **A warning after a write must travel as `additionalContext`.** The hooks page says: "For most events, Claude Code writes stdout to the debug log and doesn't show it in the transcript." The exceptions it lists are `UserPromptSubmit`, `UserPromptExpansion`, `SessionStart` and `PostModelSwitch`; `PostToolUse` is not one of them (t1, hooks page). The shared `green_hook` prints its notes as plain stdout (read in `shared/const_gate/pipeline.py` at `82a219c`). A warning-level excess printed as a note after a write would therefore reach the debug log and not the model. It must go out through the warn channel of `report_hook`, whatever `severity` says. Section 7 names this strain, and x2 names what it means for the sibling.
- a8. **Four ways to carry the amended month rule.** L1: a `level` per ceiling, `warning` or `error`, set by hand; review alone holds the month. L2: a `level` per ceiling plus the window of data the ceiling was set from, declared in the dials as two dates. The gate refuses `level: error` as a configuration failure when the window is shorter than a month. L3: a date per ceiling from which it blocks, compared with the clock. L4: a window the gate derives itself from git history, such as the first commit that added the ceiling.
- a9. **L3 and L4 break determinism or break in CI.** Under L3 the same tree is green one day and red the next with no commit between them. A re-run of an old commit then gives a new verdict. No verdict of any kit gate reads the clock today: at `82a219c` the only clock read in the shared code and the module scripts is the timestamp of the output log (E15). Under L4 the verdict depends on how much history the checkout holds. A shallow clone holds one commit (E12), and GitHub's checkout action fetches "Only a single commit" by default (t12). L4 would need its own configuration failure there, and a walk of history on every write.
- a10. **L2 is deterministic and needs nothing but the dials.** The rule becomes a check of the dials file, in the matrix's class "config": malformed is a configuration failure, at every read. PyYAML reads an unquoted `2026-09-14` as a date object and a quoted one as a string (E14), so the parser takes both. What "a month" means must be stated once: from 2026-09-14, one calendar month ends on 2026-10-14 (E14). A start on the 31st needs a stated rule, for example the last day of the next month. The dates are declared, not proven. Whether the window is true stays with review, which is the class the matrix already gives [requirement A11.3](../requirements.md#a11-3).

**Recommendation: C, a `PostToolUse` hook on `Write|Edit` and a scan, with the ladder carried as L2 — CONFIRMED, "gate: script, warn → block per dial (ladder)", with the ladder built per ceiling.** The hook tells the model at the write, and the scan is the backstop and the CI run. Each ceiling carries its own `level`, `warning` or `error`, and the window of data it was set from; the gate refuses `error` on a window shorter than a month. The shared `severity` keeps its one meaning, the channel of a finding after a write. A warning-level excess leaves the hook through `additionalContext` (a7). For the decider:

- **what "a month" is** (a calendar month, or a fixed count of days);
- **and whether L1 is enough**, leaving the month to review, at the cost of a rule that no check holds.

## 2. The key of a ceiling ([requirement A11.2](../requirements.md#a11-2), [requirement A11.3](../requirements.md#a11-3))

- b1. **Candidate A: path patterns in the module's own namespace.** Each ceiling is an entry with a name, `paths` in the dials file's dialect, a number, a level and a window. It reads nothing outside its namespace, save the kernel-owned `territory_dialect` that every pattern reader needs ([kernel §6](../constitution/CONVENTIONS.md#k6)). It reaches no sibling, so [law 3 of CLAUDE.md](../../CLAUDE.md#law-3) holds. It works on an empty repository with its defaults, so [law 2 of CLAUDE.md](../../CLAUDE.md#law-2) holds too. Mechanism class: dials of the module, matched by the shared `Matcher`. Maturity: the pattern of the `departures` of module [`const-styling`](../requirements.md#const-styling) and of the `territories` of four shipped gates. Cost: a kind's pattern is written twice, once as the policy's territory and once as a ceiling's paths.
- b2. **The double pattern costs nothing in YAML.** The kit's dials file already names one territory twice by an anchor and an alias. The catalogs of module [`const-catalogs`](../requirements.md#const-catalogs) point at `*decisions`, `*policies` and `*research`. The `guides` of module [`const-styling`](../requirements.md#const-styling) point at `*style`. A ceiling can write `paths: *research`: the patterns stay one text, and the module still reads only its own key. A consumer without anchors writes the patterns out, and a policy's move then needs two edits.
- b3. **Path patterns reach what no policy governs.** At `82a219c`, 40 of the kit's 128 Markdown files lie in no policy's territory (E2). Among them are `CLAUDE.md` at 20,223 characters, which the platform loads into every session, thirteen skills up to 7,869, and eleven install notes up to 7,824. A ceiling keyed by path covers them; one keyed by kind or by meta-type cannot, or only by the accident of a type field.
- b4. **Candidate B: the document kind, through policy resolution.** A ceiling is keyed by a policy's id, and the gate resolves each document to its policy through the root policy and every policy namespace. The kernel lets a module read those keys when it resolves territory ([kernel §6](../constitution/CONVENTIONS.md#k6)), and the shared `index` and `resolution` do it. Cost: the gate becomes one that resolves policies, needs a root policy, and meets the resolution defects that module [`const-meta-types`](../requirements.md#const-meta-types) already reports. It misses the 40 files outside every territory (b3). A renamed policy leaves a ceiling keyed by a dead id. This is the option the decider's standing preference ranks below a module that reads only its own namespace.
- b5. **Candidate C: the meta-type, from the envelope's `type`.** One ceiling per meta-type is the literal reading of "one per meta-type at most". It reads no dials beyond its own, only the envelope of each document through the shared `envelope` part. Two costs appear in the kit's tree (E2, E10). First, five templates carry the `type` of what they make: `templates/decision-record.md` is a `task-record`, `module-template/MODULE.md` a `current-state` document. Thirty-four files carry no `type`, `CLAUDE.md` among them. Second, one ceiling per meta-type is loose for the small kinds. The current-state documents run from 2,594 to 59,112 characters. A ceiling at the largest plus ten percent, 66,000, would leave the kernel 5.4 times its length and the intent page 9.4 times (E10). Seventeen of the 29 current-state documents lie below a third of it.
- b6. **Candidate D: path patterns with an optional filter on the meta-type.** Candidate A, where an entry may also name a `type`, read from the envelope. It stays inside the module's namespace for its dials and adds one envelope read per document. Nothing in the kit's data asks for it today: every group of E10 is a path group.
- b7. **"One per meta-type at most" under path keys.** The row caps the number of ceilings, not what keys them. Under candidate A, three entries whose `paths` list the kinds of each meta-type are that cap in its literal form. More entries are allowed by the key, and whether they are wise is review. The count cannot be checked by the gate without reading envelopes, so it stays with review, the class the matrix gives the row.
- b8. **Two ceilings over one document.** Under candidate A an entry may overlap another. Three readings exist: every matching ceiling applies, and the lowest decides; the first entry in the list wins; an overlap is a configuration failure. The first reading needs no order and no scan of the whole tree. The third can be seen in hook mode for the written file only. A frozen range that needs a higher number is then served by a departure (section 4), not by a second ceiling.

**Recommendation: A, path patterns in the module's own namespace — build.** It is the only key that reads nothing but the module's own dials, that reaches `CLAUDE.md` and the skills, and that fits a kind exactly through a YAML alias of the policy's territory. Every matching ceiling applies (b8). The default is no ceiling, since any shipped number would be a target from no data. The gate then examines nothing. It says so in one `SessionStart` line, as the hook row of [template §6](../../module-template/MODULE.md#t6) asks of such a gate, a rule of [dec-0042-interaction-module-rulings](../decisions/dec-0042-interaction-module-rulings.md). For the decider: whether "one per meta-type at most" stays as the start of the calibration (three entries) or the row's wording changes with the amendment already ruled; and the overlap reading of b8.

## 3. What a character is ([requirement A11.1](../requirements.md#a11-1))

- c1. **Five counters give five numbers on the same bytes (E1).** A family emoji built from three people and two joiners is 5 code points (Python `len`, Node's spread string, `wc -m` under `en_US.UTF-8`). It is 8 UTF-16 units (Node's `String.length`), 18 bytes (`wc -m` under `LC_ALL=C`, which counts bytes, and `wc -c`), and 1 grapheme cluster (`regex`, `Intl.Segmenter`). A Cyrillic word of six letters is 6 code points and 12 bytes. The word "café" is 4 code points when its accent is one character (NFC) and 5 when it is a letter plus a combining mark (NFD). A line ending CRLF is two code points and one grapheme cluster.
- c2. **Grapheme clusters change with the Unicode version.** An Indic conjunct of three code points is 2 clusters under the grapheme library's Unicode 13.0.0 and 1 under `regex` and under Node's Unicode 16.0 (E1). Python's standard `re` has no `\X` (E1), so clusters need a library the gate would have to declare and preflight. Code points do not change between Unicode versions.
- c3. **Bytes punish every language but English.** A Cyrillic document of 30,000 characters and an English one of 60,000 get the same verdict from a byte counter (E6). The kernel's reason for characters, that a tokenizer "silently" redefines a token ceiling, holds for bytes against non-Latin scripts in the same way.
- c4. **In the kit's tree the counters agree.** At `82a219c` the 128 Markdown files hold 1,878,389 code points and 1,889,040 bytes. Grapheme clusters equal code points in every file, and no file holds a CRLF (E2). The largest share of bytes over code points in one file is 1.08 percent. The choice of definition decides nothing in the kit today; it decides for a consumer who writes in another script, or on another platform.
- c5. **Line endings.** Under `core.autocrlf` a Windows checkout turns each LF into CRLF, so a count of code points "as on disk" would differ by one per line between two machines. Limit 9 of [kit-shared-gate-code §4](../../shared/GATE.md#g4) states the kit's aim that one repository gets one verdict everywhere. Counting a CRLF as one character keeps that aim, and changes nothing in a tree that has no CRLF.
- c6. **What the count should cover.** At `82a219c` the envelopes are 1.7 percent of all characters, fenced code 0.9 percent, HTML anchors 0.4 percent and link targets 6.3 percent (E2). Taking out any of them needs a Markdown parser, and parsers differ on what they take out. Vale's `characters` counts the prose alone. It gives 3,178 for the requirements document of 28,103 characters, whose rows are tables (E8). The model loads the whole file when it reads one, envelope and URLs included. A whole-file count can be repeated with `wc -m` under a UTF-8 locale and with `len` in any language.
- c7. **How other tools define it.** `check-added-large-files` counts kilobytes (E6), `textlint-rule-max-number-of-lines` counts lines (E7), ESLint's `max-lines` counts lines (t11, read), Vale's `characters` counts prose (E8), and webpack's `maxAssetSize` counts bytes (t11, read). The Claude Code pages speak of characters for the hook output cap and the skill listing (section 6) without saying which unit of Unicode they count (t1).
- c8. **The shared code already counts code points.** The shared `shown` cuts a value by Python `len` and prints its length as "characters", and the column of a YAML error is counted the same way (read in `shared/const_gate/messages.py` at `82a219c`). The shared `read_text` opens a file as text with `errors="replace"` (read in `shared/const_gate/repository.py`). So it already reads a CRLF, and a lone CR, as one LF. A byte-order mark stays as one character, and each invalid UTF-8 sequence becomes one replacement character (E1).

**Recommendation: a character is one Unicode code point of the file read as UTF-8, a CRLF counted as one, nothing normalized and nothing left out — CONFIRMED as definitional, the definition stated once in the module's document and repeated by no one else.** It needs only the standard library, it does not move with Unicode versions, it treats every script alike, and it matches what the shared code already counts. The shared `read_text` already gives this count, save one choice (c8). An invalid UTF-8 sequence is counted as one character there, where a strict reading would refuse the file. For the decider: whether an invalid sequence is counted or refused; and whether this definition belongs in [kernel §7](../constitution/CONVENTIONS.md#k7) instead, since the template's always-on budget and the shared `shown` count characters too, and a concept two modules need is the kernel's by [law 3 of CLAUDE.md](../../CLAUDE.md#law-3).

## 4. Documents that cannot get shorter ([requirement A11.2](../requirements.md#a11-2))

- d1. **What may change in a frozen document.** An accepted record takes only the typo fixes and wording edits of [rule 14 of plc-0004-decision-records](../policies/plc-0004-decision-records.md#r14). A frozen comparison takes the same, and the few edits of [rule 7 of plc-0005-research](../policies/plc-0005-research.md#r7). Neither edit may remove a fact, so a frozen document over a ceiling can never be brought under it by an edit its policy allows.
- d2. **Wording edits make documents longer.** One kind, the sentence split, drops a joining word, but it adds a full stop and a capital. The others add bold marks, code-span marks or bullets. In the two commits that made the kit's wording edits, every frozen document grew (E5). The three comparisons grew by 12 to 58 characters. The ten accepted records grew by 29 to 101. The largest share was 1.5 percent of the record's length.
- d3. **The largest frozen documents.** At `82a219c` the longest record has 30,126 characters and the longest comparison 71,590 (E2). A ceiling set from observed data covers them on the day it is set: the data include them. Only a ceiling lowered later, to hold new documents shorter, can fall below a frozen one.
- d4. **Candidate A: a `departures` dial,** as modules [`const-styling`](../requirements.md#const-styling) and [`const-language`](../requirements.md#const-language) have one. An entry holds `paths` (a kind by pattern, a number range by a character class, one file by its path), `allow` naming ceilings by name, and a one-line `reason`. A matched document is not held to the allowed ceilings; the others still apply. An entry that matches no covered document is a note on every scan. Mechanism class: dials of the module. Maturity: shipped twice in the kit. It is the pattern [dec-0045-frozen-documents-stay-in-the-style-scan](../decisions/dec-0045-frozen-documents-stay-in-the-style-scan.md) and [dec-0048-frozen-documents-take-wording-edits](../decisions/dec-0048-frozen-documents-take-wording-edits.md) set: the document stays in the gate's territory and the exception carries its reason.
- d5. **Candidate B: a ceiling of its own over the range.** Path keys allow it: an entry for `docs/research/res-000[0-9]*.md` at a higher number. Under the reading "every matching ceiling applies" (b8) the general ceiling still applies to the range, so B needs the first-match reading or a negated pattern in the general entry. The negated pattern takes the range out of one ceiling, not out of the gate; but it reads as an exclusion and carries no reason.
- d6. **Candidate C: a negated pattern in the gate's territory.** The form both records above reversed. Rejected.
- d7. **Candidate D: a per-document freeze.** Each frozen document may not grow past its own length at freeze. The wording edits of d2 would then be refused, so D contradicts the two policies.
- d8. **Headroom for wording edits.** A ceiling a few percent above the largest frozen document of its paths leaves room for every wording edit the kit has made (d2). The day-one proposal of section 5 adds ten percent.

**Recommendation: A, a `departures` dial of the siblings' shape, empty on day one — build.** It is the kit's pattern, the reason is required, and the stale-entry note keeps it honest. No departure is needed while each ceiling sits above the frozen documents it covers (d3). The first one is due when a ceiling is lowered below a frozen document.

## 5. Observed data and how a ceiling is derived ([requirement A11.3](../requirements.md#a11-3))

- e1. **Git history holds every committed version.** Walking every commit of the clone, 525 of them, gave 43,708 versions of Markdown files, from 1,415 distinct blobs, over 189 paths and 15 days, 2026-09-14 to 2026-09-28 (E3). The walk took 15.2 s, since each blob was decoded and counted once. The data are retroactive: the kit's two weeks exist already, and a consumer adopting the module has its whole history.
- e2. **The output log cannot hold a month.** Each gate's log rotates at 1,048,576 bytes and keeps one old file (read in `shared/const_gate/output.py` at `82a219c`). In the kit's own working tree, the two files of the log of module [`const-interaction`](../requirements.md#const-interaction) spanned 2026-09-25 to 2026-09-28. One file of the language gate held a single scan (E3). The log is also per clone, git-ignored, and holds only what was printed. It is evidence of runs, not a record of lengths.
- e3. **A shallow clone has no history.** `git clone --depth 1` gave one commit (E12). A history report run in CI needs `fetch-depth: 0`, or it must say that the history is missing. It must never report a month it did not see.
- e4. **How the kit grew.** On the first-parent line of `82a219c`, the Markdown in the tree grew from 69,733 characters in 10 files on 2026-09-14 to 1,878,389 in 128 files on 2026-09-28, about 129,000 a day (E3). Documents also shrank. The requirements document peaked at 41,532 and stands at 28,103; the rollout plan peaked at 45,026 and stands at 13,820 (E3). Module documents took over their specifications, and the ceiling data show that as a fall.
- e5. **Ceilings set early would have fired often.** A backtest set each kind's ceiling at the end of a day, at its largest version so far plus ten percent, rounded up to 1,000 (E4). It then counted the later versions over it. Set at the end of 2026-09-20, 193 of 888 later versions would have been over. At the end of 2026-09-23, 65 of 638. At the end of 2026-09-27, 11 of 151, every one of them a policy. Two weeks are enough for the large kinds and too little for a kind that is still being written. The data support the ruling that ceilings from less than a month only warn.
- e6. **How other tools derive a ceiling.** None of the tools read derives a ceiling from data. ESLint's `max-lines` ships 300 lines, and textlint's line rule ships 300 lines (t11, t8). `check-added-large-files` ships 500 KB (E6, its source read), and webpack ships 250,000 bytes for an asset (t11). size-limit takes the number the author writes (t11). Each is a fixed number, changed by hand. webpack's `hints` is the one ladder: `false`, `'warning'` or `'error'`, with `'warning'` the default in production mode, and the page recommends `'error'` for production builds (t11, read).
- e7. **Three ways to set a number from data.** The maximum of the window plus a margin; a percentile of the window; a number fixed by hand and checked against the data. A percentile leaves its tail over the ceiling on the day it is set: a p95 ceiling is red for one document in twenty. That makes the ceiling a target for the many, the reading the specification forbids. The maximum plus a margin is red for none on the day it is set, and it leaves room for wording edits (d8).
- e8. **What a report shows.** Per ceiling: the documents it covers today, the longest with its length, and the margin to the number. Over history, the largest version per day within the window, so that the reviewer sees whether the kind is still growing. Table E10 is that report for the kit, computed by hand.

- e9. **Candidate A: the scan reports, every run.** Each ceiling adds one note with its covered count, its longest document and its margin, beside the verdict. Cost: small; the data come from the files the scan reads anyway. What it cannot do: show a trend over time.
- e10. **Candidate B: a history report,** a flag of the scan with a value, `--since <date>`, walking the commits reachable from `HEAD`. It prints e8's table per ceiling and per day, and it refuses a shallow clone with a configuration failure that names `git fetch --unshallow`. **Recommendation: A and B — build; the number stays review, data-informed, as the matrix says, and the month rule becomes config (section 1).** The scan's notes give the current data at no cost. The history report gives the month the amended rule asks for, from git, the only record that holds it. The derivation to write down is the maximum of the window plus a margin, never a percentile. For the decider: the margin, and whether the kit's day-one ceilings are the ten rows of the table, at `warning`, over the window 2026-09-14 to 2026-09-28. The table's first and third rows would bind accepted records and frozen comparisons with room to spare. Three coarser entries, one per meta-type, would leave the small kinds unbounded in practice (b5).

## 6. The native surface and community practice ([requirement A11.1](../requirements.md#a11-1), [requirement A11.2](../requirements.md#a11-2))

- f1. **The platform counts in four units.** In characters: a hook's `additionalContext`, `systemMessage` and plain stdout are "capped at 10,000 characters". A skill's listing text "is capped at 1,536 characters regardless of budget", which `skillListingMaxDescChars` can change. A Bash result stays inline "up to roughly 30,000 characters by default" (t1, hooks, skills and tools reference pages). In lines: "target under 200 lines per CLAUDE.md file", and "Keep `SKILL.md` under 500 lines" (t1, memory and skills pages). In bytes: `MEMORY.md` loads its first 200 lines or first 25KB, and "Claude Code skips a file over 4 MiB" (t1, memory page). In tokens: a `Read` returns a partial view past its token limit, and compaction keeps "the first 5,000 tokens" of each invoked skill (t1, tools reference and skills pages).
- f2. **Nothing native bounds a document's length.** No setting, hook event or tool refuses or reports a Markdown file for its length. The limits of f1 cut what the model receives, and none of them tells an author the file is too long. The `InstructionsLoaded` event fires when a `CLAUDE.md` or a rule file is loaded (t1, hooks page). It could measure `CLAUDE.md` at load, but it is no write-time or scan-time check, and a scan covers the same file.
- f3. **Lines are a poor measure of the kit's documents.** The kit writes one paragraph per line. `CLAUDE.md` is 46 lines and 20,223 characters. 114 of the 128 Markdown files are under 200 lines, the longest document among them, at 71,590 characters, included (E13). Characters per line run from 27 to 676, median 111 (E13). textlint's line rule, set to 100, passed the intent page at 53 lines and flagged the 194-line comparison of 71,590 characters (E7).
- f4. **Community tools bound other things.** `check-added-large-files` bounds the kilobytes of a staged file and passes a file not staged (E6). markdownlint 0.41.1 has 53 rules and one about length, `MD013`, a line's length (t7, read). ESLint's `max-lines` bounds the lines of a script (t11, read). Vale's `metric` on `characters` bounds prose characters only, and exits 1 on an alert at `error` (E8). OpenAI's Codex stops reading instruction files "once the combined size reaches the limit defined by `project_doc_max_bytes` (32 KiB by default)" (t12, read). The Agent Skills specification sets a skill's `description` at "Max 1024 characters" and asks to keep `SKILL.md` under 500 lines (t12, read). The AGENTS.md site sets no size (t12, read).
- f5. **Tokens move with the tokenizer, most for scripts other than English.** On fifty lines of English, `cl100k_base` and `o200k_base` gave 650 tokens each. On fifty lines of Russian of the same meaning they gave 1,200 and 800 (E9). On the kit's own documents the two differed by 0.1 to 1.3 percent (E9). A ceiling in tokens would change by a third for a Russian consumer when the tokenizer changed, and not at all for an English one. That is the kernel's reason for characters, shown in numbers.
- f6. **Vale could host the check, at a cost.** A `metric` rule with `formula: characters` gave an alert per document in one Vale run (E8). But its count is prose alone (c6), it needs the binary, and it has no dial for a per-ceiling window. It adds a dependency the check does not need, so it is no candidate.

**Recommendation: no native mechanism and no third-party tool — not needed; the check is the module's own script on the platform's hook events (section 1).** The platform offers the events and cuts what the model receives, and no tool surveyed counts characters of a whole file by pattern. Step down the ladder of native-first: a platform hook runs the check, and a repository script is the check, since no platform component measures a document.
