# Constitution Rollout — Actionable Plan

*The kit's own write-head ([kernel §2](../kernel/CONVENTIONS.md#k2)): the phases and their sequence, its lifecycle as [rule 1 of plc-0008-rollout-plan](policies/plc-0008-rollout-plan.md#r1) has it. What a module must implement lives in [constitution-requirements](requirements.md), the traceability matrix and module specifications. Nothing here is a requirement or a ruling.*

*Working rule throughout: author against real files, extract when proven, install everywhere else. No module is designed against imagined content.*

<a id="phase-a"></a>
## Phase A — Kit as consumer zero: the document-shaped accumulating modules (~1 week)

The fifth and the sixth, [`const-locations`](requirements.md#const-locations) and [`const-task-close`](requirements.md#const-task-close), followed them here from Phase C. The kit is consumer zero for the kinds it creates and for the code territories its own current-state documents describe (records [dec-0035-locations-module-rulings](decisions/dec-0035-locations-module-rulings.md), [dec-0036-task-close-module-rulings](decisions/dec-0036-task-close-module-rulings.md)).*

## Phase B — Bootstrap the consumer project (~1 hour)

5. <a id="s5"></a>In the project: copy `kernel/` to `docs/constitution/`. Write a root policy and one policy per document kind under `docs/policies/` — at least a kernel policy for `docs/constitution/**` and a decision-record policy for `docs/decisions/**`. They are written for the project; the kit's policies under `docs/policies/` are examples to read, not to copy — policies are consumer content, never kernel, never module. Write `constitution.yaml` at the root with `root_policy` and each policy's territory under its id, `docs/policies/**` for the root ([kernel §3](../kernel/CONVENTIONS.md#k3)). Load the modules authored in the kit by then — the four of Phase A, [`const-locations`](requirements.md#const-locations), [`const-task-close`](requirements.md#const-task-close), [`const-questions`](requirements.md#const-questions), [`const-interaction`](requirements.md#const-interaction), [`const-styling`](requirements.md#const-styling) and [`const-language`](requirements.md#const-language) — from the kit path from the first commit, so no governed document is ever written unguarded. Run the scan of each module that ships one against the project, its runner on the throwaway repository it builds, and the live item each module's document defers to this step — [`const-meta-types`](../modules/const-meta-types/MODULE.md#t10) T54, [`const-decision-records`](../modules/const-decision-records/MODULE.md#t10) T55, [`const-catalogs`](../modules/const-catalogs/MODULE.md#t10) L5, [`const-locations`](../modules/const-locations/MODULE.md#t10) V3, [`const-referencing`](../modules/const-referencing/MODULE.md#t10) L4, [`const-task-close`](../modules/const-task-close/MODULE.md#t10) L4, [`const-questions`](../modules/const-questions/MODULE.md#t10) L4, [`const-interaction`](../modules/const-interaction/MODULE.md#t10) L4, [`const-styling`](../modules/const-styling/MODULE.md#t10) L4, [`const-language`](../modules/const-language/MODULE.md#t10) L4. <a id="phase-d"></a>
## Phase D — Publish (~1 hour, only after the six are green)

10. <a id="s10"></a>A remote with protected main and a branch-per-change PR flow: the kit's yes moves from the commit message to PR approval (decision [dec-0016-yes-on-the-change](decisions/dec-0016-yes-on-the-change.md)), and the `Accepted:` and `Carry-Audit:` trailers to the commit that merges the pull request. The protected main then holds the shared `main` where the local branch-first gate cannot. Whatever was done to a local `main` without passing the hook — `git am`, a rebase, a fast-forward asked for on the command line, a push, `git reset`, `git update-ref`, `git branch -f` — reaches the shared one only through a pull request's merge, whose review also sees the content of a merge concluded by hand. A local `main` itself stays unheld, and `scripts/git-hooks/prepare-commit-msg` stays as the fast local check. Then `profiles/`. Then the `.claude-plugin/marketplace.json` already at the kit root, each module a relative-path entry (verify private-repo team access in-session), proven by two installs under an isolated `CLAUDE_CONFIG_DIR`. The first install: the marketplace added from its git remote, whose install copies each plugin into the plugin cache and must leave `scripts/const_gate` there as a real directory, the link dereferenced within the marketplace. The second: the same marketplace added from the local directory, whose plugins load in place and whose hook processes receive a `CLAUDE_PLUGIN_ROOT` pointing at the source directory. A red in either fires the fallback of limit 3 of [kit-shared-gate-code §4](../shared/GATE.md#g4) as written, links replaced by copies and the link gate by an equality gate. Until then that fallback stands with its trigger unmet (decision [dec-0025-shared-gate-code-linked](decisions/dec-0025-shared-gate-code-linked.md)). Then CI wiring the [aspect A12](requirements.md#a12) gates — bare-repo install, kernel+single-module run, project-reference grep — together with the scan of module `const-referencing`, the range check of module `const-task-close` and the kit's own `scripts/check-carry-lists.py` and `scripts/check-yaml-style.py`. These run by hand until then; the carry-lists gate reads acceptance commits, so CI fetches the full history. Then one carry audit in full before the modules go to `0.1.0`, and validation of the kit's own `constitution.yaml` against the kernel's dials schema. The kit's own sessions load its modules through the marketplace file just named, named `constitution-kit`, with the project's settings file enabling each module — done 2026-09-26, decision [dec-0043-kit-plugins-through-project-settings](decisions/dec-0043-kit-plugins-through-project-settings.md), the yes given. The session-conduct block of [CLAUDE.md](../CLAUDE.md) is trimmed to what no module carries, the routine edit [dec-0041-questions-module-rulings](decisions/dec-0041-questions-module-rulings.md) R2 names. Modules go to `0.1.0`.
11. <a id="s11"></a>Switch the project from path load to marketplace install. From here every project is a consumer; all module development stays in the kit repo.

<a id="phase-e"></a>
## Phase E — Steady state

Friction in a project → commit note → recurring notes on one theme → module authored or amended in the kit → version bump → projects update. That is the principle [p2 of the intent page](../INTENT.md#p2), and, for a document of a kind no policy governs yet, [rule 5 of plc-0001-root-policy](policies/plc-0001-root-policy.md#r5). Onboarding = clone, install, read one page of `CONVENTIONS.md`.
