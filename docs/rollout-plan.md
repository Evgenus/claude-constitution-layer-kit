# Constitution Rollout — Actionable Plan

*The kit's own write-head ([kernel §2](../kernel/CONVENTIONS.md#k2)): the phases and their sequence, `active` while a phase remains, `inactive` when Phase E is reached. What a module must implement lives in [constitution-requirements](requirements.md), the traceability matrix and module specifications; nothing here is a requirement or a ruling.*

*Working rule throughout: author against real files, extract when proven, install everywhere else. No module is designed against imagined content.*

5. In the project: copy `kernel/` to `docs/constitution/`; a root policy and one policy per document kind under `docs/policies/` — at least a kernel policy for `docs/constitution/**` and a decision-record policy for `docs/decisions/**` (written for the project; the kit's policies under `docs/policies/` are examples to read, not to copy — policies are consumer content, never kernel, never module); `constitution.yaml` at the root with `root_policy` and each policy's territory under its id, `docs/policies/**` for the root ([kernel §3](../kernel/CONVENTIONS.md#k3)); the modules authored in the kit by then — the four of Phase A and [`const-locations`](requirements.md#const-locations) — loaded from the kit path from the first commit, so no governed document is ever written unguarded. 6. Decision record #1 — "Adopt constitution kernel", `stakes: process`, `decider: <you>`, numbered by [`const-catalogs`](requirements.md#const-catalogs) — merged with your one yes: the fast lane's first run.
7. Commit each step with honest messages.

## Phase D — Publish (~1 hour, only after the six are green)

10. A remote with protected main and a branch-per-change PR flow: the kit's yes moves from the commit message to PR approval (decision [dec-0016-yes-on-the-change](decisions/dec-0016-yes-on-the-change.md)), and the `Accepted:` and `Carry-Audit:` trailers to the commit that merges the pull request. The protected main then holds the shared `main` where the local branch-first gate cannot: whatever was done to a local `main` without passing the hook — `git am`, a rebase, a fast-forward asked for on the command line, a push, `git reset`, `git update-ref`, `git branch -f` — reaches the shared one only through a pull request's merge, whose review also sees the content of a merge concluded by hand; a local `main` itself stays unheld, and `scripts/git-hooks/prepare-commit-msg` stays as the fast local check. Then `profiles/`, `.claude-plugin/marketplace.json` (verify marketplace shape and private-repo team access in-session), CI wiring the [aspect A12](requirements.md#a12) gates — bare-repo install, kernel+single-module run, project-reference grep — together with the scan of module `const-referencing` and the kit's own `scripts/check-carry-lists.py` (run by hand until then; the second reads acceptance commits, so CI fetches the full history), one carry audit in full before the modules go to `0.1.0`, and validation of the kit's own `constitution.yaml` against the kernel's dials schema. Modules go to `0.1.0`.
11. Switch the project from path load to marketplace install. From here every project is a consumer; all module development stays in the kit repo (`process` stakes, one human yes per change).

## Phase E — Steady state

Friction in a project → commit note → recurring notes on one theme → module authored/amended in the kit (`process` stakes, one human yes) → version bump → projects update. Never: a module for a failure no one has hit; a territory with no policy behind it (a territory precedes its first document, never its policy). Onboarding = clone, install, read one page of `CONVENTIONS.md`.
