# Constitution Rollout — Actionable Plan

*The kit's own write-head ([kernel §2](../kernel/CONVENTIONS.md#k2)): the phases and their sequence, its lifecycle as [rule 1 of plc-0008-rollout-plan](policies/plc-0008-rollout-plan.md#r1) has it. What a module must implement lives in [constitution-requirements](requirements.md), the traceability matrix and module specifications; nothing here is a requirement or a ruling.*

*Working rule throughout: author against real files, extract when proven, install everywhere else. No module is designed against imagined content.*

<a id="phase-a"></a>
## Phase A — Kit as consumer zero: the document-shaped accumulating modules (~1 week)

<a id="phase-d"></a>
## Phase D — Publish (~1 hour, only after the six are green)

10. <a id="s10"></a>A remote with protected main and a branch-per-change PR flow: the kit's yes moves from the commit message to PR approval (decision [dec-0016-yes-on-the-change](decisions/dec-0016-yes-on-the-change.md)), and the `Accepted:` and `Carry-Audit:` trailers to the commit that merges the pull request. The protected main then holds the shared `main` where the local branch-first gate cannot: whatever was done to a local `main` without passing the hook — `git am`, a rebase, a fast-forward asked for on the command line, a push, `git reset`, `git update-ref`, `git branch -f` — reaches the shared one only through a pull request's merge, whose review also sees the content of a merge concluded by hand; a local `main` itself stays unheld, and `scripts/git-hooks/prepare-commit-msg` stays as the fast local check. Then `profiles/`; `.claude-plugin/marketplace.json` at the kit root, each module a relative-path entry (verify marketplace shape and private-repo team access in-session), proven by two installs under an isolated `CLAUDE_CONFIG_DIR`: the marketplace added from its git remote, whose install copies each plugin into the plugin cache and must leave `scripts/const_gate` there as a real directory, the link dereferenced within the marketplace; and the same marketplace added from the local directory, whose plugins load in place and whose hook processes receive a `CLAUDE_PLUGIN_ROOT` pointing at the source directory — a red in either fires ruling 7 of [dec-0025-shared-gate-code-linked](decisions/dec-0025-shared-gate-code-linked.md) as written, links replaced by copies and the link gate by an equality gate, and until then that ruling stands with its trigger unmet; CI wiring the [aspect A12](requirements.md#a12) gates — bare-repo install, kernel+single-module run, project-reference grep — together with the scan of module `const-referencing`, the range check of module `const-task-close` and the kit's own `scripts/check-carry-lists.py` and `scripts/check-yaml-style.py` (run by hand until then; the carry-lists gate reads acceptance commits, so CI fetches the full history), one carry audit in full before the modules go to `0.1.0`, and validation of the kit's own `constitution.yaml` against the kernel's dials schema; the kit's own sessions load its modules per clone, the mechanism a decision of its own, and the session-conduct block of [CLAUDE.md](../CLAUDE.md) then trims to what no module carries, a routine edit naming [dec-0041-questions-module-rulings](decisions/dec-0041-questions-module-rulings.md). Modules go to `0.1.0`.
11. <a id="s11"></a>Switch the project from path load to marketplace install. From here every project is a consumer; all module development stays in the kit repo.

<a id="phase-e"></a>
## Phase E — Steady state

Friction in a project → commit note → recurring notes on one theme → module authored or amended in the kit → version bump → projects update — the principle [p2 of the intent page](../INTENT.md#p2), and, for a document of a kind no policy governs yet, [rule 5 of plc-0001-root-policy](policies/plc-0001-root-policy.md#r5). Onboarding = clone, install, read one page of `CONVENTIONS.md`.
