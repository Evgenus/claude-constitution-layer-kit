# Developing a module — the steps from the template copy to the version bump

This page is read before a module is authored or changed — its document, its plugin, its tests or its eval cases. [CLAUDE.md](../../CLAUDE.md) links it from its section "Developing a module".

1. <a id="s1"></a>`cp -r module-template/ modules/const-<name>/` — kebab-case, `const-` prefix; name it in its manifest, in `MODULES` of `scripts/gate-list.sh` (a scan also in `GATES`, `job()` and `commands()`), in `.claude-plugin/marketplace.json`, as `const-<name>@<marketplace name>` in `.claude/settings.json`, in its pair in `const-task-close.coverage` of `constitution.yaml` (code `modules/const-<name>/plugin/scripts/**`, `plugin/hooks/**`, `plugin/skills/**`, `tests/**` and `evals/**` for the folders it has, docs its `MODULE.md`) and, where it has a scan, in the `bash check=scan` block of `INSTALL.md` step 8, all held by `scripts/check-gate-lists.py`. The pair also lists, by its path, each file of a pinned tool that stands outside `plugin/scripts/`; review holds that, since the check asks only for the five folders. The template's relative links gain one `../` level in the copy; the scan of module [`const-referencing`](../requirements.md#const-referencing) turns red until they are fixed.
2. <a id="s2"></a>Research first: a subagent surveys how this module's matrix rows are addressed today — official Claude Code documentation for the native surface, community harnesses, applicable tools — and returns one dated comparison in kit vocabulary at `docs/research/res-<nnnn>-const-<name>.md` — created through the command of module [`const-locations`](../requirements.md#const-locations) from `templates/research-comparison.md`, the subagent filling its placeholders, numbered as rule 6 of [plc-0005-research](../policies/plc-0005-research.md#r6) says: candidate approaches, mechanism class, maturity, cost, one recommendation per mechanism with reasoning (decision [dec-0010-module-research-per-module](../decisions/dec-0010-module-research-per-module.md)). Earlier design work is a clue set, never a source: nothing enters unverified, and its vocabulary — its aspects numbered one to ten, its D-numbers, its register rulings — does not enter at all. Raw material stays in the subagent; only the comparison returns.
3. <a id="s3"></a>Fill `MODULE.md` top-down from the module's matrix rows, moving the module's specification from the requirements document into it and leaving a one-line stub under its anchor there, which stays the module's handle; every section filled or "none" with one line of reasoning. Before writing the artifacts table, confirm or overturn the matrix's recommended enforcement for each row from the comparison, naming on every step down what the native option cannot do.
4. <a id="s4"></a>Implement artifacts: hooks/scripts for gates (paths via `${CLAUDE_PLUGIN_ROOT}`), skills for procedures and advisory rules, eval cases, `INSTALL.md` with at most one CLAUDE.md pointer line, and `README.md`, the module's landing page for a reader on GitHub, filled from the template's `README.md`. That page is of the root README's kind — user-facing, informational, in no policy's territory, with no envelope, binding nothing. Its first section opens with the manifest's `description` as written and says the rest in plain words; its second states the problem and how the module resolves it; its implementation is told at a high level, one paragraph per tool, then one on its settings; its links are the module's own `INSTALL.md` and `MODULE.md` alone, never a requirement row, a record or a comparison. [Law 2 of CLAUDE.md](../../CLAUDE.md#law-2) holds for it by review, since the kit's portability check reads a module's installed components alone. A change to it is routine, like one to the root README (decision [dec-0077-module-readme-pages](../decisions/dec-0077-module-readme-pages.md)). The eval cases sit in `evals/<case>/case.yaml`, at least one per module, each named as an `eval` item of the module's acceptance table. A case sits outside its plugin, so it names it: `plugins:` lists `../../plugin`. There is one per skill, held by `tool_used` on `Skill`, by a `regex` on the run's trace that no `Write` or `Edit` comes before the call that names it, by a grader on the work's result where the work leaves one, since the `regex` does not see a change made through `Bash`, and, where the skill's moment is a command, by `tool_order` putting the skill before it. There is one per command a rule makes mandatory, a script the module ships, held by `tool_used` on `Bash` and by a grader on what it did, joined with its skill's case where the skill makes it mandatory at its own moment; and one per start rule that carries a rule of its own, held by `regex` where a pattern can see the rule and by `llm` only where none can. A run starts in an empty folder, so a case that needs a project has a `scaffold.sh` beside it. The parts that install sit in the module's `plugin/` folder, the plugin root: `.claude-plugin/` and `INSTALL.md`, and those of `hooks/`, `skills/`, `scripts/`, `requirements.txt`, `commands/` and `agents/` that the module has, and a pinned tool's own files, which [the configuration row](../../module-template/slot-guidance.md#s13) places. A project installs that folder alone. `MODULE.md`, `README.md`, `tests/` and `evals/` sit beside it and are never installed (decision [dec-0098-modules-install-from-a-plugin-subfolder](../decisions/dec-0098-modules-install-from-a-plugin-subfolder.md)). Only `.claude-plugin/plugin.json` lives inside `.claude-plugin/`; the other parts sit at the plugin root, a pinned tool's files where the configuration row places them. Each manifest names `Apache-2.0` in `license`; in `author`, a module's names the author `NOTICE` names and the template's keeps a placeholder. The Apache License 2.0 is the kit's one license for the whole tree, documents and code alike: `LICENSE` at the kit root is its text, `NOTICE` beside it its credit, which holds no email address, and no file takes a license header (decision [dec-0063-apache-license-with-notice](../decisions/dec-0063-apache-license-with-notice.md)). Script runtime (decision [dec-0015-pre-module-audit-rulings](../decisions/dec-0015-pre-module-audit-rulings.md)): a script that reads YAML — the envelope, the dials file — is Python 3 with PyYAML; one that reads none may be POSIX shell. A missing interpreter or library is a configuration failure, never a silent pass: exit 1, with where to get the interpreter or the library's install command in the message. The one exception is the shared package. Its failure names the module's `INSTALL.md`, since one command that installs an exact tag could replace a newer release another module needs (R16 of [dec-0099-shared-code-installed-as-a-pip-package](../decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r16)). The Python floor has one source, `FLOOR` in `shared/constitution_layer_kit/preflight.py`; every copy of it, records and comparisons aside, and each entry's [`C1`, `C14`, `C15`, `C16` and `C17`](../../shared/MESSAGES.md#g3) clause are held by the kit's `scripts/check-copies.py`, an entry of the gate list with `--self-test` as its fixture. Every Python script follows the sixteen rules of [kit-gate-script-rules](../../module-template/gate-script-rules.md) (decisions [dec-0020-gate-script-rules](../decisions/dec-0020-gate-script-rules.md), [dec-0026-imports-at-the-top](../decisions/dec-0026-imports-at-the-top.md)). The configuration of the linter, formatter and type checker — `ruff`, `mypy --strict` — is the kit's own development routine, in `pyproject.toml` at the kit root with the commands to run; no module ships a configuration of those tools. Its lint holds ruff's `C901` at a complexity of 15 over the modules, the shared code and the kit's scripts. The functions above it when the rule came in, on 2026-10-13, were split below it since and lost their marks. Any function above it, one of those included, carries `# noqa: C901` only where a change marks it, with its reason on the `def` line; a reason in a module's files or in the shared code names no record. A new mark is held by review, and a commit of the change that adds it says in its message why the function stays whole (decisions [dec-0088-ruff-complexity-limit](../decisions/dec-0088-ruff-complexity-limit.md) and [dec-0090-complexity-marks-split-away](../decisions/dec-0090-complexity-marks-split-away.md)). Shared gate code: what every gate needs has one source under `shared/`, described in [kit-shared-gate-code](../../shared/GATE.md). It reaches a project as the Python distribution `constitution-layer-kit`, which pip installs from a git tag, and a plugin holds none of it. A module's Python entry files state the release they need, `REQUIRES`, import the package, and call `cli.version_failure` right after they import `cli`. Its `INSTALL.md` gives the pip command at that tag, and `scripts/check-copies.py` holds both. Its tests link to the package and to the module's own packages by relative symbolic links. The package holds the shared test files in its subpackage `testing`. A plain file, `tests/test_shared_items.py`, brings the shared items in. `scripts/check-shared-links.py` is the gate, red for anything at `plugin/scripts/constitution_layer_kit` (R5, R6, R7, R8 and R15 of [dec-0099-shared-code-installed-as-a-pip-package](../decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r5); R2 of [dec-0107-shared-test-files-in-the-distribution](../decisions/dec-0107-shared-test-files-in-the-distribution.md#r2) for the plain file). A module fills the interface of [its §2](../../shared/GATE.md#g2), and writes only its own model, messages, checks and modes. What may be admitted there, and when a shared part may be widened for one module, is rule 2 of [plc-0009-shared-code](../policies/plc-0009-shared-code.md#r2); a change to the package raises its `__version__` as [rule 11 of that policy](../policies/plc-0009-shared-code.md#r11) says. A change to the shared code bumps no module's version by itself: after it, a module's version moves only when the module needs a later release and raises its `REQUIRES`, a bump made by hand ([rule 7 of that policy](../policies/plc-0009-shared-code.md#r7)). Territory matching in the default dialect goes through `git check-ignore`, verified at authoring.
5. <a id="s5"></a>Prove twice: fixtures against a bare temp repo (the parts of [law 2 of CLAUDE.md](../../CLAUDE.md#law-2) and [law 3](../../CLAUDE.md#law-3) a run can test, in the kit's CI: the [A12.1](../requirements.md#a12-1) grep of [law 2](../../CLAUDE.md#law-2), `scripts/check-portability.py`, and each module's bare-repo install alone, from the change's GitHub repository and branch — a pull request's head, or `main` on a push — `scripts/check-bare-install.py`, entries of the gate list each with its `--self-test` as its fixture; the rest of [law 3](../../CLAUDE.md#law-3), sibling references only as optional enhancements, by review), then live. The live proof is in this repository for modules whose objects the kit holds: governed documents of a kind it holds, the code territories its own current-state documents describe, its own session conduct, both the rules its guide keeps and those its modules carry (the kit is consumer zero) — and in a consumer project: session in the project, plugin loaded from the module's `plugin/` folder in this repo (check current plugin-dir and marketplace mechanics against the official docs, never memory). A project's install holds no tests. A project may run the fixtures from a kit clone at the commit its install records. When no consumer exists yet, the record and the yes follow the kit-live proof; the consumer-live proof is a named step of the consumer's bootstrap, and a finding there is a fix — with a version bump once the module is published — priced by its stakes. Each acceptance item names the matrix rows it proves ([kit-template-slot-guidance](../../module-template/slot-guidance.md#s3)). The eval cases are proven by a local run, `python3 scripts/run-evals.py --token-file <file> --module <name>`, whose receipt `scripts/check-eval-receipts.py` holds. A `live` item that proves a session's behaviour alone, and whose proof does not run in a consumer project, becomes an `eval` item where a case covers it whole: the `eval` item replaces it, and the proof it asks for is owed no more. Every other `live` item stays `live`, and the proof it asks for stays owed: one that no case covers whole, one that proves a scan over the kit's tree, and one whose proof runs in a consumer project, deferred or not. A scan item and a consumer-project item stay `live` because an eval runs in an empty folder, which a scaffold seeds where a case needs a project: it proves no scan over the kit's tree, and it runs in no consumer project. An `eval` item counts as run when its module's receipt is current: green when its last attempt passes, red when it does not. That is a run that was declared, not one the kit sees. The kit's `scripts/check-aspects.py` holds those tags, one entry of the gate list; with `--run` it runs the tests and gives each matrix row the result of its own items — a status derived on each run and stored nowhere, never a green for a row no run examined. `--module <name>` narrows the run, `--self-test` is its fixture (decision [dec-0054-acceptance-items-name-their-rows](../decisions/dec-0054-acceptance-items-name-their-rows.md)).
6. <a id="s6"></a>Validate fresh-context before the human yes, in two passes, both mandatory. First, a subagent holding only the module's files, the template, [CLAUDE.md](../../CLAUDE.md), this page, and the module's matrix rows — never the authoring reasoning — reviews against [law 2 of CLAUDE.md](../../CLAUDE.md#law-2) to [law 7](../../CLAUDE.md#law-7) and every template section. Its mutation probes run through the `mutation-probe-runner` agent of `.claude/agents/`, and the live items of step 5 through the `live-proof-runner` agent there, each on a copy or a clone in the scratch directory, the kit read-only to both. A headless run in a clone or copy the platform has not been told to trust silently loads no plugin through settings, so the runners pass `--plugin-dir` per module. Second, the carry audit of [rule 2 of plc-0004-decision-records](../policies/plc-0004-decision-records.md#r2), run through the kit's `carry-audit` skill — its regression and confirming readers the `regression-reader` and `confirming-reader` agents of `.claude/agents/`: fresh readers, each round pinned to one commit, their scope computed by `scripts/check-carry-lists.py --scope` and never chosen. Full readers read in full the records the change adds or edits and those the module's decisions section cites; regression readers, every other record that cites a file the change touched, asked only whether that file still states what the record ruled. For each added record, a blind reader who never sees it answers the author's questions from the current-state documents alone. Where the change makes wording edits in accepted records or frozen comparisons, one more reader reads each against the kinds their policies list. Every finding of either pass is fixed or justified in a commit message of the change, the merge commit included — never only in the pull request's description, which git does not keep (decision [dec-0009-module-routine-validation-and-inputs](../decisions/dec-0009-module-routine-validation-and-inputs.md), and R9 of [dec-0057-pr-flow-merge-names-the-yes](../decisions/dec-0057-pr-flow-merge-names-the-yes.md#r9) for the commit message). The commit that names the yes carries the audit's receipt of [rule 5 of plc-0004-decision-records](../policies/plc-0004-decision-records.md#r5); `scripts/check-carry-lists.py` gates the carry lists, every ruling's anchor and the receipt — which shows that an audit was declared and accounted for, not that it was run — and whether a ruling is carried stays the readers' judgment.
7. <a id="s7"></a>Version bump on every change of a module once published, save a change to the shared code, which bumps none by itself (step 4); consumer projects update by version. A draft, at `0.0.x`, need not be bumped — for a change of its own or a consumer-live finding alike — and may still be bumped within `0.0.x` (decision [dec-0053-drafts-keep-their-versions](../decisions/dec-0053-drafts-keep-their-versions.md)).
