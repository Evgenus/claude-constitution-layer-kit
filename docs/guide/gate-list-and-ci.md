# The gate list and CI — what the kit runs on every change

<a id="g1"></a>
This page is read before a change to the kit's tooling — the gate list, a kit check, the workflow, the eval runner — and when a gate of the list or a job of CI is red. [CLAUDE.md](../../CLAUDE.md) links it from its rule "Work starts on a branch".

The whole gate list — the scans of the modules, the kit's own checks each with its `--self-test` where it has one, the self-test of the eval runner, `scripts/run-evals.py --self-test`, and the range check — is the gate group of `scripts/gate-list.sh`, the kit's one list. Its extra group holds each module's fixtures, lint and types, the branch gate's fixture, the fixture of `scripts/setup-claude.sh`, the kit's lint and types, and the types of `scripts/layered-fixture/`. That folder holds a gate of another layer. `scripts/check-layered-items.py`, an entry of the gate group, runs every shared item on it. A module's scan in the list runs with `PYTHONPATH="$PWD/shared"`, since no plugin carries the shared code. The entry `shared-package`, `scripts/check-shared-package.py` with `--self-test` as its fixture, builds the package from `shared/`, installs it into a fresh virtual environment and imports it there, the one entry that needs the package index (R19 of [dec-0099-shared-code-installed-as-a-pip-package](../decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r19)). A module's fixtures run through `python3 scripts/check-aspects.py --run --module <module>`, which collects its tests under pytest, then runs them once, prints pytest's own output whenever it exits other than 0, and holds the tests' items against the module's acceptance table both ways (decision [dec-0080-fixtures-run-through-check-aspects](../decisions/dec-0080-fixtures-run-through-check-aspects.md)). The same run holds a count typed on the Runner line of the document's section 10, `<digits> items green` outside code fences, against the tests run. A Runner line without that form, or none, is no finding. Every script under the kit's `scripts/` is kit tooling, never shipped in a module. One of them is no entry of the list: `sh scripts/effect-reports.sh --transcripts ~/.claude/projects`, the effect report of every module over the kit's own sessions, which runs each module's entry from the tree, since the kit never installs its modules and the shared entry finds none here ([template §13](../../module-template/MODULE.md#t13)); it is a report and blocks nothing.

The kit's CI runs the whole list, `.github/workflows/gates.yml`, on every pull request and on `main` after each merge: one job per module holding its entries, one job `install-guide` running the commands of `INSTALL.md` through `scripts/check-install-guide.py` (decision [dec-0062-install-guide-governed-kind](../decisions/dec-0062-install-guide-governed-kind.md)), and one job `kit` for the rest, in parallel, from the list's `--json`; and a job `gates`, green only when every other job is. After its verdict, the job `gates` runs `scripts/metrics.py`, a report of each module's numbers and never a check, and its list of the most complex functions, and uploads both JSON files as the artifact `metrics`. Those steps run unless the run is cancelled. Their failure never changes the verdict (decision [dec-0087-module-metrics-report](../decisions/dec-0087-module-metrics-report.md)). In each module's job, the fixtures entry runs the module's tests one by one, since CI sets no `CONSTITUTION_KIT_JOBS`, under coverage.py, since CI names a folder in `CONSTITUTION_KIT_COVERAGE`. It writes the lines and branches the fixtures reach into the module's file there, uploaded as the artifact `coverage-<module>`. A failure of coverage.py is a BROKEN line of that entry. The self-test of `scripts/check-aspects.py` holds that mode, so a local run of the gate group needs coverage.py, pytest and pytest-xdist, at the versions the workflow pins. After its verdict, the job `gates` reads those files with `scripts/module-coverage.py`, a report of each module's fixture coverage and never a check, whose numbers no check holds, and uploads its JSON as the artifact `coverage`, in steps that run and fail as the metrics steps do (decision [dec-0089-module-coverage-report](../decisions/dec-0089-module-coverage-report.md)).

No local run is required, save one: a change that makes a module's eval receipt stale is merged only with a new passing receipt, made before the merge by `python3 scripts/run-evals.py --token-file <file> --module <module>`, and committed. Every case runs in a throwaway container of the image `scripts/eval-container/Dockerfile` defines, with the seccomp filter and the `/proc` mask lifted so that the eval's own sandbox can start, on the pinned Claude Code, logged in with the person's subscription token from `claude setup-token` and never billed by usage. Every receipt comes from one environment, with the change's own `shared/` mounted at `/shared` and made importable the same way. A receipt's hash covers `shared/constitution_layer_kit/` beside the module's files, since a session loads it (R18 of [dec-0099-shared-code-installed-as-a-pip-package](../decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r18)). Each module has its eval cases in `evals/`, which `claude plugin eval` runs three times each on the model `scripts/eval-model` names. A case passes when every grader passes in every run and no trace of its runs holds `C15`, `C16` or `C17` (R18 of [dec-0099-shared-code-installed-as-a-pip-package](../decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r18)). Each container refuses to run its case unless `claude auth status` reports a subscription login. The runner adds a run's attempt to the module's entry of `scripts/eval-receipts.json`. It keeps the failed ones beside the one that passed, so that a review sees each failed rerun and does not trust it away. A passing run of a module whose entry already names its files, Claude Code and model and whose last attempt passed is not added, so that a passing run made only to watch owes no commit. An attempt that is added, a failure as much as a pass, is committed. An entry whose files, Claude Code or model change starts afresh, its earlier attempts kept in git's history (decision [dec-0094-eval-runs-record-only-what-changes-the-verdict](../decisions/dec-0094-eval-runs-record-only-what-changes-the-verdict.md)). The kit's `scripts/check-eval-receipts.py`, an entry of the gate group with `--self-test` as its fixture, is red for a module whose receipt is missing, names another hash of the files a session loads and its cases, another Claude Code or model, no attempt, or a last attempt that did not pass, and for an entry that names no module folder: it holds that a passing run was declared for the files as they are, not that it ran.

In each module's job, `scripts/check-session-load.py --module <module>`, with `--self-test` as its fixture in the job `kit`, installs the module as the bare-install check does, through the steps both share in `scripts/kit_install.py`, starts one headless session with no login. It holds that the session lists the module's skills and that its start hooks answer, each with output (decision [dec-0093-module-evals-with-local-receipts](../decisions/dec-0093-module-evals-with-local-receipts.md)). Those steps also make a throwaway virtual environment of the `python3` they run under, with its system packages, whose `.pth` file names the change's own `shared/`. They put its `bin` first on `PATH` for every session, hook and scan they start, so that no run meets a release a developer installed. The guide's check does the same for its blocks (R17 of [dec-0099-shared-code-installed-as-a-pip-package](../decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r17)).

For a red before a push, the `gate-list-runner` agent of `.claude/agents/` runs the gate group, the extra group on request, and returns every red line verbatim.

The install and session entries and the guide run on the Claude Code that `scripts/claude-code.version` pins. `sh scripts/setup-claude.sh` installs it once per clone, and again after the pin moves, into `.claude-code-pinned/` beside git's common directory, which git ignores. The list puts it first on `PATH` for those entries alone, when it is there.

The kit's `scripts/check-gate-lists.py`, an entry of that list with `--self-test` as its fixture, holds the form of each module's enforcement table, and that every scan a module declares there stands in the list's gate group and in its module's job and runs with `PYTHONPATH="$PWD/shared"` before its command, every `scripts/check-*.py` git tracks at the top of `scripts/` is run by an entry of the gate group, `MODULES` names exactly the module folders, and the workflow's steps, comments aside, call the list's `--json` and `--run`. It holds that neither `scripts/gate-list.sh` nor the workflow, comments aside, names pytest save in an exact pin `pytest==<version>`, passes `--item` or names `PYTEST_ADDOPTS`, nor does a pytest configuration file at the kit root, in `modules/`, in a module's folder or in its `tests/` set `addopts`. It also holds each module folder named `const-<aspect>`, its manifest naming it, listed once in the marketplace at `./modules/<name>/plugin` and enabled, `true`, in the kit's settings, which declare the marketplace as a directory at `.`. Neither file names a plugin of that marketplace that is no module folder. It holds each marketplace `description` equal to its manifest's, every top-level `const-<aspect>` key of `constitution.yaml` naming a module folder, and the `types` entry putting on `MYPYPATH` exactly the `plugin/scripts` folders of the modules `scripts/check-schema-mirror.py` imports from, and `../shared`. It holds that the `bash check=scan` block of `INSTALL.md` lists exactly the scans the module documents declare, each as `<module>/plugin/scripts/<name>.sh` with `<name>` the declared scan's name without `.py`, a module with no scan owing no path. It holds that every module folder has its one pair in `const-task-close.coverage` of `constitution.yaml`: named after the folder, with `docs` its `MODULE.md` alone, every `code` pattern under the folder, and `modules/<m>/<path>/**` for each of `plugin/scripts`, `plugin/hooks`, `plugin/skills`, `tests` and `evals` that it has. The entries of that map that are no module's are not judged.
