# The gate list and CI — what the kit runs on every change

<a id="g1"></a>
This page is read before a change to the kit's tooling — the gate list, a kit check, the workflow, the eval runner. It is read also when a gate of the list or a job of CI is red. [CLAUDE.md](../../CLAUDE.md) links it from its rule "Work starts on a branch".

The whole gate list is the gate group of `scripts/gate-list.sh`, the kit's one list. It holds the scans of the modules, and the kit's own checks, each with its `--self-test` where it has one. It also holds the self-test of the eval runner, `scripts/run-evals.py --self-test`, the self-test of the mutation report, `scripts/module-mutation.py --self-test`, and the range check. Its extra group holds each module's fixtures, lint and types, and the branch gate's fixture. It also holds the fixture of `scripts/setup-claude.sh`, the kit's lint and types, and the types of `scripts/layered-fixture/`. That folder holds a gate of another layer. `scripts/check-layered-items.py`, an entry of the gate group, runs every shared item on it. A module's scan in the list runs with `PYTHONPATH="$PWD/shared"`, since no plugin carries the shared code. The entry `shared-package` is `scripts/check-shared-package.py`, with `--self-test` as its fixture. It builds the package from `shared/`, installs it into a fresh virtual environment and imports it there. It is the one entry that needs the package index (R19 of [dec-0099-shared-code-installed-as-a-pip-package](../decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r19)). A module's fixtures run through `python3 scripts/check-aspects.py --run --module <module>`, which collects its tests under pytest and then runs them once. It prints pytest's own output whenever pytest exits other than 0. It holds the tests' items against the module's acceptance table both ways (decision [dec-0080-fixtures-run-through-check-aspects](../decisions/dec-0080-fixtures-run-through-check-aspects.md)). The same run holds a count typed on the Runner line of the document's section 10, `<digits> items green` outside code fences, against the tests run. A Runner line without that form, or none, is no finding. Every script under the kit's `scripts/` is kit tooling, never shipped in a module. One of them is no entry of the list: `sh scripts/effect-reports.sh --transcripts ~/.claude/projects`, the effect report of every module over the kit's own sessions. It runs each module's entry from the tree, since the kit never installs its modules and the shared entry finds none here ([template §13](../../module-template/MODULE.md#t13)). It is a report and blocks nothing.

The kit's CI runs the whole list, `.github/workflows/gates.yml`, on every pull request and on `main` after each merge. It runs one job per module, holding its entries. One job, `install-guide`, runs the commands of `INSTALL.md` through `scripts/check-install-guide.py` (decision [dec-0062-install-guide-governed-kind](../decisions/dec-0062-install-guide-governed-kind.md)). One job, `kit`, runs the rest. These jobs run in parallel, from the list's `--json`. There is also a job `gates`, green only when every one of those jobs is. After its verdict, the job `gates` runs `scripts/metrics.py`, a report of each module's numbers and never a check, and its list of the most complex functions. It uploads both JSON files as the artifact `metrics`. Those steps run unless the run is cancelled. Their failure never changes the verdict (decision [dec-0087-module-metrics-report](../decisions/dec-0087-module-metrics-report.md)). In each module's job, the fixtures entry runs the module's tests one by one, since `CONSTITUTION_KIT_JOBS` is not set in CI. It runs them under coverage.py, since in CI `CONSTITUTION_KIT_COVERAGE` names a folder. It writes the lines and branches the fixtures reach into the module's file there. That file is uploaded as the artifact `coverage-<module>`. A failure of coverage.py is a BROKEN line of that entry. The self-test of `scripts/check-aspects.py` holds that mode. So a local run of the gate group needs coverage.py, pytest and pytest-xdist, at the versions the workflow pins. After its verdict, the job `gates` reads those files with `scripts/module-coverage.py`, a report of each module's fixture coverage and never a check. No check holds its numbers. The job uploads its JSON as the artifact `coverage`. These steps run and fail as the metrics steps do (decision [dec-0089-module-coverage-report](../decisions/dec-0089-module-coverage-report.md)).

<a id="g2"></a>
Once the check jobs have ended, whatever their verdict, one job for each module measures a sample of the module's mutants. That job, `mutation <module>`, uses `scripts/module-mutation.py` to do so. It does not run on a cancelled run, or where the job that lists the modules failed. A mutant is the module's own Python with one small change. A test run kills it when a test fails. The score is the share of the judged mutants that were killed, a run past its time limit counted as a kill. The key `score_percent` in the docstring of `scripts/module-mutation.py` defines it. The job runs mutants for 150 seconds, in three copies of the kit side by side, in an order that the commit seeds. Each mutant meets only the tests whose coverage reaches its lines, and the same file says how. With more than one copy, a kill by a failed test is confirmed. That test runs again on the unmutated file. A mutant whose test fails there too is left out of the score. The job writes the module's mutation file, uploaded as the artifact `mutation-<module>`. The job `mutation` then reads those files with the same script. It prints the score of each module and the list of the survivors on the run's summary page, where the coverage stands too. It uploads the JSON as the artifact `mutation`. The job `gates` needs none of these jobs, so the verdict never waits for the score. Each of their steps carries `continue-on-error`. When a report cannot be made, its job stays green. Its module is left out of the table, with a note there. The score is a report and never a check. No number is a threshold. A sample's score moves from run to run with no change in the code. So the table gives one standard error beside it, and two runs are never compared as a change. The survivors are the part a person can act on. The rule that CI runs a module's tests only through `scripts/check-aspects.py` is of the runs that give a verdict. This report gives none, and runs chosen tests itself. No workflow runs on a schedule for the score, and none measures every mutant of a module. A whole measure is a run by hand, `python3 scripts/module-mutation.py --module <module> --copies <n>`, which takes from minutes to hours. The self-test of the report is the entry `module-mutation` of the gate group, in the `kit` job. It holds the report's code on a small kit of its own, whose tests it runs itself, and judges no module. It needs coverage.py and pytest at the versions the workflow pins (decision [dec-0122-module-mutation-report](../decisions/dec-0122-module-mutation-report.md)).

No local run is required, save one. A change that makes a module's eval receipt stale is merged only with a new passing receipt. That receipt is made before the merge by `python3 scripts/run-evals.py --token-file <file> --module <module>`, and committed. Every case runs in a throwaway container of the image `scripts/eval-container/Dockerfile` defines. The seccomp filter and the `/proc` mask are lifted there so that the eval's own sandbox can start. The case runs on the pinned Claude Code, logged in with the person's subscription token from `claude setup-token`, and is never billed by usage. Every receipt comes from one environment, with the change's own `shared/` mounted at `/shared` and made importable the same way. A receipt's hash covers `shared/constitution_layer_kit/` beside the module's files, since a session loads it (R18 of [dec-0099-shared-code-installed-as-a-pip-package](../decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r18)). Each module has its eval cases in `evals/`, which `claude plugin eval` runs three times each on the model `scripts/eval-model` names. A case passes when every grader passes in every run. It also passes only when no trace of its runs holds `C15`, `C16` or `C17` (R18 of [dec-0099-shared-code-installed-as-a-pip-package](../decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r18)). Each container refuses to run its case unless `claude auth status` reports a subscription login. In `scripts/eval-receipts.json`, the runner adds a run's attempt to the module's entry. It keeps the failed ones beside the one that passed, so that a review sees each failed rerun and does not trust it away. Where a module's entry already names its files, Claude Code and model, and its last attempt passed, a passing run is not added. So a passing run made only to watch owes no commit. An attempt that is added, a failure as much as a pass, is committed. An entry whose files, Claude Code or model change starts afresh. Its earlier attempts are kept in git's history (decision [dec-0094-eval-runs-record-only-what-changes-the-verdict](../decisions/dec-0094-eval-runs-record-only-what-changes-the-verdict.md)). The kit's `scripts/check-eval-receipts.py` is an entry of the gate group, with `--self-test` as its fixture. It is red for a module whose receipt is missing, or names another hash of the files a session loads and its cases. It is also red where the receipt names another Claude Code or model, no attempt, or a last attempt that did not pass. It is red too for an entry that names no module folder. It holds that a passing run was declared for the files as they are, not that it ran.

In each module's job, `scripts/check-session-load.py --module <module>` runs, with `--self-test` as its fixture in the `kit` job. It installs the module as the bare-install check does, through the steps both share in `scripts/kit_install.py`, and starts one headless session with no login. It holds that the session lists the module's skills. It also holds that its start hooks answer, each with output (decision [dec-0093-module-evals-with-local-receipts](../decisions/dec-0093-module-evals-with-local-receipts.md)). Those steps also make a throwaway virtual environment of the `python3` they run under, with its system packages. The change's own `shared/` is named in its `.pth` file. They put its `bin` first on `PATH` for every session, hook and scan they start, so that no run meets a release a developer installed. The guide's check does the same for its blocks (R17 of [dec-0099-shared-code-installed-as-a-pip-package](../decisions/dec-0099-shared-code-installed-as-a-pip-package.md#r17)).

For a red before a push, the `gate-list-runner` agent of `.claude/agents/` runs the gate group, the extra group on request, and returns every red line verbatim.

The install and session entries and the guide run on the Claude Code that `scripts/claude-code.version` pins. `sh scripts/setup-claude.sh` installs it once per clone, and again after the pin moves, into `.claude-code-pinned/` beside git's common directory, which git ignores. The list puts it first on `PATH` for those entries alone, when it is there.

The kit's `scripts/check-gate-lists.py` is an entry of that list, with `--self-test` as its fixture. It holds the form of each module's enforcement table. It holds that every scan a module declares there stands in the list's gate group and in its module's job. Each such scan runs with `PYTHONPATH="$PWD/shared"` before its command. It holds that every `scripts/check-*.py` git tracks at the top of `scripts/` is run by an entry of the gate group. It holds that `MODULES` names exactly the module folders. It holds that the workflow's steps, comments aside, call `--json` and `--run` of the list. It holds that neither `scripts/gate-list.sh` nor the workflow, comments aside, names pytest save in an exact pin `pytest==<version>`. Neither of them passes `--item` or names `PYTEST_ADDOPTS` at all. Nor does a pytest configuration file set `addopts` in `modules/`, in a module's folder or in its `tests/`, or at the kit root. It also holds each module folder named `const-<aspect>`, with its manifest naming it. Each is listed once in the marketplace at `./modules/<name>/plugin`, and enabled, `true`, in the kit's settings. Those settings declare the marketplace as a directory at `.`. Neither file names a plugin of that marketplace that is no module folder. It holds each marketplace `description` equal to its manifest's. It holds every top-level `const-<aspect>` key of `constitution.yaml` naming a module folder. It holds the `types` entry putting on `MYPYPATH` exactly `../shared` and the `plugin/scripts` folders of the modules `scripts/check-schema-mirror.py` imports from. It holds that the `bash check=scan` block of `INSTALL.md` lists exactly the scans the module documents declare. Each is listed as `<module>/plugin/scripts/<name>.sh`, with `<name>` the declared scan's name without `.py`. A module with no scan owes no path. It holds that every module folder has its one pair in `const-task-close.coverage` of `constitution.yaml`. The pair is named after the folder, with `docs` its `MODULE.md` alone. Every `code` pattern is under the folder. It has `modules/<m>/<path>/**` for each of `plugin/scripts`, `plugin/hooks`, `plugin/skills`, `tests` and `evals` that the folder has. The entries of that map that are no module's are not judged.

The kit's `scripts/check-profiles.py` is the entry `profiles` of that list, with `--self-test` as its fixture. It holds every file of `profiles/`, as [the last section of the install guide](../../INSTALL.md#s6) says.
